# البث عبر HTTPS مع بروتوكول سياق النموذج (MCP)

يوفر هذا الفصل دليلاً شاملاً لتنفيذ البث الآمن والقابل للتوسع والفوري باستخدام بروتوكول سياق النموذج (MCP) عبر HTTPS. يغطي الدافع للبث، وآليات النقل المتاحة، وكيفية تنفيذ HTTP القابل للبث في MCP، وأفضل ممارسات الأمان، والهجرة من SSE، والإرشادات العملية لبناء تطبيقات MCP الخاصة بك للبث.

> **نظرة مستقبلية:** تصف هذه الدرس HTTP القابل للبث تحت **مواصفة MCP 2025-11-25**، حيث يتم إنشاء جلسة أثناء `initialize` وتثبيتها باستخدام رأس `Mcp-Session-Id`. يزيل إصدار المرشح النهائي `2026-07-28` المصافحة ومعرّف الجلسة بالكامل، مما يجعل كل طلب مستقلاً ويمكن توجيهه إلى أي خادم بدون جلسات لزجة. انظر [ما الذي يتغير في MCP: إصدار المرشح النهائي 2026-07-28](../../01-CoreConcepts/mcp-2026-07-28-release-candidate.md) للتفاصيل.

## آليات النقل والبث في MCP

يستعرض هذا القسم آليات النقل المختلفة المتاحة في MCP ودورها في تمكين قدرات البث للاتصال الفوري بين العملاء والخوادم.

### ما هي آلية النقل؟

تعرف آلية النقل كيفية تبادل البيانات بين العميل والخادم. يدعم MCP أنواع نقل متعددة لتناسب بيئات ومتطلبات مختلفة:

- **stdio**: الإدخال/الإخراج القياسي، مناسب للأدوات المحلية وأدوات واجهة الأوامر CLI. بسيط لكنه غير مناسب للويب أو السحابة.
- **SSE (أحداث الخادم المرسلة)**: يسمح للخوادم بدفع تحديثات فورية للعملاء عبر HTTP. جيد لواجهات الويب، لكنه محدود في القابلية للتوسع والمرونة. اعتبارًا من مواصفة MCP 2025-06-18، تم إلغاء نقل SSE المستقل واستبداله بنقل "HTTP القابل للبث".
- **HTTP القابل للبث**: نقل حديث قائم على HTTP، يدعم الإشعارات وقابلية توسع أفضل. يُنصح به لمعظم بيئات الإنتاج والسحابة.

### جدول المقارنة

ألق نظرة على جدول المقارنة أدناه لفهم الفروقات بين آليات النقل هذه:

| النقل            | التحديثات الفورية | البث          | القابلية للتوسع | حالة الاستخدام              |
|-------------------|------------------|--------------|------------------|-----------------------------|
| stdio             | لا               | لا           | منخفض           | أدوات CLI محلية             |
| SSE               | نعم              | نعم          | متوسط           | الويب، التحديثات الفورية    |
| HTTP القابل للبث  | نعم              | نعم          | عالي             | السحابة、多 عملاء             |

> **نصيحة:** اختيار النقل الصحيح يؤثر على الأداء، والقابلية للتوسع، وتجربة المستخدم. يُنصح بـ **HTTP القابل للبث** للتطبيقات الحديثة والقابلة للتوسع والمهيأة للسحابة.

لاحظ آليات النقل stdio و SSE التي تم توضيحها في الفصول السابقة وكيف أن HTTP القابل للبث هو الآلية المغطاة في هذا الفصل.

## البث: المفاهيم والدوافع

فهم المفاهيم والدوافع الأساسية وراء البث ضروري لتنفيذ أنظمة اتصال فورية فعالة.

**البث** هو تقنية في برمجة الشبكات تسمح بإرسال واستقبال البيانات في قطع صغيرة يمكن إدارتها أو كسلسلة من الأحداث، بدلاً من الانتظار لاستعداد الاستجابة كاملة. هذا مفيد بشكل خاص لـ:

- الملفات الكبيرة أو مجموعات البيانات.
- التحديثات الفورية (مثل الدردشة، أشرطة التقدم).
- الحسابات الطويلة حيث تريد إبلاغ المستخدم باستمرار.

إليك ما تحتاج معرفته عن البث على مستوى عالي:

- يتم تسليم البيانات تدريجياً، وليس دفعة واحدة.
- يمكن للعميل معالجة البيانات فور وصولها.
- يقلل من زمن الاستجابة المحسوس ويحسن تجربة المستخدم.

### لماذا نستخدم البث؟

الأسباب لاستخدام البث هي كما يلي:

- يحصل المستخدمون على ردود فعل على الفور، وليس فقط في النهاية.
- يمكن تطبيقات الوقت الحقيقي وواجهات المستخدم التفاعلية.
- استخدام أكثر كفاءة لشبكة والموارد الحاسوبية.

### مثال بسيط: خادم وعميل بث HTTP

إليك مثال بسيط لكيفية تنفيذ البث:

#### بايثون

**الخادم (بايثون، باستخدام FastAPI و StreamingResponse):**

```python
from fastapi import FastAPI
from fastapi.responses import StreamingResponse
import time

app = FastAPI()

async def event_stream():
    for i in range(1, 6):
        yield f"data: Message {i}\n\n"
        time.sleep(1)

@app.get("/stream")
def stream():
    return StreamingResponse(event_stream(), media_type="text/event-stream")
```

**العميل (بايثون، باستخدام requests):**

```python
import requests

with requests.get("http://localhost:8000/stream", stream=True) as r:
    for line in r.iter_lines():
        if line:
            print(line.decode())
```

يوضح هذا المثال خادمًا يرسل سلسلة من الرسائل إلى العميل مع توفرها، بدلاً من الانتظار لاستعداد جميع الرسائل.

**كيف يعمل:**

- الخادم يولد كل رسالة بمجرد الاستعداد.
- العميل يستقبل ويطبع كل جزء عند وصوله.

**المتطلبات:**

- يجب أن يستخدم الخادم استجابة بث (مثل `StreamingResponse` في FastAPI).
- يجب أن يعالج العميل الاستجابة كتيار (`stream=True` في requests).
- عادة ما يكون نوع المحتوى `text/event-stream` أو `application/octet-stream`.

#### جافا

**الخادم (جافا، باستخدام Spring Boot و Server-Sent Events):**

```java
@RestController
public class CalculatorController {

    @GetMapping(value = "/calculate", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    public Flux<ServerSentEvent<String>> calculate(@RequestParam double a,
                                                   @RequestParam double b,
                                                   @RequestParam String op) {
        
        double result;
        switch (op) {
            case "add": result = a + b; break;
            case "sub": result = a - b; break;
            case "mul": result = a * b; break;
            case "div": result = b != 0 ? a / b : Double.NaN; break;
            default: result = Double.NaN;
        }

        return Flux.<ServerSentEvent<String>>just(
                    ServerSentEvent.<String>builder()
                        .event("info")
                        .data("Calculating: " + a + " " + op + " " + b)
                        .build(),
                    ServerSentEvent.<String>builder()
                        .event("result")
                        .data(String.valueOf(result))
                        .build()
                )
                .delayElements(Duration.ofSeconds(1));
    }
}
```

**العميل (جافا، باستخدام Spring WebFlux WebClient):**

```java
@SpringBootApplication
public class CalculatorClientApplication implements CommandLineRunner {

    private final WebClient client = WebClient.builder()
            .baseUrl("http://localhost:8080")
            .build();

    @Override
    public void run(String... args) {
        client.get()
                .uri(uriBuilder -> uriBuilder
                        .path("/calculate")
                        .queryParam("a", 7)
                        .queryParam("b", 5)
                        .queryParam("op", "mul")
                        .build())
                .accept(MediaType.TEXT_EVENT_STREAM)
                .retrieve()
                .bodyToFlux(String.class)
                .doOnNext(System.out::println)
                .blockLast();
    }
}
```

**ملاحظات تنفيذ جافا:**

- يستخدم كومة تفاعلية في Spring Boot مع `Flux` للبث
- يوفر `ServerSentEvent` بثًا هيكليًا منظمة مع أنواع الأحداث
- `WebClient` مع `bodyToFlux()` يمكّن استهلاك البث التفاعلي
- `delayElements()` يحاكي زمن المعالجة بين الأحداث
- يمكن أن يكون للأحداث أنواع (`info`, `result`) لمعالجة أفضل على العميل

### مقارنة: البث الكلاسيكي مقابل بث MCP

يمكن تصور اختلافات كيفية عمل البث بشكل "كلاسيكي" مقابل كيفية عمله في MCP كما يلي:

| الميزة                | بث HTTP الكلاسيكي            | بث MCP (الإشعارات)            |
|----------------------|------------------------------|-------------------------------|
| الاستجابة الرئيسية    | مقسمة على أجزاء              | واحدة، في النهاية             |
| تحديثات التقدم       | ترسل كأجزاء بيانات           | ترسل كإشعارات                |
| متطلبات العميل       | يجب أن يعالج التيار           | يجب أن ينفذ معالج الرسائل     |
| حالة الاستخدام       | ملفات كبيرة، تدفقات رموز AI | التقدم، السجلات، ردود الفعل الفورية |

### الفروق الرئيسية الملحوظة

بالإضافة إلى ذلك، إليك بعض الفروق الرئيسية:

- **نمط الاتصال:**
  - البث الكلاسيكي عبر HTTP: يستخدم ترميز نقل مقطع بسيط لإرسال البيانات على أجزاء
  - بث MCP: يستخدم نظام إشعار منظم مع بروتوكول JSON-RPC

- **صيغة الرسالة:**
  - HTTP الكلاسيكي: أجزاء نصية عادية مع أسطر جديدة
  - MCP: كائنات LoggingMessageNotification منظمة مع بيانات وصفية

- **تنفيذ العميل:**
  - HTTP الكلاسيكي: عميل بسيط يعالج ردود البث
  - MCP: عميل أكثر تعقيدًا مع معالج رسائل لمعالجة أنواع مختلفة من الرسائل

- **تحديثات التقدم:**
  - HTTP الكلاسيكي: التقدم جزء من تيار الاستجابة الرئيسي
  - MCP: يرسل التقدم عبر رسائل إشعار منفصلة بينما تأتي الاستجابة الرئيسية في النهاية

### التوصيات

هناك بعض الأمور التي نوصي بها عند اختيار بين تنفيذ البث الكلاسيكي (كنقطة نهاية عرضناها أعلاه باستخدام `/stream`) مقابل اختيار البث عبر MCP.

- **للحاجات البث البسيطة:** البث الكلاسيكي عبر HTTP أبسط في التنفيذ وكافٍ للاحتياجات الأساسية.

- **للتطبيقات التفاعلية المعقدة:** يوفر بث MCP منهجًا أكثر تنظيمًا مع بيانات وصفية أعمق وفصل بين الإشعارات والنتائج النهائية.

- **لتطبيقات الذكاء الاصطناعي:** نظام إشعارات MCP مفيد خصوصًا للمهام الطويلة حيث تريد إبلاغ المستخدمين بالتقدم.

## البث في MCP

حسنًا، لقد شاهدت بعض التوصيات والمقارنات حتى الآن حول الفرق بين البث الكلاسيكي والبث في MCP. لنتعمق في التفاصيل حول كيفية الاستفادة من البث في MCP.

فهم كيفية عمل البث ضمن إطار عمل MCP ضروري لبناء تطبيقات تفاعلية توفر ردود فعل فورية للمستخدمين أثناء العمليات الطويلة.

في MCP، لا يُقصد بالبث إرسال الاستجابة الرئيسية على أجزاء، بل إرسال **الإشعارات** إلى العميل أثناء معالجة الأداة للطلب. يمكن أن تتضمن هذه الإشعارات تحديثات التقدم، أو السجلات، أو أحداث أخرى.

### كيف يعمل

لا يزال يتم إرسال النتيجة الرئيسية كرد واحد. ومع ذلك، يمكن إرسال الإشعارات كرسائل منفصلة أثناء المعالجة وبالتالي تحديث العميل في الوقت الفعلي. يجب أن يكون العميل قادرًا على التعامل مع هذه الإشعارات وعرضها.

## ما هي الإشعارات؟

قلنا "إشعار"، ماذا يعني ذلك في سياق MCP؟

الإشعار هو رسالة تُرسل من الخادم إلى العميل لإبلاغه بالتقدم، الحالة، أو أحداث أخرى أثناء عملية طويلة. تعمل الإشعارات على تحسين الشفافية وتجربة المستخدم.

على سبيل المثال، يفترض أن يرسل العميل إشعارًا بمجرد إتمام المصافحة الأولية مع الخادم.

تكون الإشعارات في شكل رسالة JSON كما يلي:

```json
{
  jsonrpc: "2.0";
  method: string;
  params?: {
    [key: string]: unknown;
  };
}
```

تنتمي الإشعارات إلى موضوع في MCP يُشار إليه كـ ["Logging"](https://modelcontextprotocol.io/specification/draft/server/utilities/logging).

> **إشعار بالإيقاف:** تشير مواصفة MCP إصدار المرشح النهائي `2026-07-28` إلى إيقاف مكون Logging لصالح `stderr` لنقلات stdio و OpenTelemetry للرصد البنيوي. يستمر Logging في العمل في `2025-11-25` ولمدة عام على الأقل بعد أي إيقاف رسمي. انظر [ما الذي يتغير في MCP: إصدار المرشح النهائي 2026-07-28](../../01-CoreConcepts/mcp-2026-07-28-release-candidate.md).

لجعل تسجيل الدخول يعمل، يحتاج الخادم إلى تمكينه كميزة/قدرة كما يلي:

```json
{
  "capabilities": {
    "logging": {}
  }
}
```

> [!NOTE]
> حسب SDK المستخدم، قد يتم تمكين التسجيل افتراضيًا، أو قد تحتاج إلى تفعيله صراحةً في تكوين خادمك.

هناك أنواع مختلفة من الإشعارات:

| المستوى   | الوصف                         | مثال لحالة الاستخدام          |
|-----------|------------------------------|-------------------------------|
| debug     | معلومات تفصيلية للتصحيح       | نقاط دخول/خروج الدالة         |
| info      | رسائل معلومات عامة            | تحديثات تقدم العملية           |
| notice    | أحداث عادية لكنها مهمة        | تغييرات التكوين               |
| warning   | حالات تحذير                   | استخدام ميزة مهجورة           |
| error     | حالات الخطأ                   | فشل العملية                   |
| critical  | حالات حرجة                   | فشل مكونات النظام             |
| alert     | يجب اتخاذ إجراء فوري          | تم الكشف عن تلف بيانات         |
| emergency | النظام غير قابل للاستخدام     | فشل النظام الكامل            |

## تنفيذ الإشعارات في MCP

لتنفيذ الإشعارات في MCP، تحتاج إلى إعداد جانب الخادم والعميل للتعامل مع التحديثات الفورية. هذا يسمح لتطبيقك بتقديم ردود فعل فورية للمستخدمين أثناء العمليات الطويلة.

### جانب الخادم: إرسال الإشعارات

لنبدأ بجانب الخادم. في MCP، تعرف أدوات يمكنها إرسال إشعارات أثناء معالجة الطلبات. يستخدم الخادم كائن السياق (عادة `ctx`) لإرسال الرسائل إلى العميل.

#### بايثون

```python
@mcp.tool(description="A tool that sends progress notifications")
async def process_files(message: str, ctx: Context) -> TextContent:
    await ctx.info("Processing file 1/3...")
    await ctx.info("Processing file 2/3...")
    await ctx.info("Processing file 3/3...")
    return TextContent(type="text", text=f"Done: {message}")
```

في المثال السابق، ترسل أداة `process_files` ثلاث إشعارات إلى العميل أثناء معالجتها لكل ملف. تُستخدم طريقة `ctx.info()` لإرسال رسائل معلوماتية.

بالإضافة إلى ذلك، لتمكين الإشعارات، تأكد من أن خادمك يستخدم نقل بث (مثل `streamable-http`) وأن عميلك ينفذ معالج رسائل لمعالجة الإشعارات. إليك كيفية إعداد الخادم لاستخدام نقل `streamable-http`:

```python
mcp.run(transport="streamable-http")
```

#### .NET

```csharp
[Tool("A tool that sends progress notifications")]
public async Task<TextContent> ProcessFiles(string message, ToolContext ctx)
{
    await ctx.Info("Processing file 1/3...");
    await ctx.Info("Processing file 2/3...");
    await ctx.Info("Processing file 3/3...");
    return new TextContent
    {
        Type = "text",
        Text = $"Done: {message}"
    };
}
```

في هذا المثال في .NET، تُزيّن أداة `ProcessFiles` بسمات `Tool` وترسل ثلاث إشعارات إلى العميل أثناء معالجتها لكل ملف. تُستخدم طريقة `ctx.Info()` لإرسال رسائل معلوماتية.

لتمكين الإشعارات في خادم MCP الخاص بك على .NET، تأكد من أنك تستخدم نقل بث:

```csharp
var builder = McpBuilder.Create();
await builder
    .UseStreamableHttp() // Enable streamable HTTP transport
    .Build()
    .RunAsync();
```

### جانب العميل: استقبال الإشعارات

يجب على العميل تنفيذ معالج رسائل لمعالجة وعرض الإشعارات فور وصولها.

#### بايثون

```python
async def message_handler(message):
    if isinstance(message, types.ServerNotification):
        print("NOTIFICATION:", message)
    else:
        print("SERVER MESSAGE:", message)

async with ClientSession(
   read_stream, 
   write_stream,
   logging_callback=logging_collector,
   message_handler=message_handler,
) as session:
```

في الكود السابق، تتحقق وظيفة `message_handler` مما إذا كانت الرسالة الواردة إشعارًا. إذا كانت كذلك، تطبع الإشعار؛ وإلاّ تعالجه كرسالة خادم عادية. لاحظ أيضًا كيف يتم تهيئة `ClientSession` مع `message_handler` للتعامل مع الإشعارات الواردة.

#### .NET

```csharp
// Define a message handler
void MessageHandler(IJsonRpcMessage message)
{
    if (message is ServerNotification notification)
    {
        Console.WriteLine($"NOTIFICATION: {notification}");
    }
    else
    {
        Console.WriteLine($"SERVER MESSAGE: {message}");
    }
}

// Create and use a client session with the message handler
var clientOptions = new ClientSessionOptions
{
    MessageHandler = MessageHandler,
    LoggingCallback = (level, message) => Console.WriteLine($"[{level}] {message}")
};

using var client = new ClientSession(readStream, writeStream, clientOptions);
await client.InitializeAsync();

// Now the client will process notifications through the MessageHandler
```

في هذا المثال في .NET، تتحقق وظيفة `MessageHandler` مما إذا كانت الرسالة الواردة إشعارًا. إذا كانت كذلك، تطبع الإشعار؛ وإلاّ تعالجه كرسالة خادم عادية. يتم تهيئة `ClientSession` بمعالج الرسائل عبر `ClientSessionOptions`.

لتمكين الإشعارات، تأكد من أن الخادم يستخدم نقل بث (مثل `streamable-http`) وأن العميل ينفذ معالج رسائل لمعالجة الإشعارات.

## إشعارات التقدم والسيناريوهات

يشرح هذا القسم مفهوم إشعارات التقدم في MCP، وأهميته، وكيفية تنفيذها باستخدام HTTP القابل للبث. ستجد أيضًا مهمة عملية لتعزيز فهمك.

إشعارات التقدم هي رسائل في الوقت الفعلي تُرسل من الخادم إلى العميل أثناء العمليات الطويلة. بدلاً من الانتظار حتى انتهاء العملية بأكملها، يحتفظ الخادم بتحديث العميل عن الحالة الحالية. هذا يحسن الشفافية وتجربة المستخدم ويسهل تصحيح الأخطاء.

**مثال:**

```text

"Processing document 1/10"
"Processing document 2/10"
...
"Processing complete!"

```

### لماذا نستخدم إشعارات التقدم؟

إشعارات التقدم ضرورية لأسباب عديدة:

- **تحسين تجربة المستخدم:** يرى المستخدمون التحديثات أثناء تقدم العمل، وليس فقط في النهاية.
- **ردود فعل فورية:** يمكن للعملاء عرض أشرطة التقدم أو السجلات، مما يجعل التطبيق يبدو تفاعليًا.
- **سهولة التصحيح والمراقبة:** يمكن للمطورين والمستخدمين رؤية مكان تباطؤ العملية أو توقفها.

### كيفية تنفيذ إشعارات التقدم

إليك كيفية تنفيذ إشعارات التقدم في MCP:

- **على الخادم:** استخدم `ctx.info()` أو `ctx.log()` لإرسال الإشعارات عند معالجة كل عنصر. يرسل هذا رسالة إلى العميل قبل استعداد النتيجة الرئيسية.
- **على العميل:** نفّذ معالج رسائل يستمع للإشعارات ويعرضها فور وصولها. يميز هذا المعالج بين الإشعارات والنتيجة النهائية.

**مثال الخادم:**


#### بايثون

```python
@mcp.tool(description="A tool that sends progress notifications")
async def process_files(message: str, ctx: Context) -> TextContent:
    for i in range(1, 11):
        await ctx.info(f"Processing document {i}/10")
    await ctx.info("Processing complete!")
    return TextContent(type="text", text=f"Done: {message}")
```

**مثال العميل:**

#### بايثون

```python
async def message_handler(message):
    if isinstance(message, types.ServerNotification):
        print("NOTIFICATION:", message)
    else:
        print("SERVER MESSAGE:", message)
```

## اعتبارات أمنية

يجب أن تكون الأمان أولوية قصوى عند تنفيذ أي خادم، خاصة عند استخدام وسائل نقل معتمدة على HTTP مثل HTTP البثي في MCP.

عند تنفيذ خوادم MCP التي تستخدم وسائل نقل تعتمد على HTTP، يصبح الأمان مسألة حاسمة تتطلب اهتمامًا دقيقًا بعدة ناقلات هجوم وآليات حماية.

### نظرة عامة

الأمان أمر حاسم عند تعريض خوادم MCP عبر HTTP. يقدم HTTP البثي أسطح هجوم جديدة ويتطلب تهيئة دقيقة.

فيما يلي بعض الاعتبارات الأمنية الرئيسية:

- **التحقق من رأس الأصل**: تحقق دائمًا من صحة رأس `Origin` لمنع هجمات إعادة ربط DNS.
- **ربط المضيف المحلي**: لأغراض التطوير المحلي، اربط الخوادم بـ `localhost` لتجنب تعريضها للإنترنت العام.
- **المصادقة**: نفذ المصادقة (مثل مفاتيح API، OAuth) لنشر الإنتاج.
- **CORS**: اضبط سياسات مشاركة الموارد عبر الأصول (CORS) لتقييد الوصول.
- **HTTPS**: استخدم HTTPS في الإنتاج لتشفير حركة المرور.

### أفضل الممارسات

بالإضافة إلى ذلك، فيما يلي بعض أفضل الممارسات التي يجب اتباعها عند تنفيذ الأمان في خادم MCP الخاص بك للبث:

- لا تثق أبدًا في الطلبات الواردة دون التحقق منها.
- سجل وراقب جميع عمليات الوصول والأخطاء.
- حدّث التبعيات بانتظام لسد الثغرات الأمنية.

### التحديات

ستواجه بعض التحديات عند تنفيذ الأمان في خوادم MCP للبث:

- موازنة الأمان مع سهولة التطوير
- ضمان التوافق مع بيئات العملاء المختلفة


## الترقية من SSE إلى HTTP البثي

بالنسبة للتطبيقات التي تستخدم حاليًا أحداث الخادم المرسلة (SSE)، توفر الترقية إلى HTTP البثي قدرات محسنة واستدامة أفضل على المدى الطويل لتطبيقات MCP الخاصة بك.

### لماذا الترقية؟

هناك سببان قويان للترقية من SSE إلى HTTP البثي:

- يقدم HTTP البثي قابلية أفضل للتوسع، وتوافقًا أكبر، ودعمًا أغنى للإشعارات مقارنة بـ SSE.
- إنه وسيلة النقل الموصى بها لتطبيقات MCP الجديدة.

### خطوات الترحيل

إليك كيفية الترحيل من SSE إلى HTTP البثي في تطبيقات MCP الخاصة بك:

- **تحديث كود الخادم** لاستخدام `transport="streamable-http"` في `mcp.run()`.
- **تحديث كود العميل** لاستخدام `streamablehttp_client` بدلًا من عميل SSE.
- **تنفيذ معالج رسائل** في العميل لمعالجة الإشعارات.
- **اختبر التوافق** مع الأدوات وسير العمل الحالية.

### المحافظة على التوافق

يُنصح بالحفاظ على التوافق مع عملاء SSE الحاليين خلال عملية الترحيل. إليك بعض الاستراتيجيات:

- يمكنك دعم كل من SSE وHTTP البثي بتشغيل كلا النقلين على نقاط نهاية مختلفة.
- قم بترحيل العملاء تدريجيًا إلى وسيلة النقل الجديدة.

### التحديات

تأكد من معالجة التحديات التالية أثناء الترحيل:

- التأكد من تحديث جميع العملاء
- التعامل مع الفروقات في تسليم الإشعارات

### المهمة: بناء تطبيق MCP للبث خاص بك

**السيناريو:**
ابنِ خادم MCP وعميل حيث يعالج الخادم قائمة من العناصر (مثل الملفات أو المستندات) ويرسل إشعارًا لكل عنصر تم معالجته. يجب أن يعرض العميل كل إشعار فور وصوله.

**الخطوات:**

1. نفذ أداة خادم تقوم بمعالجة قائمة وترسل إشعارات لكل عنصر.
2. نفذ عميلًا مع معالج رسائل لعرض الإشعارات في الوقت الحقيقي.
3. اختبر تطبيقك بتشغيل كل من الخادم والعميل، وراقب الإشعارات.
