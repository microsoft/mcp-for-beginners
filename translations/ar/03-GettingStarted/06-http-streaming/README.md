# البث عبر HTTPS باستخدام بروتوكول سياق النموذج (MCP)

يقدم هذا الفصل دليلاً شاملاً لتنفيذ بث آمن وقابل للتوسع وفي الوقت الفعلي باستخدام بروتوكول سياق النموذج (MCP) عبر HTTPS. يغطي الدوافع للبث، وآليات النقل المتوفرة، كيفية تنفيذ HTTP قابل للبث في MCP، ممارسات الأمان الفضلى، الهجرة من SSE، والإرشادات العملية لبناء تطبيقات MCP للبث الخاصة بك.

> **نظرة مستقبلية:** تصف هذه الدرسة بروتوكول HTTP القابل للبث تحت **مواصفة MCP بتاريخ 2025-11-25**، حيث يتم إنشاء جلسة خلال `initialize` وتثبيتها برأس `Mcp-Session-Id`. يزيل إصدار المرشح  `2026-07-28` المصافحة ومعرف الجلسة تمامًا، مما يجعل كل طلب مستقلًا وقابلًا للتوجيه إلى أي مثيل خادم بدون جلسات لزجة. راجع [ما الجديد في MCP: إصدار المرشح 2026-07-28](../../01-CoreConcepts/mcp-2026-07-28-release-candidate.md) للتفاصيل.

## آليات النقل والبث في MCP

تستكشف هذه القسم آليات النقل المختلفة المتوفرة في MCP ودورها في تمكين قدرات البث للاتصال في الوقت الحقيقي بين العميل والخادم.

### ما هي آلية النقل؟

تحدد آلية النقل كيفية تبادل البيانات بين العميل والخادم. يدعم MCP عدة أنواع نقل لتناسب بيئات ومتطلبات مختلفة:

- **stdio**: الإدخال/الإخراج القياسي، مناسب للأدوات المحلية والأدوات القائمة على CLI. بسيط لكنه غير مناسب للويب أو السحابة.
- **SSE (Server-Sent Events)**: يسمح للخوادم بدفع التحديثات في الوقت الحقيقي للعملاء عبر HTTP. مناسب لواجهات الويب، لكنه محدود في التوسع والمرونة. اعتبارًا من مواصفة MCP بتاريخ 2025-06-18، تم إهمال نقل SSE المستقل واستبداله بنقل "HTTP القابل للبث".
- **Streamable HTTP**: نقل بث حديث قائم على HTTP، يدعم الإشعارات وتوسع أفضل. موصى به لمعظم السيناريوهات الإنتاجية والسحابية.

### جدول المقارنة

راجع جدول المقارنة أدناه لفهم الاختلافات بين هذه آليات النقل:

| النقل               | التحديثات في الوقت الحقيقي | البث       | قابلية التوسع | حالة الاستخدام         |
|---------------------|----------------------------|------------|---------------|-------------------------|
| stdio               | لا                         | لا         | منخفض        | أدوات CLI المحلية       |
| SSE                 | نعم                        | نعم        | متوسط        | الويب، التحديثات اللحظية|
| Streamable HTTP     | نعم                        | نعم        | عالي         | السحابة، متعددي العملاء |

> **نصيحة:** اختيار نقل مناسب يؤثر على الأداء وقابلية التوسع وتجربة المستخدم. يوصى بـ **Streamable HTTP** للتطبيقات الحديثة والقابلة للتوسع والمهيأة للسحابة.

لاحظ آليات النقل stdio و SSE التي تم عرضها في الفصول السابقة وكيف أن HTTP القابل للبث هو النقل الذي يغطيه هذا الفصل.

## البث: المفاهيم والدوافع

فهم المفاهيم الأساسية والدوافع وراء البث ضروري لتنفيذ أنظمة اتصال فعالة في الوقت الحقيقي.

**البث** هي تقنية في برمجة الشبكات تسمح بإرسال واستقبال البيانات على أجزاء صغيرة أو كسلسلة أحداث، بدلاً من الانتظار حتى يكون الرد كاملاً جاهزًا. هذا مفيد خصوصًا لـ:

- الملفات أو مجموعات البيانات الكبيرة.
- التحديثات في الوقت الحقيقي (مثل الدردشة وأشرطة التقدم).
- الحسابات طويلة الأمد حيث تريد إبقاء المستخدم على اطلاع دائم.

إليك ما تحتاج لمعرفته على مستوى عالٍ عن البث:

- يتم تسليم البيانات تدريجيًا، وليس دفعة واحدة.
- يمكن للعميل معالجة البيانات فور وصولها.
- يقلل من زمن الاستجابة المحسوس ويحسن تجربة المستخدم.

### لماذا نستخدم البث؟

الأسباب لاستخدام البث هي كالتالي:

- يحصل المستخدمون على ردود فعل فورية، وليس فقط في النهاية
- يمكّن التطبيقات في الوقت الحقيقي وواجهات المستخدم التفاعلية
- استخدام أكثر كفاءة لموارد الشبكة والحوسبة

### مثال بسيط: خادم وعميل بث HTTP

إليك مثالًا بسيطًا لكيفية تنفيذ البث:

#### بايثون

**الخادم (بايثون، باستخدام FastAPI و StreamingResponse):**

```python
from fastapi import FastAPI
from fastapi.responses import StreamingResponse
import time

app = FastAPI()

async def event_stream():
    for i in range(1, 6):
        yield f"data: Message {i}\n\n"
        time.sleep(1)

@app.get("/stream")
def stream():
    return StreamingResponse(event_stream(), media_type="text/event-stream")
```

**العميل (بايثون، باستخدام requests):**

```python
import requests

with requests.get("http://localhost:8000/stream", stream=True) as r:
    for line in r.iter_lines():
        if line:
            print(line.decode())
```

يوضح هذا المثال خادمًا يرسل سلسلة من الرسائل إلى العميل حين تصبح متاحة، بدلاً من الانتظار حتى تكون جميع الرسائل جاهزة.

**كيف يعمل:**

- الخادم يُخاطب كل رسالة فور جاهزيتها.
- العميل يستلم ويطبع كل جزء حال وصوله.

**المتطلبات:**

- يجب أن يستخدم الخادم استجابة قابلة للبث (مثلاً `StreamingResponse` في FastAPI).
- يجب أن يعالج العميل الاستجابة كتيار (`stream=True` في requests).
- نوع المحتوى عادةً `text/event-stream` أو `application/octet-stream`.

#### جافا

**الخادم (جافا، باستخدام Spring Boot و Server-Sent Events):**

```java
@RestController
public class CalculatorController {

    @GetMapping(value = "/calculate", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    public Flux<ServerSentEvent<String>> calculate(@RequestParam double a,
                                                   @RequestParam double b,
                                                   @RequestParam String op) {
        
        double result;
        switch (op) {
            case "add": result = a + b; break;
            case "sub": result = a - b; break;
            case "mul": result = a * b; break;
            case "div": result = b != 0 ? a / b : Double.NaN; break;
            default: result = Double.NaN;
        }

        return Flux.<ServerSentEvent<String>>just(
                    ServerSentEvent.<String>builder()
                        .event("info")
                        .data("Calculating: " + a + " " + op + " " + b)
                        .build(),
                    ServerSentEvent.<String>builder()
                        .event("result")
                        .data(String.valueOf(result))
                        .build()
                )
                .delayElements(Duration.ofSeconds(1));
    }
}
```

**العميل (جافا، باستخدام Spring WebFlux WebClient):**

```java
@SpringBootApplication
public class CalculatorClientApplication implements CommandLineRunner {

    private final WebClient client = WebClient.builder()
            .baseUrl("http://localhost:8080")
            .build();

    @Override
    public void run(String... args) {
        client.get()
                .uri(uriBuilder -> uriBuilder
                        .path("/calculate")
                        .queryParam("a", 7)
                        .queryParam("b", 5)
                        .queryParam("op", "mul")
                        .build())
                .accept(MediaType.TEXT_EVENT_STREAM)
                .retrieve()
                .bodyToFlux(String.class)
                .doOnNext(System.out::println)
                .blockLast();
    }
}
```

**ملاحظات تنفيذ جافا:**

- يستخدم مجموعة Spring Boot التفاعلية مع `Flux` للبث
- يوفر `ServerSentEvent` تدفق أحداث منظم مع أنواع الأحداث
- `WebClient` مع `bodyToFlux()` يمكّن استهلاك البث التفاعلي
- `delayElements()` يحاكي وقت المعالجة بين الأحداث
- يمكن للأحداث أن تحتوي على أنواع (`info`, `result`) لتحكم أفضل في العميل

### مقارنة: البث الكلاسيكي مقابل بث MCP

يمكن تمثيل الفرق بين كيفية عمل البث "الكلاسيكي" مقابل بث MCP كما يلي:

| الخاصية                | بث HTTP الكلاسيكي          | بث MCP (الإشعارات)               |
|------------------------|----------------------------|----------------------------------|
| الرد الرئيسي           | مقسم إلى أجزاء             | منفرد، في النهاية                |
| تحديثات التقدم         | تُرسل على شكل أجزاء        | تُرسل كإشعارات                  |
| متطلبات العميل          | يجب معالجة التدفق          | يجب تنفيذ معالجة الرسائل         |
| حالة الاستخدام         | ملفات كبيرة، تدفقات رموز AI| التقدم، السجلات، ردود فعل في الوقت الحقيقي |

### الفروقات الرئيسية الملحوظة

بالإضافة إلى ذلك، إليك بعض الفروقات الرئيسية:

- **نمط الاتصال:**
  - البث HTTP الكلاسيكي: يستخدم ترميز النقل المجزأ البسيط لإرسال البيانات على أجزاء
  - بث MCP: يستخدم نظام إشعارات منظم مع بروتوكول JSON-RPC

- **تنسيق الرسائل:**
  - HTTP الكلاسيكي: أجزاء نصية عادية مع فواصل أسطر
  - MCP: كائنات LoggingMessageNotification منظمة مع بيانات وصفية

- **تنفيذ العميل:**
  - HTTP الكلاسيكي: عميل بسيط يعالج استجابات البث
  - MCP: عميل أكثر تقدمًا بمعالج رسائل لمعالجة أنواع مختلفة من الرسائل

- **تحديثات التقدم:**
  - HTTP الكلاسيكي: التقدم جزء من تيار الرد الرئيسي
  - MCP: التقدم يُرسل عبر رسائل إشعارات منفصلة بينما يأتي الرد الرئيسي في النهاية

### التوصيات

هناك بعض التوصيات عند الاختيار بين تنفيذ البث الكلاسيكي (كنقطة نهاية عرضناها باستخدام `/stream`) أو اختيار البث عبر MCP.

- **للحاجات البسيطة للبث:** البث HTTP الكلاسيكي أبسط في التنفيذ وكافٍ لاحتياجات البث الأساسية.

- **للتطبيقات التفاعلية المعقدة:** يوفر بث MCP نهجًا أكثر تنظيمًا مع بيانات وصفية أغنى وفصل بين الإشعارات والنتائج النهائية.

- **لتطبيقات الذكاء الاصطناعي:** نظام إشعارات MCP مفيد بشكل خاص للمهام AI الطويلة حيث ترغب في إبقاء المستخدمين على اطلاع على التقدم.

## البث في MCP

حسنًا، لقد رأيت بعض التوصيات والمقارنات حتى الآن حول الفرق بين البث الكلاسيكي والبث في MCP. لنفصل الآن كيف يمكنك الاستفادة من البث في MCP.

فهم كيفية عمل البث داخل إطار عمل MCP ضروري لبناء تطبيقات تفاعلية تقدم ردود فعل في الوقت الحقيقي للمستخدمين أثناء العمليات الطويلة.

في MCP، البث ليس عن إرسال الرد الرئيسي على أجزاء، بل عن إرسال **الإشعارات** إلى العميل أثناء معالجة أداة لطلب. يمكن أن تتضمن هذه الإشعارات تحديثات تقدم، سجلات، أو أحداث أخرى.

### كيف يعمل

النتيجة الرئيسية تُرسل بعد ذلك بشكل رد واحد. لكن يمكن إرسال الإشعارات كرسائل منفصلة خلال المعالجة وبالتالي تحديث العميل في الوقت الحقيقي. يجب أن يكون العميل قادرًا على التعامل مع هذه الإشعارات وعرضها.

## ما هي الإشعارات؟

قلنا "إشعار"، ماذا يعني ذلك في سياق MCP؟

الإشعار رسالة يُرسلها الخادم إلى العميل لإعلامه بالتقدم، الوضع، أو الأحداث الأخرى أثناء عملية طويلة. تحسن الإشعارات الشفافية وتجربة المستخدم.

على سبيل المثال، من المفترض أن يرسل العميل إشعارًا بمجرد إتمام المصافحة الأولية مع الخادم.

تشبه الإشعار رسالة JSON كما يلي:

```json
{
  jsonrpc: "2.0";
  method: string;
  params?: {
    [key: string]: unknown;
  };
}
```

تنتمي الإشعارات لموضوع في MCP يُعرف باسم ["Logging"](https://modelcontextprotocol.io/specification/draft/server/utilities/logging).

لكي يعمل التسجيل، يحتاج الخادم لتمكينه كميزة/قدرة كما يلي:

```json
{
  "capabilities": {
    "logging": {}
  }
}
```

> [!NOTE]
> اعتمادًا على SDK المستخدم، قد يكون التسجيل ممكنًا بشكل افتراضي، أو قد تحتاج إلى تفعيله صراحةً في تكوين الخادم.

هناك أنواع مختلفة من الإشعارات:

| المستوى    | الوصف                         | مثال لحالة الاستخدام          |
|------------|-------------------------------|-------------------------------|
| debug      | معلومات تصحيح تفصيلية         | نقاط دخول/خروج الدوال         |
| info       | رسائل معلومات عامة            | تحديثات تقدم العملية          |
| notice     | أحداث طبيعية ولكن مهمة        | تغييرات التهيئة              |
| warning    | حالات تحذير                  | استخدام ميزة مهجورة          |
| error      | حالات أخطاء                  | فشل العمليات                |
| critical   | حالات حرجة                   | أعطال مكونات النظام          |
| alert      | يجب اتخاذ إجراء فورًا          | اكتشاف تلف في البيانات        |
| emergency  | النظام غير قابل للاستخدام     | فشل كامل للنظام              |

## تنفيذ الإشعارات في MCP

لتنفيذ الإشعارات في MCP، تحتاج إلى إعداد كل من الخادم والعميل للتعامل مع التحديثات في الوقت الحقيقي. هذا يسمح لتطبيقك بتقديم ردود فعل فورية للمستخدمين أثناء العمليات الطويلة.

### جانب الخادم: إرسال الإشعارات

لنبدأ بجانب الخادم. في MCP، تعرف الأدوات التي يمكنها إرسال الإشعارات أثناء معالجة الطلبات. يستخدم الخادم كائن السياق (عادةً `ctx`) لإرسال الرسائل إلى العميل.

#### بايثون

```python
@mcp.tool(description="A tool that sends progress notifications")
async def process_files(message: str, ctx: Context) -> TextContent:
    await ctx.info("Processing file 1/3...")
    await ctx.info("Processing file 2/3...")
    await ctx.info("Processing file 3/3...")
    return TextContent(type="text", text=f"Done: {message}")
```

في المثال السابق، ترسل أداة `process_files` ثلاث إشعارات إلى العميل أثناء معالجتها لكل ملف. تُستخدم الطريقة `ctx.info()` لإرسال رسائل إعلامية.

بالإضافة إلى ذلك، لتمكين الإشعارات، تأكد من أن الخادم يستخدم نقلًا قابلًا للبث (مثل `streamable-http`) وأن العميل ينفذ معالج رسائل لمعالجة الإشعارات. إليك كيفية إعداد الخادم لاستخدام نقل `streamable-http`:

```python
mcp.run(transport="streamable-http")
```

#### .NET

```csharp
[Tool("A tool that sends progress notifications")]
public async Task<TextContent> ProcessFiles(string message, ToolContext ctx)
{
    await ctx.Info("Processing file 1/3...");
    await ctx.Info("Processing file 2/3...");
    await ctx.Info("Processing file 3/3...");
    return new TextContent
    {
        Type = "text",
        Text = $"Done: {message}"
    };
}
```

في هذا المثال لـ .NET، تم تزيين أداة `ProcessFiles` بوسم `Tool` وترسل ثلاث إشعارات إلى العميل أثناء معالجة كل ملف. تُستخدم الطريقة `ctx.Info()` لإرسال رسائل إعلامية.

لتمكين الإشعارات في خادم MCP الخاص بك بـ .NET، تأكد من استخدام نقل قابل للبث:

```csharp
var builder = McpBuilder.Create();
await builder
    .UseStreamableHttp() // Enable streamable HTTP transport
    .Build()
    .RunAsync();
```

### جانب العميل: استقبال الإشعارات

يجب على العميل تنفيذ معالج رسائل لمعالجة وعرض الإشعارات فور وصولها.

#### بايثون

```python
async def message_handler(message):
    if isinstance(message, types.ServerNotification):
        print("NOTIFICATION:", message)
    else:
        print("SERVER MESSAGE:", message)

async with ClientSession(
   read_stream, 
   write_stream,
   logging_callback=logging_collector,
   message_handler=message_handler,
) as session:
```

في الكود السابق، تتحقق دالة `message_handler` مما إذا كانت الرسالة الواردة إشعارًا. إذا كانت كذلك، تقوم بطباعة الإشعار؛ وإلا تعالجه كرسالة خادم عادية. لاحظ أيضًا كيف تم تهيئة `ClientSession` مع `message_handler` لمعالجة الإشعارات الواردة.

#### .NET

```csharp
// Define a message handler
void MessageHandler(IJsonRpcMessage message)
{
    if (message is ServerNotification notification)
    {
        Console.WriteLine($"NOTIFICATION: {notification}");
    }
    else
    {
        Console.WriteLine($"SERVER MESSAGE: {message}");
    }
}

// Create and use a client session with the message handler
var clientOptions = new ClientSessionOptions
{
    MessageHandler = MessageHandler,
    LoggingCallback = (level, message) => Console.WriteLine($"[{level}] {message}")
};

using var client = new ClientSession(readStream, writeStream, clientOptions);
await client.InitializeAsync();

// Now the client will process notifications through the MessageHandler
```

في هذا المثال لـ .NET، تتحقق دالة `MessageHandler` مما إذا كانت الرسالة الواردة إشعارًا. إذا كانت كذلك، تقوم بطباعة الإشعار؛ وإلا تعالجه كرسالة خادم عادية. تم تهيئة `ClientSession` بمعالج الرسائل عبر `ClientSessionOptions`.

لتمكين الإشعارات، تأكد من أن الخادم يستخدم نقلًا قابلاً للبث (مثل `streamable-http`) وأن العميل ينفذ معالج رسائل لمعالجة الإشعارات.

## إشعارات التقدم والسيناريوهات

تشرح هذه القسم مفهوم إشعارات التقدم في MCP، لماذا تهم، وكيفية تنفيذها باستخدام Streamable HTTP. ستجد أيضًا مهمة عملية لتعزيز فهمك.

إشعارات التقدم هي رسائل في الوقت الحقيقي تُرسل من الخادم إلى العميل أثناء العمليات الطويلة. بدلاً من الانتظار حتى تنتهي العملية بالكامل، يبقي الخادم العميل محدثًا بالحالة الحالية. هذا يحسن الشفافية وتجربة المستخدم ويسهل عملية التصحيح.

**مثال:**

```text

"Processing document 1/10"
"Processing document 2/10"
...
"Processing complete!"

```

### لماذا استخدام إشعارات التقدم؟

إشعارات التقدم ضرورية لأسباب عدة:

- **تحسين تجربة المستخدم:** يرى المستخدمون التحديثات أثناء تقدم العمل وليس فقط في النهاية.
- **ردود فعل في الوقت الحقيقي:** يمكن للعملاء عرض أشرطة تقدم أو سجلات، مما يجعل التطبيق يبدو أكثر تفاعلية.
- **تسهيل التصحيح والمراقبة:** يمكن للمطورين والمستخدمين رؤية أين قد تكون العملية بطيئة أو متوقفة.

### كيفية تنفيذ إشعارات التقدم

إليك كيفية تنفيذ إشعارات التقدم في MCP:

- **على الخادم:** استخدم `ctx.info()` أو `ctx.log()` لإرسال الإشعارات مع معالجة كل عنصر. هذا يرسل رسالة للعميل قبل أن يصبح الناتج الرئيسي جاهزًا.
- **على العميل:** نفذ معالج رسائل يستمع ويعرض الإشعارات فور وصولها. يميز هذا المعالج بين الإشعارات والنتيجة النهائية.

**مثال الخادم:**

#### بايثون

```python
@mcp.tool(description="A tool that sends progress notifications")
async def process_files(message: str, ctx: Context) -> TextContent:
    for i in range(1, 11):
        await ctx.info(f"Processing document {i}/10")
    await ctx.info("Processing complete!")
    return TextContent(type="text", text=f"Done: {message}")
```

**مثال العميل:**

#### بايثون

```python
async def message_handler(message):
    if isinstance(message, types.ServerNotification):
        print("NOTIFICATION:", message)
    else:
        print("SERVER MESSAGE:", message)
```

الأمان ضروري عند كشف خوادم MCP عبر HTTP. يضيف HTTP القابل للبث أسطح هجوم جديدة ويتطلب تكوينًا دقيقًا.

- **المصادقة**: نفّذ المصادقة (مثل مفاتيح API، OAuth) للنشر في بيئات الإنتاج.

- سجّل وراقب كل الوصول والأخطاء.

## الترقية من SSE إلى Streamable HTTP

لتطبيقات تستخدم حاليًا أحداث الخادم المُرسلة (SSE)، يوفر الترحيل إلى Streamable HTTP قدرات محسّنة واستدامة أفضل على المدى الطويل لتطبيقات MCP الخاصة بك.

### لماذا الترقية؟

هناك سببان مقنعان للترقية من SSE إلى Streamable HTTP:

- يوفر Streamable HTTP قابلية توسع أفضل، توافقًا أعلى، ودعم إعلام أغنى من SSE.
- هو النقل الموصى به لتطبيقات MCP الجديدة.

### خطوات الترحيل

إليك كيفية الترحيل من SSE إلى Streamable HTTP في تطبيقات MCP الخاصة بك:

- **تحديث كود الخادم** لاستخدام `transport="streamable-http"` في `mcp.run()`.
- **تحديث كود العميل** لاستخدام `streamablehttp_client` بدلاً من عميل SSE.
- **تنفيذ معالج رسائل** في العميل لمعالجة الإشعارات.
- **اختبار التوافق** مع الأدوات وسير العمل الحالية.

### الحفاظ على التوافق

من المستحسن الحفاظ على التوافق مع عملاء SSE الحاليين أثناء عملية الترحيل. إليك بعض الاستراتيجيات:

- يمكنك دعم كل من SSE و Streamable HTTP عن طريق تشغيل كليهما على نقاط نهاية مختلفة.
- قم بترحيل العملاء تدريجيًا إلى النقل الجديد.

### التحديات

تأكد من معالجة التحديات التالية أثناء الترحيل:

- ضمان تحديث جميع العملاء
- التعامل مع الفروقات في تسليم الإشعارات

**السيناريو:**

**الخطوات:**
