# پخش جریانی HTTPS با پروتکل زمینه مدل (MCP)

این فصل راهنمایی جامع برای پیاده‌سازی پخش جریانی امن، مقیاس‌پذیر و زمان واقعی با استفاده از پروتکل زمینه مدل (MCP) و HTTPS فراهم می‌کند. این فصل شامل انگیزه برای پخش جریانی، مکانیزم‌های انتقال موجود، نحوه پیاده‌سازی HTTP قابل پخش در MCP، بهترین تمرین‌های امنیتی، مهاجرت از SSE، و راهنمایی عملی برای ساخت برنامه‌های MCP پخش جریانی خودتان است.

> **نگاهی به آینده:** این درس HTTP قابل پخش را تحت **مشخصات MCP در تاریخ 2025-11-25** شرح می‌دهد، جایی که یک جلسه در طی `initialize` ایجاد شده و با هدر `Mcp-Session-Id` پین می‌شود. نسخه آزمایشی `2026-07-28` کاملاً فرایند دست دادن و شناسه جلسه را حذف می‌کند، به گونه‌ای که هر درخواست خودکفا بوده و می‌تواند به هر نمونه سرور بدون نیاز به جلسات چسبنده هدایت شود. برای جزئیات بیشتر به [چه تغییراتی در MCP رخ داده است: نسخه آزمایشی 2026-07-28](../../01-CoreConcepts/mcp-2026-07-28-release-candidate.md) مراجعه کنید.

## مکانیزم‌های انتقال و پخش جریانی در MCP

این بخش به بررسی مکانیزم‌های انتقال مختلف موجود در MCP و نقش آن‌ها در فعال‌سازی قابلیت‌های پخش جریانی برای ارتباط زمان واقعی بین کلاینت‌ها و سرورها می‌پردازد.

### مکانیزم انتقال چیست؟

مکانیزم انتقال نحوه تبادل داده بین کلاینت و سرور را تعریف می‌کند. MCP از انواع انتقال متعددی پشتیبانی می‌کند تا با محیط‌ها و نیازهای مختلف سازگار باشد:

- **stdio**: ورودی/خروجی استاندارد، مناسب ابزارهای محلی و مبتنی بر CLI. ساده اما برای وب یا فضای ابری مناسب نیست.
- **SSE (رویدادهای ارسال شده از سمت سرور)**: به سرورها اجازه می‌دهد به‌روزرسانی‌های زمان واقعی را از طریق HTTP به کلاینت‌ها ارسال کنند. برای رابط‌های وب مناسب است، اما از نظر مقیاس‌پذیری و انعطاف محدود است. طبق مشخصات MCP در تاریخ 2025-06-18، انتقال مستقل SSE منسوخ شده و با انتقال "HTTP قابل پخش" جایگزین شده است.
- **HTTP قابل پخش**: انتقال مدرن براساس HTTP برای پخش جریانی، پشتیبانی از اطلاع‌رسانی‌ها و مقیاس‌پذیری بهتر. برای اغلب سناریوهای تولید و فضای ابری توصیه می‌شود.

### جدول مقایسه

برای درک تفاوت‌های این مکانیزم‌های انتقال، جدول مقایسه زیر را بررسی کنید:

| انتقال           | به‌روزرسانی‌های زمان واقعی | پخش جریانی | مقیاس‌پذیری | مورد استفاده             |
|-------------------|---------------------------|------------|-------------|--------------------------|
| stdio             | خیر                       | خیر        | کم          | ابزارهای محلی CLI        |
| SSE               | بله                       | بله        | متوسط       | وب، به‌روزرسانی زمان واقعی |
| HTTP قابل پخش     | بله                       | بله        | بالا        | فضای ابری، چند کلاینت    |

> **نکته:** انتخاب مکانیزم انتقال مناسب بر عملکرد، مقیاس‌پذیری و تجربه کاربر تاثیرگذار است. **HTTP قابل پخش** برای برنامه‌های مدرن، مقیاس‌پذیر و آماده فضای ابری توصیه می‌شود.

توجه کنید که مکانیزم‌های stdio و SSE که در فصل‌های قبلی دیدید و این فصل پوشش دهنده انتقال HTTP قابل پخش است.

## پخش جریانی: مفاهیم و انگیزه

درک مفاهیم و انگیزه‌های اساسی پشت پخش جریانی برای پیاده‌سازی سیستم‌های ارتباطی زمان واقعی مؤثر ضروری است.

**پخش جریانی** تکنیکی در برنامه‌نویسی شبکه است که اجازه می‌دهد داده‌ها به صورت بخش‌های کوچک و قابل مدیریت یا به عنوان یک دنباله رویداد ارسال و دریافت شوند، به جای اینکه منتظر آماده شدن پاسخ کامل بود. این خصوصاً برای موارد زیر کاربردی است:

- فایل‌ها یا مجموعه داده‌های بزرگ.
- به‌روزرسانی‌های زمان واقعی (مثلاً چت، نوارهای پیشرفت).
- محاسبات طولانی‌مدت که می‌خواهید کاربر را در جریان نگه دارید.

در اینجا نکاتی که باید درباره پخش جریانی بدانید:

- داده‌ها به صورت تدریجی ارسال می‌شوند، نه همه یکجا.
- کلاینت می‌تواند داده‌ها را هنگام دریافت پردازش کند.
- به کاهش تأخیر درک شده و بهبود تجربه کاربر کمک می‌کند.

### چرا از پخش جریانی استفاده کنیم؟

دلایل استفاده از پخش جریانی عبارتند از:

- کاربران فوراً بازخورد دریافت می‌کنند، نه فقط در انتها
- امکان‌پذیر ساختن برنامه‌های زمان واقعی و رابط‌های پاسخگو
- استفاده مؤثرتر از منابع شبکه و محاسبات

### مثال ساده: سرور و کلاینت HTTP پخش جریانی

در اینجا نمونه ساده‌ای از پیاده‌سازی پخش جریانی داریم:

#### پایتون

**سرور (پایتون، با استفاده از FastAPI و StreamingResponse):**

```python
from fastapi import FastAPI
from fastapi.responses import StreamingResponse
import time

app = FastAPI()

async def event_stream():
    for i in range(1, 6):
        yield f"data: Message {i}\n\n"
        time.sleep(1)

@app.get("/stream")
def stream():
    return StreamingResponse(event_stream(), media_type="text/event-stream")
```

**کلاینت (پایتون، با استفاده از requests):**

```python
import requests

with requests.get("http://localhost:8000/stream", stream=True) as r:
    for line in r.iter_lines():
        if line:
            print(line.decode())
```

این مثال نشان می‌دهد که سرور چگونه سری پیام‌ها را به محض آماده شدن به کلاینت ارسال می‌کند، به جای اینکه منتظر آماده شدن همه پیام‌ها باشد.

**نحوه کارکرد:**

- سرور هر پیام را وقتی آماده است ارسال می‌کند.
- کلاینت هر بخش داده را هنگام دریافت دریافت و چاپ می‌کند.

**نیازمندی‌ها:**

- سرور باید از پاسخ پخش جریانی استفاده کند (مثلاً `StreamingResponse` در FastAPI).
- کلاینت باید پاسخ را به صورت جریان پردازش کند (`stream=True` در requests).
- نوع محتوا معمولاً `text/event-stream` یا `application/octet-stream` است.

#### جاوا

**سرور (جاوا، با استفاده از Spring Boot و Server-Sent Events):**

```java
@RestController
public class CalculatorController {

    @GetMapping(value = "/calculate", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    public Flux<ServerSentEvent<String>> calculate(@RequestParam double a,
                                                   @RequestParam double b,
                                                   @RequestParam String op) {
        
        double result;
        switch (op) {
            case "add": result = a + b; break;
            case "sub": result = a - b; break;
            case "mul": result = a * b; break;
            case "div": result = b != 0 ? a / b : Double.NaN; break;
            default: result = Double.NaN;
        }

        return Flux.<ServerSentEvent<String>>just(
                    ServerSentEvent.<String>builder()
                        .event("info")
                        .data("Calculating: " + a + " " + op + " " + b)
                        .build(),
                    ServerSentEvent.<String>builder()
                        .event("result")
                        .data(String.valueOf(result))
                        .build()
                )
                .delayElements(Duration.ofSeconds(1));
    }
}
```

**کلاینت (جاوا، با استفاده از Spring WebFlux WebClient):**

```java
@SpringBootApplication
public class CalculatorClientApplication implements CommandLineRunner {

    private final WebClient client = WebClient.builder()
            .baseUrl("http://localhost:8080")
            .build();

    @Override
    public void run(String... args) {
        client.get()
                .uri(uriBuilder -> uriBuilder
                        .path("/calculate")
                        .queryParam("a", 7)
                        .queryParam("b", 5)
                        .queryParam("op", "mul")
                        .build())
                .accept(MediaType.TEXT_EVENT_STREAM)
                .retrieve()
                .bodyToFlux(String.class)
                .doOnNext(System.out::println)
                .blockLast();
    }
}
```

**نکات پیاده‌سازی جاوا:**

- استفاده از استک واکنشی Spring Boot با `Flux` برای پخش جریانی
- `ServerSentEvent` پخش رویداد ساختاریافته با انواع رویدادها را فراهم می‌کند
- `WebClient` با `bodyToFlux()` مصرف پخش جریانی واکنشی را فعال می‌کند
- `delayElements()` زمان پردازش بین رویدادها را شبیه‌سازی می‌کند
- رویدادها می‌توانند انواع داشته باشند (`info`، `result`) برای مدیریت بهتر کلاینت

### مقایسه: پخش جریانی کلاسیک در برابر پخش جریانی MCP

تفاوت‌های نحوه کارکرد پخش جریانی به صورت "کلاسیک" و نحوه کارکرد آن در MCP به شکل زیر قابل نمایش است:

| ویژگی                  | پخش جریانی HTTP کلاسیک          | پخش جریانی MCP (اطلاع‌رسانی‌ها)   |
|------------------------|----------------------------------|-------------------------------------|
| پاسخ اصلی              | بخش‌بندی شده                      | تنها یک پاسخ در انتها                |
| به‌روزرسانی پیشرفت     | ارسال شده به صورت بخش‌های داده    | ارسال شده به صورت اطلاع‌رسانی‌ها    |
| نیازمندی‌های کلاینت    | باید جریان را پردازش کند           | باید پیام‌ها را مدیریت کند           |
| مورد استفاده           | فایل‌های بزرگ، جریان‌های توکن AI  | پیشرفت، لاگ‌ها، بازخورد زمان واقعی  |

### تفاوت‌های کلیدی مشاهده شده

علاوه بر این، چند تفاوت کلیدی عبارتند از:

- **الگوی ارتباط:**
  - پخش جریانی HTTP کلاسیک: از کدگذاری انتقال بخش‌بندی ساده برای ارسال داده‌ها به صورت بخش استفاده می‌کند
  - پخش جریانی MCP: از سیستم اطلاع‌رسانی ساختاریافته با پروتکل JSON-RPC استفاده می‌کند

- **فرمت پیام:**
  - HTTP کلاسیک: بخش‌های متن ساده با خطوط جدید
  - MCP: اشیای ساختاریافته LoggingMessageNotification با متادیتا

- **پیاده‌سازی کلاینت:**
  - HTTP کلاسیک: کلاینت ساده که پاسخ‌های پخش جریانی را پردازش می‌کند
  - MCP: کلاینت پیشرفته‌تر با مدیریت پیام برای پردازش انواع مختلف پیام‌ها

- **به‌روزرسانی پیشرفت:**
  - HTTP کلاسیک: پیشرفت بخشی از جریان پاسخ اصلی است
  - MCP: پیشرفت از طریق پیام‌های اطلاع‌رسانی جدا ارسال می‌شود در حالی که پاسخ اصلی در انتها می‌آید

### توصیه‌ها

هنگامی که بین پیاده‌سازی پخش جریانی کلاسیک (به عنوان یک نقطه پایانی که در بالا با `/stream` نشان دادیم) و پخش جریانی از طریق MCP انتخاب می‌کنید، موارد زیر را توصیه می‌کنیم.

- **برای نیازهای پخش جریانی ساده:** پخش جریانی HTTP کلاسیک ساده‌تر برای پیاده‌سازی است و برای نیازهای پایه کافی است.

- **برای برنامه‌های تعاملی پیچیده:** پخش جریانی MCP رویکرد ساختاریافته‌تری با متادیتای غنی‌تر و تفکیک بین اطلاع‌رسانی‌ها و نتایج نهایی ارائه می‌دهد.

- **برای برنامه‌های هوش مصنوعی:** سیستم اطلاع‌رسانی MCP به خصوص برای وظایف طولانی‌مدت AI که می‌خواهید کاربران را در جریان پیشرفت نگه دارید، مفید است.

## پخش جریانی در MCP

خب، تا کنون برخی توصیه‌ها و مقایسه‌ها درباره تفاوت بین پخش جریانی کلاسیک و پخش جریانی در MCP دیدید. حالا دقیق‌تر می‌پردازیم به نحوه استفاده از پخش جریانی در MCP.

درک نحوه کارکرد پخش جریانی در چارچوب MCP برای ساخت برنامه‌های پاسخگو که در طول عملیات‌های طولانی بازخورد زمان واقعی ارائه می‌دهند، ضروری است.

در MCP، پخش جریانی به معنای ارسال پاسخ اصلی به صورت بخش‌بندی شده نیست، بلکه ارسال **اطلاع‌رسانی‌ها** به کلاینت در حین پردازش درخواست توسط ابزار است. این اطلاع‌رسانی‌ها می‌توانند شامل به‌روزرسانی‌های پیشرفت، گزارش‌ها یا رویدادهای دیگر باشند.

### نحوه کارکرد

نتیجه اصلی همچنان به صورت یک پاسخ واحد ارسال می‌شود. با این حال، اطلاع‌رسانی‌ها می‌توانند به صورت پیام‌های جداگانه در طول پردازش ارسال شوند و بنابراین کلاینت را در زمان واقعی به‌روزرسانی کنند. کلاینت باید قادر به مدیریت و نمایش این اطلاع‌رسانی‌ها باشد.

## اطلاع‌رسانی چیست؟

گفتیم "اطلاع‌رسانی"، این در زمینه MCP به چه معناست؟

اطلاع‌رسانی پیامی است که از سرور به کلاینت ارسال می‌شود تا درباره پیشرفت، وضعیت یا رویدادهای دیگر طی یک عملیات طولانی مدت اطلاع دهد. اطلاع‌رسانی‌ها شفافیت و تجربه کاربری را بهبود می‌بخشند.

به عنوان مثال، کلاینت باید پس از انجام دست دادن اولیه با سرور، یک اطلاع‌رسانی ارسال کند.

یک اطلاع‌رسانی به صورت پیام JSON به شکل زیر است:

```json
{
  jsonrpc: "2.0";
  method: string;
  params?: {
    [key: string]: unknown;
  };
}
```

اطلاع‌رسانی‌ها به یک موضوع در MCP تعلق دارند که به آن ["Logging"](https://modelcontextprotocol.io/specification/draft/server/utilities/logging) گفته می‌شود.

> **اعلان منسوخ شدن:** نسخه آزمایشی مشخصات MCP در تاریخ `2026-07-28` عنصر Logging را به نفع `stderr` برای انتقال‌های stdio و OpenTelemetry برای مشاهدات ساختاریافته منسوخ اعلام می‌کند. Logging در `2025-11-25` و حداقل یک سال پس از هر منسوخ شدن رسمی همچنان کار می‌کند. برای جزئیات بیشتر به [چه تغییراتی در MCP رخ داده است: نسخه آزمایشی 2026-07-28](../../01-CoreConcepts/mcp-2026-07-28-release-candidate.md) مراجعه کنید.

برای فعال کردن Logging، سرور نیاز دارد آن را به عنوان ویژگی/قابلیت فعال کند به شکل زیر:

```json
{
  "capabilities": {
    "logging": {}
  }
}
```

> [!NOTE]
> بسته به SDK استفاده شده، ممکن است Logging به طور پیش‌فرض فعال باشد یا شما نیاز به فعال‌سازی صریح آن در تنظیمات سرور خود داشته باشید.

انواع مختلفی از اطلاع‌رسانی‌ها وجود دارد:

| سطح       | توضیح                      | نمونه مورد استفاده           |
|-----------|----------------------------|------------------------------|
| debug     | اطلاعات دقیق اشکال‌زدایی    | نقاط ورود/خروج توابع          |
| info      | پیام‌های اطلاعات عمومی       | به‌روزرسانی پیشرفت عملیات     |
| notice    | رویدادهای عادی اما مهم       | تغییرات تنظیمات               |
| warning   | شرایط هشدار                  | استفاده از ویژگی منسوخ شده     |
| error     | شرایط خطا                   | شکست عملیات                  |
| critical  | شرایط بحرانی                | شکست اجزای سیستمی            |
| alert     | اقدام فوری ضروری             | شناسایی فساد داده             |
| emergency | سیستم غیرقابل استفاده       | شکست کامل سیستم             |

## پیاده‌سازی اطلاع‌رسانی‌ها در MCP

برای پیاده‌سازی اطلاع‌رسانی‌ها در MCP، باید سمت سرور و کلاینت را به گونه‌ای تنظیم کنید که به‌روزرسانی‌های زمان واقعی را مدیریت کنند. این امکان را به برنامه شما می‌دهد تا در طول عملیات طولانی، بازخورد فوری به کاربران ارائه دهد.

### سمت سرور: ارسال اطلاع‌رسانی‌ها

از سمت سرور شروع کنیم. در MCP، شما ابزارهایی را تعریف می‌کنید که می‌توانند در حین پردازش درخواست‌ها اطلاع‌رسانی ارسال کنند. سرور از آبجکت زمینه (معمولاً `ctx`) برای ارسال پیام‌ها به کلاینت استفاده می‌کند.

#### پایتون

```python
@mcp.tool(description="A tool that sends progress notifications")
async def process_files(message: str, ctx: Context) -> TextContent:
    await ctx.info("Processing file 1/3...")
    await ctx.info("Processing file 2/3...")
    await ctx.info("Processing file 3/3...")
    return TextContent(type="text", text=f"Done: {message}")
```

در مثال قبل، ابزار `process_files` سه اطلاع‌رسانی به کلاینت ارسال می‌کند در حالی که هر فایل را پردازش می‌کند. متد `ctx.info()` برای ارسال پیام‌های اطلاعاتی استفاده شده است.

همچنین، برای فعال کردن اطلاع‌رسانی‌ها، اطمینان حاصل کنید که سرورتان از انتقال پخش جریانی (مثل `streamable-http`) استفاده می‌کند و کلاینت شما مدیریت‌کننده پیام برای پردازش اطلاع‌رسانی‌ها پیاده‌سازی کرده است. اینجا نحوه تنظیم سرور برای استفاده از انتقال `streamable-http` آمده است:

```python
mcp.run(transport="streamable-http")
```

### سمت کلاینت: دریافت اطلاع‌رسانی‌ها

کلاینت باید مدیریت‌کننده پیام را پیاده‌سازی کند تا اطلاع‌رسانی‌ها را هنگام دریافت پردازش و نمایش دهد.

#### پایتون

```python
async def message_handler(message):
    if isinstance(message, types.ServerNotification):
        print("NOTIFICATION:", message)
    else:
        print("SERVER MESSAGE:", message)

async with ClientSession(
   read_stream, 
   write_stream,
   logging_callback=logging_collector,
   message_handler=message_handler,
) as session:
```

در کد بالا، تابع `message_handler` بررسی می‌کند آیا پیام ورودی یک اطلاع‌رسانی است یا خیر. اگر باشد، اطلاع‌رسانی را چاپ می‌کند؛ در غیر این صورت، آن را به عنوان پیام معمولی سرور پردازش می‌کند. همچنین توجه کنید که `ClientSession` با `message_handler` برای مدیریت اطلاع‌رسانی‌های ورودی مقداردهی اولیه شده است.

#### .NET

```csharp
// Define a message handler
void MessageHandler(IJsonRpcMessage message)
{
    if (message is ServerNotification notification)
    {
        Console.WriteLine($"NOTIFICATION: {notification}");
    }
    else
    {
        Console.WriteLine($"SERVER MESSAGE: {message}");
    }
}

// Create and use a client session with the message handler
var clientOptions = new ClientSessionOptions
{
    MessageHandler = MessageHandler,
    LoggingCallback = (level, message) => Console.WriteLine($"[{level}] {message}")
};

using var client = new ClientSession(readStream, writeStream, clientOptions);
await client.InitializeAsync();

// Now the client will process notifications through the MessageHandler
```

در مثال .NET، تابع `MessageHandler` بررسی می‌کند آیا پیام ورودی یک اطلاع‌رسانی است یا خیر. اگر باشد، اطلاع‌رسانی را چاپ می‌کند؛ در غیر این صورت، آن را به عنوان پیام معمولی سرور پردازش می‌کند. `ClientSession` با مدیریت‌کننده پیام از طریق `ClientSessionOptions` مقداردهی اولیه شده است.

برای فعال کردن اطلاع‌رسانی‌ها، اطمینان حاصل کنید که سرور از انتقال پخش جریانی (مانند `streamable-http`) استفاده می‌کند و کلاینت شما یک مدیریت‌کننده پیام برای پردازش اطلاع‌رسانی‌ها پیاده‌سازی کرده است.

## اطلاع‌رسانی‌های پیشرفت و سناریوها

این بخش مفهوم اطلاع‌رسانی‌های پیشرفت در MCP، اهمیت آن‌ها و نحوه پیاده‌سازی آن‌ها با استفاده از HTTP قابل پخش را توضیح می‌دهد. همچنین یک تمرین عملی برای تقویت درک شما ارائه شده است.

اطلاع‌رسانی‌های پیشرفت پیام‌های زمان واقعی هستند که در طول عملیات طولانی از سرور به کلاینت ارسال می‌شوند. به جای انتظار برای اتمام کل فرایند، سرور کلاینت را درباره وضعیت جاری به‌روزرسانی می‌کند. این امر شفافیت، تجربه کاربری و اشکال‌زدایی را بهبود می‌بخشد.

**مثال:**

```text

"Processing document 1/10"
"Processing document 2/10"
...
"Processing complete!"

```

### چرا از اطلاع‌رسانی‌های پیشرفت استفاده کنیم؟

اطلاع‌رسانی‌های پیشرفت به دلایل متعددی ضروری هستند:

- **تجربه کاربری بهتر:** کاربران در حین پیشرفت کار به‌روزرسانی‌ها را می‌بینند، نه فقط در انتها.
- **بازخورد زمان واقعی:** کلاینت‌ها می‌توانند نوار پیشرفت یا لاگ‌ها را نمایش دهند که باعث احساس پاسخگویی برنامه می‌شود.
- **اشکال‌زدایی و نظارت آسان‌تر:** توسعه‌دهندگان و کاربران می‌توانند ببینند کجا ممکن است یک فرایند کند یا گیر کند.

### نحوه پیاده‌سازی اطلاع‌رسانی‌های پیشرفت

در اینجا نحوه پیاده‌سازی اطلاع‌رسانی‌های پیشرفت در MCP آمده است:

- **در سرور:** از `ctx.info()` یا `ctx.log()` برای ارسال اطلاع‌رسانی‌ها به محض پردازش هر مورد استفاده کنید. این پیام‌ها قبل از آماده شدن نتیجه اصلی به کلاینت ارسال می‌شوند.
- **در کلاینت:** یک مدیریت‌کننده پیام پیاده‌سازی کنید که به اطلاع‌رسانی‌ها گوش داده و آن‌ها را هنگام دریافت نمایش دهد. این مدیریت‌کننده بین اطلاع‌رسانی‌ها و نتیجه نهایی تمایز قائل می‌شود.

## ملاحظات امنیتی

امنیت باید در اولویت بالایی هنگام پیاده‌سازی هر سروری باشد، به‌ویژه هنگام استفاده از انتقال‌دهنده‌های مبتنی بر HTTP مانند Streamable HTTP در MCP.

زمانی که سرورهای MCP را با انتقال‌دهنده‌های مبتنی بر HTTP پیاده‌سازی می‌کنید، امنیت به یک نگرانی بسیار مهم تبدیل می‌شود که نیازمند توجه دقیق به چندین بردار حمله و مکانیسم‌های حفاظتی است.

### مرور کلی

امنیت در زمانی که سرورهای MCP را بر روی HTTP در معرض قرار می‌دهید حیاتی است. Streamable HTTP سطوح حمله جدیدی معرفی می‌کند و نیازمند تنظیمات دقیق می‌باشد.

در اینجا برخی از ملاحظات کلیدی امنیتی آمده است:

- **اعتبارسنجی هدر Origin**: همیشه هدر `Origin` را برای جلوگیری از حملات بازتنظیم DNS اعتبارسنجی کنید.
- **بایندینگ localhost**: برای توسعه محلی، سرورها را به `localhost` متصل کنید تا آنها را از دسترس عموم اینترنت دور نگه دارید.
- **احراز هویت**: برای استقرارهای تولید، احراز هویت (مثلاً کلیدهای API، OAuth) را پیاده‌سازی کنید.
- **CORS**: سیاست‌های اشتراک‌گذاری منابع چندمنشأ (CORS) را برای محدود کردن دسترسی تنظیم کنید.
- **HTTPS**: در محیط تولید از HTTPS برای رمزگذاری ترافیک استفاده کنید.

### بهترین شیوه‌ها

علاوه بر این، چندین بهترین شیوه برای پیاده‌سازی امنیت در سرور استریم MCP شما وجود دارد:

- هرگز به درخواست‌های دریافتی بدون اعتبارسنجی اعتماد نکنید.
- تمام دسترسی‌ها و خطاها را ثبت و نظارت کنید.
- وابستگی‌ها را به‌طور مرتب به‌روزرسانی کنید تا آسیب‌پذیری‌های امنیتی رفع شوند.

### چالش‌ها

هنگام پیاده‌سازی امنیت در سرورهای استریم MCP با چند چالش مواجه خواهید شد:

- تعادل بین امنیت و سهولت توسعه
- اطمینان از سازگاری با محیط‌های مختلف مشتری


## ارتقا از SSE به Streamable HTTP

برای برنامه‌هایی که در حال حاضر از رویدادهای ارسال شده توسط سرور (SSE) استفاده می‌کنند، مهاجرت به Streamable HTTP امکانات پیشرفته‌تر و پایداری بلندمدت بهتر برای پیاده‌سازی‌های MCP شما فراهم می‌کند.

### چرا ارتقا دهیم؟

دو دلیل قانع‌کننده برای ارتقا از SSE به Streamable HTTP وجود دارد:

- Streamable HTTP قابلیت افزایش بهتر، سازگاری بالاتر، و پشتیبانی غنی‌تر از اعلان‌ها نسبت به SSE ارائه می‌دهد.
- این روش انتقال برای برنامه‌های جدید MCP توصیه می‌شود.

### مراحل مهاجرت

در اینجا نحوه مهاجرت از SSE به Streamable HTTP در برنامه‌های MCP شما آمده است:

- **کد سرور را به‌روزرسانی کنید** تا در `mcp.run()` از `transport="streamable-http"` استفاده شود.
- **کد مشتری را به‌روزرسانی کنید** تا به جای مشتری SSE از `streamablehttp_client` استفاده گردد.
- **یک هندلر پیام در مشتری پیاده‌سازی کنید** تا اعلان‌ها را پردازش کند.
- **سازگاری را با ابزارها و جریان‌های کاری موجود تست کنید**.

### حفظ سازگاری

توصیه می‌شود که در طول فرایند مهاجرت سازگاری با مشتریان SSE موجود حفظ شود. در اینجا برخی استراتژی‌ها آورده شده است:

- می‌توانید از هر دو روش SSE و Streamable HTTP با اجرای هر دو انتقال بر روی نقاط انتهایی مختلف پشتیبانی کنید.
- به‌تدریج مشتری‌ها را به روش انتقال جدید مهاجرت دهید.

### چالش‌ها

در طول مهاجرت مطمئن شوید که چالش‌های زیر را برطرف می‌کنید:

- اطمینان از به‌روزرسانی تمام مشتری‌ها
- مدیریت تفاوت‌ها در تحویل اعلان‌ها

### تمرین: ساخت برنامه استریم MCP خودتان

**سناریو:**
یک سرور و مشتری MCP بسازید که سرور یک فهرست آیتم‌ها (مثلاً فایل‌ها یا اسناد) را پردازش کند و برای هر آیتم پردازش شده یک اعلان ارسال کند. مشتری باید هر اعلان را به محض رسیدن نمایش دهد.

**مراحل:**

1. پیاده‌سازی یک ابزار سرور که یک فهرست را پردازش کرده و برای هر آیتم اعلان ارسال کند.
2. پیاده‌سازی مشتری با هندلر پیام برای نمایش اعلان‌ها در زمان واقعی.
3. اجرای همزمان سرور و مشتری برای تست پیاده‌سازی و مشاهده اعلان‌ها.
