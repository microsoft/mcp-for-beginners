# মডেল কন্টেক্সট প্রোটোকল (MCP) দিয়ে HTTPS স্ট্রিমিং

এই অধ্যায়টি নিরাপদ, স্কেলযোগ্য, এবং রিয়েল-টাইম স্ট্রিমিং বাস্তবায়নের জন্য মডেল কন্টেক্সট প্রোটোকল (MCP) ব্যবহার করে HTTPS এর সাথে একটি বিস্তৃত নির্দেশিকা প্রদান করে। এটি স্ট্রিমিংয়ের প্রয়োজনীয়তা, উপলভ্য পরিবহন প্রক্রিয়া, MCP তে স্ট্রিমেবল HTTP কিভাবে বাস্তবায়িত হয়, সুরক্ষা সেরা পদ্ধতি, SSE থেকে স্থানান্তর, এবং নিজের স্ট্রিমিং MCP অ্যাপ্লিকেশন তৈরি করার ব্যবহারিক নির্দেশনা কভার করে।

> **আগামী ভবিষ্যত:** এই পাঠটি **MCP স্পেসিফিকেশন 2025-11-25** অনুসারে স্ট্রিমেবল HTTP বর্ণনা করে, যেখানে একটি সেশন `initialize` এর সময় প্রতিষ্ঠিত হয় এবং `Mcp-Session-Id` হেডারের মাধ্যমে পিন করা হয়। `2026-07-28` রিলিজ প্রার্থীরা সম্পূর্ণ হ্যান্ডশেক এবং সেশন আইডি মুছে ফেলে, ফলে প্রতিটি রিকোয়েস্ট স্বয়ংসম্পূর্ণ এবং যেকোনো সার্ভার ইন্সট্যান্সে রাউটেবল হয়, কোনো স্টিকি সেশন ছাড়াই। বিস্তারিত জানতে দেখুন [MCP তে কি পরিবর্তন হচ্ছে: 2026-07-28 রিলিজ প্রার্থী](../../01-CoreConcepts/mcp-2026-07-28-release-candidate.md)।

## MCP তে পরিবহন প্রক্রিয়া এবং স্ট্রিমিং

এই অংশে MCP তে উপলভ্য বিভিন্ন পরিবহন প্রক্রিয়া এবং ক্লায়েন্ট ও সার্ভার মধ্যে রিয়েল-টাইম কমিউনিকেশনের জন্য স্ট্রিমিং সক্ষম করার তাদের ভূমিকা আলোচনা করা হয়েছে।

### পরিবহন প্রক্রিয়া কি?

পরিবহন প্রক্রিয়া সংজ্ঞায়িত করে কিভাবে ডেটা ক্লায়েন্ট এবং সার্ভার মধ্যে বিনিময় হয়। MCP বিভিন্ন পরিবহন ধরনের সমর্থন করে বিভিন্ন পরিবেশ ও প্রয়োজন অনুসারে:

- **stdio**: স্ট্যান্ডার্ড ইনপুট/আউটপুট, লোডাল এবং CLI-ভিত্তিক টুলের জন্য উপযুক্ত। সরল কিন্তু ওয়েব বা ক্লাউডের জন্য উপযোগী নয়।
- **SSE (সার্ভার-সেন্ট ইভেন্টস)**: সার্ভারকে ক্লায়েন্টকে HTTP এর মাধ্যমে রিয়েল-টাইম আপডেট পুশ করার অনুমতি দেয়। ওয়েব ইউআই এর জন্য ভালো, তবে স্কেলিবিলিটি এবং নমনীয়তায় সীমাবদ্ধ। MCP স্পেসিফিকেশন 2025-06-18 থেকে, পৃথক SSE পরিবহন অব্যবহৃত হয়ে গেছে এবং "স্ট্রিমেবল HTTP" পরিবহনে পরিবর্তিত হয়েছে।
- **স্ট্রিমেবল HTTP**: আধুনিক HTTP-ভিত্তিক স্ট্রিমিং পরিবহন, নোটিফিকেশন এবং উন্নত স্কেলিবিলিটি সহ। অধিকাংশ প্রোডাকশন ও ক্লাউড পরিস্থিতির জন্য সুপারিশকৃত।

### তুলনা টেবিল

নিম্নের তুলনা টেবিলে এই পরিবহন প্রক্রিয়াগুলোর পার্থক্য বুঝুন:

| পরিবহন              | রিয়েল-টাইম আপডেট | স্ট্রিমিং | স্কেলিবিলিটি | ব্যবহারের ক্ষেত্র            |
|--------------------|--------------------|-----------|--------------|-----------------------------|
| stdio              | না                 | না        | কম          | স্থানীয় CLI টুল            |
| SSE                | হ্যাঁ               | হ্যাঁ      | মধ্যম       | ওয়েব, রিয়েল-টাইম আপডেট  |
| স্ট্রিমেবল HTTP   | হ্যাঁ               | হ্যাঁ      | উচ্চ         | ক্লাউড, বহু-গ্রাহক          |

> **টিপ:** সঠিক পরিবহন নির্বাচন কর্মদক্ষতা, স্কেলিবিলিটি, এবং ব্যবহারকারীর অভিজ্ঞতায় প্রভাব ফেলে। আধুনিক, স্কেলযোগ্য এবং ক্লাউড-সক্ষম অ্যাপ্লিকেশনের জন্য **স্ট্রিমেবল HTTP** সুপারিশ করা হয়।

লক্ষ্য করুন পূর্ববর্তী অধ্যায়ে দেখানো stdio এবং SSE পরিবহন এবং এই অধ্যায়ে কভার করা স্ট্রিমেবল HTTP পরিবহন।

## স্ট্রিমিং: ধারণা এবং প্রেরণা

স্ট্রিমিংয়ের মৌলিক ধারণা এবং প্রেরণা বোঝা কার্যকর রিয়েল-টাইম যোগাযোগ ব্যবস্থা বাস্তবায়নের জন্য অপরিহার্য।

**স্ট্রিমিং** হল একটি নেটওয়ার্ক প্রোগ্রামিং কৌশল যা ডেটাকে ছোট, নিয়ন্ত্রণযোগ্য অংশ বা ইভেন্টের ধারাবাহিক আকারে প্রেরণ এবং গ্রহণ করতে দেয়, সম্পূর্ণ প্রতিক্রিয়ার জন্য অপেক্ষা না করে। এটি বিশেষ করে কাজে আসে:

- বড় ফাইল বা ডেটাসেটের ক্ষেত্রে।
- রিয়েল-টাইম আপডেট (যেমন, চ্যাট, প্রগ্রেস বার)।
- দীর্ঘমেয়াদী গণনায় যেখানে ব্যবহারকারীকে তথ্য দেয়া জরুরি।

এখানে স্ট্রিমিং সম্পর্কে উচ্চ স্তরের কিছু বিষয়:

- ডেটা ধাপে ধাপে সরবরাহ হয়, একবারে নয়।
- ক্লায়েন্ট ডেটা আসতে শুরু করলে প্রক্রিয়া করতে পারে।
- অনুভূত লেটেন্সি কমে এবং ব্যবহারকারীর অভিজ্ঞতা উন্নত হয়।

### কেন স্ট্রিমিং ব্যবহার করবেন?

স্ট্রিমিং ব্যবহারের কারণগুলো হলো:

- ব্যবহারকারীরা অবিলম্বে প্রতিক্রিয়া পায়, শুধু শেষে নয়
- রিয়েল-টাইম অ্যাপ্লিকেশন এবং সাড়া প্রদানকারী ইউআই সক্ষম করে
- নেটওয়ার্ক এবং কম্পিউটিং রিসোর্সের আরও কার্যকর ব্যবহার

### সহজ উদাহরণ: HTTP স্ট্রিমিং সার্ভার ও ক্লায়েন্ট

এখানে স্ট্রিমিং কিভাবে বাস্তবায়িত হয় তার একটি সহজ উদাহরণ:

#### পাইথন

**সার্ভার (পাইথন, FastAPI এবং StreamingResponse ব্যবহার করে):**

```python
from fastapi import FastAPI
from fastapi.responses import StreamingResponse
import time

app = FastAPI()

async def event_stream():
    for i in range(1, 6):
        yield f"data: Message {i}\n\n"
        time.sleep(1)

@app.get("/stream")
def stream():
    return StreamingResponse(event_stream(), media_type="text/event-stream")
```

**ক্লায়েন্ট (পাইথন, requests ব্যবহার করে):**

```python
import requests

with requests.get("http://localhost:8000/stream", stream=True) as r:
    for line in r.iter_lines():
        if line:
            print(line.decode())
```

এই উদাহরণে, সার্ভার ক্লায়েন্টকে একটি সিরিজের বার্তা পাঠায় উপরন্তু প্রত্যেকবার যখন বার্তাগুলো উপলব্ধ হয়, সমস্ত বার্তা প্রস্তুত হওয়ার জন্য অপেক্ষা করে না।

**কিভাবে কাজ করে:**

- সার্ভার প্রত্যেক বার্তা প্রস্তুত হলে সেটি পাঠায়।
- ক্লায়েন্ট প্রত্যেক অংশ গ্রহণ ও প্রদর্শন করে।

**শর্তাবলী:**

- সার্ভার অবশ্যই স্ট্রিমিং রেসপন্স ব্যবহার করবে (যেমন, FastAPI তে `StreamingResponse`)।
- ক্লায়েন্ট রেসপন্সকে স্ট্রিম হিসেবে প্রক্রিয়া করবে (`stream=True` requests এ)।
- কনটেন্ট-টাইপ সাধারণত `text/event-stream` অথবা `application/octet-stream` হয়।

#### জাভা

**সার্ভার (জাভা, Spring Boot এবং Server-Sent Events ব্যবহার করে):**

```java
@RestController
public class CalculatorController {

    @GetMapping(value = "/calculate", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    public Flux<ServerSentEvent<String>> calculate(@RequestParam double a,
                                                   @RequestParam double b,
                                                   @RequestParam String op) {
        
        double result;
        switch (op) {
            case "add": result = a + b; break;
            case "sub": result = a - b; break;
            case "mul": result = a * b; break;
            case "div": result = b != 0 ? a / b : Double.NaN; break;
            default: result = Double.NaN;
        }

        return Flux.<ServerSentEvent<String>>just(
                    ServerSentEvent.<String>builder()
                        .event("info")
                        .data("Calculating: " + a + " " + op + " " + b)
                        .build(),
                    ServerSentEvent.<String>builder()
                        .event("result")
                        .data(String.valueOf(result))
                        .build()
                )
                .delayElements(Duration.ofSeconds(1));
    }
}
```

**ক্লায়েন্ট (জাভা, Spring WebFlux WebClient ব্যবহার করে):**

```java
@SpringBootApplication
public class CalculatorClientApplication implements CommandLineRunner {

    private final WebClient client = WebClient.builder()
            .baseUrl("http://localhost:8080")
            .build();

    @Override
    public void run(String... args) {
        client.get()
                .uri(uriBuilder -> uriBuilder
                        .path("/calculate")
                        .queryParam("a", 7)
                        .queryParam("b", 5)
                        .queryParam("op", "mul")
                        .build())
                .accept(MediaType.TEXT_EVENT_STREAM)
                .retrieve()
                .bodyToFlux(String.class)
                .doOnNext(System.out::println)
                .blockLast();
    }
}
```

**জাভা বাস্তবায়ন নোটস:**

- Spring Boot এর প্রতিবিম্ব প্রতিস্থাপনের স্ট্যাক `Flux` ব্যবহার করে স্ট্রিমিং
- `ServerSentEvent` ইভেন্ট টাইপ সহ গঠনমূলক ইভেন্ট স্ট্রিমিং প্রদান করে
- `WebClient` এর `bodyToFlux()` প্রতিবিম্ব স্ট্রিমিং গ্রহণ সক্ষম করে
- `delayElements()` ইভেন্টগুলোর মধ্যে প্রক্রিয়াকরণ সময় অনুকরণ করে
- ইভেন্টগুলো শ্রেণীবদ্ধ হতে পারে (`info`, `result`) যাতে ক্লায়েন্ট সঠিকভাবে পরিচালনা করতে পারে

### তুলনা: ক্লাসিক স্ট্রিমিং বনাম MCP স্ট্রিমিং

"ক্লাসিক" স্ট্রিমিং এবং MCP স্ট্রিমিং-এর পার্থক্য নিম্নরূপ:

| বৈশিষ্ট্য               | ক্লাসিক HTTP স্ট্রিমিং          | MCP স্ট্রিমিং (নোটিফিকেশন)       |
|------------------------|-------------------------------|----------------------------------|
| প্রধান রেসপন্স          | টুকরাটাকরা                     | একক, শেষে                         |
| প্রগ্রেস আপডেট         | ডেটা টুকরো হিসেবে পাঠানো হয়  | নোটিফিকেশন হিসেবে পাঠানো হয়      |
| ক্লায়েন্ট প্রয়োজন    | স্ট্রিম প্রসেস করতে হবে         | মেসেজ হ্যান্ডলার বাস্তবায়ন করতে হবে |
| ব্যবহারের ক্ষেত্র       | বড় ফাইল, AI টোকেন স্ট্রিম    | প্রগ্রেস, লগ, রিয়েল-টাইম ফিডব্যাক |

### প্রধান পার্থক্যসমূহ

অগ্রন্তু, এখানে কয়েকটি প্রধান পার্থক্য:

- **যোগাযোগের ধরন:**
  - ক্লাসিক HTTP স্ট্রিমিং: সহজ টুকরাটাকরা ট্রান্সফার এনকোডিং ব্যবহার করে ডেটা পাঠায়
  - MCP স্ট্রিমিং: JSON-RPC প্রোটোকল সহ গঠিত নোটিফিকেশন সিস্টেম ব্যবহার করে

- **মেসেজ ফর্ম্যাট:**
  - ক্লাসিক HTTP: নতুন লাইনের সাথে প্লেইন টেক্সট টুকরো
  - MCP: মেটাডেটাসহ গঠিত LoggingMessageNotification অবজেক্ট

- **ক্লায়েন্ট বাস্তবায়ন:**
  - ক্লাসিক HTTP: স্ট্রিমিং রেসপন্স প্রক্রিয়া করে এমন সরল ক্লায়েন্ট
  - MCP: বিভিন্ন ধরনের মেসেজ প্রক্রিয়াজনিত করার জন্য মেসেজ হ্যান্ডলারসহ আরো উন্নত ক্লায়েন্ট

- **প্রগ্রেস আপডেট:**
  - ক্লাসিক HTTP: প্রগ্রেস প্রধান রেসপন্স স্ট্রিমের অংশ
  - MCP: প্রধান রেসপন্স শেষে আসলেও প্রগ্রেস আলাদা নোটিফিকেশন হিসেবে পাঠানো হয়

### সুপারিশসমূহ

ক্লাসিকাল স্ট্রিমিং (`/stream` পয়েন্ট ব্যবহার করে) এবং MCP স্ট্রিমিংয়ের মধ্যে পছন্দ করার সময় কিছু সুপারিশ রয়েছে।

- **সরল স্ট্রিমিংয়ের জন্য:** ক্লাসিক HTTP স্ট্রিমিং সহজেই বাস্তবায়িত এবং মৌলিক স্ট্রিমিংয়ের জন্য যথেষ্ট।

- **জটিল, ইন্টারেক্টিভ অ্যাপ্লিকেশন জন্য:** MCP স্ট্রিমিং গঠিত পদ্ধতি প্রদান করে উন্নত মেটাডেটা এবং নোটিফিকেশন ও চূড়ান্ত ফলাফল আলাদা থাকার সুবিধা নিয়ে।

- **AI অ্যাপ্লিকেশনগুলির জন্য:** MCP এর নোটিফিকেশন সিস্টেম দীর্ঘস্থায়ী AI কাজের প্রগ্রেস আপডেটের জন্য বিশেষ ভাবে উপযোগী।

## MCP তে স্ট্রিমিং

এখন পর্যন্ত আমরা ক্লাসিকাল স্ট্রিমিং এবং MCP স্ট্রিমিংয়ের পার্থক্য নিয়ে কিছু সুপারিশ এবং তুলনা দেখেছি। আসুন বিস্তারিত দেখা যাক MCP তে স্ট্রিমিং কিভাবে ব্যবহার করা যায়।

MCP কাঠামোর মধ্যে স্ট্রিমিং কিভাবে কাজ করে সেটি বোঝা জরুরি, যাতে দীর্ঘ সময়সাপেক্ষ কাজের সময় ব্যবহারকারীদের প্রতি রিয়েল-টাইম ফিডব্যাক প্রদানে সক্ষম অ্যাপ্লিকেশন তৈরি করা যায়।

MCP তে স্ট্রিমিং মানে প্রধান রেসপন্সকে টুকরো টুকরা পাঠানো নয়, বরং ক্লায়েন্টকে নোটিফিকেশন পাঠানো যখন একটি টুল রিকোয়েস্ট প্রক্রিয়া করছে। এই নোটিফিকেশনে থাকতে পারে প্রগ্রেস আপডেট, লগ, বা অন্যান্য ইভেন্ট।

### কিভাবে কাজ করে

প্রধান ফলাফলটি একক রেসপন্স হিসেবে পাঠানো হয়। তবে প্রক্রিয়াজনিত সময়ে নোটিফিকেশন আলাদা মেসেজ হিসেবে পাঠানো হয়, যা ক্লায়েন্টকে রিয়েল-টাইমে আপডেট রাখে। ক্লায়েন্টকে এই নোটিফিকেশনগুলি প্রক্রিয়া এবং প্রদর্শন করতে সক্ষম হতে হবে।

## নোটিফিকেশন কী?

আমরা বললাম "নোটিফিকেশন", MCP প্রেক্ষাপটে এর অর্থ কী?

একটি নোটিফিকেশন হল সার্ভার থেকে ক্লায়েন্টকে পাঠানো একটি বার্তা যা দীর্ঘমেয়াদী অপারেশনের সময় প্রগ্রেস, অবস্থা বা অন্যান্য ঘটনার তথ্য দেয়। নোটিফিকেশন পরিবদ্রশিতা এবং ব্যবহারকারীর অভিজ্ঞতা উন্নত করে।

উদাহরণস্বরূপ, ক্লায়েন্টকে সার্ভারের সঙ্গে প্রাথমিক হ্যান্ডশেক শেষ হলে একটি নোটিফিকেশন পাঠাতে হবে।

একটি নোটিফিকেশন দেখতে এভাবে JSON বার্তা হয়:

```json
{
  jsonrpc: "2.0";
  method: string;
  params?: {
    [key: string]: unknown;
  };
}
```

নোটিফিকেশন MCP এ ["Logging"](https://modelcontextprotocol.io/specification/draft/server/utilities/logging) নামে পরিচিত একটি টপিকের অন্তর্ভুক্ত।

> **বিরতি বিজ্ঞপ্তি:** `2026-07-28` MCP স্পেসিফিকেশন রিলিজ প্রার্থী Logging প্রিমিটিভকে অব্যবহৃত হিসেবে চিহ্নিত করেছে, stdio পরিবহনের জন্য `stderr` এবং গঠিত পর্যবেক্ষণের জন্য OpenTelemetry কে এক্ষেত্রে গ্রহণ করছে। Logging `2025-11-25` এবং আনুষ্ঠানিক অব্যবহৃতের এক বছর পরেও কাজ করবে। বিস্তারিত জানতে দেখুন [MCP তে কি পরিবর্তন হচ্ছে: 2026-07-28 রিলিজ প্রার্থী](../../01-CoreConcepts/mcp-2026-07-28-release-candidate.md)।

লগিং চালু করতে, সার্ভারকে ফিচার/ক্ষমতা হিসেবে এটি সক্ষম করতে হবে যেমন:

```json
{
  "capabilities": {
    "logging": {}
  }
}
```

> [!NOTE]
> ব্যবহৃত SDK অনুসারে, লগিং ডিফল্টরূপে সক্ষম থাকতে পারে অথবা আপনাকে সার্ভারের কনফিগারেশনে এটিকে স্পষ্টভাবে সক্ষম করতে হতে পারে।

## MCP তে নোটিফিকেশন বাস্তবায়ন

MCP তে নোটিফিকেশন বাস্তবায়নের জন্য, আপনাকে সার্ভার এবং ক্লায়েন্ট উভয় দিকে স্থাপন করতে হবে যাতে রিয়েল-টাইম আপডেট পরিচালনা করা যায়। এটি দীর্ঘমেয়াদী অপারেশনের সময় ব্যবহারকারীদের অবিলম্বে প্রতিক্রিয়া দেওয়ার সুযোগ সৃষ্টি করে।

### সার্ভার-সাইড: নোটিফিকেশন প্রেরণ

শুরু করা যাক সার্ভার থেকে। MCP তে, আপনি এমন টুল ডেফাইন করেন যা রিকোয়েস্ট প্রক্রিয়ার সময় নোটিফিকেশন পাঠাতে পারে। সার্ভার কন্টেক্সট অবজেক্ট (সাধারণত `ctx`) ব্যবহার করে ক্লায়েন্টকে মেসেজ পাঠায়।

#### পাইথন

```python
@mcp.tool(description="A tool that sends progress notifications")
async def process_files(message: str, ctx: Context) -> TextContent:
    await ctx.info("Processing file 1/3...")
    await ctx.info("Processing file 2/3...")
    await ctx.info("Processing file 3/3...")
    return TextContent(type="text", text=f"Done: {message}")
```

পূর্বের উদাহরণে, `process_files` টুল ক্লায়েন্টকে তিনটি নোটিফিকেশন পাঠায় যখন এটি প্রতিটি ফাইল প্রক্রিয়া করে। `ctx.info()` মেথড তথ্যবহুল বার্তা পাঠাতে ব্যবহৃত হয়।

অতিরিক্তভাবে, নোটিফিকেশন সক্ষম করতে, নিশ্চিত করুন সার্ভার একটি স্ট্রিমিং পরিবহন ব্যবহার করছে (যেমন `streamable-http`) এবং ক্লায়েন্ট একটি মেসেজ হ্যান্ডলার বাস্তবায়িত করেছে যা নোটিফিকেশনগুলো প্রক্রিয়া করে। নিচে দেখানো হয়েছে কিভাবে সার্ভার `streamable-http` পরিবহন ব্যবহার করতে পারে:

```python
mcp.run(transport="streamable-http")
```

#### .NET

```csharp
[Tool("A tool that sends progress notifications")]
public async Task<TextContent> ProcessFiles(string message, ToolContext ctx)
{
    await ctx.Info("Processing file 1/3...");
    await ctx.Info("Processing file 2/3...");
    await ctx.Info("Processing file 3/3...");
    return new TextContent
    {
        Type = "text",
        Text = $"Done: {message}"
    };
}
```

এই .NET উদাহরণে, `ProcessFiles` টুলটি `Tool` এট্রিবিউট দ্বারা শোভিত এবং ক্লায়েন্টকে তিনটি নোটিফিকেশন পাঠায় প্রতিটি ফাইল প্রক্রিয়া করার সময়। `ctx.Info()` মেথড তথ্যবহুল বার্তা পাঠাতে ব্যবহৃত হয়।

আপনার .NET MCP সার্ভারে নোটিফিকেশন সক্ষম করতে, নিশ্চিত করুন আপনি একটি স্ট্রিমিং পরিবহন ব্যবহার করছেন:

```csharp
var builder = McpBuilder.Create();
await builder
    .UseStreamableHttp() // Enable streamable HTTP transport
    .Build()
    .RunAsync();
```

### ক্লায়েন্ট-সাইড: নোটিফিকেশন গ্রহণ

ক্লায়েন্ট অবশ্যই একটি মেসেজ হ্যান্ডলার বাস্তবায়িত করবে যা আগত নোটিফিকেশন প্রক্রিয়া ও প্রদর্শন করবে।

#### পাইথন

```python
async def message_handler(message):
    if isinstance(message, types.ServerNotification):
        print("NOTIFICATION:", message)
    else:
        print("SERVER MESSAGE:", message)

async with ClientSession(
   read_stream, 
   write_stream,
   logging_callback=logging_collector,
   message_handler=message_handler,
) as session:
```

পূর্বের কোডে, `message_handler` ফাংশন পরীক্ষা করে এটি আসা মেসেজ নোটিফিকেশন কিনা। যদি হয়, নোটিফিকেশন মুদ্রণ করে; অন্যথায় এটি সাধারণ সার্ভার মেসেজ হিসেবে প্রক্রিয়া করে। এছাড়াও লক্ষ্য করুন `ClientSession` কে `message_handler` দিয়ে ইনিশিয়ালাইজ করা হয়েছে যাতে আগত নোটিফিকেশন পরিকল্পনা করা যায়।

#### .NET

```csharp
// Define a message handler
void MessageHandler(IJsonRpcMessage message)
{
    if (message is ServerNotification notification)
    {
        Console.WriteLine($"NOTIFICATION: {notification}");
    }
    else
    {
        Console.WriteLine($"SERVER MESSAGE: {message}");
    }
}

// Create and use a client session with the message handler
var clientOptions = new ClientSessionOptions
{
    MessageHandler = MessageHandler,
    LoggingCallback = (level, message) => Console.WriteLine($"[{level}] {message}")
};

using var client = new ClientSession(readStream, writeStream, clientOptions);
await client.InitializeAsync();

// Now the client will process notifications through the MessageHandler
```

এই .NET উদাহরণে, `MessageHandler` ফাংশন পরীক্ষা করে মেসেজটি নোটিফিকেশন কিনা। যদি হয়, নোটিফিকেশন মুদ্রণ করে; অন্যথায় এটি সাধারণ সার্ভার মেসেজ হিসেবে প্রক্রিয়া করে। `ClientSession` ইনিশিয়ালাইজ করা হয় মেসেজ হ্যান্ডলারসহ `ClientSessionOptions` এর মাধ্যমে।

নোটিফিকেশন সক্ষম করতে, নিশ্চিত করুন সার্ভার একটি স্ট্রিমিং পরিবহন ব্যবহার করছে (যেমন `streamable-http`) এবং ক্লায়েন্ট একটি মেসেজ হ্যান্ডলার বাস্তবায়িত করেছে।

## প্রগ্রেস নোটিফিকেশন ও পরিস্থিতি

এই অংশে MCP তে প্রগ্রেস নোটিফিকেশনের ধারণা, এর গুরুত্ব এবং Streamable HTTP ব্যবহার করে কিভাবে বাস্তবায়ন করবেন তা ব্যাখ্যা করা হয়েছে। আপনার বোঝাপড়া দৃঢ় করার জন্য একটি ব্যবহারিক কাজও থাকবে।

প্রগ্রেস নোটিফিকেশন হলো সার্ভার থেকে ক্লায়েন্টকে পাঠানো রিয়েল-টাইম বার্তা দীর্ঘমেয়াদী অপারেশনের সময়। পুরো প্রক্রিয়া শেষ হবার জন্য অপেক্ষা না করে, সার্ভার ক্লায়েন্টকে বর্তমান অবস্থা সম্পর্কে জানিয়ে রাখে। এটি স্বচ্ছতা, ব্যবহারকারীর অভিজ্ঞতা উন্নত করে এবং ডিবাগিং সহজ করে।

**উদাহরণ:**

```text

"Processing document 1/10"
"Processing document 2/10"
...
"Processing complete!"

```

### কেন প্রগ্রেস নোটিফিকেশন ব্যবহার করবেন?

প্রগ্রেস নোটিফিকেশন গুরুত্বপূর্ণ বিভিন্ন কারণে:

- **ভালো ব্যবহারকারীর অভিজ্ঞতা:** ব্যবহারকারীরা কাজের অগ্রগতি দেখতে পান, শুধু শেষে নয়।
- **রিয়েল-টাইম ফিডব্যাক:** ক্লায়েন্ট প্রগ্রেস বার বা লগ ডিসপ্লে করতে পারে, অ্যাপ্লিকেশনটি দ্রুত প্রতিক্রিয়াশীল মনে হয়।
- **সবচেয়ে সহজ ডিবাগিং ও মনিটরিং:** ডেভেলপার ও ব্যবহারকারী দেখতে পারেন প্রক্রিয়াটি কোথায় ধীর বা আটকে আছে।

### কিভাবে প্রগ্রেস নোটিফিকেশন বাস্তবায়ন করবেন

এখানে MCP তে প্রগ্রেস নোটিফিকেশন বাস্তবায়নের পদ্ধতি:

- **সার্ভারে:** `ctx.info()` বা `ctx.log()` ব্যবহার করে প্রতিটি আইটেম প্রক্রিয়া করার সময় নোটিফিকেশন পাঠান। এটি প্রধান ফলাফলের আগে ক্লায়েন্টকে বার্তা দেয়।
- **ক্লায়েন্টে:** এমন একটি মেসেজ হ্যান্ডলার বাস্তবায়িত করুন যা আগত নোটিফিকেশন শুনে প্রদর্শন করবে। হ্যান্ডলার নোটিফিকেশন এবং চূড়ান্ত ফলাফল আলাদা করবে।

**সার্ভার উদাহরণ:**


#### Python

```python
@mcp.tool(description="A tool that sends progress notifications")
async def process_files(message: str, ctx: Context) -> TextContent:
    for i in range(1, 11):
        await ctx.info(f"Processing document {i}/10")
    await ctx.info("Processing complete!")
    return TextContent(type="text", text=f"Done: {message}")
```

**ক্লায়েন্ট উদাহরণ:**

#### Python

```python
async def message_handler(message):
    if isinstance(message, types.ServerNotification):
        print("NOTIFICATION:", message)
    else:
        print("SERVER MESSAGE:", message)
```

## নিরাপত্তা বিবেচনা

কোন সার্ভার ইমপ্লিমেন্ট করার সময় নিরাপত্তা সর্বোচ্চ অগ্রাধিকার হওয়া উচিত, বিশেষ করে MCP এ Streamable HTTP মতো HTTP-ভিত্তিক ট্রান্সপোর্ট ব্যবহার করার সময়।

HTTP-ভিত্তিক ট্রান্সপোর্ট সহ MCP সার্ভার ইমপ্লিমেন্ট করার সময়, নিরাপত্তা একটি অত্যন্ত গুরুত্বপূর্ণ বিষয় যা একাধিক আক্রমণ স্তর এবং সুরক্ষা ব্যবস্থাপনার প্রতি সতর্ক মনোযোগ দাবি করে।

### সারাংশ

MCP সার্ভার HTTP এর মাধ্যমে প্রকাশ করার সময় নিরাপত্তা অত্যন্ত জরুরি। Streamable HTTP নতুন আক্রমণ পয়েন্ট যোগ করে এবং সাবধানী কনফিগারেশন প্রয়োজন।

এখানে কিছু প্রধান নিরাপত্তা বিবেচনা দেওয়া হলো:

- **Origin হেডার যাচাই করুন**: DNS rebinding আক্রমণ প্রতিরোধে সবসময় `Origin` হেডার যাচাই করুন।
- **Localhost Binding**: স্থানীয় উন্নয়নের জন্য, সার্ভারগুলোকে `localhost` এ বেঁধে দিন যাতে সেগুলো পাবলিক ইন্টারনেটে প্রकट না হয়।
- **প্রমাণীকরণ**: প্রোডাকশনে ডিপ্লয়মেন্টের জন্য প্রমাণীকরণ (যেমন, API কী, OAuth) ইমপ্লিমেন্ট করুন।
- **CORS**: Cross-Origin Resource Sharing (CORS) নীতি কনফিগার করুন যাতে অ্যাক্সেস সীমাবদ্ধ থাকে।
- **HTTPS**: প্রোডাকশনে ট্র্যাফিক এনক্রিপ্ট করার জন্য HTTPS ব্যবহার করুন।

### সেরা অনুশীলন

তদুপরি, MCP স্ট্রিমিং সার্ভারে নিরাপত্তা প্রয়োগের সময় নিম্নলিখিত সেরা অনুশীলনগুলো অনুসরণ করুন:

- ইনকামিং রিকোয়েস্ট যাচাই ছাড়া কখনই বিশ্বাস করবেন না।
- সব অ্যাক্সেস এবং ত্রুটি লগ করুন এবং পর্যবেক্ষণ করুন।
- নিরাপত্তা দুর্বলতাগুলি মার্জ করার জন্য নিয়মিত ডিপেন্ডেন্সি আপডেট করুন।

### চ্যালেঞ্জ

MCP স্ট্রিমিং সার্ভারে নিরাপত্তা ইমপ্লিমেন্ট করার সময় আপনি কিছু চ্যালেঞ্জের সম্মুখীন হবেন:

- নিরাপত্তার সঙ্গে উন্নয়নের সহজতা সামঞ্জস্য করা
- বিভিন্ন ক্লায়েন্ট পরিবেশের সাথে সামঞ্জস্য নিশ্চিত করা


## SSE থেকে Streamable HTTP এ আপগ্রেডিং

বর্তমানে Server-Sent Events (SSE) ব্যবহার করা অ্যাপ্লিকেশনগুলির জন্য, Streamable HTTP তে মাইগ্রেট করলে উন্নত ক্ষমতা এবং দীর্ঘমেয়াদি টেকসইতা আসে MCP ইমপ্লিমেন্টেশনের জন্য।

### কেন আপগ্রেড করবেন?

SSE থেকে Streamable HTTP তে আপগ্রেড করার দুটি প্রধান কারণ রয়েছে:

- Streamable HTTP এসএসই থেকে ভালো স্কেলেবিলিটি, সামঞ্জস্য এবং সমৃদ্ধ নোটিফিকেশন সাপোর্ট দেয়।
- এটি নতুন MCP অ্যাপ্লিকেশনগুলোর জন্য পরামর্শকৃত ট্রান্সপোর্ট।

### মাইগ্রেশন ধাপগুলো

আপনার MCP অ্যাপ্লিকেশনগুলোতে SSE থেকে Streamable HTTP তে কীভাবে মাইগ্রেট করবেন:

- **সার্ভার কোড আপডেট করুন** `mcp.run()` এ `transport="streamable-http"` ব্যবহার করার জন্য।
- **ক্লায়েন্ট কোড আপডেট করুন** SSE ক্লায়েন্টের পরিবর্তে `streamablehttp_client` ব্যবহার করতে।
- **একটি মেসেজ হ্যান্ডলার ইমপ্লিমেন্ট করুন** যাতে ক্লায়েন্ট নোটিফিকেশন প্রক্রিয়া করতে পারে।
- **বিদ্যমান টুল এবং ওয়ার্কফ্লোগুলোর সাথে সামঞ্জস্য পরীক্ষা করুন**।

### সামঞ্জস্য বজায় রাখা

মাইগ্রেশনের সময় বিদ্যমান SSE ক্লায়েন্টের সঙ্গে সামঞ্জস্য বজায় রাখা পরামর্শ দেওয়া হয়। নিম্নলিখিত কৌশলগুলো প্রয়োগ করুন:

- SSE এবং Streamable HTTP দুইটাকে আলাদা এন্ডপয়েন্টে চালিয়ে দুই ট্রান্সপোর্টকে সমর্থন করতে পারেন।
- ধাপে ধাপে ক্লায়েন্টদের নতুন ট্রান্সপোর্টে স্থানান্তর করুন।

### চ্যালেঞ্জ

মাইগ্রেশনের সময় নিম্নলিখিত চ্যালেঞ্জগুলি মোকাবেলা করতে হবে:

- সকল ক্লায়েন্ট আপডেট হয়েছে কি না নিশ্চিত করা
- নোটিফিকেশন ডেলিভারির পার্থক্যগুলো পরিচালনা করা

### অ্যাসাইনমেন্ট: নিজের MCP স্ট্রিমিং অ্যাপ তৈরি করুন

**দৃশ্যপট:**
একটি MCP সার্ভার এবং ক্লায়েন্ট তৈরি করুন যেখানে সার্ভার একটি আইটেমের তালিকা (যেমন, ফাইল বা ডকুমেন্ট) প্রসেস করে এবং প্রতিটি আইটেমের জন্য একটি নোটিফিকেশন পাঠায়। ক্লায়েন্ট প্রত্যেক নোটিফিকেশন পৌঁছলেই দেখাবে।

**ধাপগুলো:**

1. একটি সার্ভার টুল ইমপ্লিমেন্ট করুন যা তালিকা প্রসেস করবে এবং প্রতিটি আইটেমের জন্য নোটিফিকেশন পাঠাবে।
2. একটি ক্লায়েন্ট ইমপ্লিমেন্ট করুন যেখানে মেসেজ হ্যান্ডলার থাকবে এবং তা রিয়েল-টাইমে নোটিফিকেশন প্রদর্শন করবে।
3. আপনার ইমপ্লিমেন্টেশন পরীক্ষা করতে সার্ভার এবং ক্লায়েন্ট উভয় রান করুন, এবং নোটিফিকেশনগুলো পর্যবেক্ষণ করুন।
