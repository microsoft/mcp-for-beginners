# Корені MCP (спадкова функція)

> [!WARNING]
> Корені є застарілими починаючи з MCP `2026-07-28`. Вони залишаються у цій редакції для
> сумісності і можуть бути видалені у першій специфікації,
> випущеній 28 липня 2027 року або пізніше. Нові реалізації повинні передавати
> каталоги або файли через параметри інструменту, URI ресурсів або конфігурацію сервера.


## Огляд

Корені дозволяють клієнту MCP повідомити сервер, які розташування файлової системи є релевантними
для поточного запиту. Корінь містить обов’язковий URI `file://` та необов’язкове
зручне для людини ім’я.

Корені є інформаційними підказками. Вони не є контейнерами історії розмов,
сесіями протоколу, або механізмом контролю доступу. Протокол не
вимагає, щоб сервер залишався в межах зазначених коренів.

## Навчальні цілі

До кінця цього уроку ви зможете:

- Пояснити, що таке корені MCP і чого вони не представляють.
- Впізнавати поточний багатократний обмін `roots/list`.
- Застосовувати заходи безпеки незалежно від коренів.
- Перейти на підтримувані альтернативи для нових реалізацій.

## Дані коренів

Клієнт повертає кожен корінь як URI `file://` з необов’язковим ім’ям для відображення:

```json
{
  "roots": [
    {
      "uri": "file:///home/user/projects/weather-service",
      "name": "Weather Service"
    }
  ]
}
```

Клієнти повинні показувати лише розташування, схвалені користувачем. Сервери повинні розглядати
результат як орієнтир щодо релевантних файлів, а не як підтвердження авторизації.

## Поток MCP 2026-07-28

Клієнт, що підтримує корені, оголошує цю можливість у кожному запиті:

```json
{
  "_meta": {
    "io.modelcontextprotocol/clientCapabilities": {
      "roots": {}
    }
  }
}
```

Під час обробки запиту клієнта сервер може повернути
`InputRequiredResult`, що містить запит вводу `roots/list`:

```json
{
  "resultType": "input_required",
  "inputRequests": {
    "workspaceRoots": {
      "method": "roots/list"
    }
  },
  "requestState": "opaque-state-from-server"
}
```

Клієнт збирає схвалені корені і повторює початковий запит з відповідними `inputResponses` та незмінним `requestState`. Цей багатократний обмін
зберігає безстанний протокол; немає рукопотискання `initialize` або
сесії на рівні протоколу.


## Спадкова поведінка 2025-11-25

У MCP `2025-11-25` клієнти оголошували корені під час ініціалізації. Сервер
міг ініціювати прямий запит `roots/list`, а клієнт міг надсилати
`notifications/roots/list_changed` коли його корені змінювались.

Цей життєвий цикл є спадковою поведінкою. Не поєднуйте його приклади ініціалізації та
повідомлень з реалізацією `2026-07-28`.

## Рекомендовані заміни

### Параметри інструменту

Зробіть обов’язковим каталог або файл явним у схемі інструменту:

```json
{
  "name": "analyze_project",
  "inputSchema": {
    "type": "object",
    "properties": {
      "projectDirectory": {
        "type": "string",
        "description": "Approved project directory to analyze"
      }
    },
    "required": ["projectDirectory"]
  }
}
```

### URI ресурсів

Використовуйте ресурси MCP, коли сервер може надати релевантні файли через стабільні
URI. Це робить виявлення та отримання явними.

### Конфігурація сервера

Для фіксованих розгортань налаштуйте дозволені каталоги під час запуску сервера.
Це часто є зрозумілішим, ніж виявляти їх під час виклику інструменту.

## Вимоги безпеки

Яку б заміну ви не обрали:

- Отримайте згоду користувача перед відкриттям доступу до розташувань файлової системи.
- Канонізуйте та перевіряйте шляхи, щоб уникнути обходу.
- Застосовуйте авторизацію та ізоляцію незалежно від значень коренів.
- Перевіряйте дозволи під час доступу до файлу, а не лише при його переліку.
- Уникайте повернення чутливих шляхів у логах або повідомленнях про помилки.

## Основні висновки

- Корені описують релевантні розташування файлової системи; вони не зберігають
  стан розмови.
- Корені є орієнтирами, а не межею контролю доступу.
- MCP `2026-07-28` передає можливість у кожному запиті та використовує
  `InputRequiredResult` для `roots/list`.
- Нові реалізації повинні використовувати параметри інструменту, URI ресурсів або
  конфігурацію сервера.
