# HTTPS потокова передача з протоколом контексту моделі (MCP)

Цей розділ надає всебічний посібник з реалізації безпечної, масштабованої та миттєвої потокової передачі за допомогою протоколу контексту моделі (MCP) через HTTPS. Він охоплює мотивацію для потокової передачі, доступні транспортні механізми, як реалізувати потоковий HTTP у MCP, кращі практики безпеки, міграцію з SSE та практичні рекомендації для створення власних потокових застосунків MCP.

> **Дивлячись уперед:** цей урок описує Streamable HTTP згідно зі **специфікацією MCP 2025-11-25**, де сесія встановлюється під час `initialize` і закріплюється заголовком `Mcp-Session-Id`. Кандидат на випуск `2026-07-28` повністю видаляє рукостискання та ідентифікатор сесії, роблячи кожен запит самодостатнім і направним на будь-який екземпляр сервера без необхідності "липких" сесій. Деталі дивіться в [Що змінюється в MCP: кандидат на випуск 2026-07-28](../../01-CoreConcepts/mcp-2026-07-28-release-candidate.md).

## Транспортні механізми та потокова передача в MCP

У цьому розділі розглядаються різні доступні транспортні механізми в MCP та їх роль у забезпеченні можливостей потокової передачі для реального часу між клієнтами та серверами.

### Що таке транспортний механізм?

Транспортний механізм визначає, як здійснюється обмін даними між клієнтом і сервером. MCP підтримує кілька типів транспорту для різних середовищ та вимог:

- **stdio**: Стандартний ввід/вивід, підходить для локальних інструментів та командного рядка. Простий, але не підходить для вебу чи хмари.
- **SSE (Server-Sent Events)**: Дозволяє серверам пушити оновлення у реальному часі клієнтам через HTTP. Добре для веб-інтерфейсів, але обмежено у масштабованості та гнучкості. Згідно зі специфікацією MCP 2025-06-18, автономний транспорт SSE (Server-Sent Events) застарілий і замінений транспортом "Streamable HTTP".
- **Streamable HTTP**: Сучасний стрімінговий транспорт на базі HTTP, який підтримує сповіщення та кращу масштабованість. Рекомендується для більшості виробничих і хмарних сценаріїв.

### Таблиця порівняння

Перегляньте таблицю порівняння нижче, щоб зрозуміти відмінності між цими транспортними механізмами:

| Транспорт         | Оновлення в реальному часі | Потокова передача | Масштабованість | Сценарій використання   |
|-------------------|----------------------------|-------------------|-----------------|------------------------|
| stdio             | Ні                         | Ні                | Низька          | Локальні CLI інструменти |
| SSE               | Так                        | Так               | Середня         | Веб, оновлення в реальному часі |
| Streamable HTTP   | Так                        | Так               | Висока          | Хмара, мультиклієнтська робота |

> **Порада:** Вибір правильного транспорту впливає на продуктивність, масштабованість та користувацький досвід. **Streamable HTTP** рекомендується для сучасних, масштабованих і готових до хмари застосунків.

Зверніть увагу на транспорти stdio та SSE, які були показані в попередніх розділах, та на те, що Streamable HTTP є транспортом, розглянутим у цьому розділі.

## Потокова передача: концепції та мотивація

Розуміння основних концепцій та мотивації потокової передачі є важливим для реалізації ефективних систем миттєвого зв’язку.

**Потокова передача** — це техніка у мережевому програмуванні, що дозволяє надсилати та отримувати дані невеликими, керованими частинами або як послідовність подій, замість очікування готовності всієї відповіді. Це особливо корисно для:

- Великих файлів або наборів даних.
- Оновлень у реальному часі (наприклад, чат, індикатори прогресу).
- Тривалих обчислень, коли потрібно тримати користувача в курсі.

Ось що потрібно знати про потокову передачу на високому рівні:

- Дані доставляються поступово, а не всі одразу.
- Клієнт може обробляти дані по мірі їх надходження.
- Зменшує сприйману затримку та покращує досвід користувача.

### Чому варто використовувати потокову передачу?

Причини для використання потокової передачі такі:

- Користувачі отримують зворотний зв’язок негайно, а не лише в кінці.
- Дозволяє створювати додатки в реальному часі та адаптивні інтерфейси.
- Ефективніше використовує мережеві та обчислювальні ресурси.

### Простий приклад: HTTP сервер і клієнт для потокової передачі

Ось простий приклад, як можна реалізувати потокову передачу:

#### Python

**Сервер (Python, з використанням FastAPI та StreamingResponse):**

```python
from fastapi import FastAPI
from fastapi.responses import StreamingResponse
import time

app = FastAPI()

async def event_stream():
    for i in range(1, 6):
        yield f"data: Message {i}\n\n"
        time.sleep(1)

@app.get("/stream")
def stream():
    return StreamingResponse(event_stream(), media_type="text/event-stream")
```

**Клієнт (Python, з використанням requests):**

```python
import requests

with requests.get("http://localhost:8000/stream", stream=True) as r:
    for line in r.iter_lines():
        if line:
            print(line.decode())
```

Цей приклад демонструє, як сервер надсилає серію повідомлень клієнту по мірі їх готовності, а не очікує на всі повідомлення одночасно.

**Як це працює:**

- Сервер віддає кожне повідомлення по мірі його готовності.
- Клієнт отримує і виводить кожен фрагмент даних при надходженні.

**Вимоги:**

- Сервер має використовувати відповідь у вигляді потоку (наприклад, `StreamingResponse` у FastAPI).
- Клієнт повинен обробляти відповідь як потік (`stream=True` у requests).
- Тип вмісту зазвичай `text/event-stream` або `application/octet-stream`.

#### Java

**Сервер (Java, з використанням Spring Boot та Server-Sent Events):**

```java
@RestController
public class CalculatorController {

    @GetMapping(value = "/calculate", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    public Flux<ServerSentEvent<String>> calculate(@RequestParam double a,
                                                   @RequestParam double b,
                                                   @RequestParam String op) {
        
        double result;
        switch (op) {
            case "add": result = a + b; break;
            case "sub": result = a - b; break;
            case "mul": result = a * b; break;
            case "div": result = b != 0 ? a / b : Double.NaN; break;
            default: result = Double.NaN;
        }

        return Flux.<ServerSentEvent<String>>just(
                    ServerSentEvent.<String>builder()
                        .event("info")
                        .data("Calculating: " + a + " " + op + " " + b)
                        .build(),
                    ServerSentEvent.<String>builder()
                        .event("result")
                        .data(String.valueOf(result))
                        .build()
                )
                .delayElements(Duration.ofSeconds(1));
    }
}
```

**Клієнт (Java, з використанням Spring WebFlux WebClient):**

```java
@SpringBootApplication
public class CalculatorClientApplication implements CommandLineRunner {

    private final WebClient client = WebClient.builder()
            .baseUrl("http://localhost:8080")
            .build();

    @Override
    public void run(String... args) {
        client.get()
                .uri(uriBuilder -> uriBuilder
                        .path("/calculate")
                        .queryParam("a", 7)
                        .queryParam("b", 5)
                        .queryParam("op", "mul")
                        .build())
                .accept(MediaType.TEXT_EVENT_STREAM)
                .retrieve()
                .bodyToFlux(String.class)
                .doOnNext(System.out::println)
                .blockLast();
    }
}
```

**Примітки щодо реалізації на Java:**

- Використовує реактивний стек Spring Boot з `Flux` для потокової передачі
- `ServerSentEvent` забезпечує структуровану подієву передачу з типами подій
- `WebClient` з `bodyToFlux()` дозволяє споживати потокову передачу реактивним способом
- `delayElements()` імітує час обробки між подіями
- Події можуть мати типи (`info`, `result`) для кращої обробки клієнтом

### Порівняння: Класична потокова передача vs Потокова передача MCP

Відмінності між класичною потоковою передачею та тією, що працює в MCP, можна зобразити так:

| Особливість               | Класична HTTP потокова передача | Потокова передача MCP (Сповіщення) |
|--------------------------|----------------------------------|-------------------------------------|
| Основна відповідь         | Розділена на фрагменти           | Одна, в кінці                      |
| Оновлення прогресу        | Надсилаються як фрагменти даних  | Надсилаються як сповіщення          |
| Вимоги до клієнта         | Повинен обробляти потік           | Повинен реалізувати обробник повідомлень |
| Сценарій використання     | Великі файли, стріми AI токенів   | Прогрес, логи, зв’язок у реальному часі |

### Ключові відмінності

Крім того, ось деякі ключові відмінності:

- **Модель комунікації:**
  - Класична HTTP потокова передача: Використовує просте кодування розбиття на фрагменти.
  - MCP потокова передача: Використовує структуровану систему сповіщень із протоколом JSON-RPC.

- **Формат повідомлень:**
  - Класична HTTP: Простий текст із розбиттям на фрагменти з розривами рядків.
  - MCP: Структуровані об’єкти LoggingMessageNotification з метаданими.

- **Реалізація клієнта:**
  - Класична HTTP: Простий клієнт, що обробляє потокові відповіді.
  - MCP: Більш складний клієнт з обробником повідомлень для різних типів повідомлень.

- **Оновлення прогресу:**
  - Класична HTTP: Прогрес є частиною основного потоку відповіді.
  - MCP: Прогрес надсилається окремими повідомленнями-сповіщеннями, в той час як основний результат приходить наприкінці.

### Рекомендації

Є дещо, що ми рекомендуємо при виборі між реалізацією класичної потокової передачі (як кінцева точка `/stream`, яку ми показували вище) і потоковою передачею через MCP.

- **Для простих потокових потреб:** Класична HTTP потокова передача простіша у реалізації і достатня для базових потреб.

- **Для складних, інтерактивних застосунків:** MCP потокова передача дає більш структурований підхід з багатшими метаданими та розділенням між сповіщеннями і кінцевими результатами.

- **Для AI-застосунків:** Система сповіщень MCP особливо корисна для тривалих AI-завдань, де потрібно тримати користувачів у курсі прогресу.

## Потокова передача в MCP

Отже, ви вже бачили деякі рекомендації і порівняння щодо відмінностей класичної потокової передачі і MCP. Тепер розглянемо детальніше, як саме можна використовувати потокову передачу у MCP.

Розуміння того, як потокова передача працює в межах MCP, важливе для створення адаптивних додатків, які надають зворотний зв’язок у реальному часі користувачам під час тривалих операцій.

У MCP потокова передача — це не надсилання основної відповіді у фрагментах, а надсилання **сповіщень** клієнту під час обробки запиту інструментом. Ці сповіщення можуть містити оновлення прогресу, логи або інші події.

### Як це працює

Основний результат все ще надсилається однією відповіддю. Однак під час обробки можуть надсилатися окремі повідомлення-сповіщення, які в реальному часі оновлюють клієнта. Клієнт повинен мати можливість обробляти та відображати ці сповіщення.

## Що таке сповіщення?

Ми згадали "сповіщення", що це означає у контексті MCP?

Сповіщення — це повідомлення, надіслане від сервера до клієнта для інформування про прогрес, стан або інші події під час тривалої операції. Сповіщення покращують прозорість і користувацький досвід.

Наприклад, клієнт повинен надіслати сповіщення, коли початкове рукостискання з сервером відбулося.

Сповіщення виглядають як JSON-повідомлення:

```json
{
  jsonrpc: "2.0";
  method: string;
  params?: {
    [key: string]: unknown;
  };
}
```

Сповіщення належать до теми MCP під назвою ["Logging"](https://modelcontextprotocol.io/specification/draft/server/utilities/logging).

> **Повідомлення про застарівання:** кандидат на випуск специфікації MCP 2026-07-28 позначає примітив Logging як застарілий на користь `stderr` для stdio транспортів та OpenTelemetry для структурованої спостережуваності. Logging продовжує працювати у `2025-11-25` і принаймні рік після будь-якого офіційного застарівання. Деталі дивіться в [Що змінюється в MCP: кандидат на випуск 2026-07-28](../../01-CoreConcepts/mcp-2026-07-28-release-candidate.md).

Щоб працювати з логуванням, сервер повинен увімкнути цю функцію/можливість так:

```json
{
  "capabilities": {
    "logging": {}
  }
}
```

> [!NOTE]
> Залежно від використовуваного SDK, логування може бути увімкнено за замовчуванням або його потрібно явно увімкнути в конфігурації сервера.

Існують різні типи сповіщень:

| Рівень    | Опис                          | Приклад використання           |
|-----------|-------------------------------|-------------------------------|
| debug     | Детальна інформація для відлагодження | Точки входу/виходу функцій    |
| info      | Загальна інформаційна повідомлення | Оновлення прогресу операції   |
| notice    | Звичайні, але значущі події      | Зміни конфігурації            |
| warning   | Умови попередження              | Використання застарілих функцій |
| error     | Умови помилки                  | Збої операцій                 |
| critical  | Критичні умови                 | Збої компонентів системи      |
| alert     | Потрібно негайне втручання     | Виявлення пошкодження даних   |
| emergency | Система непридатна до використання | Повний збій системи          |

## Реалізація сповіщень у MCP

Для реалізації сповіщень у MCP необхідно налаштувати як серверну, так і клієнтську частини для обробки миттєвих оновлень. Це дозволяє вашому застосунку надавати користувачам миттєвий зворотний зв’язок під час тривалих операцій.

### Серверна сторона: надсилання сповіщень

Розглянемо серверну сторону. У MCP ви визначаєте інструменти, які можуть надсилати сповіщення під час обробки запитів. Сервер використовує контекстний об’єкт (зазвичай `ctx`) для надсилання повідомлень клієнту.

#### Python

```python
@mcp.tool(description="A tool that sends progress notifications")
async def process_files(message: str, ctx: Context) -> TextContent:
    await ctx.info("Processing file 1/3...")
    await ctx.info("Processing file 2/3...")
    await ctx.info("Processing file 3/3...")
    return TextContent(type="text", text=f"Done: {message}")
```

У наведеному прикладі інструмент `process_files` надсилає три сповіщення клієнту під час обробки кожного файлу. Для надсилання інформаційних повідомлень використовується метод `ctx.info()`.

Крім того, щоб увімкнути сповіщення, переконайтеся, що ваш сервер використовує стрімінговий транспорт (наприклад, `streamable-http`), а клієнт реалізує обробник повідомлень для обробки сповіщень. Ось як ви можете налаштувати сервер для використання транспорту `streamable-http`:

```python
mcp.run(transport="streamable-http")
```

#### .NET

```csharp
[Tool("A tool that sends progress notifications")]
public async Task<TextContent> ProcessFiles(string message, ToolContext ctx)
{
    await ctx.Info("Processing file 1/3...");
    await ctx.Info("Processing file 2/3...");
    await ctx.Info("Processing file 3/3...");
    return new TextContent
    {
        Type = "text",
        Text = $"Done: {message}"
    };
}
```

У цьому прикладі на .NET інструмент `ProcessFiles` позначено атрибутом `Tool` і він надсилає три сповіщення клієнту під час обробки кожного файлу. Для відправлення інформаційних повідомлень використовується метод `ctx.Info()`.

Щоб увімкнути сповіщення в MCP сервері .NET, переконайтеся, що використовується стрімінговий транспорт:

```csharp
var builder = McpBuilder.Create();
await builder
    .UseStreamableHttp() // Enable streamable HTTP transport
    .Build()
    .RunAsync();
```

### Клієнтська сторона: отримання сповіщень

Клієнт повинен реалізувати обробник повідомлень для обробки та відображення сповіщень, які надходять.

#### Python

```python
async def message_handler(message):
    if isinstance(message, types.ServerNotification):
        print("NOTIFICATION:", message)
    else:
        print("SERVER MESSAGE:", message)

async with ClientSession(
   read_stream, 
   write_stream,
   logging_callback=logging_collector,
   message_handler=message_handler,
) as session:
```

У наведеному коді функція `message_handler` перевіряє, чи є вхідне повідомлення сповіщенням. Якщо так, вона виводить сповіщення; інакше обробляє його як звичайне повідомлення сервера. Також помітно, як `ClientSession` ініціалізується з обробником повідомлень для обробки вхідних сповіщень.

#### .NET

```csharp
// Define a message handler
void MessageHandler(IJsonRpcMessage message)
{
    if (message is ServerNotification notification)
    {
        Console.WriteLine($"NOTIFICATION: {notification}");
    }
    else
    {
        Console.WriteLine($"SERVER MESSAGE: {message}");
    }
}

// Create and use a client session with the message handler
var clientOptions = new ClientSessionOptions
{
    MessageHandler = MessageHandler,
    LoggingCallback = (level, message) => Console.WriteLine($"[{level}] {message}")
};

using var client = new ClientSession(readStream, writeStream, clientOptions);
await client.InitializeAsync();

// Now the client will process notifications through the MessageHandler
```

У цьому прикладі на .NET функція `MessageHandler` перевіряє, чи є вхідне повідомлення сповіщенням. Якщо так, вона виводить сповіщення; інакше обробляє його як звичайне повідомлення сервера. `ClientSession` ініціалізується з обробником повідомлень через `ClientSessionOptions`.

Щоб увімкнути сповіщення, переконайтеся, що сервер використовує стрімінговий транспорт (наприклад, `streamable-http`), а клієнт реалізує обробник повідомлень для обробки сповіщень.

## Сповіщення про прогрес та сценарії

У цьому розділі пояснюється концепція сповіщень про прогрес у MCP, чому вони важливі і як реалізувати їх за допомогою Streamable HTTP. Також ви знайдете практичне завдання для закріплення знань.

Сповіщення про прогрес — це повідомлення в реальному часі, які сервер надсилає клієнту під час тривалих операцій. Замість того, щоб чекати завершення всієї роботи, сервер тримає клієнта в курсі поточного стану. Це підвищує прозорість, покращує користувацький досвід і полегшує налагодження.

**Приклад:**

```text

"Processing document 1/10"
"Processing document 2/10"
...
"Processing complete!"

```

### Чому варто використовувати сповіщення про прогрес?

Сповіщення про прогрес важливі з кількох причин:

- **Кращий досвід користувача:** Користувачі бачать оновлення під час виконання роботи, а не лише в кінці.
- **Зворотний зв’язок у реальному часі:** Клієнти можуть відображати індикатори прогресу або логи, роблячи додаток більш відзивним.
- **Легше налагодження та моніторинг:** Розробники та користувачі можуть бачити, де процес може бути повільним або завислим.

### Як реалізувати сповіщення про прогрес

Ось як можна реалізувати сповіщення про прогрес у MCP:

- **На сервері:** Використовуйте `ctx.info()` або `ctx.log()` для надсилання сповіщень при обробці кожного елемента. Це надсилає повідомлення клієнту ще до того, як основний результат буде готовий.
- **На клієнті:** Реалізуйте обробник повідомлень, який прослуховує та відображає сповіщення по мірі їх надходження. Обробник розрізняє сповіщення і кінцевий результат.

**Приклад для сервера:**


#### Python

```python
@mcp.tool(description="A tool that sends progress notifications")
async def process_files(message: str, ctx: Context) -> TextContent:
    for i in range(1, 11):
        await ctx.info(f"Processing document {i}/10")
    await ctx.info("Processing complete!")
    return TextContent(type="text", text=f"Done: {message}")
```

**Приклад клієнта:**

#### Python

```python
async def message_handler(message):
    if isinstance(message, types.ServerNotification):
        print("NOTIFICATION:", message)
    else:
        print("SERVER MESSAGE:", message)
```

## Міркування щодо безпеки

Безпека має бути пріоритетом під час впровадження будь-якого сервера, особливо при використанні транспортів на основі HTTP, таких як Streamable HTTP у MCP.

Під час впровадження серверів MCP з транспортами на основі HTTP безпека стає першочерговим питанням, що вимагає уважної уваги до багатьох векторів атак та механізмів захисту.

### Огляд

Безпека є критично важливою при відкритті серверів MCP через HTTP. Streamable HTTP створює нові поверхні для атак і вимагає ретельного налаштування.

Ось деякі ключові міркування щодо безпеки:

- **Перевірка заголовка Origin:** Завжди перевіряйте заголовок `Origin`, щоб запобігти атакам DNS rebinding.
- **Прив’язка до localhost:** Для локальної розробки пов’язуйте сервери з `localhost`, щоб не робити їх публічно доступними.
- **Аутентифікація:** Реалізуйте аутентифікацію (наприклад, API-ключі, OAuth) для продуктивних розгортань.
- **CORS:** Налаштуйте політики Cross-Origin Resource Sharing (CORS) для обмеження доступу.
- **HTTPS:** Використовуйте HTTPS у продуктивному середовищі для шифрування трафіку.

### Найкращі практики

Окрім того, ось кілька найкращих практик для забезпечення безпеки у вашому потоковому сервері MCP:

- Ніколи не довіряйте вхідним запитам без перевірки.
- Логувати та моніторити весь доступ і помилки.
- Регулярно оновлюйте залежності для усунення вразливостей безпеки.

### Виклики

Ви зіткнетеся з такими викликами при впровадженні безпеки у потокових серверах MCP:

- Балансування між безпекою та зручністю розробки
- Забезпечення сумісності з різними клієнтськими середовищами


## Оновлення з SSE до Streamable HTTP

Для застосунків, які наразі використовують Server-Sent Events (SSE), міграція до Streamable HTTP надає розширені можливості та кращу довгострокову стабільність для ваших реалізацій MCP.

### Чому варто оновитися?

Існують дві вагомі причини оновити SSE до Streamable HTTP:

- Streamable HTTP пропонує кращу масштабованість, сумісність і ширшу підтримку повідомлень, ніж SSE.
- Це рекомендований транспорт для нових MCP-додатків.

### Кроки міграції

Ось як можна перейти від SSE до Streamable HTTP у ваших MCP-додатках:

- **Оновіть код сервера**, використовуючи `transport="streamable-http"` у `mcp.run()`.
- **Оновіть код клієнта**, замінивши SSE клієнта на `streamablehttp_client`.
- **Реалізуйте обробник повідомлень** на клієнті для обробки сповіщень.
- **Перевірте сумісність** із існуючими інструментами та робочими процесами.

### Підтримка сумісності

Рекомендується підтримувати сумісність з існуючими клієнтами SSE під час процесу міграції. Ось деякі стратегії:

- Ви можете підтримувати обидва протоколи SSE і Streamable HTTP, запускаючи їх на різних кінцевих точках.
- Поступово мігруйте клієнтів на новий транспорт.

### Виклики

Переконайтеся, що ви вирішуєте такі виклики під час міграції:

- Забезпечення оновлення усіх клієнтів
- Обробка відмінностей у доставці повідомлень

### Завдання: Побудуйте власний потоковий MCP-додаток

**Сценарій:**
Побудуйте сервер та клієнт MCP, де сервер обробляє список елементів (наприклад, файлів або документів) і надсилає сповіщення для кожного обробленого елемента. Клієнт має відображати кожне сповіщення по мірі його надходження.

**Кроки:**

1. Реалізуйте серверний інструмент, який обробляє список і надсилає сповіщення для кожного елемента.
2. Реалізуйте клієнта з обробником повідомлень для відображення сповіщень у реальному часі.
3. Перевірте свою реалізацію, запустивши сервер і клієнт, та спостерігайте сповіщення.
