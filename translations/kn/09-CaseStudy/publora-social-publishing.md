# ಪ್ರಕರಣ ಅಧ್ಯಯನ: ದೂರ MCP ಸರ್ವರ್ ಹೊಂದಿರುವ ಏಜೆಂಟ್‌ನಿಂದ ಸಾಮಾಜಿಕ ಜಾಲತಾಣಗಳಿಗೆ ಪ್ರಕಟಿಸುವುದು

> **ತಪ್ಪು ಜಾಹಿರಾತು:** ಹಲವು ಸೇವೆಗಳು ಮತ್ತು ಓಪನ್-ಸೋರ್ಸ್ ಪ್ರಾಜೆಕ್ಟ್‌ಗಳು ಸಾಮಾಜಿಕ ಜಾಲತಾಣಗಳಿಗೆ ಪ್ರಕಟಿಸಬಹುದು, ಮತ್ತು ಒಂದು ತಂಡ ಪ್ರತಿ ಜಾಲತಾಣದ API ಅನ್ನು ನೇರವಾಗಿ ಸಂಯೋಜಿಸಬಹುದು. ಕೆಳಗಿನ ಸ್ಥಿತಿ ಒಂದೊಂದು **ಬರೆಯುವ ಸಾಮರ್ಥ್ಯವಿರುವ ದೂರದ MCP ಸರ್ವರ್** ಹೇಗೆ ವಿನ್ಯಾಸಗೊಳಿಸಬಹುದು ಮತ್ತು ಬಳಸಬಹುದು ಎಂಬುದರ ಉದಾಹರಣೆಯಾಗಿದೆ. Publora ಒಂದು ವಾಣಿಜ್ಯ ಸೇವೆ ಮತ್ತು ಉಚಿತ ಮಟ್ಟವನ್ನು ಹೊಂದಿದೆ; ಇಲ್ಲಿ ವಿವರಣೆ ಮಾಡಿದ ಮಾದರಿಗಳು ಬಳಕೆದಾರರ ಪರವಾಗಿ ಅನಿರ್ವರ್ಯ ಕ್ರಿಯೆಗಳನ್ನು ನಡೆಸುವ ಯಾವುದೇ MCP ಸರ್ವರ್‌ಗೆ ಅನ್ವಯಿಸುತ್ತವೆ.

## ಅವಲೋಕನ

ಏಜೆಂಟ್‌ಗಳು ವಿಷಯವನ್ನು ರಚಿಸುವಲ್ಲಿ ಉತ್ತಮವಾಗಿದ್ದು, ಅದನ್ನು ವಿತರಿಸುವಲ್ಲಿ ಕಂબંધವಾಗಿವೆ. ಒಂದು ಮಾದರಿ ಸೆಕೆಂಡುಗಳಲ್ಲಿ ಬಿಡುಗಡೆ ಘೋಷಣೆಯನ್ನು ಬರೆಯಬಹುದು, ಮತ್ತು ನಂತರ ಕೆಲಸ ನಿಂತಿರುತ್ತದೆ: ಇದನ್ನು ಪ್ರಕಟಿಸುವುದು ಪ್ರತಿ ಜಾಲತಾಣಕ್ಕಾಗಿ API, ಪ್ರತಿ ಜಾಲತಾಣಕ್ಕಾಗಿ OAuth ಆ್ಯಪ್, ಮತ್ತು ಪ್ರತಿ ಜಾಲತಾಣಕ್ಕೆ ವಿಭಿನ್ನ ಮಾಧ್ಯಮ ನಿಯಮಗಳನ್ನು ಸಂಬಳಿಸುವುದು. ಬಹುತೇಕ ತಂಡಗಳು ಇದನ್ನು ಕೈಯಿಂದ ಬ್ರೌಸರ್‌ಗೆ ಪಠ್ಯವನ್ನು ನಕಲಿಸುವುದರ ಮೂಲಕ ಪರಿಹರಿಸುತ್ತವೆ.

ಈ ಪ್ರಕರಣ ಅಧ್ಯಯನ ಆ ಕೊನೆಯ ಹಂತವನ್ನು ಒಂದೊಂದು ದೂರ MCP ಸರ್ವರ್ ಮೂಲಕ ಹೇಗೆ ಮುಚ್ಚಬಹುದು ಎಂಬುದನ್ನು ನೋಡುತ್ತದೆ, ಮತ್ತು — ಯಾವುದೇ ಒಬ್ಬರೂ ಇದರಲ್ಲಿ ಸೇರಿಸಿಕೊಳ್ಳುತ್ತಿರುವವರು ಹೆಚ್ಚು ಉಪಯುಕ್ತವಾಗಿ — **ಬರೆಯುವ ಸಾಮರ್ಥ್ಯವಿರುವ** ಸರ್ವರ್ ಸರಿಯಾಗಿ ಹೊಂದಬೇಕಾದ ವಿನ್ಯಾಸ ನಿರ್ಧಾರಗಳನ್ನು. ಡೇಟಾ ಓದುವುದು ಕ್ಷಮಿಸುವುದು; ಪ್ರಕಟಿಸುವುದು ಅಲ್ಲ: ತಪ್ಪು ಉಪಕರಣ ಕರೆ ಪ್ರೇಕ್ಷಕರಿಗೆ ಸ್ಪಷ್ಟವಾಗುತ್ತದೆ ಮತ್ತು ಹಿಂದಕ್ಕೆ ತಿರುಗಿಸಲಾಗುವುದಿಲ್ಲ.

## ಪರಿಸ್ಥಿತಿ

ಒಂದು ಚಿಕ್ಕ ಡೆವಲಪರ್-ಸಂಬಂಧಗಳ ತಂಡ ಏಜೆಂಟ್ (Claude, VS Code, Cursor — ಕ್ಲೈಂಟ್ ಯಾವುದೇ ಆಗಬಹುದು) ಒಳಗೆ ಪೋಸ್ಟ್‌ಗಳನ್ನು ರಚಿಸುತ್ತದೆ. ಅವರು ಏಜೆಂಟ್‌ನಿಂದ ಬಯಸುತ್ತಾರೆ:

- ತಂಡವು ಸಂಪರ್ಕಿಸಿದ սոցիಯಲ್ ಖಾತೆಗಳನ್ನು ನೋಡಬೇಕೆಂದು,
- ಪೋಸ್ಟ್ ಅನ್ನು ರಚಿಸಿ, ಮನುಷ್ಯನ ಅನುಮೋದನೆಗಾಗಿ ಡ್ರಾಫ್ಟ್ ಆಗಿ ಇಟ್ಟುಕೊಳ್ಳಲು,
- ಚಿತ್ರ ಜೋಡಿಸಲು,
- ಆಯ್ಕೆಮಾಡಿದ ಸಮಯದಲ್ಲಿ ಹಲವು ಜಾಲತಾಣಗಳಿಗೆ ಸಮಯ ನಿಗದಿ ಮಾಡಲು,
- ಮತ್ತು ನಂತರ ಅದರ ಸಾಧನೆಯ ಕುರಿತು ವರದಿ ಮಾಡಲು.

ಪ್ರಮುಖವಾಗಿ, ಅವರ ಪ್ರಯೋಗಾಚರಣೆಯ ಮಧ್ಯದಲ್ಲಿದ್ದಾರೆಂದು ಏಜೆಂಟ್ ತಪ್ಪಾಗಿ ಪ್ರಕಟಿಸಬಾರದು.

## ಬಳಸಿದ ಸಾಧನಗಳು

- [Publora MCP Server](https://github.com/publora/mcp-server) — ದೂರ MCP ಸರ್ವರ್ (`streamable-http`) ಇದರಲ್ಲಿ ಪ್ರಕಟಣೆ, ನಿಗದಿ, ಮಾಧ್ಯಮ ಮತ್ತು LinkedIn ವಿಶ್ಲೇಷಣೆ ಉಪಕರಣಗಳನ್ನು ಒಳಗೊಂಡಿದೆ. ಅಧಿಕೃತ MCP ರಜಿಸ್ಟ್ರಿಯಲ್ಲಿ `com.publora/mcp-server` ಎನಿಸಿಕೊಂಡಿದೆ.

## ಹಂತ ನಿಜಗೊಳಿಸುವ ಕೆಲಸದ ಹರಿವು

1. **ಸರ್ವರ್‌ನ್ನು ಸಂಪರ್ಕಿಸಿ.** OAuth ಮಾತನಾಡುವ ಕ್ಲೈಂಟ್‌ಗಳು ಸರ್ವರ್ ಸ್ವಂತ ಅನುಮೋದನೆ ಪರದೆಯ ವಿರುದ್ಧ PKCE ಮೂಲಕ ಅನುಮೋದನೆ-ಕೋಡ್ ಪ್ರಕ್ರಿಯೆಯನ್ನು ಮುಗಿಸುತ್ತವೆ; ಇದರಲ್ಲಿ ಇಲ್ಲದಿದ್ದರೆ, उदाहरणಕ್ಕೆ ಮುಖ್ಯವಿಲ್ಲದ CLI ಗಳು, ಹೆಡರ್‌ನಲ್ಲಿ Publora API ಕೀ ಬಳಸುತ್ತವೆ. ಎರಡೂ ಮಾರ್ಗಗಳು ಬೆಂಬಲಿತವಾಗಿವೆ ಮತ್ತು ನೀವು ಯಾವ ಮಾರ್ಗ ಪಡೆಯುತ್ತೀರೋ ಅದು ಕ್ಲೈಂಟ್ ಮೇಲೆ ಅವಲಂಬಿಸಿದೆ, ಸರ್ವರ್ ಮೇಲೆ ಅಲ್ಲ.
2. **ಸಂಪರ್ಕಗಳನ್ನು ಪಟ್ಟಿ ಮಾಡಿ.** ಏಜೆಂಟ್ `list_connections` ಅನ್ನು ಕರೆಮಾಡುತ್ತದೆ ಮತ್ತು ಗುರುತಿಸಿಕೊಂಡಿರುವ ಖಾತೆಗಳನ್ನು ಸ್ವೀಕರಿಸುತ್ತದೆ.
3. **ಡ್ರಾಫ್ಟ್ ಮಾಡಿ.** ಏಜೆಂಟ್ `create_post` ಅನ್ನು *ನಿಗದಿತ ಸಮಯವಿಲ್ಲದೆ* ಕರೆಮಾಡುತ್ತದೆ. ಪೋಸ್ಟ್ ಡ್ರಾಫ್ಟ್ ಆಗಿ ಸಂಗ್ರಹಿಸಲಾಗುತ್ತದೆ — ಯಾವುದೂ ಪ್ರಕಟಿಸಲ್ಪಡುತ್ತಿಲ್ಲ.
4. **ಮಾಧ್ಯಮವನ್ನು ಜೋಡಿಸಿ.** ಸಾರ್ವಜನಿಕ ಚಿತ್ರ URL ಗಳು ಅಂದೇ ಕರೆನಲ್ಲಿ ನೀಡಲಾಗುತ್ತದೆ; ಸರ್ವರ್ ಅವುಗಳನ್ನು ಡೌನ್ಲೋಡ್ ಮಾಡಿ ಪರಿಶೀಲಿಸುತ್ತದೆ.
5. **ನಿಗದಿ ಮಾಡಿ.** ಮನುಷ್ಯ ಅನುಮೋದಿಸಿದ ನಂತರ, `update_post` ಸ್ಥಿತಿಯನ್ನು ISO 8601 ಸಮಯದೊಂದಿಗೆ ನಿಗದಿತ ಎಂದು ಸೆಟ್ ಮಾಡುತ್ತದೆ.
6. **ಅಳವಡಿಕೆ ಮಾಡಿ.** LinkedIn ಗಾಗಿ, `linkedin_post_stats` ಪೋಸ್ಟ್ ಲೈವ್ ಆದನಂತರ ಸಂವಹನವನ್ನು ತರುತ್ತದೆ.

## ತಾಂತ್ರಿಕ ಅನುಷ್ಠಾನ

ಕೆಳಗಿನ ಪಾಠಗಳು ಈ ಪ್ರಕರಣ ಅಧ್ಯಯನದ ವರ್ಗಾಯಿಸಬಹುದಾದ ಭಾಗವಾಗಿದೆ.

### ತೆರೆಯಲಾದ ಕಂಡುಹಿಡಿತ, ದೃಢೀಕರಿಸಲಾದ ಅನುಷ್ಠಾನ

`tools/list` ಕ್ರೆಡೆನ್ಷಿಯಲ್ಸ್ ಇಲ್ಲದೆ ಒದಗಿಸಲಾಗುತ್ತದೆ; ಪ್ರತಿ `tools/call` ಗೆ ಟೋಕನ್ ಅಗತ್ಯವಿದೆ
ಮತ್ತು ಇಲ್ಲದಿದ್ದಲ್ಲಿ `401` ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು `WWW-Authenticate` ಹೆಡರ್ ಜೊತೆಯಾಗಿ
ರಕ್ಷಿತ ಸಂಪನ್ಮೂಲ ಮೆಟಾಡೇಟಾವನ್ನು ಸೂಚಿಸುತ್ತದೆ. ಸರ್ವರ್‌ನ ಹಳೆಯ ಎಂಡ್‍ಪಾಯಿಂದ
ಪ್ರೋಟೋಕಾಲ್ ಸಂಸ್ಕರಣೆಗೆ ಮುನ್ನ `initialize` ಗೆ ಯಾವುದೇ ದೃಢೀಕರಣವಿಲ್ಲದೇ ಉತ್ತರ ನೀಡಬಹುದು;
ಇತ್ತೀಚಿನ ಕ್ಲೈಂಟ್‌ಗಳು ಆ ಕೈಪಿಡಿಯನ್ನು ಬಳಸುವುದಿಲ್ಲ.

ಈ ಸರ್ವರ್-ನಿರ್ದಿಷ್ಟ ವಿಭಜನವು ರಜಿಸ್ಟ್ರಿಗಳು, ಪಟ್ಟಿ-ಪುಸ್ತಕಗಳು ಮತ್ತು ಕ್ಲೈಂಟ್‌ಗಳು ಉಪಕರಣ
ಹೆಸರನ್ನು, ಯೋಜನೆಗಳನ್ನು ಮತ್ತು ಟಿಪ್ಪಣಿಗಳನ್ನು ಗುಪ್ತವಿಲ್ಲದೆ ಪರಿಶೀಲಿಸುವಂತೆ ಮಾಡುತ್ತದೆ ಆದರೆ anonimous
ಕಾರ್ಯಾಚರಣೆಯನ್ನು ತಡೆಯುತ್ತದೆ. ತೆರೆಯಲಾದ ಕಂಡುಹಿಡಿತವು ನಿಯೋಜನೆಯ ಆಯ್ಕೆಯಾಗಿದೆ, MCP ಅವಶ್ಯಕತೆ ಅಲ್ಲ; ಒಂದು
ರಕ್ಷಿತ ನಿಯೋಜನೆಗೆ `tools/list` ಗೆ ಅನುಮೋದನೆ ಬೇಕಾಗಬಹುದು.

### ನೋಂದಣಿ: ಗತಿಯುತ ಕ್ಲೈಂಟ್ ನೋಂದಣಿ ಮತ್ತು ಇದನ್ನು ಬದಲಾಯಿಸುವುದು ಯಾವುದು

ಸರ್ವರ್ `/.well-known/oauth-protected-resource` ಮತ್ತು `/.well-known/oauth-authorization-server` ಅನ್ನು ಜಾಹಿರ ಮಾಡುತ್ತದೆ, ಮತ್ತು PKCE (`S256`), ರಿಫ್ರೆಶ್ ಟೋಕನ್ ಮತ್ತು **ಗತಿಯುತ ಕ್ಲೈಂಟ್ ನೋಂದಣಿ** ಆಯ್ಕೆಗಳನ್ನು ಬೆಂಬಲಿಸುತ್ತದೆ.

ಗತಿಯುತ ನೋಂದಣಿಯು ಹಳೆಯ ಕ್ಲೈಂಟ್‌ಗಳ ಕೈಯಲ್ಲಿ ಕೈಮುಗಿದು: ಅದಿಲ್ಲದೆ,
ಪ್ರತಿ ಕ್ಲೈಂಟ್‌ಗೆ ವಿತರಕನಿಂದ ಮೊದಲು ನೀಡಲಾದ `client_id` ಬೇಕಾಗಿತ್ತು.

ಇದನ್ನು ವಿನ್ಯಾಸ-ನಕಲಿಸಲು ವಿನ್ಯಾಸವಲ್ಲದೆ ಹೊಂದಾಣಿಕೆಯ ವರ್ತನೆ ಎಂದು ಕೊಳ್ಳಿರಿ.  `2026-07-28` ಸಂಶೋಧನೆಯು ದೈನಂದಿನ ಕ್ಲೈಂಟ್ ನೋಂದಣಿಯನ್ನು ನಿಷೇವಿಸಲು ಮತ್ತು ಕ್ಲೈಂಟ್ ಐಡಿ ಮೆಟಾಡೇಟಾ ಡಾಕ್ಯುಮೆಂಟ್‌ಗಳಿಗೆ ಬದಲಾಯಿಸುತ್ತದೆ, ಅಲ್ಲಿ ಕ್ಲೈಂಟ್ ಒಂದು ಸ್ಥಿರ HTTPS URL ನಲ್ಲಿ ಒಂದು ಮೆಟಾಡೇಟಾ ಡಾಕ್ಯುಮೆಂಟ್ ಅನ್ನು ಹೋಸ್ಟ್ ಮಾಡುತ್ತದೆ ಮತ್ತು ಆ URL ಆಗಿಯೇ `client_id` ಆಗಿದೆ. DCR ಈಗಲೂ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತದೆ, ಆದರೆ ಇಂದಿನಿಂದ ನಿರ್ಮಿಸುವ ಸರ್ವರ್ CIMD ಗೆ ಯೋಜಿಸಬೇಕು ಮತ್ತು DCR ಅನ್ನು ಹಳೆಯ ಕ್ಲೈಂಟ್‌ಗಳಿಗಾಗಿ ಮಾತ್ರ ಇಡುವುದು ಉತ್ತಮ.

### ಉಪಕರಣ ಟಿಪ್ಪಣಿಗಳು ಅಲಂಕಾರವಲ್ಲ

ಪ್ರತಿ ಉಪಕರಣವು `title` ಮತ್ತು ಅನ್ವಯಿಸುವ ಸೂಚನೆಗಳನ್ನು ಹೊಂದುತ್ತದೆ: `readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`.

ಇದಕ್ಕೆ ಎರಡು ಕಾರಣಗಳಿವೆ. ಮೊದಲು, ಕ್ಲೈಂಟ್‌ಗಳು ಸೂಚನೆಗಳನ್ನು ಬಳಸಿ ಬಳಕೆದಾರನೊಂದಿಗೆ ಯಾವ ವಿಷಯವನ್ನು ದೃಢೀಕರಿಸಬೇಕೆಂದು ನಿರ್ಧರಿಸುತ್ತವೆ — ಒಂದು ಕ್ಲೈಂಟ್ ಓದಲು ಮಾತ್ರ Lookup ಅನ್ನು ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಮಾಡಬಹುದು ಮತ್ತು ಅಳಿಸುವ ಮೊದಲು ಅನುಮೋದನೆಗಾಗಿ ನಿಂತಿರಬಹುದು. ನಿಯಮವು ಸ್ಪಷ್ಟವಾಗಿ ಹೇಳುತ್ತದೆ ಟಿಪ್ಪಣಿಗಳು ನಂಬಬಾರದ ಸೂಚನೆಗಳು ಮತ್ತು ಅನುಮೋದನಾ ಯಂತ್ರವಲ್ಲ; ಅವು ಕ್ಲೈಂಟ್ ಯಾವ ಕಾರ್ಯವನ್ನು ನಿರ್ವಹಿಸಲು ಒದಗಿಸುತ್ತದೆ ಎನ್ನುವುದನ್ನು ರೂಪಿಸುತ್ತದೆ, ಅವು ಸರ್ವರ್‌ನಲ್ಲಿ ಯಾವುದನ್ನೂ ನಿಲ್ಲಿಸುವುದಿಲ್ಲ, ಮತ್ತು ಸರ್ವರ್ ತನ್ನ ನಿಯಮಗಳನ್ನು ಅನುಷ್ಠಾನಗೊಳಿಸಬೇಕು. ಎರಡನೆಯದಾಗಿ, ಪ್ರಮುಖ ಸಂಪರ್ಕ ಡೈರೆಕ್ಟರಿಗಳು ಈಗ ಅವಶ್ಯಕತೆ ಮಾಡುತ್ತವೆ; ಉಪಕರಣಗಳಿಗೆ ಶೀರ್ಷಿಕೆಗಳು ಮತ್ತು ಸೂಚನೆಗಳಿಲ್ಲದ ಸರ್ವರ್ ಕಾರ್ಯಕ್ಷಮತೆ ಎಷ್ಟಿದ್ದರೂ ತಿರಸ್ಕರಿಸಲಾಗುತ್ತದೆ.

### ಗುರುತಿಸುವಿಕೆಗಳನ್ನು ಕಲ್ಪನೆ ಮಾಡದಂತೆ ಮಾಡಿ

ವೇದಿಕೆಗಳ ಗುರುತಿಸುವಿಕೆಗಳು `list_connections` ಮೂಲಕ ನೀಡಲ್ಪಡುವ ಅಜ್ಞಾತ ಸಾಲುಗಳು, ಮತ್ತು ಯೋಜನೆಯ ವಿವರಣೆಯು ಸ್ಪಷ್ಟವೆಂದೇ ತಿಳಿಸುತ್ತದೆ ಅವುಗಳನ್ನು ನಕಲಿಸಿ ಬಿಡಬೇಕು ಮತ್ತು ಊಹಿಸಲು ಪರವಾನಗಿ ಇಲ್ಲ. ಸರ್ವರ್ ಇತೇರಾದ ಯಾವುದನ್ನಾದರೂ ನಿರಾಕರಿಸುತ್ತದೆ.

ಮಾದರಿಗಳು ದಕ್ಷ ಊಹಿಸುವವರಾಗಿವೆ. ಯಾವುದೇ ಬರೆಯುವ ಸಾಮರ್ಥ್ಯವಿರುವ ಸರ್ವರ್ ಅಂತಿಮವಾಗಿ ಗುರುತಿಸುವಿಕೆಯನ್ನು ಹೊಂಚು ಹಿಡಿದರೆ ಆಗ ಅದರ ಮಾರ್ಗವನ್ನು ತ್ವರಿತ ಮತ್ತು ಗಟ್ಟಿಯಾಗಿ ವಿಫಲ ಮಾಡಬೇಕು, ಸಾಧ್ಯತೆ ಇರುವ ಮೌಲ್ಯದ ಮೇಲೆ ಕಾರ್ಯನಿರ್ವಹಿಸುವುದಕ್ಕಿಂತ.

### ಪ್ರಕಟಿಸುವ ಮುನ್ನ ವಿಫಲ ಮಾಡಿ, ಕಾರ್ಯಸಾಧ್ಯ ಸಂದೇಶದೊಂದಿಗೆ

ಕೆಲ ಜಾಲತಾಣಗಳು ಪಠ್ಯ ಮಾತ್ರದ ಪೋಸ್ಟ್‌ಗಳನ್ನು ನಿರಾಕರಿಸಿ ಚಿತ್ರ ಅಥವಾ ವೀಡಿಯೋ ಅಗತ್ಯವಿರುತ್ತದೆ. ಆ ಸಮಯದಲ್ಲಿ ಪರಿಶೀಲನೆ ಮಾಡಲಾಗುತ್ತದೆ, ಮತ್ತು ದೋಷವು ವೇದಿಕೆಯನ್ನು ಮತ್ತು ಕೊರತೆಯ ಅವಶ್ಯಕತೆಯನ್ನು ಸೂಚಿಸುತ್ತದೆ.

ಏಜೆಂಟ್‌ಗಳು "Instagram ಗೆ ಮಾಧ್ಯಮ ಬೇಕು — ಚಿತ್ರ ಅಥವಾ ವೀಡಿಯೋ ಜೋಡಿಸಿ" ನಂತರ ಮತ್ತೊಂದು ದಾಡು ಇಲ್ಲದೆ ಮರುಮಾಡಬಹುದು. ಅದು ಸಾಮಾನ್ಯ `400` ದೋಷದಿಂದ ಮರುಮಾಡಲು ಸಾಧ್ಯವಿಲ್ಲ.

### ಮರುಪ್ರಯತ್ನಗಳನ್ನು ಸುರಕ್ಷಿತವಾಗಿ ಇರಿಸಿ

ವಿಷಯ ಸೃಷ್ಟಿಸುವ ಎರಡು ಉಪಕರಣಗಳು, `create_post` ಮತ್ತು `update_post`, idempotency ಕೀಲಿಯನ್ನು ಸ್ವೀಕರಿಸುತ್ತವೆ: ಅದನ್ನು ಅದೇ ವಿನಂತಿಯಿಂದ ಮರು ಪ್ರಯತ್ನಿಸುವುದರಿಂದ ಮೂಲ ಪ್ರತಿಕ್ರಿಯೆಯ ನಕಲನ್ನು ಪ್ರದರ್ಶಿಸುತ್ತದೆ ಮತ್ತು ಎರಡನೇ ಪೋಸ್ಟ್ ಸೃಷ್ಟಿಸುವುದಿಲ್ಲ. ಏಜೆಂಟ್ ರನ್‍ಟೈಮ್‌ಗಳು ಸಮಯ ಮೀರಿದಾಗ ಮರು ಪ್ರಯತ್ನಿಸುತ್ತವೆ; idempotency ಇಲ್ಲದೆ ವಿಳಂಬ ಪ್ರತಿಕ್ರಿಯೆ ನಕಲಿ ಪ್ರಕಟಣೆ ಆಗುತ್ತದೆ. ಇತರ ಬರೆಯುವ ಉಪಕರಣಗಳು — ಡಿಲೀಶನ್‌ಗಳು, ಮಾಧ್ಯಮ ಹಂತಗಳು, LinkedIn ಪ್ರತಿಕ್ರಿಯೆಗಳು ಮತ್ತು ಕಾಮೆಂಟ್‌ಗಳು — idempotency ತೆಗೆದುಕೊಳ್ಳುವುದಿಲ್ಲ, ಆದ್ದರಿಂದ ಅಲ್ಲಿ ಮರು ಪ್ರಯತ್ನ ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಸುರಕ್ಷಿತ ಅಲ್ಲ. ನೀವು ಯಾವವೂ ಅನೇಕತೆಗಳನ್ನು ರಕ್ಷಿಸುತ್ತೀರಿ ಮತ್ತು ಯಾವವು ಮಾಡುತ್ತೀರಿ ಎಂದು ತಿಳಿದುಕೊಳ್ಳುವುದು ಸೂಕ್ತ.

### ಯಾವುದನ್ನೂ ಪ್ರಕಟಿಸದ ಪರೀಕ್ಷಿಸುವ ಮಾರ್ಗವನ್ನು ನೀಡಿ


ಸರ್ವರ್ ಸಂರಕ್ಷಿತ ಗುರಿಯನ್ನು ಸ್ವೀಕರಿಸುತ್ತದೆ, `publora-playground`, ಇದು ನಿಜವಾದ ಗುರಿಯಾಗಿ ಪರಿಶೀಲಿಸಲಾಗುತ್ತದೆ ಮತ್ತು ಒಪ್ಪಿಗೆಯಾದ ನಂತರ ತಿರಸ್ಕರಿಸಲಾಗುತ್ತದೆ — ಲೈವ್ ಖಾತೆಗೆ ಯಾವುದು ತಲುಪುವುದಿಲ್ಲ. ಇದರ ವಿವರಣೆ ಯಂತ್ರ ಮಾದರಿಯಲ್ಲಿಯೂ ಇದೆ, ಯಾವುದೇ ಗ್ರಾಹಕನು ಪ್ರಮಾಣಪತ್ರಗಳಿಲ್ಲದೆ ಓದಿ ತಿಳಿದುಕೊಳ್ಳಬಹುದು: `create_post` ನ `platforms` ಕ್ಷೇತ್ರದಲ್ಲಿ ಇದನ್ನು "ಯಾವುದೇ ನಿಜವಾದ ಸಂಪರ್ಕ ಅಗತ್ಯವಿಲ್ಲದ ಸಂಪರ್ಕ-ಪರೀಕ್ಷಾ ಗುರಿ — ಪೋಸ್ಟ್ ಅನ್ನು ಒಪ್ಪಿಕೊಂಡು ತಿರಸ್ಕರಿಸಲಾಗುತ್ತದೆ, ಯಾವುದೂ ಪ್ರಕಟಿಸಲಾಗುವುದಿಲ್ಲ" ಎಂದು ದಾಖಲಿಸಲಾಗಿದೆ. ಇದನ್ನು ಏಕೈಕ ಪ್ರವೇಶವಾಗಿ ಪಾಸ್ ಮಾಡುವ ಮೂಲಕ ಕರೆಸಬಹುದು: `platforms: ["publora-playground"]`.

ಇದು ಸಂಪೂರ್ಣ ಮುಖಮೂರ್ತಿಯ ಅತ್ಯಂತ ಉಪಯುಕ್ತ ವಿವರಗಳಲ್ಲಿ ಒಂದಾಗಿ ಹೊರಬಂದಿದೆ. ಸಂಪರ್ಕಕ ನಿರ್ದೇಶನಗಳ ವಿಮರ್ಶಕರು, ಅನುದಾನ ದಾನಿಗಳು ಮತ್ತು ಸಿಐ ಪೂರ್ಣ ವೃಂದದ ಲೇಖನ ಮಾರ್ಗವನ್ನು ಯಾವುದೇ ನಿಜವಾದ ಪ್ರೇಕ್ಷಕರಿಗೆ ಅಪಾಯವಿಲ್ಲದೆ ಸಮಾಪ್ತಿಗೊಳಿಸಬಹುದು. ಯಾವುದೇ MCP ಸರ್ವರ್ ಅಪ್ರತಿವೃತ್ತ ಕ್ರಮಗಳೊಂದಿಗೆ ದಾಖಲೆಬದ್ಧ ನಿಷ್ಪ್ರಭ ಗುರಿಯಿಂದ ಲಾಭ ಪಡೆಯುತ್ತದೆ.

## ಫಲಿತಾಂಶಗಳು ಮತ್ತು ಪರಿಣಾಮ

- ಪ್ರಕಟಣಾ ಹಂತವು ಬ್ರೌಸರ್ ನಿಂದಲೇ ವಿಷಯ ಬರೆದ ಸಂವಾದದ ಭಾಗವನ್ನಾಗಿದ್ದು, ಪ್ರಾಥಮಿಕವಾದ ಖಾಕಿ ತಪ್ಪು ತಿದ್ದುವ ಸವಣಿಕೆ ಮಾನವವನ್ನು ಲೂಪಿನಲ್ಲಿ ಇಡುತ್ತದೆ. ಅದೇನೋ ಎಂಬುದರಲ್ಲಿ ಖಚಿತವಾಗಿರಿ: ಒಂದು ಖಾಕಿ ಸಂಪ್ರದಾಯ ಅಥವಾ ಗಡಿ ಅಲ್ಲ. ಅದೇ ಪ್ರಮಾಣಪತ್ರದಲ್ಲಿ ಯೋಜಿಸಬಹುದು ಅಥವಾ ಪ್ರಕಟಿಸಬಹುದು, ಆದಕಾರಣ ನಿಜವಾದ ಅನುಮೋದನೆಗೆ ಯಾವುದಾದರೂ ಬೇಕಾದರೆ ಅದನ್ನು ಅದುರುತ್ತದೆ ತನಕದ ಹೊರಗಿನ ಉಪಕರಣ ಮುಖಾಂತರ — ವಿಭಿನ್ನ ಪ್ರಮಾಣಪತ್ರಗಳು ಅಥವಾ ಸರ್ವರ್ನ ಮುಂಭಾಗದಲ್ಲಿನ ನೀತಿ ಪದರ.
- ಪ್ರತಿ-ನೀಟ್ವರ್ಕ್ ವ್ಯತ್ಯಾಸಗಳು — ಮಾಧ್ಯಮ ಅಗತ್ಯಗಳು, ದಾರಿರೇಖೆ, ಪ್ರತಿಕ್ರಿಯೆಯ ನಿಯಂತ್ರಣಗಳು — ಪ್ರತಿ ಏಜೆಂಟಿಗಲ್ಲದೆ ಸರ್ವರ್ ನಲ್ಲಿ ಒಮ್ಮೆ ನಿಭಾಯಿಸಲ್ಪಡುತ್ತವೆ.
- ಅದೇ ಸರ್ವರ್ ಹಲವು MCP ಗ್ರಾಹಕರಿಗೆ ಪೂರ್ವ-ಜಾರಿ ಪ್ರಮಾಣಪತ್ರಗಳಿಲ್ಲದೆ ಬೆಂಬಲಿಸುತ್ತದೆ.
    ಪ್ರಸ್ತುತ ಗ್ರಾಹಕರು ಗ್ರಾಹಕ ಐಡಿ ಮೆಟಾಡೇಟಾ ದಸ್ತಾವೇಜುಗಳನ್ನು ಬಳಸಬಹುದು; DCR ಹಳೆಯ ಗ್ರಾಹಕರಿಗೆ ಉಳಿದಿದೆ
    .
- ಮೇಲಿನ ವಿನ್ಯಾಸ ನಿರ್ಬಂಧಗಳನ್ನು ಬಳಕೆದಾರರಷ್ಟೇ ಅಲ್ಲದೆ ಸಂಪರ್ಕ ನಿರ್ದೇಶನ ವಿಮರ್ಶೆಗಳು ಸಹ ರೂಪಿಸಿಕೊಂಡವು: ಟಿಪ್ಪಣಿಗಳು, OAuth ಮತ್ತು ಸುರಕ್ಷಿತ ಪರೀಕ್ಷಾ ಗುರಿ ಒಂದೆರಡು ಒದಗಿಸುವವರಿಗೆ ಬೇಕಾಗಿರುತ್ತಿತ್ತು.

## ಮುಂದಿನ ಹಾದಿ

- ನೀವು ನಿರ್ಮಿಸುತ್ತಿರುವ MCP ಸರ್ವರ್ ಅನ್ನು ತೆಗೆದು ಇಲ್ಲಿ ಮೂರು ಅತಿ ಕಡಿಮೆ ವೆಚ್ಚದ ಗೆಲುವುಗಳನ್ನು ಪರೀಕ್ಷಿಸಿ: ಪ್ರತಿ ಉಪಕರಣದ ಮೇಲೆ ಟಿಪ್ಪಣಿಗಳು, ಪ್ರತಿ ಬರವಣಿಗೆಯ ಮೇಲ್ಮಟ್ಟದ್ದು ಅಪ್ರತಿರೂಪಣ ಕೀ, ಮತ್ತು ದಾಖಲೆಬದ್ಧ ನಿಷ್ಪ್ರಭ ಗುರಿ.
- ತೆರೆಯಲಾದ-ಅನ್ವೇಷಣಾ ವಿಭಜನೆಯ ಪ್ರಯತ್ನ ಮಾಡಿ: ಯಾವುದೇ ಪ್ರಮಾಣಪತ್ರಗಳಿಲ್ಲದೆ ಸಾರ್ವಜನಿಕ ದೂರದ ಸರ್ವರ್ ವಿರುದ್ಧ `tools/list` ಅನ್ನು ಕರೆ ಮಾಡಿ, ನಂತರ ಉಪಕರಣವನ್ನು ಕರೆ ಮಾಡಿ ಮತ್ತು `401` ಚಾಲೆಂಜ್ ಅನ್ನು ಪರಿಶೀಲಿಸಿ.
- ನಿಮ್ಮ ಕ್ಷೇತ್ರಕ್ಕೆ "ಮುಂದುವರಿಯುವ" (undo) ಅರ್ಥವೇನು ಎಂದು ಪರಿಗಣಿಸಿ. ಪ್ರಕಟಣೆಗೆ ಖಾಕಿಗಳು ಮತ್ತು ಅಳಿಸುವಿಕೆ ಇವೆ; ನಿಮ್ಮ ಕ್ರಮಗಳಿಗೆ ಸಮಾನಾರ್ಥಕವಿಲ್ಲದಿದ್ದರೆ, ದೃಢೀಕರಣವು ಉಪಕರಣ ವಿನ್ಯಾಸದಲ್ಲಿರಬೇಕಾದದ್ದು, ಪ್ರಾಂಪ್ಟ್ ನಲ್ಲಿ ಅಲ್ಲ.
