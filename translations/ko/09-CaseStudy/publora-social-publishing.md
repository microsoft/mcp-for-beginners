# 사례 연구: 원격 MCP 서버가 있는 에이전트에서 소셜 네트워크에 게시하기

> **면책 조항:** 여러 서비스와 오픈 소스 프로젝트가 소셜 네트워크에 게시할 수 있으며, 팀이 각 네트워크의 API를 직접 통합할 수도 있습니다. 아래 시나리오는 <strong>쓰기 가능한 원격 MCP 서버</strong>를 설계하고 사용하는 방법의 한 작업 예제로 제공됩니다. Publora는 무료 등급이 있는 상업 서비스이며, 여기에서 설명하는 패턴은 사용자를 대신하여 되돌릴 수 없는 작업을 수행하는 모든 MCP 서버에 적용됩니다.

## 개요

에이전트는 콘텐츠 초안 작성에는 능하지만 게시에는 약합니다. 모델은 몇 초 만에 발표문 초안을 작성할 수 있지만, 그 이후 작업은 멈춥니다: 게시하려면 네트워크마다 API, 네트워크마다 OAuth 앱, 그리고 각각 다른 미디어 규칙 세트가 필요합니다. 대부분 팀은 텍스트를 브라우저에 수동 복사하는 방식으로 이 문제를 해결합니다.

이 사례 연구는 마지막 단계를 단일 원격 MCP 서버로 해결하는 방법과 — 이를 구축하는 모든 사람에게 더 유용하게도 — **쓰기 가능한** 서버가 반드시 올바르게 처리해야 하는 설계 결정들을 살펴봅니다. 데이터를 읽는 것은 관대하지만, 게시하는 것은 그렇지 않습니다: 잘못된 도구 호출은 청중에게 공개되고 취소할 수 없습니다.

## 시나리오

소규모 개발자 관계 팀이 에이전트 내부(Claude, VS Code, Cursor — 클라이언트는 중요하지 않음)에서 게시물을 초안 작성합니다. 그들은 에이전트가 다음을 원합니다:

- 팀이 연결한 소셜 계정을 확인할 수 있고,
- 게시물 초안을 작성하고 사람이 승인할 수 있도록 초안 상태로 유지하며,
- 이미지를 첨부하고,
- 선택한 시간에 여러 네트워크에 게시 예약을 설정하며,
- 나중에 게시물 성과를 보고할 수 있기를 원합니다.

결정적으로, 그들은 에이전트가 아직 실험 중일 때 실수로 게시하지 못하도록 하길 원합니다.

## 사용 도구

- [Publora MCP 서버](https://github.com/publora/mcp-server) — 게시, 예약, 미디어 및 LinkedIn 분석 도구를 공개하는 원격 MCP 서버(`streamable-http`). 공식 MCP 레지스트리에 `com.publora/mcp-server`로 등록되어 있습니다.

## 단계별 작업 흐름

1. **서버 연결.** OAuth를 사용하는 클라이언트는 서버 자체 동의 화면을 대상으로 PKCE가 포함된 권한 코드 흐름을 완료합니다; 헤드리스 CLI와 같이 그렇지 않은 클라이언트는 헤더에 Publora API 키를 사용합니다. 두 경로 모두 지원되며, 어떤 경로를 사용하는지는 서버가 아닌 클라이언트에 따라 달라집니다.
2. **연결 목록.** 에이전트가 `list_connections`를 호출하면 연결된 계정과 해당 식별자를 받습니다.
3. **초안 작성.** 에이전트가 *예약 시간 없이* `create_post`를 호출합니다. 게시물은 초안으로 저장되며 게시되지 않습니다.
4. **미디어 첨부.** 공개 이미지 URL은 동일 호출에 전달되고, 서버가 다운로드하고 검증합니다.
5. **예약.** 사람이 승인한 후, `update_post`가 ISO 8601 시간으로 상태를 예약됨으로 설정합니다.
6. **측정.** LinkedIn의 경우, 게시물이 라이브가 되면 `linkedin_post_stats`가 참여도를 반환합니다.

## 예시 프롬프트

```text
Which social accounts do I have connected?
Draft a post announcing our new changelog page, attach the screenshot at
https://example.com/changelog.png, and keep it as a draft — do not publish it.
Once I approve, schedule it to LinkedIn and Bluesky for tomorrow at 09:00 UTC.
```

## 기술 구현

아래 교훈들은 이 사례 연구에서 전이 가능한 부분입니다.

### 열린 탐색, 인증된 실행

`tools/list`는 인증 없이 제공되고; 모든 `tools/call`은 토큰이 필요하며
그렇지 않으면 `WWW-Authenticate` 헤더와 함께 `401`을 반환합니다.

보호된 리소스 메타데이터. 서버의 레거시 엔드포인트는 또한 프로토콜 버전 `2026-07-28` 이전의 클라이언트를 위한 인증되지 않은 `initialize` 요청에도 응답합니다; 현재 클라이언트는 해당 핸드셰이크를 사용하지 않습니다.





### 등록: 동적 클라이언트 등록 및 그것을 대체하는 것




동적 등록은 레거시 클라이언트의 수동 단계를 제거했습니다: 이것이 없으면 각 클라이언트는 공급업체에서 사전 발급된 `client_id`가 필요했습니다.


이 동작을 복사할 설계가 아니라 호환성 동작으로 간주하십시오. 사양의 `2026-07-28` 개정은 클라이언트가 안정적인 HTTPS URL에 메타데이터 문서를 호스팅하고 그 URL이 `client_id`인 클라이언트 ID 메타데이터 문서(CIMD)를 선호하며 동적 클라이언트 등록은 사용 중단합니다. DCR은 당분간 작동하지만, 오늘 구축 중인 서버는 CIMD를 계획하고 DCR은 구형 클라이언트에만 유지해야 합니다.









### 식별자를 임의로 만들 수 없게 하십시오

플랫폼 식별자는 `list_connections`가 반환하는 불투명한 문자열이며, 스키마 설명도 이것을 문자 그대로 복사하고 추측하지 말아야 한다고 명시합니다. 서버는 다른 것은 거부합니다.

모델들은 유창한 추측자입니다. 작성 가능한 서버는 식별자가 결국 상상될 것이라 가정하고 즉시 문제를 발생시키도록 해야 하며, 그럴듯해 보이는 값에 기반해 작동하지 않아야 합니다.

### 게시 전에 실패하며, 실행 가능한 메시지를 제공합니다

일부 네트워크는 텍스트 전용 게시물을 거부하고 이미지 또는 비디오를 요구합니다. 이 점은 게시 일정 시 검증되고, 오류 메시지는 플랫폼과 누락된 요구 사항을 지정합니다.

에이전트는 "Instagram은 미디어를 요구합니다 — 이미지 또는 비디오를 첨부하세요" 메시지에서 추가 왕복 없이 복구할 수 있습니다. 일반적인 `400` 오류에서는 복구할 수 없습니다.

### 재시도를 안전하게 만드십시오

콘텐츠를 생성하는 두 도구, `create_post`와 `update_post`는 멱등성 키를 수락합니다: 동일한 요청에 키를 재사용하면 원래 응답을 재생하며 두 번째 게시물을 만들지 않습니다. 에이전트 런타임은 시간 초과 시 재시도하는데, 멱등성이 없으면 느린 응답이 중복 게시로 이어집니다. 다른 쓰기 도구들 — 삭제, 미디어 단계, LinkedIn 반응과 댓글 — 은 멱등성 키를 받지 않으므로 그곳에서 재시도는 자동으로 안전하지 않습니다. 자신의 변이 중 어떤 것이 보호되고 어떤 것이 아닌지 아는 것이 중요합니다.


### 아무것도 게시하지 않는 테스트 방법 제공


서버는 예약된 대상인 `publora-playground`를 받아들입니다. 이는 실제 목적지처럼 검증되고 승인되지만 버려집니다 — 실제 계정에 도달하는 것은 아무것도 없습니다. 이는 어느 클라이언트나 자격 증명 없이 읽을 수 있는 도구 스키마 자체에 설명되어 있습니다: `create_post`의 `platforms` 필드에서 "실제 연결을 요구하지 않는 연결 테스트 대상 — 게시물은 승인되고 버려지며, 아무것도 게시되지 않음"으로 문서화되어 있습니다. 유일한 항목으로 `platforms: ["publora-playground"]`를 전달하여 호출합니다.

이것은 전체 표면에서 가장 유용한 세부 정보 중 하나로 판명되었습니다. 커넥터 디렉터리의 리뷰어, 기여자 및 CI는 실제 청중에게 위험 없이 끝까지 전체 쓰기 경로를 실행할 수 있습니다. 되돌릴 수 없는 작업이 있는 모든 MCP 서버는 문서화된 무작동 대상의 혜택을 받습니다.

## 결과 및 영향

- 게시 단계가 브라우저에서 콘텐츠가 작성되는 동일한 대화로 이동했고, 초안 우선 습관이 사람을 참여시키는 고리를 유지합니다. 정확히 말하자면, 초안은 경계가 아닌 관례입니다. 동일한 자격 증명으로 예약하거나 게시할 수 있으므로 실제 승인 게이트가 필요한 사람은 도구 표면 외부에서 이를 시행해야 합니다 — 별도의 자격증명 또는 서버 앞의 정책 계층.
- 네트워크 별 차이 — 미디어 요구사항, 스레딩, 응답 컨트롤 — 이 각각 통신하는 모든 에이전트가 아니라 서버에서 한 번 처리됩니다.
- 동일한 서버가 사전 발급된 자격 증명 없이 여러 MCP 클라이언트를 지원합니다.
    현재 클라이언트는 Client ID 메타데이터 문서를 사용할 수 있으며; DCR은
    이전 클라이언트를 위한 대체 수단으로 남아 있습니다.
- 위의 설계 제약 조건은 사용자만큼 커넥터 디렉터리 리뷰로부터도 형성되었습니다: 주석, OAuth 및 안전한 테스트 대상은 각각 적어도 하나 이상에 의해 요구되었습니다.
