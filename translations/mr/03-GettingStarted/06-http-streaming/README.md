# मॉडेल कॉन्टेक्स्ट प्रोटोकॉल (MCP) सह HTTPS स्ट्रिमिंग

हा प्रकरण HTTPS वापरून मॉडेल कॉन्टेक्स्ट प्रोटोकॉल (MCP) सह सुरक्षित, स्केलेबल आणि रिअल-टाइम स्ट्रिमिंग कसे अंमलात आणायचे याबाबत सविस्तर मार्गदर्शक प्रदान करते. यात स्ट्रिमिंगचे प्रेरणा, उपलब्ध ट्रान्सपोर्ट मेकॅनिझम, MCP मध्ये स्ट्रिमेबल HTTP कसे अंमलात आणायचे, सुरक्षा सर्वोत्तम पद्धती, SSE कडून स्थलांतर, आणि स्वतःचे स्ट्रिमिंग MCP अॅप्लिकेशन्स तयार करण्यासाठी व्यावहारिक मार्गदर्शन यांचा समावेश आहे.

> **पुढे पाहणे:** हा धडा **MCP Specification 2025-11-25** अंतर्गत स्ट्रिमेबल HTTP चे वर्णन करतो, जिथे `initialize` दरम्यान सत्र स्थापन केले जाते आणि `Mcp-Session-Id` हेडरने पinned केले जाते. `2026-07-28` रिलीज कँडिडेट पूर्णपणे हाताळणी आणि सत्र आयडी काढून टाकतो, ज्यामुळे प्रत्येक विनंती स्वतःमध्ये संपूर्ण आणि कोणत्याही सर्व्हर इंस्टन्सकडे स्टिकी सत्रांशिवाय मार्गदर्शित केली जाऊ शकते. तपशीलांसाठी [MCP मध्ये काय बदलत आहे: 2026-07-28 रिलीज कँडिडेट](../../01-CoreConcepts/mcp-2026-07-28-release-candidate.md) पाहा.

## MCP मध्ये ट्रान्सपोर्ट मेकॅनिझम आणि स्ट्रिमिंग

हा विभाग MCP मध्ये उपलब्ध विविध ट्रान्सपोर्ट मेकॅनिझम आणि त्यांच्या कूपर्साठी स्ट्रिमिंग क्षमता सक्षम करण्यातील त्यांच्या भूमिकेचा अभ्यास करतो.

### ट्रान्सपोर्ट मेकॅनिझम काय आहे?

ट्रान्सपोर्ट मेकॅनिझम म्हणजे क्लायंट आणि सर्व्हर दरम्यान डेटा कसा बदलला जातो हे निश्चित करणारी पद्धत. MCP वेगवेगळ्या पर्यावरण आणि गरजांसाठी अनेक प्रकारच्या ट्रान्सपोर्टचे समर्थन करते:

- **stdio**: मानक इनपुट/आउटपुट, स्थानिक आणि CLI-आधारित साधनांसाठी योग्य. सोपे पण वेब किंवा क्लाउडसाठी योग्य नाही.
- **SSE (सर्व्हर-सेंट इव्हेंट्स)**: सर्व्हर्सना HTTP वरून क्लायंटसाठी रिअल-टाइम अद्यतने पुश करण्याची परवानगी देतो. वेब UI साठी चांगले, परंतु स्केलेबिलिटी आणि लवचिकतेमध्ये मर्यादित. MCP Specification 2025-06-18 नुसार, स्वतंत्र SSE ट्रान्सपोर्ट वापर बंद करण्यात आला आहे आणि "Streamable HTTP" ट्रान्सपोर्टने त्याची जागा घेतली आहे.
- **Streamable HTTP**: आधुनिक HTTP-आधारित स्ट्रिमिंग ट्रान्सपोर्ट, सूचना आणि चांगली स्केलेबिलिटी समर्थित. बहुतेक उत्पादन आणि क्लाउड परिस्थितीसाठी शिफारस केलेले.

### तुलना सारणी

या ट्रान्सपोर्ट मेकॅनिझममधील फरक समजण्यासाठी खालील तुलना सारणी पहा:

| ट्रान्सपोर्ट         | रिअल-टाइम अद्यतने | स्ट्रिमिंग | स्केलेबिलिटी | उपयोग प्रकरण               |
|-------------------|------------------|-----------|-------------|-------------------------|
| stdio             | नाही              | नाही       | कमी          | स्थानिक CLI साधने        |
| SSE               | होय               | होय        | मध्यम        | वेब, रिअल-टाइम अद्यतने  |
| Streamable HTTP   | होय               | होय        | जास्त        | क्लाउड, मल्टी-क्लायंट     |

> **टीप:** योग्य ट्रान्सपोर्ट निवडल्याने कार्यक्षमता, स्केलेबिलिटी आणि वापरकर्ता अनुभवावर प्रभाव होतो. **Streamable HTTP** आधुनिक, स्केलेबल, आणि क्लाउड-तयार अ‍ॅप्लिकेशन्ससाठी शिफारस केले जाते.

लक्षात घ्या की तुम्हाला मागील प्रकरणांमध्ये stdio आणि SSE ट्रान्सपोर्ट दाखवले गेले होते, आणि या प्रकरणात स्ट्रिमेबल HTTP ट्रान्सपोर्ट कसे वापरायचे हे समजवले आहे.

## स्ट्रिमिंग: संकल्पना आणि प्रेरणा

स्ट्रिमिंगमागील मूलभूत संकल्पना आणि प्रेरणा समजून घेणे प्रभावी रिअल-टाइम संवाद प्रणाली तयार करण्यासाठी आवश्यक आहे.

**स्ट्रिमिंग** एक नेटवर्क प्रोग्रामिंग तंत्र आहे ज्यामुळे डेटा लहान, व्यवस्थापनयोग्य तुकड्यांमध्ये किंवा एका घटना श्रेणीत पाठवता आणि प्राप्त करता येतो, पूर्ण प्रतिसादाची प्रतीक्षा करण्याऐवजी. हे विशेषतः उपयुक्त आहे:

- मोठ्या फाइल्स किंवा डेटासेटसाठी.
- रिअल-टाइम अद्यतने (उदा., चॅट, प्रगती पट्ट्या).
- दीर्घकालीन गणनांसाठी जिथे वापरकर्त्याला सतत माहिती देणे आवश्यक आहे.

स्ट्रिमिंग विषयी उच्च-स्तरीय माहितीसाठी येथे आहेत मुख्य मुद्दे:

- डेटा प्रगतिशीलपणे वितरित केला जातो, सगळा एकाच वेळेत नाही.
- क्लायंट डेटा प्राप्त झाल्यावर लगेच प्रक्रिया करू शकतो.
- दिसणारी विलंब कमी होते आणि वापरकर्ता अनुभव सुधारतो.

### स्ट्रिमिंग का वापरावे?

स्ट्रिमिंग वापरण्याची कारणे पुढीलप्रमाणे आहेत:

- वापरकर्त्यांना लगेच अभिप्राय मिळतो, केवळ शेवटी नाही
- रिअल-टाइम अॅप्लिकेशन्स आणि प्रतिसादात्मक UI सक्षम करतो
- नेटवर्क आणि संगणन संसाधनांचा अधिक कार्यक्षम वापर

### सोपा उदाहरण: HTTP स्ट्रिमिंग सर्व्हर आणि क्लायंट

स्ट्रिमिंग कसे अंमलात आणता येईल याचा सोपा उदाहरण येथे आहे:

#### पायथन

**सर्व्हर (पायथन, FastAPI आणि StreamingResponse वापरून):**

```python
from fastapi import FastAPI
from fastapi.responses import StreamingResponse
import time

app = FastAPI()

async def event_stream():
    for i in range(1, 6):
        yield f"data: Message {i}\n\n"
        time.sleep(1)

@app.get("/stream")
def stream():
    return StreamingResponse(event_stream(), media_type="text/event-stream")
```

**क्लायंट (पायथन, requests वापरून):**

```python
import requests

with requests.get("http://localhost:8000/stream", stream=True) as r:
    for line in r.iter_lines():
        if line:
            print(line.decode())
```

हे उदाहरण सर्व्हर कसे संदेशांची मालिका क्लायंटकडे पाठवतो जेव्हा ते उपलब्ध होतात, सगळ्या संदेशांची प्रतीक्षा न करता याचे दर्शन घडवते.

**कार्य कसे करते:**

- सर्व्हर प्रत्येक संदेश तयार होताच तो पाठवतो.
- क्लायंट प्रत्येक येणारा तुकडा प्राप्त करून प्रिंट करतो.

**आवश्यकताः**

- सर्व्हरला स्ट्रिमिंग प्रतिसाद वापरावा लागतो (उदा., FastAPI मधील `StreamingResponse`).
- क्लायंटला प्रतिसाद स्ट्रीम म्हणून प्रक्रिया करावा लागतो (`stream=True` requests मध्ये).
- कॉन्टेंट-टाइप सामान्यत: `text/event-stream` किंवा `application/octet-stream` असतो.

#### जावा

**सर्व्हर (जावा, Spring Boot आणि Server-Sent Events वापरून):**

```java
@RestController
public class CalculatorController {

    @GetMapping(value = "/calculate", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    public Flux<ServerSentEvent<String>> calculate(@RequestParam double a,
                                                   @RequestParam double b,
                                                   @RequestParam String op) {
        
        double result;
        switch (op) {
            case "add": result = a + b; break;
            case "sub": result = a - b; break;
            case "mul": result = a * b; break;
            case "div": result = b != 0 ? a / b : Double.NaN; break;
            default: result = Double.NaN;
        }

        return Flux.<ServerSentEvent<String>>just(
                    ServerSentEvent.<String>builder()
                        .event("info")
                        .data("Calculating: " + a + " " + op + " " + b)
                        .build(),
                    ServerSentEvent.<String>builder()
                        .event("result")
                        .data(String.valueOf(result))
                        .build()
                )
                .delayElements(Duration.ofSeconds(1));
    }
}
```

**क्लायंट (जावा, Spring WebFlux WebClient वापरून):**

```java
@SpringBootApplication
public class CalculatorClientApplication implements CommandLineRunner {

    private final WebClient client = WebClient.builder()
            .baseUrl("http://localhost:8080")
            .build();

    @Override
    public void run(String... args) {
        client.get()
                .uri(uriBuilder -> uriBuilder
                        .path("/calculate")
                        .queryParam("a", 7)
                        .queryParam("b", 5)
                        .queryParam("op", "mul")
                        .build())
                .accept(MediaType.TEXT_EVENT_STREAM)
                .retrieve()
                .bodyToFlux(String.class)
                .doOnNext(System.out::println)
                .blockLast();
    }
}
```

**जावा अंमलबजावणी टीपः**

- `Flux` सह Spring Boot चा प्रतिक्रियाशील स्टॅक वापरतो
- `ServerSentEvent` इव्हेंट प्रकारांसह संरचित स्ट्रिमिंग देते
- `WebClient` चे `bodyToFlux()` प्रतिक्रियाशील स्ट्रिमिंग घेण्यास सक्षम करतो
- `delayElements()` इव्हेंट दरम्यान प्रक्रिया वेळेचे अनुकरण करतो
- इव्हेंटमध्ये प्रकार (`info`, `result`) असू शकतात क्लायंट हँडलिंग सुधारण्यासाठी

### तुलना: पारंपरिक स्ट्रिमिंग विरुद्ध MCP स्ट्रिमिंग

पारंपरिक स्ट्रिमिंग आणि MCP मधील स्ट्रिमिंगमध्ये फरक खालील प्रमाणे दाखवला जाऊ शकतो:

| वैशिष्ट्य               | पारंपरिक HTTP स्ट्रिमिंग          | MCP स्ट्रिमिंग (सूचना)          |
|------------------------|-------------------------------|-------------------------------------|
| मुख्य प्रतिसाद          | तुकड्यांमध्ये                     | एकदाच, शेवटी                     |
| प्रगती अद्यतने          | डेटा तुकड्यांनुसार पाठवली       | सूचनांच्या रूपात पाठवली          |
| क्लायंट आवश्यकता       | स्ट्रिम प्रक्रिया करणे आवश्यक       | संदेश हँडलर अंमलात आणणे आवश्यक  |
| उपयोग प्रकरण           | मोठ्या फाइल्स, AI टोकन प्रवाह    | प्रगती, लॉग्स, रिअल-टाइम फीडबॅक  |

### मुख्य फरक

पुढील काही मुख्य फरक देखील आहेत:

- **संवाद पद्धत:**
  - पारंपरिक HTTP स्ट्रिमिंग: सोपी तुकड्यांमध्ये डेटा पाठवण्यासाठी चंक ट्रान्सफर एन्कोडिंग वापरतो
  - MCP स्ट्रिमिंग: JSON-RPC प्रोटोकॉलसह संरचित सूचना प्रणाली वापरते

- **संदेश फॉरमॅट:**
  - पारंपरिक HTTP: साधी टेक्स्ट तुकडे नवीन ओळींसह
  - MCP: मेटाडेटासह स्ट्रक्चर्ड LoggingMessageNotification वस्तू

- **क्लायंट अंमलबजावणी:**
  - पारंपरिक HTTP: स्ट्रिमिंग प्रतिसाद प्रक्रिया करणारा सोपा क्लायंट
  - MCP: वेगवेगळ्या प्रकारचे संदेश प्रक्रिया करण्यासाठी संदेश हँडलर असलेला अधिक प्रगत क्लायंट

- **प्रगती अद्यतने:**
  - पारंपरिक HTTP: प्रगती मुख्य प्रतिसाद स्ट्रिमचा भाग आहे
  - MCP: प्रगती वेगळ्या सूचना संदेशांद्वारे पाठवली जाते ज्यावेळी मुख्य प्रतिसाद शेवटी येतो

### शिफारसी

पारंपरिक स्ट्रिमिंग (जसे आम्ही `/stream` वापरून दाखवले) आणि MCP द्वारे स्ट्रिमिंगमध्ये निवड करताना काही गोष्टी आम्ही शिफारस करतो.

- **साध्या स्ट्रिमिंग गरजांसाठी:** पारंपरिक HTTP स्ट्रिमिंग सोपे आणि मूलभूत गरजांसाठी पुरेसे आहे.

- **जटिल, इंटरऐक्टिव अॅप्लिकेशन्ससाठी:** MCP स्ट्रिमिंग अधिक संरचित पद्धत देते ज्यामध्ये माहितीपूर्ण मेटाडेटा आणि सूचना आणि अंतिम निकाल यांच्यात भेद असतो.

- **AI अॅप्लिकेशन्ससाठी:** दीर्घकालीन AI कार्यांसाठी प्रगतीबद्दल वापरकर्त्यांना सतत माहिती देण्यासाठी MCP ची सूचना प्रणाली उपयुक्त आहे.

## MCP मध्ये स्ट्रिमिंग

बरं, तुम्ही आतापर्यंत पारंपरिक स्ट्रिमिंग आणि MCP मधील स्ट्रिमिंग यातील फरकांची काही शिफारशी आणि तुलना पाहिली आहे. आता आपण तपशीलवार पाहू कसे तुम्ही MCP मध्ये स्ट्रिमिंगचा उपयोग करू शकता.

MCP फ्रेमवर्कमध्ये स्ट्रिमिंग कसे कार्य करते ते समजून घेणे आवश्यक आहे जेणेकरून तुम्ही दीर्घकालीन ऑपरेशन्समध्ये वापरकर्त्यांना त्वरित फीडबॅक देणारी प्रतिसादात्मक अॅप्लिकेशन्स तयार करू शकाल.

MCP मध्ये, स्ट्रिमिंग म्हणजे मुख्य प्रतिसाद तुकड्यांमध्ये पाठवणे नाही, तर एखाद्या टूलने विनंती प्रक्रिया करताना क्लायंटला **सूचना** पाठवणे होय. या सूचनांमध्ये प्रगती अद्यतने, लॉग्स किंवा इतर घटना असू शकतात.

### हे कसे कार्य करते

मुख्य निकाल अजूनही एकाच प्रतिसादात पाठवला जातो. परंतु प्रक्रिया सुरू असताना सूचनांचे स्वतंत्र संदेश पाठवले जाऊ शकतात ज्यामुळे क्लायंटना रिअल-टाइममध्ये अपडेट करता येते. क्लायंटला हे संदेश हँडल करता यावे लागते आणि प्रदर्शित करावे लागते.

## सूचना म्हणजे काय?

"सूचना" म्हणायचे म्हणजे MCP संदर्भात काय?

सूचना म्हणजे सर्व्हरकडून क्लायंटला पाठवला जाणारा संदेश जो प्रगती, स्थिती किंवा दीर्घकालीन ऑपरेशन दरम्यान इतर घटना याबाबत माहिती देतो. सूचना पारदर्शकता आणि वापरकर्ता अनुभव सुधारतात.

उदाहरणार्थ, क्लायंटने सर्व्हरशी प्राथमिक हँडशेक झाल्यावर सूचना पाठवणे अपेक्षित आहे.

सूचना JSON संदेश म्हणून अशा प्रकारे दिसते:

```json
{
  jsonrpc: "2.0";
  method: string;
  params?: {
    [key: string]: unknown;
  };
}
```

सूचना MCP मधील ["Logging"](https://modelcontextprotocol.io/specification/draft/server/utilities/logging) या विषयाशी संबंधित आहेत.

> **डिप्रिसीशन सूचना:** `2026-07-28` MCP स्पेसिफिकेशन रिलीज कँडिडेट लॉगिंग प्रिमिटिव्ह `stderr` साठी stdio ट्रान्सपोर्ट आणि OpenTelemetry साठी संरचित निरीक्षणाबाबत डिप्रिसिएट करते. लॉगिंग `2025-11-25` मध्ये आणि कोणत्याही औपचारिक डिप्रिसिएशन नंतर किमान एक वर्ष कार्यरत राहील. तपशीलांसाठी [MCP मध्ये काय बदलत आहे: 2026-07-28 रिलीज कँडिडेट](../../01-CoreConcepts/mcp-2026-07-28-release-candidate.md) पाहा.

लॉगिंग कार्यान्वित करण्यासाठी सर्व्हरने खालीलप्रमाणे फीचर/क्षमता सक्षम करावी लागते:

```json
{
  "capabilities": {
    "logging": {}
  }
}
```

> [!NOTE]
> SDK वापरावर अवलंबून, लॉगिंग डीफॉल्टने सक्षम असू शकते किंवा तुमच्या सर्व्हर कॉन्फिगरेशनमध्ये स्पष्टपणे सक्षम करावे लागू शकते.

वेगवेगळ्या प्रकारच्या सूचनां आहेत:

| स्तर       | वर्णन                      | उदाहरण उपयोग प्रकरण         |
|-----------|----------------------------|------------------------------|
| debug     | सविस्तर डीबगिंग माहिती      | फंक्शनची प्रवेश/निर्गम बिंदू   |
| info      | सामान्य माहिती संदेश         | ऑपरेशन प्रगती अद्यतने        |
| notice    | सामान्य पण महत्त्वाच्या घटना  | कॉन्फिगरेशन बदल              |
| warning   | इशारा स्थिती               | वापरलेले चुकलेले फिचर         |
| error     | त्रुटी स्थिती               | ऑपरेशन अयशस्वी               |
| critical  | गंभीर स्थिती               | सिस्टम घटक अपयश               |
| alert     | त्वरित कारवाई आवश्यक आहे      | डेटा भ्रष्टाचार आढळला       |
| emergency | सिस्टम वापरण्यायोग्य नाही      | पूर्ण सिस्टम अपयश            |

## MCP मध्ये सूचना अंमलात आणणे

MCP मध्ये सूचना अंमलात आणण्यासाठी, तुम्हाला सर्व्हर आणि क्लायंट दोन्ही बाजूस रिअल-टाइम अद्यतन हाताळण्यासाठी व्यवस्था करावी लागेल. यामुळे तुमची अ‍ॅप्लिकेशन दीर्घकालीन ऑपरेशन्स दरम्यान त्वरित अभिप्राय देऊ शकते.

### सर्व्हर बाजू: सूचना पाठवणे

सर्व्हर बाजूने सुरुवात करूया. MCP मध्ये, तुम्ही असे टूल ठरवता जे विनंती प्रक्रिया करताना सूचना पाठवू शकतात. सर्व्हर संदर्भ ऑब्जेक्ट (सामान्यतः `ctx`) वापरून क्लायंटला संदेश पाठवतो.

#### पायथन

```python
@mcp.tool(description="A tool that sends progress notifications")
async def process_files(message: str, ctx: Context) -> TextContent:
    await ctx.info("Processing file 1/3...")
    await ctx.info("Processing file 2/3...")
    await ctx.info("Processing file 3/3...")
    return TextContent(type="text", text=f"Done: {message}")
```

मागील उदाहरणात, `process_files` टूल प्रत्येक फाईल प्रक्रिया करताना क्लायंटला तीन सूचना पाठवते. `ctx.info()` मेथड माहितीपर संदेश पाठवण्यासाठी वापरले जाते.

याव्यतिरिक्त, सूचनांना सक्षम करण्यासाठी, तुमचा सर्व्हर स्ट्रीमिंग ट्रान्सपोर्ट (उदा., `streamable-http`) वापरत असल्याची खात्री करा आणि तुमच्या क्लायंटकडे सूचना प्रक्रिया करण्यासाठी संदेश हँडलर असावा. खाली `streamable-http` ट्रान्सपोर्ट वापरण्यासाठी सर्व्हर कसे सेट करायचे दाखवले आहे:

```python
mcp.run(transport="streamable-http")
```

#### .NET

```csharp
[Tool("A tool that sends progress notifications")]
public async Task<TextContent> ProcessFiles(string message, ToolContext ctx)
{
    await ctx.Info("Processing file 1/3...");
    await ctx.Info("Processing file 2/3...");
    await ctx.Info("Processing file 3/3...");
    return new TextContent
    {
        Type = "text",
        Text = $"Done: {message}"
    };
}
```

या .NET उदाहरणात, `ProcessFiles` टूल `Tool` अ‍ॅट्रीब्यूटसह सजवले आहे आणि प्रत्येक फाईल प्रक्रिया करताना क्लायंटला तीन सूचना पाठवते. `ctx.Info()` मेथड माहितीपर संदेश पाठवण्यासाठी वापरले जाते.

तुमच्या .NET MCP सर्व्हरमध्ये सूचना सक्षम करण्यासाठी स्ट्रीमिंग ट्रान्सपोर्ट वापरत असल्याची खात्री करा:

```csharp
var builder = McpBuilder.Create();
await builder
    .UseStreamableHttp() // Enable streamable HTTP transport
    .Build()
    .RunAsync();
```

### क्लायंट बाजू: सूचना प्राप्त करणे

क्लायंटला येणाऱ्या सूचनांची प्रक्रिया करण्यासाठी आणि त्यांना प्रदर्शित करण्यासाठी संदेश हँडलर अंमलात आणावा लागतो.

#### पायथन

```python
async def message_handler(message):
    if isinstance(message, types.ServerNotification):
        print("NOTIFICATION:", message)
    else:
        print("SERVER MESSAGE:", message)

async with ClientSession(
   read_stream, 
   write_stream,
   logging_callback=logging_collector,
   message_handler=message_handler,
) as session:
```

मागील कोडमध्ये, `message_handler` फंक्शन तपासते की येणारा संदेश सूचना आहे की नाही. असल्यास तो सूचना प्रिंट करतो; अन्यथा, तो सरसकट सर्व्हर संदेशासाठी प्रक्रिया करतो. तसेच `ClientSession` ला `message_handler` सह प्रारंभ केले आहे जेणेकरून येणाऱ्या सूचनांवर प्रक्रिया करता येईल.

#### .NET

```csharp
// Define a message handler
void MessageHandler(IJsonRpcMessage message)
{
    if (message is ServerNotification notification)
    {
        Console.WriteLine($"NOTIFICATION: {notification}");
    }
    else
    {
        Console.WriteLine($"SERVER MESSAGE: {message}");
    }
}

// Create and use a client session with the message handler
var clientOptions = new ClientSessionOptions
{
    MessageHandler = MessageHandler,
    LoggingCallback = (level, message) => Console.WriteLine($"[{level}] {message}")
};

using var client = new ClientSession(readStream, writeStream, clientOptions);
await client.InitializeAsync();

// Now the client will process notifications through the MessageHandler
```

या .NET उदाहरणात, `MessageHandler` फंक्शन तपासते की येणारा संदेश सूचना आहे की नाही. असल्यास तो सूचना प्रिंट करतो; अन्यथा, तो सरसकट सर्व्हर संदेश प्रक्रिया करतो. `ClientSession` ला `ClientSessionOptions` मधील मेसेज हँडलर सह प्रारंभ केले आहे.

सूचना सक्षम करण्यासाठी, तुमचा सर्व्हर स्ट्रीमिंग ट्रान्सपोर्ट वापरत असल्याची खात्री करा (उदा., `streamable-http`) आणि तुम्ही क्लायंटकडे सूचना प्रक्रिया करण्यासाठी संदेश हँडलर वापरत आहात.

## प्रगती सूचना आणि परिस्थिती

हा विभाग MCP मधील प्रगती सूचनांचा संकल्पना, महत्त्व, आणि Streamable HTTP वापरून त्यांचे अंमलबजावणी कशी करावी याचे स्पष्टीकरण करतो. समज वाढवण्यासाठी एक व्यावहारिक असाइनमेंट सुद्धा आहे.

प्रगती सूचना म्हणजे दीर्घकालीन ऑपरेशन्स दरम्यान सर्व्हरकडून क्लायंटला पाठवले जाणारे रिअल-टाइम संदेश. संपूर्ण प्रक्रिया पूर्ण होण्याची प्रतीक्षा करण्याऐवजी सर्व्हर क्लायंटला वर्तमान स्थितीबद्दल अपडेट ठेवतो. हे पारदर्शकता, वापरकर्ता अनुभव सुधारतो आणि डिबगिंग सुलभ करते.

**उदाहरण:**

```text

"Processing document 1/10"
"Processing document 2/10"
...
"Processing complete!"

```

### प्रगती सूचनांचा उपयोग का करावा?

प्रगती सूचनांचे महत्त्व अनेक कारणास्तव आहे:

- **वापरकर्ता अनुभव सुधारतो:** वापरकर्ते काम प्रगतीत असल्याचे पाहतात, शेवटी नाही.
- **रिअल-टाइम अभिप्राय:** क्लायंट प्रगती पट्ट्या किंवा लॉग्स दाखवू शकतात, ज्यामुळे अ‍ॅप प्रतिसादक्षम वाटते.
- **सुलभ डिबगिंग आणि निरीक्षण:** विकसक आणि वापरकर्ते पाहू शकतात की प्रक्रिया कुठे धीमी किंवा अडकली आहे.

### प्रगती सूचनांची अंमलबजावणी कशी करावी

खालीलप्रमाणे तुम्ही MCP मध्ये प्रगती सूचनांची अंमलबजावणी करू शकता:

- **सर्व्हरवर:** `ctx.info()` किंवा `ctx.log()` वापरून प्रत्येक आयटम प्रक्रिया होताना सूचना पाठवा. मुख्य निकाल तयार होण्यापूर्वी क्लायंटला संदेश पाठवला जातो.
- **क्लायंटवर:** संदेश हँडलर अंमलात आणा जो येणाऱ्या सूचनांना ऐकतो आणि प्रदर्शित करतो. हा हँडलर सूचनांना आणि अंतिम निकालाला वेगळ्या प्रकारे ओळखतो.

**सर्व्हर उदाहरण:**


#### पायथन

```python
@mcp.tool(description="A tool that sends progress notifications")
async def process_files(message: str, ctx: Context) -> TextContent:
    for i in range(1, 11):
        await ctx.info(f"Processing document {i}/10")
    await ctx.info("Processing complete!")
    return TextContent(type="text", text=f"Done: {message}")
```

**क्लायंट उदाहरण:**

#### पायथन

```python
async def message_handler(message):
    if isinstance(message, types.ServerNotification):
        print("NOTIFICATION:", message)
    else:
        print("SERVER MESSAGE:", message)
```

## सुरक्षा विचार

कोणताही सर्व्हर अंमलात आणताना सुरक्षा सर्वोच्च प्राधान्य असावी, विशेषत: जेव्हा HTTP-आधारित ट्रान्सपोर्ट्स जसे की MCP मध्ये Streamable HTTP वापरले जातात.

HTTP-आधारित ट्रान्सपोर्टसह MCP सर्व्हर तयार करताना सुरक्षा एक महत्वाचा विषय असतो ज्यासाठी अनेक हल्ल्यांच्या मार्गांवर आणि संरक्षण यंत्रणा यावर काळजीपूर्वक लक्ष देणे आवश्यक असते.

### आढावा

MCP सर्व्हर HTTP वर एक्सपोज केल्यावर सुरक्षा अत्यंत महत्त्वाची ठरते. Streamable HTTP नवीन हल्ल्यांच्या संभाव्यता निर्माण करते आणि विशेष कॉन्फिगरेशनची गरज असते.

येथे काही मुख्य सुरक्षा विचार आहेत:

- **Origin Header Validation**: DNS रीबाइंडिंग हल्ले टाळण्यासाठी नेहमी `Origin` हेडरची प्रमाणीकरण करा.
- **Localhost Binding**: स्थानिक विकासासाठी सर्व्हर `localhost` वर बांधा जेणेकरून सार्वजनिक इंटरनेटवर ते एक्सपोज होणार नाहीत.
- **Authentication**: उत्पादन तैनातीसाठी प्रमाणीकरण (उदा. API कीज, OAuth) अंमलात आणा.
- **CORS**: सीमित प्रवेशासाठी Cross-Origin Resource Sharing (CORS) धोरणे कॉन्फिगर करा.
- **HTTPS**: ट्राफिक एन्क्रिप्ट करण्यासाठी उत्पादनामध्ये HTTPS वापरा.

### सर्वोत्तम पद्धती

शिवाय, येथे काही सर्वोत्तम पद्धती आहेत ज्यांचे पालन करणे आवश्यक आहे जेव्हा तुम्ही तुमच्या MCP स्लेटिंग सर्व्हरमध्ये सुरक्षा राबवत असता:

- येणाऱ्या विनंत्यांवर प्रमाणीकरणाशिवाय कधीही विश्वास ठेऊ नका.
- सर्व प्रवेश व त्रुटींचे लॉगिंग आणि निरीक्षण करा.
- सुरक्षा दोष दुरुस्त करण्यासाठी नियमितपणे अवलंबित पॅकेजेस अपडेट करा.

### आव्हाने

MCP स्ट्रीमिंग सर्व्हरमध्ये सुरक्षा राबवताना तुम्हाला काही आव्हानांना सामोरे जावे लागेल:

- विकास सुलभतेशी सुरक्षा संतुलन राखणे
- विविध क्लायंट पर्यावरणांशी सुसंगतता सुनिश्चित करणे


## SSE पासून Streamable HTTP कडे अपग्रेड करणे

सध्या Server-Sent Events (SSE) वापरणाऱ्या अनुप्रयोगांसाठी Streamable HTTP कडे स्थलांतर केल्याने MCP अंमलबजावणींसाठी वाढीव क्षमता आणि चांगली दीर्घकालीन टिकाऊपणा प्राप्त होतो.

### का अपग्रेड करावे?

SSE पासून Streamable HTTP कडे अपग्रेड करण्यासाठी दोन ठोस कारणे आहेत:

- Streamable HTTP SSE पेक्षा उत्तम स्केलेबिलिटी, सुसंगतता, आणि अधिक समृद्ध सूचना समर्थन प्रदान करते.
- हे नवीन MCP अनुप्रयोगांसाठी शिफारस केलेले ट्रान्सपोर्ट आहे.

### स्थलांतर पद्धती

आपल्या MCP अनुप्रयोगांमध्ये SSE कडून Streamable HTTP कडे स्थलांतर करण्याचा मार्ग येथे आहे:

- `mcp.run()` मध्ये `transport="streamable-http"` वापरण्यासाठी सर्व्हर कोड अद्यतनित करा.
- SSE क्लायंटच्या ऐवजी `streamablehttp_client` वापरून क्लायंट कोड अद्यतनित करा.
- सूचना प्रक्रिया करण्यासाठी क्लायंटमध्ये एक संदेश हाताळणारा तयार करा.
- विद्यमान टूल्स आणि वर्कफ्लोजसोबत सुसंगतता साठी चाचणी करा.

### सुसंगतता राखणे

स्थलांतर प्रक्रियेमध्ये विद्यमान SSE क्लायंटसह सुसंगतता राखणे शिफारसीय आहे. येथे काही धोरणे आहेत:

- तुम्ही वेगवेगळ्या एंडपॉइंटवर दोन्ही SSE आणि Streamable HTTP चालवून दोन्ही ट्रान्सपोर्टस समर्थन करू शकता.
- हळूहळू क्लायंटना नवीन ट्रान्सपोर्टकडे स्थलांतर करा.

### आव्हाने

स्थलांतर दरम्यान खालील आव्हाने हाताळणे आवश्यक आहे:

- सर्व क्लायंट अद्ययावत करणे सुनिश्चित करणे
- सूचनांच्या वितरणातील फरक हाताळणे

### असाइनमेंट: स्वतःचा स्ट्रीमिंग MCP अ‍ॅप तयार करा

**परिस्थिती:**
असे MCP सर्व्हर आणि क्लायंट तयार करा जिथे सर्व्हर आयटम्सची यादी (उदा. फाइल्स किंवा दस्तऐवज) प्रक्रिया करतो आणि प्रत्येक प्रक्रिया केलेल्या आयटमसाठी सूचना पाठवतो. क्लायंटस प्रत्येक सूचना येताच त्याचे प्रदर्शन करावे.

**पायऱ्या:**

1. यादी प्रक्रिया करणारा आणि प्रत्येक आयटमसाठी सूचना पाठवणारा सर्व्हर टूल अंमलात आणा.
2. रिअल-टाइममध्ये सूचना प्रदर्शित करण्यासाठी संदेश हाताळणारा असलेला क्लायंट तयार करा.
3. तुमचे अंमलबजावणी सर्व्हर आणि क्लायंट एकत्र चालवून चाचणी करा आणि सूचना पहा.

- [Microsoft: ASP.NET Core मधील CORS](https://learn.microsoft.com/aspnet/core/security/cors?view=aspnetcore-8.0&WT.mc_id=%3Fwt.mc_id%3DMVP_452430)
