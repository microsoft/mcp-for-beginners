# שורשי MCP (תכונה מיושנת)

> [!WARNING]
> שורשים מיושנים החל מ-MCP `2026-07-28`. הם נשארים בגרסה זו לצורך
> תאימות ויכולים להיות מוסרים בעדכון הראשון של המפרט
> שייפורסם ב-28 ביולי 2027 או לאחר מכן. מימושים חדשים צריכים להעביר
> ספריות או קבצים דרך פרמטרים של כלי, URI של משאבים, או
> קביעות תצורה של השרת.

## סקירה כללית

שורשים מאפשרים ללקוח MCP להודיע לשרת אילו מיקומי מערכת קבצים רלוונטיים
לבקשה הנוכחית. שורש מכיל URI מסוג `file://` נדרש ושם קריא אופציונלי.


לא מופעי פרוטוקול, ולא מנגנון בקרת גישה. הפרוטוקול אינו
מחייב שהשרת יישאר בתוך השורשים שצוינו.


## מטרות הלמידה

בסוף שיעור זה, תוכל:

- להסביר מה השורשים מייצגים ומה הם אינם מייצגים.
- לזהות את הזרימה הרב-שלבית של `roots/list` הנוכחית.
- ליישם בקרות אבטחה באופן עצמאי משורשים.
- להמיר מימושים חדשים לאלטרנטיבות נתמכות.

## נתוני שורש

הלקוח מחזיר כל שורש כ-URI מסוג `file://` עם שם תצוגה אופציונלי:

```json
{
  "roots": [
    {
      "uri": "file:///home/user/projects/weather-service",
      "name": "Weather Service"
    }
  ]
}
```

יש להציג ללקוחות רק מיקומים שאושרו על ידי המשתמש. השרתים צריכים להתייחס
לתוצאה כהכוונה לגבי קבצים רלוונטיים, לא כהוכחה לאוטוריזציה.

## זרימת MCP של 2026-07-28

לקוח התומך בשורשים מצהיר על היכולת בכל בקשה:

```json
{
  "_meta": {
    "io.modelcontextprotocol/clientCapabilities": {
      "roots": {}
    }
  }
}
```

במהלך עיבוד בקשת לקוח, השרת יכול להחזיר
`InputRequiredResult` המכיל בקשת קלט `roots/list`:

```json
{
  "resultType": "input_required",
  "inputRequests": {
    "workspaceRoots": {
      "method": "roots/list"
    }
  },
  "requestState": "opaque-state-from-server"
}
```

הלקוח אוסף את השורשים המאושרים ומנסה שוב את הבקשה המקורית עם ה-
`inputResponses` התואמים ו-`requestState` ללא שינוי. תבנית רב-שלבית זו
שומרת את הפרוטוקול ללא מצב; אין חיבור `initialize` או
מפגש ברמת הפרוטוקול.

## התנהגות מיושנת 2025-11-25

ב-MCP `2025-11-25`, לקוחות פרסמו שורשים במהלך האתחול. השרת
יכול היה להוציא בקשה ישירה `roots/list`, והלקוח יכול היה לשלוח
`notifications/roots/list_changed` כשהשורשים השתנו.

מחזור חיים זה הוא התנהגות מיושנת. אין לשלב את דוגמאות האתחול או
ההתראה עם מימוש של `2026-07-28`.

## תחליפים מומלצים

### פרמטרים של כלי

להפוך את הספרייה או הקובץ הנדרש לברור במבנה הכלי:

```json
{
  "name": "analyze_project",
  "inputSchema": {
    "type": "object",
    "properties": {
      "projectDirectory": {
        "type": "string",
        "description": "Approved project directory to analyze"
      }
    },
    "required": ["projectDirectory"]
  }
}
```

### URI של משאבים

השתמש במשאבי MCP כאשר השרת יכול להציג את הקבצים הרלוונטיים דרך URI יציבים.
זה שומר על גילוי ושליפה במפורש.

### קונפיגורציית שרת

בפריסות קבועות, קבע את הספריות המורשות בעת הפעלת השרת.
זה לעיתים קרובות ברור יותר מלגלות אותם במהלך קריאה לכלי.

## דרישות אבטחה

מכל החלופות שתבחר:

- קבל הסכמת משתמש לפני חשיפת מיקומי מערכת הקבצים.
- קנוניקליזציה ואימות נתיבים למניעת חציית סביבות.
- אכוף הרשאות וסנדרה בנפרד מערכי השורש.
- בדוק הרשאות מחדש בעת גישה לקובץ, לא רק בזמן רישומו.
- הימנע מהחזרת נתיבים רגישים ביומנים או בהודעות שגיאה.

## נקודות מרכזיות לזכור

- שורשים מתארים מיקומים רלוונטיים במערכת הקבצים; הם אינם מאחסנים
  מצב שיחה.
- שורשים הם הכוונה, לא גבול בקרת גישה.
- MCP `2026-07-28` נושא את היכולת לפי בקשה ומשתמש ב-
  `InputRequiredResult` עבור `roots/list`.
- מימושים חדשים צריכים להשתמש בפרמטרי כלי, URI של משאבים, או
  קונפיגורציית שרת במקום זאת.
