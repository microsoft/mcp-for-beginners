# HTTPS стриминг са протоколом контекста модела (MCP)

Ово поглавље пружа свеобухватан водич за имплементацију безбедног, скалабилног и стриминг у реалном времену помоћу протокола контекста модела (MCP) користећи HTTPS. Обухвата мотивацију за стриминг, доступне механизме транспорта, како имплементирати стриминг HTTP у MCP-у, најбоље безбедносне праксе, миграцију са SSE, и практичне смернице за изградњу сопствених стриминг MCP апликација.

> **Поглед унапред:** ова лекција описује стриминг HTTP под **MCP спецификацијом 2025-11-25**, где се сесија успоставља током `initialize` и фиксира са `Mcp-Session-Id` хедером. Кандидат за издање од `2026-07-28` укида handshake и session ID у потпуности, чинећи сваки захтев самосталним и усмеривим ка било којој серверској инстанци без "стики" сесија. Погледајте [Шта се мења у MCP: кандидат за издање 2026-07-28](../../01-CoreConcepts/mcp-2026-07-28-release-candidate.md) за детаље.

## Механизми транспорта и стриминг у MCP

Одељак проучава различите механизме транспорта доступне у MCP-у и њихову улогу у омогућавању способности стриминга за комуникацију у реалном времену између клијената и сервера.

### Шта је механизам транспорта?

Механизам транспорта дефинише како се подаци размењују између клијента и сервера. MCP подржава више типова транспорта како би одговарао различитим окружењима и захтевима:

- **stdio**: Стандардни улаз/излаз, погодан за локалне и CLI алате. Једноставан али непогодан за веб или облак.
- **SSE (Server-Sent Events)**: Омогућава серверима да у реалном времену шаљу ажурирања клијентима преко HTTP. Добар за веб интерфејсе, али са ограниченим скалабилношћу и флексибилношћу. По MCP спецификацији 2025-06-18, самостални SSE транспорт је укинут и замењен "Streamable HTTP" транспортом.
- **Streamable HTTP**: Модерни HTTP-базирани стриминг транспорт, који подржава обавештења и бољу скалабилност. Препоручује се за већину продукционих и облачних сценарија.

### Табела поређења

Погледајте табелу поређења у наставку да бисте разумели разлике између ових механизама транспорта:

| Транспорт         | Ажурирања у реалном времену | Стриминг | Скалабилност | Примена                |
|-------------------|------------------------------|----------|--------------|-----------------------|
| stdio             | Не                           | Не       | Ниска        | Локални CLI алати     |
| SSE               | Да                           | Да       | Средња       | Веб, ажурирања у реалном времену |
| Streamable HTTP   | Да                           | Да       | Висока       | Облак, више клијената |

> **Савет:** Избор правог транспорта утиче на перформансе, скалабилност и корисничко искуство. **Streamable HTTP** се препоручује за модерне, скалабилне и облачно-прилагођене апликације.

Имајте у виду транспорте stdio и SSE које сте видели у претходним поглављима и како је стриминг HTTP транспорт који покривамо у овом поглављу.

## Стриминг: Концепти и мотивација

Разумевање основних концепата и мотивације иза стриминга је кључно за имплементацију ефикасних система комуникације у реалном времену.

**Стриминг** је техника у мрежном програмирању која омогућава слање и примање података у малим, управљивим деловима или као секвенца догађаја, уместо да се чека цео одговор да буде спреман. Ово је посебно корисно за:

- Велике фајлове или скупове података.
- Ажурирања у реалном времену (нпр. чет, траке напретка).
- Дуготрајне обраде где желите да корисник буде информисан.

Ево шта треба знати о стримингу на високом нивоу:

- Подаци се испоручују постепено, не сви одједном.
- Клијент може обрађивати податке како долазе.
- Смањује перципирану латенцију и побољшава корисничко искуство.

### Зашто користити стриминг?

Разлози за коришћење стриминга су следећи:

- Корисници добијају повратну информацију одмах, не само на крају
- Омогућује апликације у реалном времену и интерактивне UI
- Ефикаснија употреба мрежних и рачунарских ресурса

### Једноставан пример: HTTP стриминг сервер и клијент

Ево једноставног примера како се стриминг може имплементирати:

#### Python

**Сервер (Python, користећи FastAPI и StreamingResponse):**

```python
from fastapi import FastAPI
from fastapi.responses import StreamingResponse
import time

app = FastAPI()

async def event_stream():
    for i in range(1, 6):
        yield f"data: Message {i}\n\n"
        time.sleep(1)

@app.get("/stream")
def stream():
    return StreamingResponse(event_stream(), media_type="text/event-stream")
```

**Клијент (Python, користећи requests):**

```python
import requests

with requests.get("http://localhost:8000/stream", stream=True) as r:
    for line in r.iter_lines():
        if line:
            print(line.decode())
```

Овај пример приказује сервер који шаље серију порука клијенту како постају доступне, уместо да чека да све поруке буду спремне.

**Како ради:**

- Сервер шаље сваку поруку како је спремна.
- Клијент прима и исписује сваки део како стиже.

**Захтеви:**

- Сервер мора користити стриминг одговор (нпр. `StreamingResponse` у FastAPI).
- Клијент мора обрадити одговор као стрим (`stream=True` у requests).
- Content-Type је обично `text/event-stream` или `application/octet-stream`.

#### Java

**Сервер (Java, користећи Spring Boot и Server-Sent Events):**

```java
@RestController
public class CalculatorController {

    @GetMapping(value = "/calculate", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    public Flux<ServerSentEvent<String>> calculate(@RequestParam double a,
                                                   @RequestParam double b,
                                                   @RequestParam String op) {
        
        double result;
        switch (op) {
            case "add": result = a + b; break;
            case "sub": result = a - b; break;
            case "mul": result = a * b; break;
            case "div": result = b != 0 ? a / b : Double.NaN; break;
            default: result = Double.NaN;
        }

        return Flux.<ServerSentEvent<String>>just(
                    ServerSentEvent.<String>builder()
                        .event("info")
                        .data("Calculating: " + a + " " + op + " " + b)
                        .build(),
                    ServerSentEvent.<String>builder()
                        .event("result")
                        .data(String.valueOf(result))
                        .build()
                )
                .delayElements(Duration.ofSeconds(1));
    }
}
```

**Клијент (Java, користећи Spring WebFlux WebClient):**

```java
@SpringBootApplication
public class CalculatorClientApplication implements CommandLineRunner {

    private final WebClient client = WebClient.builder()
            .baseUrl("http://localhost:8080")
            .build();

    @Override
    public void run(String... args) {
        client.get()
                .uri(uriBuilder -> uriBuilder
                        .path("/calculate")
                        .queryParam("a", 7)
                        .queryParam("b", 5)
                        .queryParam("op", "mul")
                        .build())
                .accept(MediaType.TEXT_EVENT_STREAM)
                .retrieve()
                .bodyToFlux(String.class)
                .doOnNext(System.out::println)
                .blockLast();
    }
}
```

**Напомене о имплементацији у Јави:**

- Користи реактивни стек Spring Boot-а са `Flux` за стриминг
- `ServerSentEvent` пружа структуриран стриминг догађаја са типовима догађаја
- `WebClient` са `bodyToFlux()` омогућава реактивну потрошњу стриминга
- `delayElements()` симулира време обраде између догађаја
- Догађаји могу имати типове (`info`, `result`) за бољу обраду на клијенту

### Поређење: класични стриминг против MCP стриминга

Разлике између класичног начина стриминга и како то функционише у MCP могу бити представљене овако:

| Карактеристика           | Класични HTTP стриминг        | MCP стриминг (Обавештења)         |
|-------------------------|-------------------------------|-----------------------------------|
| Главни одговор           | Подељен у делове (chunked)    | Један, на крају                    |
| Ажурирања напретка       | Слање као делови података     | Слање као обавештења              |
| Захтеви клијента          | Мора обрадити стрим           | Мора имплементирати обраду порука |
| Примена                  | Велики фајлови, токови токена AI | Напредак, логови, повратне информације у реалном времену |

### Кључне разлике

Поред тога, ево неких кључних разлика:

- **Обрасци комуникације:**
  - Класични HTTP стриминг: Користи једноставно кодирање преноса у деловима за слање података
  - MCP стриминг: Користи структуриран систем обавештења са JSON-RPC протоколом

- **Формат поруке:**
  - Класични HTTP: Текстуални делови са новим редом
  - MCP: Структурисани LoggingMessageNotification објекти са метаподацима

- **Имплементација клијента:**
  - Класични HTTP: Једноставан клијент који обрађује стриминг одговоре
  - MCP: Сложенији клијент са обрадом порука за различите типове порука

- **Ажурирања напретка:**
  - Класични HTTP: Напредак је део главног одговора у стриму
  - MCP: Напредак се шаље преко посебних обавештења, док главни одговор долази на крају

### Препоруке

Постоје неке ствари које препоручујемо када је у питању избор између класичног стриминга (као крајње тачке `/stream` као што смо приказали) и стриминга преко MCP.

- **За једноставне потребе стриминга:** Класични HTTP стриминг је једноставнији за имплементацију и довољан за основне потребе стриминга.

- **За сложене, интерактивне апликације:** MCP стриминг нуди структуранији приступ са богатијим метаподацима и разликом између обавештења и коначних резултата.

- **За AI апликације:** MCP-ов систем обавештења је посебно користан за дуготрајне AI задатке где желите да кориснике редовно информришете о напретку.

## Стриминг у MCP

Дакле, видели сте неке препоруке и поређења до сада о разликама између класичног стриминга и MCP стриминга. Хајде да детаљно погледамо како тачно можете искористити стриминг у MCP-у.

Разумевање како стриминг функционише у оквиру MCP-а је кључно за изградњу интерактивних апликација које пружају повратне информације у реалном времену корисницима током дуготрајних операција.

У MCP-у, стриминг није слање главног одговора у деловима, већ слање **обавештења** клијенту док алат обрађује захтев. Та обавештења могу укључивати ажурирања напретка, логове или друге догађаје.

### Како функционише

Главни резултат се и даље шаље као један одговор. Међутим, обавештења могу бити послата као посебне поруке током обраде и тиме ажурирати клијента у реалном времену. Клијент мора моћи да обрађује и приказује ова обавештења.

## Шта је обавештење?

Рекли смо "Обавештење", шта то значи у контексту MCP-а?

Обавештење је порука коју сервер шаље клијенту да информише о напретку, статусу или другим догађајима током дуготрајне операције. Обавештења побољшавају транспарентност и корисничко искуство.

На пример, клијент треба да пошаље обавештење када је иницијална размена руку са сервером завршена.

Обавештење изгледа овако као JSON порука:

```json
{
  jsonrpc: "2.0";
  method: string;
  params?: {
    [key: string]: unknown;
  };
}
```

Обавештења припадају теми у MCP-у познатој као ["Logging"](https://modelcontextprotocol.io/specification/draft/server/utilities/logging).

> **Обавештење о депрецјацији:** MCP спецификациони кандидат за издање од 2026-07-28 означава Logging примитив као застарелу у корист `stderr` за stdio транспорте и OpenTelemetry за структуирану посматрачност. Logging наставља да ради у `2025-11-25` и најмање годину дана након формалне депрецјације. Погледајте [Шта се мења у MCP: кандидат за издање 2026-07-28](../../01-CoreConcepts/mcp-2026-07-28-release-candidate.md).

Да бисте омогућили логовање, сервер треба да га омогући као функцију/могућност овако:

```json
{
  "capabilities": {
    "logging": {}
  }
}
```

> [!NOTE]
> У зависности од коришћеног SDK-а, логовање може бити омогућено подразумевано или може бити потребно експлицитно га укључити у конфигурацији сервера.

Постоје различити типови обавештења:

| Ниво      | Опис                          | Пример примене                 |
|-----------|-------------------------------|--------------------------------|
| debug     | Детаљне информације за дебаг  | Улози/излази функција          |
| info      | Опште информационе поруке     | Ажурирања напретка операције  |
| notice    | Нормални али значајни догађаји| Промене конфигурације          |
| warning   | Упозорења                    | Коришћење застареле функције  |
| error     | Грешке                      | Неуспеси операције             |
| critical  | Критични услови              | Неуспеси компоненти система    |
| alert     | Одмах је потребна акција      | Откривена корупција података  |
| emergency | Систем није употребљив       | Потпуни пад система           |

## Имплементација обавештења у MCP-у

Да бисте имплементирали обавештења у MCP-у, потребно је поставити и серверску и клијентску страну да рукују ажурирањима у реалном времену. Ово омогућава вашој апликацији да пружи тренутне повратне информације корисницима током дуготрајних операција.

### Серверска страна: слање обавештења

Почнимо са серверском страном. У MCP-у дефинишете алате који могу слати обавештења током обраде захтева. Сервер користи context објекат (обично `ctx`) за слање порука клијенту.

#### Python

```python
@mcp.tool(description="A tool that sends progress notifications")
async def process_files(message: str, ctx: Context) -> TextContent:
    await ctx.info("Processing file 1/3...")
    await ctx.info("Processing file 2/3...")
    await ctx.info("Processing file 3/3...")
    return TextContent(type="text", text=f"Done: {message}")
```

У претходном примеру, алат `process_files` шаље три обавештења клијенту док обрађује сваки фајл. Метода `ctx.info()` користи се за слање информативних порука.

Поред тога, како бисте омогућили обавештења, уверите се да сервер користи стриминг транспорт (нпр. `streamable-http`) и да клијент имплементира обраду порука за руковање обавештењима. Ево како да конфигуришете сервер за коришћење `streamable-http` транспорта:

```python
mcp.run(transport="streamable-http")
```

#### .NET

```csharp
[Tool("A tool that sends progress notifications")]
public async Task<TextContent> ProcessFiles(string message, ToolContext ctx)
{
    await ctx.Info("Processing file 1/3...");
    await ctx.Info("Processing file 2/3...");
    await ctx.Info("Processing file 3/3...");
    return new TextContent
    {
        Type = "text",
        Text = $"Done: {message}"
    };
}
```

У овом .NET примеру, алат `ProcessFiles` је означен са `Tool` атрибутом и шаље три обавештења клијенту док обрађује сваки фајл. Метода `ctx.Info()` користи се за слање информативних порука.

Да бисте омогућили обавештења на вашем .NET MCP серверу, уверите се да користите стриминг транспорт:

```csharp
var builder = McpBuilder.Create();
await builder
    .UseStreamableHttp() // Enable streamable HTTP transport
    .Build()
    .RunAsync();
```

### Клијентска страна: примање обавештења

Клијент мора имплементирати обрађивач порука који прима и приказује обавештења како пристижу.

#### Python

```python
async def message_handler(message):
    if isinstance(message, types.ServerNotification):
        print("NOTIFICATION:", message)
    else:
        print("SERVER MESSAGE:", message)

async with ClientSession(
   read_stream, 
   write_stream,
   logging_callback=logging_collector,
   message_handler=message_handler,
) as session:
```

У претходном коду, функција `message_handler` проверава да ли је долазна порука обавештење. Ако јесте, исписује обавештење; у супротном, обрађује је као обичну поруку сервера. Такође, обратите пажњу како је `ClientSession` иницијализована са `message_handler` за руковање долазним обавештењима.

#### .NET

```csharp
// Define a message handler
void MessageHandler(IJsonRpcMessage message)
{
    if (message is ServerNotification notification)
    {
        Console.WriteLine($"NOTIFICATION: {notification}");
    }
    else
    {
        Console.WriteLine($"SERVER MESSAGE: {message}");
    }
}

// Create and use a client session with the message handler
var clientOptions = new ClientSessionOptions
{
    MessageHandler = MessageHandler,
    LoggingCallback = (level, message) => Console.WriteLine($"[{level}] {message}")
};

using var client = new ClientSession(readStream, writeStream, clientOptions);
await client.InitializeAsync();

// Now the client will process notifications through the MessageHandler
```

У овом .NET примеру, функција `MessageHandler` проверава да ли је долазна порука обавештење. Ако јесте, исписује обавештење; у супротном, обрађује је као обичну поруку сервера. `ClientSession` је иницијализована са обрадом порука преко `ClientSessionOptions`.

Да бисте омогућили обавештења, уверите се да ваш сервер користи стриминг транспорт (нпр. `streamable-http`) и да ваш клијент имплементира обраду порука за обавештења.

## Обавештења о напретку и сценарији

Овај одељак објашњава појам обавештења о напретку у MCP-у, зашто су важна и како их имплементирати користећи Streamable HTTP. Такође ћете пронаћи практичан задатак за јачање разумевања.

Обавештења о напретку су поруке у реалном времену које сервер шаље клијенту током дуготрајних операција. Уместо да се чека да цео процес заврши, сервер стално обавештава клијента о тренутном статусу. Ово побољшава транспарентност, корисничко искуство и олакшава отклањање грешака.

**Пример:**

```text

"Processing document 1/10"
"Processing document 2/10"
...
"Processing complete!"

```

### Зашто користити обавештења о напретку?

Обавештења о напретку су важна из неколико разлога:

- **Боље корисничко искуство:** Корисници виде ажурирања како рад напредује, не само на крају.
- **Повратне информације у реалном времену:** Клијенти могу приказивати траке напретка или логове, што апликацију чини одзивном.
- **Лакоћа дебаговања и праћења:** Програмери и корисници могу видети где процес може бити спор или застојен.

### Како имплементирати обавештења о напретку

Ево како можете имплементирати обавештења о напретку у MCP-у:

- **На серверу:** Користите `ctx.info()` или `ctx.log()` за слање обавештења како се сваки елемент обрађује. Ово шаље поруку клијенту пре него што главни резултат буде спреман.
- **На клијенту:** Имплементирајте обраду порука која слуша и приказује обавештења како пристижу. Овај обрађивач разликује обавештења од коначног резултата.

**Пример сервера:**


#### Python

```python
@mcp.tool(description="A tool that sends progress notifications")
async def process_files(message: str, ctx: Context) -> TextContent:
    for i in range(1, 11):
        await ctx.info(f"Processing document {i}/10")
    await ctx.info("Processing complete!")
    return TextContent(type="text", text=f"Done: {message}")
```

**Пример клијента:**

#### Python

```python
async def message_handler(message):
    if isinstance(message, types.ServerNotification):
        print("NOTIFICATION:", message)
    else:
        print("SERVER MESSAGE:", message)
```

## Безбедносне напомене

Безбедност треба да буде највиши приоритет при имплементацији било ког сервера, посебно када се користе HTTP базирани транспортни механизми као што је Streamable HTTP у MCP.

При имплементацији MCP сервера са HTTP базираним транспортом, безбедност постаје најважнији аспект који захтева пажљиво разматрање више могућих напада и механизаме заштите.

### Преглед

Безбедност је критична при излагању MCP сервера преко HTTP-а. Streamable HTTP уводи нове површине за нападе и захтева пажљиву конфигурацију.

Ево неколико кључних безбедносних напомена:

- **Валидација Origin заглавља**: Увек верификујте `Origin` заглавље да бисте спречили DNS ребајндинг нападе.
- **Локално повезивање (localhost)**: За локални развој, повежите сервере на `localhost` да бисте избегли изложеност јавном интернету.
- **Аутентификација**: Имплементирајте аутентификацију (нпр. API кључеве, OAuth) за продукционе окружења.
- **CORS**: Конфигуришите Cross-Origin Resource Sharing (CORS) политике како бисте ограничили приступ.
- **HTTPS**: Користите HTTPS у продукцији за енкрипцију саобраћаја.

### Најбоље праксе

Поред тога, ево неколико најбољих пракси које треба пратити при имплементацији безбедности у вашем MCP стриминг серверу:

- Никада не верујте улазним захтевима без провере.
- Логујте и пратите сав приступ и грешке.
- Редовно ажурирајте зависности ради исправке безбедносних рањивости.

### Изазови

Суочићете се са неким изазовима при имплементацији безбедности у MCP стриминг серверима:

- Усклађивање безбедности са лакоћом развоја
- Осигурати компатибилност са различитим клијентским окружењима


## Надоградња са SSE на Streamable HTTP

За апликације које тренутно користе Server-Sent Events (SSE), миграција на Streamable HTTP пружа побољшане могућности и бољу дугорочну одрживост за ваше MCP имплементације.

### Зашто надоградити?

Постоје два убедљива разлога за надоградњу са SSE на Streamable HTTP:

- Streamable HTTP нуди бољу скалабилност, компатибилност и богатију подршку за нотификације од SSE.
- То је препоручени транспорт за нове MCP апликације.

### Кораци миграције

Ево како можете мигрирати са SSE на Streamable HTTP у вашим MCP апликацијама:

- **Ажурирајте серверски код** да користи `transport="streamable-http"` у `mcp.run()`.
- **Ажурирајте клијентски код** да користи `streamablehttp_client` уместо SSE клијента.
- **Имплементирајте обраду порука** у клијенту за обраду нотификација.
- **Тестирајте компатибилност** са постојећим алатима и радним токовима.

### Одржавање компатибилности

Препоручује се одржавање компатибилности са постојећим SSE клијентима током процеса миграције. Ево неких стратегија:

- Можете подржати и SSE и Streamable HTTP тако што ћете покретати оба транспорта на различитим ендпојнтима.
- Постепено мигрирајте клијенте на нови транспорт.

### Изазови

Осигурајте да адресирате следеће изазове током миграције:

- Осигурати да су сви клијенти ажурирани
- Рад са разликама у испоруци нотификација

### Задатак: Направите своју MCP стриминг апликацију

**Сценарио:**
Направите MCP сервер и клијента где сервер обрађује листу ставки (нпр. фајлова или докумената) и шаље нотификацију за сваку обрађену ставку. Клијент треба да приказује сваку нотификацију по доласку.

**Кораци:**

1. Имплементирајте серверски алат који обрађује листу и шаље нотификације за сваку ставку.
2. Имплементирајте клијента са обрадом порука који приказује нотификације у реалном времену.
3. Тестирајте вашу имплементацију покретањем сервера и клијента и пратите нотификације.
