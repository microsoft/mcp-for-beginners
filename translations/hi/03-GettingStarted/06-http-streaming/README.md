# मॉडल कॉन्टेक्स्ट प्रोटोकॉल (MCP) के साथ HTTPS स्ट्रीमिंग

यह अध्याय HTTPS का उपयोग करके मॉडल कॉन्टेक्स्ट प्रोटोकॉल (MCP) के साथ सुरक्षित, स्केलेबल और रियल-टाइम स्ट्रीमिंग लागू करने के लिए एक व्यापक मार्गदर्शिका प्रदान करता है। इसमें स्ट्रीमिंग के प्रेरणा, उपलब्ध परिवहन तंत्र, MCP में स्ट्रीम करने योग्य HTTP को लागू करने का तरीका, सुरक्षा सर्वोत्तम प्रथाओं, SSE से माइग्रेशन, और अपने स्वयं के स्ट्रीमिंग MCP अनुप्रयोगों के निर्माण के लिए व्यावहारिक मार्गदर्शन शामिल हैं।

> **आगे देखते हुए:** यह पाठ **MCP विनिर्देशन 2025-11-25** के अंतर्गत स्ट्रीम करने योग्य HTTP का वर्णन करता है, जहां एक सत्र `initialize` के दौरान स्थापित किया जाता है और `Mcp-Session-Id` हेडर के साथ पिन किया जाता है। `2026-07-28` रिलीज उम्मीदवार पूरी तरह से हैंडशेक और सत्र ID को हटा देता है, जिससे हर अनुरोध स्व-निहित और किसी भी सर्वर उदाहरण को निरधारित बिना रूटेबल होता है। विवरण के लिए देखें [MCP में क्या बदल रहा है: 2026-07-28 रिलीज उम्मीदवार](../../01-CoreConcepts/mcp-2026-07-28-release-candidate.md)।

## MCP में परिवहन तंत्र और स्ट्रीमिंग

यह अनुभाग MCP में उपलब्ध विभिन्न परिवहन तंत्र और क्लाइंट और सर्वर के बीच रियल-टाइम संचार के लिए स्ट्रीमिंग क्षमताओं को सक्षम करने में उनकी भूमिका की खोज करता है।

### परिवहन तंत्र क्या है?

एक परिवहन तंत्र यह परिभाषित करता है कि डेटा क्लाइंट और सर्वर के बीच कैसे आदान-प्रदान किया जाता है। MCP विभिन्न परिवहन प्रकारों का समर्थन करता है जो विभिन्न वातावरण और आवश्यकताओं के लिए उपयुक्त हैं:

- **stdio**: मानक इनपुट/आउटपुट, स्थानीय और CLI-आधारित उपकरणों के लिए उपयुक्त। सरल लेकिन वेब या क्लाउड के लिए उपयुक्त नहीं।
- **SSE (सर्वर-सेंट इवेंट्स)**: सर्वर को HTTP के माध्यम से क्लाइंट को रियल-टाइम अपडेट पुश करने की अनुमति देता है। वेब UI के लिए अच्छा, लेकिन स्केलेबिलिटी और लचीलापन में सीमित। MCP विनिर्देशन 2025-06-18 के अनुसार, स्टैंडअलोन SSE परिवहन को अप्रचलित कर दिया गया है और इसे "स्ट्रीम करने योग्य HTTP" परिवहन से प्रतिस्थापित किया गया है।
- **स्ट्रीम करने योग्य HTTP**: आधुनिक HTTP-आधारित स्ट्रीमिंग परिवहन, अधिसूचनाओं और बेहतर स्केलेबिलिटी का समर्थन करता है। अधिकांश उत्पादन और क्लाउड परिदृश्यों के लिए सिफारिश की जाती है।

### तुलना तालिका

नीचे तुलना तालिका देखें ताकि आप इन परिवहन तंत्रों के बीच विभिन्नताएं समझ सकें:

| परिवहन          | रियल-टाइम अपडेट्स | स्ट्रीमिंग | स्केलेबिलिटी | उपयोग मामला              |
|-------------------|------------------|-----------|-------------|-------------------------|
| stdio             | नहीं              | नहीं       | कम          | स्थानीय CLI उपकरण       |
| SSE               | हाँ               | हाँ        | मध्यम       | वेब, रियल-टाइम अपडेट्स |
| स्ट्रीम करने योग्य HTTP | हाँ               | हाँ        | उच्च        | क्लाउड, बहु-क्लाइंट     |

> **टिप:** सही परिवहन चुनना प्रदर्शन, स्केलेबिलिटी, और उपयोगकर्ता अनुभव को प्रभावित करता है। **स्ट्रीम करने योग्य HTTP** आधुनिक, स्केलेबल और क्लाउड-तैयार अनुप्रयोगों के लिए सिफारिश की जाती है।

नोट करें कि stdio और SSE परिवहन जो आपको पिछले अध्यायों में दिखाए गए थे, और कैसे इस अध्याय में स्ट्रीम करने योग्य HTTP परिवहन को कवर किया गया है।

## स्ट्रीमिंग: अवधारणाएं और प्रेरणा

स्ट्रीमिंग के मूलभूत सिद्धांतों और प्रेरणाओं को समझना प्रभावी रियल-टाइम संचार सिस्टम लागू करने के लिए आवश्यक है।

**स्ट्रीमिंग** नेटवर्क प्रोग्रामिंग में एक तकनीक है जो डेटा को छोटे, प्रबंधनीय टुकड़ों में या घटनाओं की श्रृंखला के रूप में भेजने और प्राप्त करने की अनुमति देती है, बजाय इसके कि पूरे प्रतिक्रिया के तैयार होने का इंतजार किया जाए। यह विशेष रूप से उपयोगी है:

- बड़े फ़ाइलें या डेटासेट।
- रियल-टाइम अपडेट (जैसे, चैट, प्रोग्रेस बार)।
- लंबी अवधि के गणनाएं जहां आप उपयोगकर्ता को सूचित रखना चाहते हैं।

उच्च स्तर पर आपको स्ट्रीमिंग के बारे में यह जानना चाहिए:

- डेटा धीरे-धीरे प्रगति के रूप में वितरित किया जाता है, सभी एक साथ नहीं।
- क्लाइंट डेटा को जैसे ही प्राप्त करता है, प्रोसेस कर सकता है।
- सांकेतिक विलंबता को कम करता है और उपयोगकर्ता अनुभव में सुधार करता है।

### स्ट्रीमिंग क्यों उपयोग करें?

स्ट्रीमिंग उपयोग करने के कारण निम्नलिखित हैं:

- उपयोगकर्ता तुरंत प्रतिक्रिया प्राप्त करते हैं, केवल अंत में नहीं।
- रियल-टाइम अनुप्रयोग और उत्तरदायी UI सक्षम होते हैं।
- नेटवर्क और कंप्यूट संसाधनों का अधिक प्रभावी उपयोग।

### सरल उदाहरण: HTTP स्ट्रीमिंग सर्वर और क्लाइंट

यहां एक सरल उदाहरण है कि स्ट्रीमिंग कैसे लागू की जा सकती है:

#### पायथन

**सर्वर (पायथन, FastAPI और StreamingResponse का उपयोग):**

```python
from fastapi import FastAPI
from fastapi.responses import StreamingResponse
import time

app = FastAPI()

async def event_stream():
    for i in range(1, 6):
        yield f"data: Message {i}\n\n"
        time.sleep(1)

@app.get("/stream")
def stream():
    return StreamingResponse(event_stream(), media_type="text/event-stream")
```

**क्लाइंट (पायथन, requests का उपयोग):**

```python
import requests

with requests.get("http://localhost:8000/stream", stream=True) as r:
    for line in r.iter_lines():
        if line:
            print(line.decode())
```

यह उदाहरण दिखाता है कि सर्वर कैसे उपलब्ध होते ही क्लाइंट को संदेशों की एक श्रृंखला भेजता है, बजाय इसके कि सभी संदेश तैयार होने तक इंतजार किया जाए।

**कैसे काम करता है:**

- सर्वर प्रत्येक संदेश को तैयार होते ही निकालता है।
- क्लाइंट हर हिस्से को प्राप्त करके प्रिंट करता है।

**आवश्यकताएँ:**

- सर्वर को स्ट्रीमिंग प्रतिक्रिया (जैसे, FastAPI में `StreamingResponse`) का उपयोग करना चाहिए।
- क्लाइंट को प्रतिक्रिया को स्ट्रीम के रूप में प्रोसेस करना चाहिए (`requests` में `stream=True`)।
- सामग्री प्रकार आमतौर पर `text/event-stream` या `application/octet-stream` होता है।

#### जावा

**सर्वर (जावा, Spring Boot और Server-Sent Events का उपयोग):**

```java
@RestController
public class CalculatorController {

    @GetMapping(value = "/calculate", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    public Flux<ServerSentEvent<String>> calculate(@RequestParam double a,
                                                   @RequestParam double b,
                                                   @RequestParam String op) {
        
        double result;
        switch (op) {
            case "add": result = a + b; break;
            case "sub": result = a - b; break;
            case "mul": result = a * b; break;
            case "div": result = b != 0 ? a / b : Double.NaN; break;
            default: result = Double.NaN;
        }

        return Flux.<ServerSentEvent<String>>just(
                    ServerSentEvent.<String>builder()
                        .event("info")
                        .data("Calculating: " + a + " " + op + " " + b)
                        .build(),
                    ServerSentEvent.<String>builder()
                        .event("result")
                        .data(String.valueOf(result))
                        .build()
                )
                .delayElements(Duration.ofSeconds(1));
    }
}
```

**क्लाइंट (जावा, Spring WebFlux WebClient का उपयोग):**

```java
@SpringBootApplication
public class CalculatorClientApplication implements CommandLineRunner {

    private final WebClient client = WebClient.builder()
            .baseUrl("http://localhost:8080")
            .build();

    @Override
    public void run(String... args) {
        client.get()
                .uri(uriBuilder -> uriBuilder
                        .path("/calculate")
                        .queryParam("a", 7)
                        .queryParam("b", 5)
                        .queryParam("op", "mul")
                        .build())
                .accept(MediaType.TEXT_EVENT_STREAM)
                .retrieve()
                .bodyToFlux(String.class)
                .doOnNext(System.out::println)
                .blockLast();
    }
}
```

**जावा कार्यान्वयन नोट्स:**

- `Flux` के साथ Spring Boot का प्रतिक्रियाशील स्टैक स्ट्रीमिंग के लिए उपयोग करता है
- `ServerSentEvent` घटना प्रकारों के साथ संरचित इवेंट स्ट्रीमिंग प्रदान करता है
- `WebClient` और `bodyToFlux()` प्रतिक्रियाशील स्ट्रीमिंग उपभोग को सक्षम करता है
- `delayElements()` घटनाओं के बीच प्रोसेसिंग समय का अनुकरण करता है
- घटनाओं में बेहतर क्लाइंट हैंडलिंग के लिए प्रकार (`info`, `result`) हो सकते हैं

### तुलना: पारंपरिक स्ट्रीमिंग बनाम MCP स्ट्रीमिंग

"पारंपरिक" तरीके से स्ट्रीमिंग कैसे काम करती है और MCP में कैसे काम करती है इनके बीच के अंतर को इस प्रकार दिखाया जा सकता है:

| विशेषता                   | पारंपरिक HTTP स्ट्रीमिंग          | MCP स्ट्रीमिंग (अधिसूचनाएं)          |
|------------------------|-------------------------------|-------------------------------------|
| मुख्य प्रतिक्रिया         | टुकड़ों में                      | एकल, अंत में                        |
| प्रगति अपडेट्स           | डेटा टुकड़ों के रूप में भेजे जाते हैं| अधिसूचनाओं के रूप में भेजे जाते हैं     |
| क्लाइंट आवश्यकताएँ       | स्ट्रीम को प्रोसेस करना आवश्यक  | संदेश हैंडलर लागू करना आवश्यक          |
| उपयोग मामला              | बड़े फ़ाइलें, AI टोकन स्ट्रीम्स  | प्रगति, लॉग, रियल-टाइम फीडबैक          |

### देखे गए मुख्य अंतर

इसके अलावा, कुछ मुख्य अंतर यहां हैं:

- **संचार पैटर्न:**
  - पारंपरिक HTTP स्ट्रीमिंग: सरल टुकड़ा ट्रांसफर एन्कोडिंग का उपयोग करके डेटा भेजता है
  - MCP स्ट्रीमिंग: JSON-RPC प्रोटोकॉल के साथ संरचित अधिसूचना प्रणाली का उपयोग करता है

- **संदेश प्रारूप:**
  - पारंपरिक HTTP: नई लाइनों के साथ साधारण टेक्स्ट टुकड़े
  - MCP: मेटाडेटा के साथ संरचित LoggingMessageNotification ऑब्जेक्ट्स

- **क्लाइंट कार्यान्वयन:**
  - पारंपरिक HTTP: स्ट्रीमिंग प्रतिक्रियाओं को प्रोसेस करने वाला सरल क्लाइंट
  - MCP: विभिन्न प्रकार के संदेशों को प्रोसेस करने के लिए एक अधिक परिष्कृत संदेश हैंडलर वाला क्लाइंट

- **प्रगति अपडेट्स:**
  - पारंपरिक HTTP: प्रगति मुख्य प्रतिक्रिया स्ट्रीम का हिस्सा होती है
  - MCP: प्रगति अलग-अलग अधिसूचना संदेशों के माध्यम से भेजी जाती है जबकि मुख्य प्रतिक्रिया अंत में आती है

### सिफारिशें

क्लासिक स्ट्रीमिंग (जैसे हमने ऊपर `/stream` का उपयोग कर दिखाया) लागू करने और MCP के माध्यम से स्ट्रीमिंग चुनने के बीच चयन पर कुछ सिफारिशें हैं।

- **सरल स्ट्रीमिंग आवश्यकताओं के लिए:** क्लासिक HTTP स्ट्रीमिंग लागू करना सरल है और बुनियादी स्ट्रीमिंग आवश्यकताओं के लिए पर्याप्त है।

- **जटिल, इंटरैक्टिव अनुप्रयोगों के लिए:** MCP स्ट्रीमिंग एक अधिक संरचित दृष्टिकोण प्रदान करता है जिसमें समृद्ध मेटाडेटा और अधिसूचनाओं और अंतिम परिणामों के बीच पृथक्करण शामिल है।

- **एआई अनुप्रयोगों के लिए:** MCP की अधिसूचना प्रणाली विशेष रूप से लंबी अवधि के AI कार्यों के लिए उपयोगी है जहां आप उपयोगकर्ताओं को प्रगति की जानकारी देते रहना चाहते हैं।

## MCP में स्ट्रीमिंग

तो अब तक आपने क्लासिक स्ट्रीमिंग और MCP में स्ट्रीमिंग के बीच कुछ सिफारिशें और तुलना देखी हैं। आइए विस्तार से देखें कि MCP में स्ट्रीमिंग का उपयोग कैसे करें।

MCP फ्रेमवर्क के भीतर स्ट्रीमिंग कैसे काम करती है इसे समझना प्रतिक्रियाशील अनुप्रयोगों के निर्माण के लिए आवश्यक है जो लंबी चलने वाली प्रक्रियाओं के दौरान उपयोगकर्ताओं को रियल-टाइम फीडबैक प्रदान करते हैं।

MCP में, स्ट्रीमिंग का मतलब मुख्य प्रतिक्रिया को टुकड़ों में भेजना नहीं है, बल्कि एक उपकरण द्वारा अनुरोध प्रोसेसिंग के दौरान क्लाइंट को **अधिसूचनाएं** भेजना है। ये अधिसूचनाएं प्रगति अपडेट, लॉग, या अन्य घटनाएं हो सकती हैं।

### यह कैसे काम करता है

मुख्य परिणाम अभी भी एकल प्रतिक्रिया के रूप में भेजा जाता है। हालांकि, अधिसूचनाएं प्रोसेसिंग के दौरान अलग संदेशों के रूप में भेजी जा सकती हैं और इस प्रकार क्लाइंट को रियल टाइम में अपडेट किया जा सकता है। क्लाइंट को अधिसूचनाओं को संभालने और प्रदर्शित करने में सक्षम होना चाहिए।

## अधिसूचना क्या है?

हमने "अधिसूचना" कहा, इसका MCP संदर्भ में क्या अर्थ है?

एक अधिसूचना वह संदेश है जो सर्वर से क्लाइंट को भेजा जाता है ताकि एक लंबी चलने वाली प्रक्रिया के दौरान प्रगति, स्थिति या अन्य घटनाओं के बारे में जानकारी दी जा सके। अधिसूचनाएं पारदर्शिता और उपयोगकर्ता अनुभव में सुधार करती हैं।

उदाहरण के लिए, एक क्लाइंट को सर्वर के साथ प्रारंभिक हैंडशेक पूरी हो जाने के बाद एक अधिसूचना भेजनी होती है।

एक अधिसूचना इस प्रकार दिखती है, जो एक JSON संदेश के रूप में होती है:

```json
{
  jsonrpc: "2.0";
  method: string;
  params?: {
    [key: string]: unknown;
  };
}
```

अधिसूचनाएं MCP में एक विषय से संबंधित होती हैं, जिसे ["Logging"](https://modelcontextprotocol.io/specification/draft/server/utilities/logging) कहा जाता है।

> **अप्रचलन सूचना:** `2026-07-28` MCP विनिर्देशन रिलीज उम्मीदवार लॉगिंग प्रिमिटिव को stdio परिवहन के लिए `stderr` और संरचित अवलोकन के लिए OpenTelemetry के पक्ष में अप्रचलित घोषित करता है। लॉगिंग `2025-11-25` और औपचारिक अप्रचलन के कम से कम एक वर्ष तक काम करता रहेगा। देखें [MCP में क्या बदल रहा है: 2026-07-28 रिलीज उम्मीदवार](../../01-CoreConcepts/mcp-2026-07-28-release-candidate.md)।

लॉगिंग को काम करने के लिए, सर्वर को इसे फीचर/क्षमता के रूप में सक्षम करना होता है, जैसे:

```json
{
  "capabilities": {
    "logging": {}
  }
}
```

> [!NOTE]
> उपयोग किए गए SDK के आधार पर, लॉगिंग डिफ़ॉल्ट रूप से सक्षम हो सकता है, या आपको इसे अपने सर्वर विन्यास में स्पष्ट रूप से सक्षम करना पड़ सकता है।

अधिसूचनाओं के विभिन्न प्रकार होते हैं:

| स्तर        | विवरण                       | उदाहरण उपयोग मामला             |
|------------|-----------------------------|-------------------------------|
| debug      | विस्तृत डिबगिंग जानकारी    | फंक्शन प्रवेश/निकास बिंदु      |
| info       | सामान्य सूचनात्मक संदेश    | संचालन प्रगति अपडेट          |
| notice     | सामान्य लेकिन महत्वपूर्ण घटनाएं | विन्यास परिवर्तन           |
| warning    | चेतावनी स्थितियाँ          | अप्रचलित फीचर उपयोग          |
| error      | त्रुटि स्थितियाँ            | संचालन विफलताएं              |
| critical   | गंभीर स्थितियाँ            | सिस्टम घटक विफलताएं          |
| alert      | तुरंत कार्रवाई आवश्यक      | डेटा भ्रष्टाचार का पता चला  |
| emergency  | सिस्टम अनुपयोगी है         | पूरी प्रणाली विफल           |

## MCP में अधिसूचनाओं को लागू करना

MCP में अधिसूचनाओं को लागू करने के लिए, आपको रियल-टाइम अपडेट को संभालने के लिए सर्वर और क्लाइंट दोनों पक्षों को सेट अप करना होगा। यह आपकी एप्लिकेशन को लंबी चलने वाली प्रक्रियाओं के दौरान उपयोगकर्ताओं को तुरंत प्रतिक्रिया प्रदान करने में सक्षम बनाता है।

### सर्वर-साइड: अधिसूचनाएं भेजना

चलिए सर्वर साइड से शुरू करते हैं। MCP में, आप ऐसे उपकरण परिभाषित करते हैं जो अनुरोधों को प्रोसेस करते समय अधिसूचनाएं भेज सकते हैं। सर्वर क्लाइंट को संदेश भेजने के लिए संदर्भ ऑब्जेक्ट (आमतौर पर `ctx`) का उपयोग करता है।

#### पायथन

```python
@mcp.tool(description="A tool that sends progress notifications")
async def process_files(message: str, ctx: Context) -> TextContent:
    await ctx.info("Processing file 1/3...")
    await ctx.info("Processing file 2/3...")
    await ctx.info("Processing file 3/3...")
    return TextContent(type="text", text=f"Done: {message}")
```

पिछले उदाहरण में, `process_files` टूल प्रत्येक फ़ाइल को प्रोसेस करते समय क्लाइंट को तीन अधिसूचनाएं भेजता है। सूचना संदेश भेजने के लिए `ctx.info()` मेथड का उपयोग किया गया है।

इसके अलावा, अधिसूचनाओं को सक्षम करने के लिए, सुनिश्चित करें कि आपका सर्वर स्ट्रीमिंग परिवहन (जैसे `streamable-http`) का उपयोग करता है और आपका क्लाइंट अधिसूचनाओं को प्रोसेस करने के लिए संदेश हैंडलर लागू करता है। यह सर्वर को `streamable-http` परिवहन का उपयोग करने के लिए सेटअप करने का तरीका है:

```python
mcp.run(transport="streamable-http")
```

#### .NET

```csharp
[Tool("A tool that sends progress notifications")]
public async Task<TextContent> ProcessFiles(string message, ToolContext ctx)
{
    await ctx.Info("Processing file 1/3...");
    await ctx.Info("Processing file 2/3...");
    await ctx.Info("Processing file 3/3...");
    return new TextContent
    {
        Type = "text",
        Text = $"Done: {message}"
    };
}
```

इस .NET उदाहरण में, `ProcessFiles` टूल `Tool` एट्रिब्यूट के साथ सजाया गया है और प्रत्येक फ़ाइल को प्रोसेस करते समय क्लाइंट को तीन अधिसूचनाएं भेजता है। सूचना संदेश भेजने के लिए `ctx.Info()` मेथड का उपयोग किया गया है।

अपने .NET MCP सर्वर में अधिसूचनाओं को सक्षम करने के लिए, सुनिश्चित करें कि आप स्ट्रीमिंग परिवहन का उपयोग कर रहे हैं:

```csharp
var builder = McpBuilder.Create();
await builder
    .UseStreamableHttp() // Enable streamable HTTP transport
    .Build()
    .RunAsync();
```

### क्लाइंट-साइड: अधिसूचनाएं प्राप्त करना

क्लाइंट को संदेशों की जांच करने और उन्हें प्राप्त होते ही प्रदर्शित करने के लिए एक संदेश हैंडलर लागू करना चाहिए।

#### पायथन

```python
async def message_handler(message):
    if isinstance(message, types.ServerNotification):
        print("NOTIFICATION:", message)
    else:
        print("SERVER MESSAGE:", message)

async with ClientSession(
   read_stream, 
   write_stream,
   logging_callback=logging_collector,
   message_handler=message_handler,
) as session:
```

पिछले कोड में, `message_handler` फ़ंक्शन जांचता है कि क्या आने वाला संदेश एक अधिसूचना है। अगर हाँ, तो वह अधिसूचना को प्रिंट करता है; अन्यथा, इसे एक सामान्य सर्वर संदेश के रूप में प्रोसेस करता है। ध्यान दें कि `ClientSession` को इनकमिंग अधिसूचनाओं को संभालने के लिए `message_handler` के साथ इनिशियलाइज़ किया जाता है।

#### .NET

```csharp
// Define a message handler
void MessageHandler(IJsonRpcMessage message)
{
    if (message is ServerNotification notification)
    {
        Console.WriteLine($"NOTIFICATION: {notification}");
    }
    else
    {
        Console.WriteLine($"SERVER MESSAGE: {message}");
    }
}

// Create and use a client session with the message handler
var clientOptions = new ClientSessionOptions
{
    MessageHandler = MessageHandler,
    LoggingCallback = (level, message) => Console.WriteLine($"[{level}] {message}")
};

using var client = new ClientSession(readStream, writeStream, clientOptions);
await client.InitializeAsync();

// Now the client will process notifications through the MessageHandler
```

इस .NET उदाहरण में, `MessageHandler` फ़ंक्शन जांचता है कि क्या आने वाला संदेश एक अधिसूचना है। यदि हाँ, तो वह अधिसूचना को प्रिंट करता है; अन्यथा, इसे एक सामान्य सर्वर संदेश के रूप में प्रोसेस करता है। `ClientSession` को `ClientSessionOptions` के माध्यम से संदेश हैंडलर के साथ इनिशियलाइज़ किया गया है।

अधिसूचनाएं सक्षम करने के लिए, सुनिश्चित करें कि आपका सर्वर स्ट्रीमिंग परिवहन (जैसे `streamable-http`) का उपयोग करता है और आपका क्लाइंट अधिसूचनाओं को प्रोसेस करने के लिए संदेश हैंडलर लागू करता है।

## प्रगति अधिसूचनाएं और परिदृश्य

यह अनुभाग MCP में प्रगति अधिसूचनाओं की अवधारणा, उनका महत्व और Streamable HTTP का उपयोग करके उन्हें कैसे लागू करें, इस पर प्रकाश डालता है। आप अपनी समझ को मजबूत करने के लिए एक व्यावहारिक असाइनमेंट भी पाएंगे।

प्रगति अधिसूचनाएं रियल-टाइम संदेश होते हैं जो लंबे समय तक चलने वाली प्रक्रियाओं के दौरान सर्वर से क्लाइंट को भेजे जाते हैं। पूरी प्रक्रिया समाप्त होने का इंतजार करने के बजाय, सर्वर क्लाइंट को वर्तमान स्थिति के बारे में अपडेट रखता है। यह पारदर्शिता, उपयोगकर्ता अनुभव में सुधार करता है, और डिबगिंग को आसान बनाता है।

**उदाहरण:**

```text

"Processing document 1/10"
"Processing document 2/10"
...
"Processing complete!"

```

### प्रगति अधिसूचनाओं का उपयोग क्यों करें?

प्रगति अधिसूचनाएं कई कारणों से आवश्यक हैं:

- **बेहतर उपयोगकर्ता अनुभव:** उपयोगकर्ता अपडेट को देख सकते हैं क्योंकि काम प्रगति पर है, केवल अंत में नहीं।
- **रियल-टाइम फीडबैक:** क्लाइंट प्रगति बार या लॉग प्रदर्शित कर सकते हैं, जिससे ऐप उत्तरदायी महसूस होता है।
- **आसान डिबगिंग और निगरानी:** डेवलपर और उपयोगकर्ता देख सकते हैं कि प्रक्रिया कहाँ धीमी या फंसी हो सकती है।

### प्रगति अधिसूचनाओं को कैसे लागू करें

यहां बताया गया है कि आप MCP में प्रगति अधिसूचनाओं को कैसे लागू कर सकते हैं:

- **सर्वर पर:** प्रत्येक आइटम के प्रोसेस होने पर `ctx.info()` या `ctx.log()` का उपयोग करके अधिसूचनाएं भेजें। यह मुख्य परिणाम तैयार होने से पहले क्लाइंट को संदेश भेजता है।
- **क्लाइंट पर:** एक संदेश हैंडलर लागू करें जो अधिसूचनाओं को सुनकर उन्हें प्राप्त होते ही प्रदर्शित करे। यह हैंडलर अधिसूचनाओं और अंतिम परिणाम के बीच अंतर पहचानता है।

**सर्वर उदाहरण:**


#### पाइथन

```python
@mcp.tool(description="A tool that sends progress notifications")
async def process_files(message: str, ctx: Context) -> TextContent:
    for i in range(1, 11):
        await ctx.info(f"Processing document {i}/10")
    await ctx.info("Processing complete!")
    return TextContent(type="text", text=f"Done: {message}")
```

**क्लाइंट उदाहरण:**

#### पाइथन

```python
async def message_handler(message):
    if isinstance(message, types.ServerNotification):
        print("NOTIFICATION:", message)
    else:
        print("SERVER MESSAGE:", message)
```

## सुरक्षा विचार

किसी भी सर्वर को लागू करते समय सुरक्षा सर्वोच्च प्राथमिकता होनी चाहिए, विशेष रूप से MCP में Streamable HTTP जैसी HTTP-आधारित ट्रांसपोर्ट का उपयोग करते समय।

HTTP-आधारित ट्रांसपोर्ट के साथ MCP सर्वर लागू करते समय, सुरक्षा एक प्रमुख चिंता बन जाती है जिसे कई हमले के तरीकों और सुरक्षा तंत्रों पर सावधानीपूर्वक ध्यान देना आवश्यक होता है।

### अवलोकन

MCP सर्वरों को HTTP के माध्यम से एक्सपोज़ करते समय सुरक्षा महत्वपूर्ण होती है। Streamable HTTP नए हमले के रास्ते प्रस्तुत करता है और सावधानीपूर्वक कॉन्फ़िगरेशन की आवश्यकता होती है।

यहाँ कुछ मुख्य सुरक्षा विचार हैं:

- **Origin हेडर सत्यापन**: DNS रिबाइंडिंग हमलों को रोकने के लिए हमेशा `Origin` हेडर को सत्यापित करें।
- **Localhost बाइंडिंग**: स्थानीय विकास के लिए, सर्वरों को `localhost` से बाइंड करें ताकि वे सार्वजनिक इंटरनेट पर एक्सपोज़ न हों।
- **प्रामाणिकता**: प्रोडक्शन तैनाती के लिए प्रमाणीकरण लागू करें (जैसे, API कुंजी, OAuth)।
- **CORS**: अभिगम को सीमित करने के लिए क्रॉस-ओरिजिन रिसोर्स शेयरिंग (CORS) नीतियाँ कॉन्फ़िगर करें।
- **HTTPS**: ट्रैफिक एन्क्रिप्ट करने के लिए प्रोडक्शन में HTTPS का उपयोग करें।

### सर्वोत्तम प्रथाएं

इसके अतिरिक्त, अपनी MCP स्ट्रीमिंग सर्वर में सुरक्षा लागू करते समय कुछ सर्वोत्तम प्रथाओं का पालन करें:

- बिना सत्यापन के आने वाले अनुरोधों पर कभी भरोसा न करें।
- सभी अभिगम और त्रुटियों को लॉग और मॉनिटर करें।
- सुरक्षा कमजोरियों को ठीक करने के लिए नियमित रूप से निर्भरता अपडेट करें।

### चुनौतियाँ

MCP स्ट्रीमिंग सर्वरों में सुरक्षा लागू करते समय आपको कुछ चुनौतियों का सामना करना पड़ेगा:

- विकास की सरलता के साथ सुरक्षा का संतुलन
- विभिन्न क्लाइंट वातावरणों के साथ संगतता सुनिश्चित करना


## SSE से Streamable HTTP में अपग्रेड करना

वर्तमान में Server-Sent Events (SSE) का उपयोग करने वाले अनुप्रयोगों के लिए, Streamable HTTP में माइग्रेट करना आपकी MCP कार्यान्वयन के लिए बेहतर क्षमताएँ और दीर्घकालिक स्थिरता प्रदान करता है।

### क्यों अपग्रेड करें?

SSE से Streamable HTTP में अपग्रेड करने के दो महत्वपूर्ण कारण हैं:

- Streamable HTTP बेहतर स्केलेबिलिटी, संगतता और अधिक समृद्ध अधिसूचना समर्थन प्रदान करता है।
- यह नए MCP अनुप्रयोगों के लिए अनुशंसित ट्रांसपोर्ट है।

### माइग्रेशन चरण

अपने MCP अनुप्रयोगों में SSE से Streamable HTTP में माइग्रेट करने के तरीके इस प्रकार हैं:

- **सर्वर कोड अपडेट करें** ताकि `mcp.run()` में `transport="streamable-http"` का उपयोग किया जा सके।
- **क्लाइंट कोड अपडेट करें** ताकि SSE क्लाइंट के बजाय `streamablehttp_client` उपयोग करें।
- **क्लाइंट में एक संदेश हैंडलर लागू करें** ताकि अधिसूचनाएँ संसाधित की जा सकें।
- **मौजूद उपकरणों और वर्कफ़्लो के साथ संगतता परीक्षण करें**।

### संगतता बनाए रखना

माइग्रेशन प्रक्रिया के दौरान वर्तमान SSE क्लाइंट्स के साथ संगतता बनाए रखना सुझाया जाता है। यहां कुछ रणनीतियाँ हैं:

- आप दोनों ट्रांसपोर्ट अलग-अलग एंडपॉइंट्स पर चला कर SSE और Streamable HTTP दोनों का समर्थन कर सकते हैं।
- धीरे-धीरे क्लाइंट्स को नए ट्रांसपोर्ट पर माइग्रेट करें।

### चुनौतियाँ

माइग्रेशन के दौरान निम्नलिखित चुनौतियों को संबोधित करना सुनिश्चित करें:

- सुनिश्चित करें कि सभी क्लाइंट्स अपडेट हों
- अधिसूचना डिलीवरी में अंतर को संभालना

### असाइनमेंट: अपना स्वयं का स्ट्रीमिंग MCP ऐप बनाएं

**परिदृश्य:**
एक MCP सर्वर और क्लाइंट बनाएं जहां सर्वर वस्तुओं (जैसे, फाइलें या दस्तावेज़) की सूची संसाधित करता है और प्रत्येक संसाधित वस्तु के लिए अधिसूचना भेजता है। क्लाइंट को प्रत्येक अधिसूचना को आते ही दिखाना चाहिए।

**चरण:**

1. एक सर्वर टूल लागू करें जो एक सूची को संसाधित करता है और प्रत्येक आइटम के लिए अधिसूचनाएं भेजता है।
2. एक क्लाइंट लागू करें जिसमें एक संदेश हैंडलर हो जो अधिसूचनाओं को वास्तविक समय में दिखाए।
3. अपने कार्यान्वयन का परीक्षण करें, सर्वर और क्लाइंट दोनों चलाएं, और अधिसूचनाओं को देखें।
