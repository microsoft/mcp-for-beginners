# Кейс: Публикация в социальные сети из агента с удалённым MCP-сервером

> **Отказ от ответственности:** Существует множество сервисов и проектов с открытым исходным кодом, которые могут публиковать записи в социальные сети, и команда также может интегрировать API каждой сети напрямую. Представленный ниже сценарий — это один из примеров того, как можно спроектировать и использовать **удалённый MCP-сервер с возможностью записи**. Publora — коммерческий сервис с бесплатным тарифом; описанные здесь подходы применимы к любому MCP-серверу, который выполняет необратимые действия от имени пользователя.

## Обзор

Агенты хорошо справляются с созданием черновиков контента, но плохо — с их публикацией. Модель может за секунды написать объявление о релизе, и на этом работа останавливается: публикация означает наличие API для каждой сети, OAuth-приложения для каждой сети и различные правила работы с медиафайлами для каждой. Большинство команд решают эту задачу вручную — копируя текст в браузер.

В этом кейсе рассматривается, как последний шаг закрывается с помощью одного удалённого MCP-сервера, а также — полезно для тех, кто собирается строить подобное решение — какие проектные решения в **сервере с возможностью записи** должны быть приняты правильно. Чтение данных прощает ошибки. Публикация — нет: неправильный вызов инструмента заметен аудитории и не может быть отменён.

## Сценарий

Небольшая команда разработчиков публикует посты внутри агента (Claude, VS Code, Cursor — клиент не важен). Они хотят, чтобы агент мог:

- видеть, какие социальные аккаунты подключены у команды,
- создавать черновик поста и сохранять его для утверждения человеком,
- прикреплять изображение,
- планировать публикацию поста в нескольких сетях на выбранное время,
- и позже показывать отчёт о его эффективности.

Крайне важно, чтобы агент *не мог* случайно опубликовать что-то во время экспериментов.

## Используемые инструменты

- [Publora MCP Server](https://github.com/publora/mcp-server) — удалённый MCP-сервер (`streamable-http`), который предоставляет инструменты для публикации, планирования, работы с медиа и аналитики LinkedIn. Зарегистрирован в официальном реестре MCP как `com.publora/mcp-server`.

## Пошаговый рабочий процесс

1. **Подключение к серверу.** Клиенты, поддерживающие OAuth, проходят поток авторизации с кодом и PKCE через собственный экран согласия сервера; клиенты без поддержки, например безголовые CLI, используют ключ API Publora в заголовке. Поддерживаются оба варианта, и какой из них используется зависит от клиента, а не от сервера.
2. **Получение списка подключений.** Агент вызывает `list_connections` и получает список подключенных аккаунтов с их идентификаторами.
3. **Создание черновика.** Агент вызывает `create_post` *без* указания запланированного времени. Пост сохраняется как черновик — ничего не публикуется.
4. **Прикрепление медиа.** Публичные URL изображений передаются в том же вызове; сервер загружает и проверяет их.
5. **Планирование.** После утверждения человеком `update_post` меняет статус на запланированное с указанием времени в формате ISO 8601.
6. **Измерение.** Для LinkedIn `linkedin_post_stats` возвращает вовлечённость, когда пост опубликован.

## Пример запроса

```text
Which social accounts do I have connected?
Draft a post announcing our new changelog page, attach the screenshot at
https://example.com/changelog.png, and keep it as a draft — do not publish it.
Once I approve, schedule it to LinkedIn and Bluesky for tomorrow at 09:00 UTC.
```

## Техническая реализация

Ниже приведены уроки, применимые для других реализаций.

### Открытое обнаружение, аутентифицированное выполнение

`tools/list` предоставляется без учётных данных; для каждого `tools/call` требуется токен,
иначе возвращается `401` с заголовком `WWW-Authenticate`, указывающим на
метаданные защищённого ресурса. Также у сервера есть устаревшая конечная точка, которая
отвечает на неаутентифицированный `initialize` для клиентов со старыми протоколами
до `2026-07-28`; современные клиенты этот обмен не используют.

Это разделение, завязанное на сервер, позволяет реестрам, каталогам и клиентам
просматривать имена, схемы и аннотации инструментов без секрета, при этом не позволяя анонимно
выполнять действия. Открытое обнаружение — это настройка развертывания, а не требование MCP; в
защищённом развертывании также может потребоваться авторизация для `tools/list`.

### Регистрация: динамическая регистрация клиентов и её замена

Сервер рекламирует `/.well-known/oauth-protected-resource` и `/.well-known/oauth-authorization-server`, и поддерживает поток авторизации с кодом и PKCE (`S256`), refresh-токены и **динамическую регистрацию клиентов**.

Динамическая регистрация устранила ручной этап для устаревших клиентов: без неё
каждому клиенту требовался заранее выданный `client_id` от поставщика.

Рассматривайте это как поведение для совместимости, а не как модель для копирования. В версии спецификации от `2026-07-28` динамическая регистрация клиентов устарела в пользу документов метаданных Client ID, где клиент размещает метаданные по стабильному HTTPS-URL, и этот URL *является* `client_id`. DCR пока работает, но сервер, который строится сегодня, должен планировать на CIMD и сохранять DCR только для устаревших клиентов.

### Аннотации инструментов — не просто украшение

Каждый инструмент содержит `title` и соответствующие подсказки: `readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`.

Два важнейших применения. Во-первых, клиенты используют подсказки, чтобы решать, что подтверждать у пользователя — клиент может автоматически выполнить запрос только для чтения и остановиться на подтверждении перед удалением. Спецификация чётко указывает, что аннотации — это ненадёжные подсказки, а не механизм авторизации: они формируют, что клиент предполагает сделать, но не блокируют действия на сервере, который должен все равно применять свои правила. Во-вторых, крупные каталоги коннекторов теперь *требуют* аннотации для ревью; сервер без заголовков и подсказок будет отклонён независимо от качества работы.

### Делайте идентификаторы невозможными для выдумки

Идентификаторы платформ — это непрозрачные строки, возвращаемые `list_connections`, и в описании схемы говорится явно: их надо копировать дословно и никогда не угадывать. Сервер отвергает всё прочее.

Модели склонны к гаданию. Любой сервер с возможностью записи должен предполагать, что идентификатор рано или поздно будет смоделирован и сделать такой путь очевидным и быстрым провалом, а не пытаться действовать по правдоподобному значению.

### Провал до публикации с информативным сообщением

Некоторые сети не принимают посты только с текстом и требуют изображение или видео. Это проверяется при планировании публикации, а ошибка указывает платформу и недостающие требования.

Агент может восстановиться из ситуации "Instagram требует медиа — прикрепите изображение или видео" без дополнительного запроса. Он не может восстановиться из общего `400`.

### Обеспечивайте безопасность повторных попыток

Два инструмента, создающих контент — `create_post` и `update_post` — принимают ключ идемпотентности: повторное использование с идентичным запросом проигрывает исходный ответ, а не создаёт второй пост. Среды исполнения агентов делают повторные попытки при таймаутах; без идемпотентности медленный ответ превращается в дублирующую публикацию. Другие инструменты записи — удаления, работа с медиа, реакции и комментарии LinkedIn — ключ не принимают, поэтому повторная попытка там автоматически не безопасна. Важно знать, какие свои изменения вы защищаете, а какие — нет.

### Обеспечьте способ тестирования без публикации

Сервер принимает зарезервированную цель `publora-playground`, которая проверяется и подтверждается как реальная, а затем отбрасывается — ничего не попадает в живой аккаунт. Это описано в самой схеме инструмента, доступной для прочтения любым клиентом без учётных данных: поле `platforms` в `create_post` описывает её как "цель для теста подключения, которая не требует реального подключения — пост подтверждается и отбрасывается, ничего не публикуется". Используйте, передав её как единственную запись: `platforms: ["publora-playground"]`.

Это оказалось одним из самых полезных деталей всей поверхности. Рецензенты каталогов коннекторов, участники и CI могут отработать полный путь записи от начала до конца без риска для реальной аудитории. Любой MCP-сервер с необратимыми действиями выиграет от документированной цели no-op.

## Результаты и влияние

- Шаг публикации переместился из браузера в тот же разговор, где пишется контент, а привычка сначала черновика сохраняет человека в цикле. Будьте точны: черновик — это соглашение, а не граница. Те же учётные данные могут как планировать, так и публиковать, поэтому настоящий одобрительный шлюз нужно реализовывать вне инструмента — отдельными учётными данными или политическим уровнем перед сервером.
- Различия между сетями — требования к медиа, поток сообщений, управление ответами — обрабатываются один раз на сервере, а не в каждом агенте отдельно.
- Один и тот же сервер обслуживает несколько MCP-клиентов без заранее выданных учётных данных.
    Современные клиенты могут использовать документы метаданных Client ID; DCR остаётся запасным вариантом
    для устаревших клиентов.
- Проектные ограничения выше формировались под влиянием ревью каталогов коннекторов не меньше, чем пользователей: аннотации, OAuth и безопасная тестовая цель были требованием как минимум одного из них.

- Возьмите MCP-сервер, который вы строите, и проверьте три самые дешёвые меры: аннотации для каждого инструмента, ключ идемпотентности для каждой записи и документированную цель no-op.
- Попробуйте открытое обнаружение: вызовите `tools/list` на публичном удалённом сервере без учётных данных, затем вызовите инструмент и проверьте `401` с вызовом аутентификации.
- Подумайте, что «отмена» значит для вашей области. Публикация включает черновики и удаление; если у ваших действий нет эквивалентов, подтверждение должно быть частью дизайна инструмента, а не подсказки.
