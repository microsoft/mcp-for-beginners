## Транспортные механизмы и потоковая передача в MCP

В этом разделе рассматриваются различные доступные транспортные механизмы в MCP и их роль в обеспечении возможностей потоковой передачи для коммуникации в реальном времени между клиентами и серверами.

### Что такое транспортный механизм?

Транспортный механизм определяет, как данные обмениваются между клиентом и сервером. MCP поддерживает несколько типов транспорта для разных сред и требований:

- **stdio**: стандартный ввод/вывод, подходит для локальных и CLI-инструментов. Простой, но не подходит для веба или облака.
- **HTTP+SSE**: устаревший удаленный транспорт, отменённый в MCP `2025-03-26`
    и заменён Streamable HTTP. Не используйте для новых реализаций.
- **Streamable HTTP**: современный потоковый транспорт на базе HTTP, поддерживающий уведомления и лучшую масштабируемость. Рекомендуется для большинства производственных и облачных сценариев.

### Таблица сравнения

Посмотрите таблицу сравнения ниже, чтобы понять различия между этими транспортными механизмами:

| Транспорт | Статус | Уведомления | Типичное использование |
|---|---|---|---|
| stdio | Актуальный | Да | Локальные подпроцессы |
| HTTP+SSE | Устарел | Да | Устаревшие удалённые реализации |
| Streamable HTTP | Актуальный | Да | Удалённые и облачные серверы |

> **Совет:** выбор правильного транспорта влияет на производительность, масштабируемость и пользовательский опыт. **Streamable HTTP** рекомендуется для современных масштабируемых облачных приложений.

Стандартными транспортами являются stdio и Streamable HTTP. HTTP+SSE присутствует
только в старых примерах.

## Потоковая передача: концепции и мотивация

Понимание фундаментальных концепций и мотивации потоковой передачи необходимо для эффективной реализации систем коммуникации в реальном времени.

**Потоковая передача** — это техника в сетевом программировании, позволяющая отправлять и получать данные небольшими управляемыми порциями или в виде последовательности событий, а не ждать готовности всего ответа. Это особенно полезно для:

- больших файлов или наборов данных.
- обновлений в реальном времени (например, чат, индикаторы прогресса).
- длительных вычислений, когда нужно держать пользователя в курсе.

Кратко о потоковой передаче:

- Данные доставляются постепенно, а не сразу полностью.
- Клиент может обрабатывать данные по мере их прибытия.
- Снижает воспринимаемую задержку и улучшает пользовательский опыт.

### Зачем использовать потоковую передачу?

Причины использования потоковой передачи следующие:

- Пользователи получают обратную связь немедленно, а не только в конце
- Позволяет создавать приложения в реальном времени и отзывчивые интерфейсы
- Более эффективное использование сетевых и вычислительных ресурсов

### Простой пример: HTTP-сервер и клиент с потоковой передачей

Вот простой пример реализации потоковой передачи:

#### Python

**Сервер (Python, с использованием FastAPI и StreamingResponse):**

```python
from fastapi import FastAPI
from fastapi.responses import StreamingResponse
import time

app = FastAPI()

async def event_stream():
    for i in range(1, 6):
        yield f"data: Message {i}\n\n"
        time.sleep(1)

@app.get("/stream")
def stream():
    return StreamingResponse(event_stream(), media_type="text/event-stream")
```

**Клиент (Python, с использованием requests):**

```python
import requests

with requests.get("http://localhost:8000/stream", stream=True) as r:
    for line in r.iter_lines():
        if line:
            print(line.decode())
```

Этот пример демонстрирует сервер, отправляющий серию сообщений клиенту по мере их готовности, а не ожидающий всех сообщений.

**Как это работает:**

- Сервер выдает каждое сообщение по мере готовности.
- Клиент получает и выводит каждую порцию по мере поступления.

**Требования:**

- Сервер должен использовать потоковый ответ (например, `StreamingResponse` в FastAPI).
- Клиент должен обрабатывать ответ как поток (`stream=True` в requests).
- Content-Type обычно `text/event-stream` или `application/octet-stream`.

#### Java

**Сервер (Java, используя Spring Boot и Server-Sent Events):**

```java
@RestController
public class CalculatorController {

    @GetMapping(value = "/calculate", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    public Flux<ServerSentEvent<String>> calculate(@RequestParam double a,
                                                   @RequestParam double b,
                                                   @RequestParam String op) {
        
        double result;
        switch (op) {
            case "add": result = a + b; break;
            case "sub": result = a - b; break;
            case "mul": result = a * b; break;
            case "div": result = b != 0 ? a / b : Double.NaN; break;
            default: result = Double.NaN;
        }

        return Flux.<ServerSentEvent<String>>just(
                    ServerSentEvent.<String>builder()
                        .event("info")
                        .data("Calculating: " + a + " " + op + " " + b)
                        .build(),
                    ServerSentEvent.<String>builder()
                        .event("result")
                        .data(String.valueOf(result))
                        .build()
                )
                .delayElements(Duration.ofSeconds(1));
    }
}
```

**Клиент (Java, используя Spring WebFlux WebClient):**

```java
@SpringBootApplication
public class CalculatorClientApplication implements CommandLineRunner {

    private final WebClient client = WebClient.builder()
            .baseUrl("http://localhost:8080")
            .build();

    @Override
    public void run(String... args) {
        client.get()
                .uri(uriBuilder -> uriBuilder
                        .path("/calculate")
                        .queryParam("a", 7)
                        .queryParam("b", 5)
                        .queryParam("op", "mul")
                        .build())
                .accept(MediaType.TEXT_EVENT_STREAM)
                .retrieve()
                .bodyToFlux(String.class)
                .doOnNext(System.out::println)
                .blockLast();
    }
}
```

**Заметки по реализации на Java:**

- Использует реактивный стек Spring Boot с `Flux` для потоковой передачи
- `ServerSentEvent` обеспечивает структурированную потоковую передачу событий с типами событий
- `WebClient` с `bodyToFlux()` позволяет реактивно потреблять поток
- `delayElements()` имитирует время обработки между событиями
- События могут иметь типы (`info`, `result`) для лучшей обработки на клиенте

### Сравнение: классическая потоковая передача и потоковая передача MCP

Различия между классической потоковой передачей и потоковой передачей в MCP можно представить так:

| Особенность               | Классическая HTTP-потоковая передача | MCP-потоковая передача (уведомления)  |
|--------------------------|-------------------------------------|---------------------------------------|
| Основной ответ            | Фрагментированный                    | Единственный, в конце                  |
| Обновления прогресса      | Отправляются как фрагменты данных   | Отправляются как уведомления           |
| Требования к клиенту      | Должен обрабатывать поток            | Должен реализовывать обработчик сообщений |
| Сценарий использования    | Большие файлы, потоки AI-токенов    | Прогресс, логи, обратная связь в реальном времени |

### Ключевые наблюдаемые различия

Кроме того, вот некоторые ключевые различия:

- **Схема коммуникации:**
  - Классическая HTTP-потоковая передача: использует простую чанковую передачу для отправки данных частями
  - Потоковая передача MCP: использует структурированную систему уведомлений с протоколом JSON-RPC

- **Формат сообщений:**
  - Классическая HTTP: простые текстовые фрагменты с переносами строки
  - MCP: структурированные объекты LoggingMessageNotification с метаданными

- **Реализация клиента:**
  - Классическая HTTP: простой клиент, обрабатывающий потоковые ответы
  - MCP: более сложный клиент с обработчиком сообщений для обработки разных типов сообщений

- **Обновления прогресса:**
  - Классическая HTTP: прогресс входит в основной поток ответа
  - MCP: прогресс отправляется отдельными уведомлениями, основной ответ приходит в конце

### Рекомендации

Мы рекомендуем учитывать некоторые моменты при выборе между реализацией классической потоковой передачи (как показано выше с `/stream`) и потоковой передачей через MCP.

- **Для простых задач потоковой передачи:** классическая HTTP-потоковая передача проще в реализации и достаточна для базовых потребностей потоковой передачи.


- **Для сложных, интерактивных приложений:** потоковая передача MCP предоставляет более структурированный подход с расширенными метаданными и разделением между уведомлениями и окончательными результатами.

- **Для AI-приложений:** система уведомлений MCP особенно полезна для долгих AI-задач, когда нужно информировать пользователей о прогрессе.

## Потоковая передача в MCP

Хорошо, вы уже видели некоторые рекомендации и сравнения классической потоковой передачи и потоковой передачи в MCP. Давайте подробно разберём, как именно можно использовать потоковую передачу в MCP.

Понимание того, как работает потоковая передача внутри фреймворка MCP, необходимо для создания отзывчивых приложений, которые предоставляют пользователям обратную связь в реальном времени во время длительных операций.

В MCP потоковая передача — это не отправка основного ответа по частям, а отправка **уведомлений** клиенту во время обработки запроса инструментом. Эти уведомления могут включать обновления прогресса, журналы или другие события.

### Как это работает

Основной результат всё ещё отправляется как единичный ответ. Однако уведомления могут отправляться как отдельные сообщения во время обработки и таким образом обновлять клиента в реальном времени. Клиент должен уметь обрабатывать и отображать эти уведомления.

### Опциональное упражнение: подключение к размещённому серверу MCP

Вы также можете использовать Streamable HTTP без запуска локального сервера. Этот пример
подключается к [Parallel Search MCP](https://docs.parallel.ai/integrations/mcp/search-mcp),
обнаруживает его инструменты и ищет публичную документацию MCP, используя тот же
Python SDK, что и [локальный клиент](../../../../03-GettingStarted/06-http-streaming/solution/python/client.py).

Анонимная конечная точка Parallel не требует учётной записи или API-ключа. Бесплатный доступ
имеет ограничение по количеству запросов. Выполнение этого скрипта отправляет поисковые запросы, цель и
случайный идентификатор сессии в Parallel. Сервис также предлагает `web_fetch`,
который отправляет запрошенные URL и любой предоставленный контекст в Parallel. Используйте общедоступную
информацию для этого упражнения; смотрите его [условия](https://parallel.ai/customer-terms)
и [политику конфиденциальности](https://parallel.ai/privacy-policy).

С Python 3.10 или новее и активированной виртуальной средой установите SDK:

```sh
python -m pip install "mcp>=1.10,<2"
```

Сохраните это как `hosted_search.py` и запустите `python hosted_search.py`:

```python
import asyncio
from uuid import uuid4

from mcp import ClientSession
from mcp.client.streamable_http import streamablehttp_client


async def main() -> None:
    session_id = str(uuid4())
    async with streamablehttp_client("https://search.parallel.ai/mcp") as (
        read_stream,
        write_stream,
        _,
    ):
        async with ClientSession(read_stream, write_stream) as session:
            await session.initialize()
            tools = await session.list_tools()
            print("Available tools:", [tool.name for tool in tools.tools])

            result = await session.call_tool(
                "web_search",
                {
                    "objective": "Find the official MCP Streamable HTTP documentation",
                    "search_queries": ["MCP Streamable HTTP documentation"],
                    "session_id": session_id,
                },
            )
            if result.isError:
                raise RuntimeError(f"Search tool failed: {result.content}")
            for block in result.content:
                if block.type == "text":
                    print(block.text)


async def run() -> None:
    await asyncio.wait_for(main(), timeout=60)


if __name__ == "__main__":
    asyncio.run(run())
```

Ожидайте, что обнаружение включит `web_search` и `web_fetch`, затем последует поисковый
ответ с URL источников и выдержками текста. Результаты могут отличаться или быть пустыми.
Скрипт проверяет `isError`, так как инструмент может потерпеть неудачу, даже если HTTP-запрос
выполнен успешно. Если доступ ограничен по количеству запросов, подождите перед следующей попыткой. Повторно используйте тот же
`session_id`, если расширяете скрипт связанными поисковыми или выборочными вызовами.

Streamable HTTP поддерживает как JSON, так и SSE-ответы; этот сервер может вернуть
полный JSON-результат без уведомлений о прогрессе. SDK обрабатывает
транспорт. Продолжайте с локальным примером ниже, чтобы узнать об уведомлениях.
Этот опциональный скрипт выполняет один явный поиск и закрывает соединение после
завершения. Если вы позже откроете эти инструменты для агента, агент может вызывать
их во время своей работы; рассматривайте извлечённый веб-текст как ненадёжные данные.

## Что такое уведомление?

Мы сказали «уведомление», что это значит в контексте MCP?

Уведомление — это JSON-RPC сообщение, которое не имеет `id` и не
получает ответа. MCP использует уведомления для прогресса, отмены и
других односторонних событий.

В MCP `2025-11-25` клиент отправляет `notifications/initialized` после
рукопожатия инициализации. В MCP `2026-07-28` рукопожатия нет,
так что это уведомление — поведение старой версии.

Уведомление выглядит так в формате JSON:

```json
{
  jsonrpc: "2.0";
  method: string;
  params?: {
    [key: string]: unknown;
  };
}
```

Логирование — это одна из функций, использующих уведомления; сами уведомления являются
общим типом сообщений JSON-RPC.

> **Устарело в MCP `2026-07-28`:** функция логирования остаётся доступной
> для совместимости, но может быть удалена в первом обновлении спецификации,
> выпущенном 28 июля 2027 года или позже. Новые реализации должны использовать
> `stderr` с stdio или OpenTelemetry для структурируемой наблюдаемости.

Существуют различные типы уведомлений:

| Уровень   | Описание                    | Пример использования           |

## Реализация уведомлений в MCP

Чтобы реализовать уведомления в MCP, необходимо настроить как серверную, так и клиентскую часть для обработки обновлений в реальном времени. Это позволяет вашему приложению предоставлять пользователям мгновенную обратную связь при долгих операциях.

### Серверная часть: отправка уведомлений

Начнём с серверной части. В MCP вы определяете инструменты, которые могут отправлять уведомления во время обработки запросов. Сервер использует объект контекста (обычно `ctx`) для отправки сообщений клиенту.

#### Python

```python
@mcp.tool(description="A tool that sends progress notifications")
async def process_files(message: str, ctx: Context) -> TextContent:
    await ctx.info("Processing file 1/3...")
    await ctx.info("Processing file 2/3...")
    await ctx.info("Processing file 3/3...")
    return TextContent(type="text", text=f"Done: {message}")
```

В приведённом примере инструмент `process_files` отправляет клиенту три уведомления во время обработки каждого файла. Метод `ctx.info()` используется для отправки информационных сообщений.

Кроме того, чтобы включить уведомления, убедитесь, что ваш сервер использует потоковый транспорт (например, `streamable-http`), а клиент реализует обработчик сообщений для обработки уведомлений. Вот как можно настроить сервер для использования транспорта `streamable-http`:

```python
mcp.run(transport="streamable-http")
```

#### .NET

```csharp
[Tool("A tool that sends progress notifications")]
public async Task<TextContent> ProcessFiles(string message, ToolContext ctx)
{
    await ctx.Info("Processing file 1/3...");
    await ctx.Info("Processing file 2/3...");
    await ctx.Info("Processing file 3/3...");
    return new TextContent
    {
        Type = "text",
        Text = $"Done: {message}"
    };
}
```

В этом примере .NET инструмент `ProcessFiles` аннотирован атрибутом `Tool` и отправляет клиенту три уведомления во время обработки каждого файла. Метод `ctx.Info()` используется для отправки информационных сообщений.

Чтобы включить уведомления в вашем .NET сервере MCP, убедитесь, что вы используете потоковый транспорт:

```csharp
var builder = McpBuilder.Create();
await builder
    .UseStreamableHttp() // Enable streamable HTTP transport
    .Build()
    .RunAsync();
```

### Клиентская часть: получение уведомлений

Клиент должен реализовать обработчик сообщений для обработки и отображения уведомлений по мере их поступления.

#### Python

```python
async def message_handler(message):
    if isinstance(message, types.ServerNotification):
        print("NOTIFICATION:", message)
    else:
        print("SERVER MESSAGE:", message)

async with ClientSession(
   read_stream, 
   write_stream,
   logging_callback=logging_collector,
   message_handler=message_handler,
) as session:
```

В приведённом коде функция `message_handler` проверяет, является ли входящее сообщение уведомлением. Если да, она выводит уведомление; иначе обрабатывает его как обычное серверное сообщение. Также обратите внимание, как `ClientSession` инициализируется с `message_handler` для обработки входящих уведомлений.

#### .NET

```csharp
// Define a message handler
void MessageHandler(IJsonRpcMessage message)
{
    if (message is ServerNotification notification)
    {
        Console.WriteLine($"NOTIFICATION: {notification}");
    }
    else
    {
        Console.WriteLine($"SERVER MESSAGE: {message}");
    }
}

// Create and use a client session with the message handler
var clientOptions = new ClientSessionOptions
{
    MessageHandler = MessageHandler,
    LoggingCallback = (level, message) => Console.WriteLine($"[{level}] {message}")
};

using var client = new ClientSession(readStream, writeStream, clientOptions);
await client.InitializeAsync();

// Now the client will process notifications through the MessageHandler
```


В этом примере на .NET функция `MessageHandler` проверяет, является ли входящее сообщение уведомлением. Если да, оно выводит уведомление; если нет, обрабатывает сообщение как обычное серверное сообщение. `ClientSession` инициализируется с обработчиком сообщений через `ClientSessionOptions`.

Чтобы включить уведомления, убедитесь, что ваш сервер использует потоковый транспорт (например, `streamable-http`), а клиент реализует обработчик сообщений для обработки уведомлений.

## Уведомления о ходе выполнения и сценарии

В этом разделе объясняется концепция уведомлений о ходе выполнения в MCP, почему они важны и как реализовать их с использованием Streamable HTTP. Также вы найдете практическое задание для закрепления знаний.

Уведомления о ходе выполнения — это сообщения в реальном времени, отправляемые сервером клиенту во время длительных операций. Вместо того чтобы ждать завершения всего процесса, сервер информирует клиента о текущем статусе. Это повышает прозрачность, улучшает пользовательский опыт и упрощает отладку.

**Пример:**

```text

"Processing document 1/10"
"Processing document 2/10"
...
"Processing complete!"

```

### Зачем использовать уведомления о ходе выполнения?

Уведомления о ходе выполнения важны по нескольким причинам:

- **Лучший пользовательский опыт:** пользователи видят обновления по мере выполнения работы, а не только в конце.
- **Обратная связь в реальном времени:** клиенты могут отображать индикаторы прогресса или логи, делая приложение отзывчивым.
- **Упрощение отладки и мониторинга:** разработчики и пользователи могут видеть, где процесс идет медленно или застрял.

### Как реализовать уведомления о ходе выполнения

Вот как вы можете реализовать уведомления о ходе выполнения в MCP:

- **На сервере:** используйте `ctx.info()` или `ctx.log()`, чтобы отправлять уведомления по мере обработки каждого элемента. Это отправляет сообщение клиенту до того, как основной результат будет готов.
- **На клиенте:** реализуйте обработчик сообщений, который будет слушать и отображать уведомления по мере их поступления. Этот обработчик различает уведомления и окончательный результат.

**Пример сервера:**

#### Python

```python
@mcp.tool(description="A tool that sends progress notifications")
async def process_files(message: str, ctx: Context) -> TextContent:
    for i in range(1, 11):
        await ctx.info(f"Processing document {i}/10")
    await ctx.info("Processing complete!")
    return TextContent(type="text", text=f"Done: {message}")
```

**Пример клиента:**

#### Python

```python
async def message_handler(message):
    if isinstance(message, types.ServerNotification):
        print("NOTIFICATION:", message)
    else:
        print("SERVER MESSAGE:", message)
```

## Вопросы безопасности

Безопасность должна быть главным приоритетом при реализации любого сервера, особенно при использовании транспортов на основе HTTP, таких как Streamable HTTP в MCP.

При реализации MCP-серверов с транспортами на основе HTTP безопасность становится ключевым вопросом, требующим внимательного рассмотрения множества векторов атак и механизмов защиты.

### Обзор

Безопасность критична при обнародовании MCP-серверов через HTTP. Streamable HTTP вводит новые поверхности атаки и требует внимательной настройки.

Вот некоторые ключевые моменты безопасности:

- **Проверка заголовка Origin:** всегда проверяйте заголовок `Origin`, чтобы предотвратить атаки типа DNS rebinding.
- **Привязка к localhost:** для локальной разработки привязывайте серверы к `localhost`, чтобы не открывать доступ через интернет.
- **Аутентификация:** реализуйте аутентификацию (например, API ключи, OAuth) для производственных развертываний.
- **CORS:** настройте политики Cross-Origin Resource Sharing (CORS) для ограничения доступа.
- **HTTPS:** используйте HTTPS в продакшене для шифрования трафика.

### Лучшие практики

Также следуйте этим лучшим практикам при реализации безопасности в вашем MCP потоковом сервере:

- Никогда не доверяйте входящим запросам без проверки.
- Ведите логи и мониторинг всех доступов и ошибок.
- Регулярно обновляйте зависимости для устранения уязвимостей безопасности.

### Трудности

При реализации безопасности в MCP потоковых серверах вы столкнетесь с некоторыми трудностями:

- Балансировка безопасности и удобства разработки
- Обеспечение совместимости с разными клиентскими средами


## Обновление с SSE на Streamable HTTP

Для приложений, которые сейчас используют Server-Sent Events (SSE), переход на Streamable HTTP обеспечивает расширенные возможности и лучшую долгосрочную поддержку ваших MCP реализаций.

### Зачем обновляться?

Существует две веские причины для перехода с SSE на Streamable HTTP:

- Streamable HTTP предлагает лучшую масштабируемость, совместимость и более богатую поддержку уведомлений по сравнению с SSE.
- Это рекомендуемый транспорт для новых MCP приложений.

### Шаги миграции

Вот как можно перейти с SSE на Streamable HTTP в ваших MCP приложениях:

- **Обновите код сервера** для использования `transport="streamable-http"` в `mcp.run()`.
- **Обновите код клиента** для использования `streamablehttp_client` вместо SSE клиента.
- **Реализуйте обработчик сообщений** в клиенте для обработки уведомлений.
- **Проверьте совместимость** с существующими инструментами и рабочими процессами.

### Сохранение совместимости

Рекомендуется сохранять совместимость с существующими SSE клиентами во время процесса миграции. Вот некоторые стратегии:

- Можно поддерживать одновременно SSE и Streamable HTTP, запустив оба транспорта на разных эндпоинтах.
- Пошагово перевести клиентов на новый транспорт.

### Трудности

Убедитесь, что вы учитываете следующие трудности во время миграции:

- Обновление всех клиентов
- Обработка различий в доставке уведомлений
