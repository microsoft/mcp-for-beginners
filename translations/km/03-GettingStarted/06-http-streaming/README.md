# ការផ្ទុកស្ទ្រីម HTTPS ជាមួយ Model Context Protocol (MCP)

វិស្ស័យនេះផ្តល់ជូននូវមគ្គុទ្ទេសក៍ពេញលេញសម្រាប់អនុវត្តបច្ចេកវិទ្យាស្ទ្រីមដែលមានសុវត្ថិភាព អាចពង្រីកបាន និងមានពេលវេលាអចិន្រ្តៃយ៍ជាមួយ Model Context Protocol (MCP) ដោយប្រើ HTTPS។ វាដាក់បង្ហាញអំពីមូលហេតុសម្រាប់ការផ្ទុកស្ទ្រីម គ្រឿងច្រវាក់ដឹកជញ្ជូនដែលមានស្រាប់ របៀបអនុវត្ត HTTP ដែលអាចផ្ទុកស្ទ្រីមក្នុង MCP ប្រតិបត្តិការល្អបំផុតសុវត្ថិភាព ការផ្លាស់ប្តូរពី SSE និងមគ្គុទ្ទេសក៍ជាក់លាក់សម្រាប់ការបង្កើតកម្មវិធី MCP ផ្ទុកស្ទ្រីមរបស់អ្នកឯង។

> **មើលទៅមុខ:** មេរៀននេះពិពណ៌នាអំពី Streamable HTTP នៅក្រោម **MCP Specification 2025-11-25** ដែលនៅក្នុងសម័យសម្របសម្រួល (session) ត្រូវបានបង្កើតឡើងនៅពេល `initialize` ហើយត្រូវបានបង្រួបបង្រួមជាមួយ `Mcp-Session-Id` header។ កំណែចេញផ្សាយ `2026-07-28` នឹងដកហូតការដៃគូហើយ ID សម័យរួចចោល ធ្វើឲ្យសំណើរ៉ាល់កំពុងផ្ទុកខ្លួនឯង និងអាចផ្ញើទៅម៉ាស៊ីនមេណាមួយបានដោយគ្មានសម័យភ្ជាប់ជាប់។ សូមមើល [មានអ្វីប្រែប្រួលនៅក្នុង MCP: កំណែចេញផ្សាយ 2026-07-28](../../01-CoreConcepts/mcp-2026-07-28-release-candidate.md) សម្រាប់ព័ត៌មានលម្អិត។

## គ្រឿងច្រវាក់ដឹកជញ្ជូន និងការផ្ទុកស្ទ្រីមក្នុង MCP

ផ្នែកនេះវាយតម្លៃអំពីគ្រឿងច្រវាក់ដឹកជញ្ជូនផ្សេងៗដែលមានស្រាប់នៅក្នុង MCP និងតួនាទីរបស់ពួកវាក្នុងការផ្ដល់សមត្ថភាពផ្ទុកស្ទ្រីមសម្រាប់ការប្រាស្រ័យទាក់ទងពេលវេលាចាំបាច់រវាងអតិថិជន និងម៉ាស៊ីនមេ។

### គ្រឿងច្រវាក់ដឹកជញ្ជូនគឺជាអ្វី?

គ្រឿងច្រវាក់ដឹកជញ្ជូនកំណត់ពីរបៀបដែលទិន្នន័យត្រូវបានប្តូរជាមួយបណ្តាញរវាងអតិថិជន និងម៉ាស៊ីនមេ។ MCP គាំទ្រតារាងដឹកជញ្ជូនចម្លងជាច្រើនដើម្បីឱ្យសមស្របនឹងបរិយាកាស និងតម្រូវការផ្សេងៗ៖

- **stdio**: បញ្ចូល/បញ្ចេញស្តង់ដារ, សមស្របសម្រាប់ឧបករណ៍ក្នុងលក្ខខណ្ឌក្នុង និងបញ្ជារបញ្ជា CLI។ ងាយស្រួលប៉ុន្តែមិនសមសម្រាប់បណ្តាញធំ ឬពពក។
- **SSE (Server-Sent Events)**: អនុញ្ញាតឲ្យម៉ាស៊ីនមេបញ្ចូនបច្ចុប្បន្នភាពពេលវេលាពិតទៅហើយអតិថិជនតាម HTTP។ ល្អសម្រាប់ UI វិបសាយ ប៉ុន្តែមួយមិនពេញលេញក្នុងការពង្រីក និងការបត់បែន។ ចាប់ពី MCP Specification 2025-06-18 បានបង្រួមជម្រើស SSE (Server-Sent Events) ដាច់ដោយឡែក ហើយបានជំនួសដោយ "Streamable HTTP"។
- **Streamable HTTP**: ដឹកជញ្ជូនស្ទ្រីមលើ HTTP ជាន់ទំនើប ដែលគាំទ្រជូនដំណឹង និងពង្រីកល្អជាង។ ត្រូវបានផ្តល់អនុសាសន៍សម្រាប់បរិយាកាសផលិតកម្ម និងពពកភាគច្រើន។

### តារាងប្រៀបធៀប

សូមមើលតារាងប្រៀបធៀបខាងក្រោមដើម្បីយល់ពីភាពខុសគ្នារវាងគ្រឿងច្រវាក់ដឹកជញ្ជូនទាំងនេះ៖

| ដឹកជញ្ជូន         | ការធ្វើបច្ចុប្បន្នភាពពេលវេលាពិត | ផ្ទុកស្ទ្រីម | ការពង្រីក | ករណីប្រើប្រាស់                |
|-------------------|-----------------------------|------------|-----------|----------------------------|
| stdio             | ទេ                          | ទេ         | ទាប       | ឧបករណ៍ CLI ក្នុងស្រុក         |
| SSE               | បាទ                        | បាទ        | មធ្យម      | វែប សម្រាប់បច្ចុប្បន្នភាពពេលវេលាពិត  |
| Streamable HTTP   | បាទ                        | បាទ        | ខ្ពស់      | ពពក កម្មវិធីច្រើនអតិថិជន     |

> **ជំនួយៈ** ការជ្រើសរើសដឹកជញ្ជូនដែលត្រឹមត្រូវមានឥទ្ធិពលដល់សមត្ថភាព ប្រសិទ្ធភាព និងបទពិសោធន៏អ្នកប្រើ។ **Streamable HTTP** ត្រូវបានផ្តល់អនុសាសន៍សម្រាប់កម្មវិធីទំនើប ពហុផ្ទាំង និងរួមបញ្ចូលពពក។

សូមគោរពដល់ដឹកជញ្ជូន stdio និង SSE ដែលបានបង្ហាញក្នុងជំពូកមុន និងរបៀប Streamable HTTP ជាដឹកជញ្ជូនដែលពិភាក្សានៅក្នុងជំពូកនេះ។

## ការផ្ទុកស្ទ្រីម៖ គំនិត និងមូលហេតុ

ការយល់ដឹងអំពីគំនិតដើម និងមូលហេតុខាងក្រោយនៃការផ្ទុកស្ទ្រីមជារឿងសំខាន់សម្រាប់អភិវឌ្ឍប្រព័ន្ធការប្រាស្រ័យទាក់ទងពេលវេលាពិតដែលមានប្រសិទ្ធភាព។

**ការផ្ទុកស្ទ្រីម** ជាបច្ចេកវិទ្យា នៅក្នុងកម្មវិធីបណ្ដាញដែលអនុញ្ញាតឲ្យទិន្នន័យត្រូវបានផ្ញើ និងទទួលជាជំហានតូចៗ ឬជាលំដាប់ព្រឹត្តិការណ៍ ដោយមិនចាំរង់ចាំធាតុត្រឡប់ពេញលេញ។ វាសមស្របជាចម្បងសម្រាប់៖

- ឯកសារឬទិន្នន័យធំៗ។
- បច្ចុប្បន្នភាពពេលវេលាពិត (ឧ. ប្រាស្រ័យសារតាមផ្ទះបទពិសោធន៍, របារជំនាន់)។
- ការគណនារយៈពេលយូរដែលចង់រក្សាអ្នកប្រើឲ្យទាន់ដឹង។

នេះជាអ្វីដែលអ្នកត្រូវដឹងអំពីការផ្ទុកស្ទ្រីមជាទូទៅ៖

- ទិន្នន័យត្រូវបានផ្តល់ជាបន្តៗមួយ មិនមែនរួចជាសព្វនៅពេលតែមួយទេ។
- អតិថិជនអាចដំណើរការទិន្នន័យនៅពេលវាកំពុងមកដល់។
- កាត់បន្ថយការពន្យារពេលដែលមើលឃើញ ហើយបង្កើនបទពិសោធន៍អ្នកប្រើ។

### ហេតុអ្វីបានជាប្រើការផ្ទុកស្ទ្រីម?

មូលហេតុនៃការប្រើការផ្ទុកស្ទ្រីមមានដូចតទៅ៖

- អ្នកប្រើទទួលបានមតិយោបល់ភ្លាមភ្លាត មិនមែននៅចុងក្រោយទេ
- អាចបង្កើតកម្មវិធីពេលវេលាពិត និង UI ដែលឆ្លើយតប
- ប្រើប្រាស់ធនធានបណ្តាញ និងកុំព្យូទ័រប្រសើរឡើង

### ឧទាហរណ៍សាមញ្ញ៖ ម៉ាស៊ីនបម្រើ និងអតិថិជនការផ្ទុកស្ទ្រីម HTTP

នេះជាឧទាហរណ៍សាមញ្ញដែលបង្ហាញពីរបៀបអនុវត្តការផ្ទុកស្ទ្រីម៖

#### Python

**ម៉ាស៊ីនបម្រើ (Python, ប្រើប្រាស់ FastAPI និង StreamingResponse):**

```python
from fastapi import FastAPI
from fastapi.responses import StreamingResponse
import time

app = FastAPI()

async def event_stream():
    for i in range(1, 6):
        yield f"data: Message {i}\n\n"
        time.sleep(1)

@app.get("/stream")
def stream():
    return StreamingResponse(event_stream(), media_type="text/event-stream")
```

**អតិថិជន (Python, ប្រើប្រាស់ requests):**

```python
import requests

with requests.get("http://localhost:8000/stream", stream=True) as r:
    for line in r.iter_lines():
        if line:
            print(line.decode())
```

ឧទាហរណ៍នេះបង្ហាញពីម៉ាស៊ីនបម្រើផ្ញើសារៗទៅអតិថិជនខណៈពេលពួកវាជាលក្ខណៈវៃហ្ស្សូមផ្ទាល់ជូនទៅមុខមិនត្រូវរង់ចាំសារទាំងអស់ក៏ខណៈពេលមកដល់។

**របៀបវាដំណើរការ៖**

- ម៉ាស៊ីនបម្រើបញ្ចេញសារនីមួយៗនៅពេលវាចាំបាច់។
- អតិថិជនទទួល និងបង្ហាញមួយៗនៅពេលវាគឺមកដល់។

**តម្រូវការ៖**

- ម៉ាស៊ីនមេត្រូវប្រើ StreamingResponse ដើម្បីឲ្យមានប្រព័ន្ធផ្ទុកស្ទ្រីម (ឧ. `StreamingResponse` ក្នុង FastAPI)។
- អតិថិជនត្រូវដំណើរការឆ្លើយតបជាស្ទ្រីម (`stream=True` ក្នុង requests)។
- ប្រភេទខ្លឹមសារ (Content-Type) ជាទូទៅជា `text/event-stream` ឬ `application/octet-stream`។

#### Java

**ម៉ាស៊ីនបម្រើ (Java, ប្រើ Spring Boot និង Server-Sent Events):**

```java
@RestController
public class CalculatorController {

    @GetMapping(value = "/calculate", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    public Flux<ServerSentEvent<String>> calculate(@RequestParam double a,
                                                   @RequestParam double b,
                                                   @RequestParam String op) {
        
        double result;
        switch (op) {
            case "add": result = a + b; break;
            case "sub": result = a - b; break;
            case "mul": result = a * b; break;
            case "div": result = b != 0 ? a / b : Double.NaN; break;
            default: result = Double.NaN;
        }

        return Flux.<ServerSentEvent<String>>just(
                    ServerSentEvent.<String>builder()
                        .event("info")
                        .data("Calculating: " + a + " " + op + " " + b)
                        .build(),
                    ServerSentEvent.<String>builder()
                        .event("result")
                        .data(String.valueOf(result))
                        .build()
                )
                .delayElements(Duration.ofSeconds(1));
    }
}
```

**អតិថិជន (Java, ប្រើ Spring WebFlux WebClient):**

```java
@SpringBootApplication
public class CalculatorClientApplication implements CommandLineRunner {

    private final WebClient client = WebClient.builder()
            .baseUrl("http://localhost:8080")
            .build();

    @Override
    public void run(String... args) {
        client.get()
                .uri(uriBuilder -> uriBuilder
                        .path("/calculate")
                        .queryParam("a", 7)
                        .queryParam("b", 5)
                        .queryParam("op", "mul")
                        .build())
                .accept(MediaType.TEXT_EVENT_STREAM)
                .retrieve()
                .bodyToFlux(String.class)
                .doOnNext(System.out::println)
                .blockLast();
    }
}
```

**កំណត់សម្គាល់ការអនុវត្ត Java៖**

- ប្រើ Spring Boot នូវវិធី reactive ជាមួយ `Flux` សម្រាប់ការផ្ទុកស្ទ្រីម
- `ServerSentEvent` ផ្ដល់ការផ្ទុកព្រឹត្តិការណ៍មានរចនាសម្ព័ន្ធជាមួយប្រភេទព្រឹត្តិការណ៍
- `WebClient` ជាមួយ `bodyToFlux()` អនុញ្ញាតឲ្យទទួលការផ្ទុកស្ទ្រីមប្រភេទ reactive
- `delayElements()` នាំមកកំពុងសម្រួលពេលវេលាការដំណើរការពន្លឿនរវាងព្រឹត្តិការណ៍
- ព្រឹត្តិការណ៍អាចមានប្រភេទ (`info`, `result`) សម្រាប់ការគ្រប់គ្រងអតិថិជនកាន់តែប្រសើរ

### ប្រៀបធៀប៖ ការផ្ទុកស្ទ្រីមបែបបុរាណ ប្រៀបធៀបនឹង MCP Streaming

ភាពខុសគ្នារវាងការផ្ទុកស្ទ្រីមនៅបែបបុរាណ និង MCP ត្រូវបានបង្ហាញដូចតទៅ៖

| លក្ខណៈពិសេស          | ការផ្ទុកស្ទ្រីម HTTP បែបបុរាណ      | MCP Streaming (ការជូនដំណឹង)  |
|------------------------|-------------------------------|-------------------------------|
| ផលបត់ចេញសំខាន់       | ការផ្ទុកជាលំដាប់                    | ផ្ទុកដោយសេរីនៅចុងក្រោយ             |

| តម្រូវការអតិថិជន       | ត្រូវដំណើរការស្ទ្រីម                    | ត្រូវអនុវត្តអ្នកដំណើរការសារណ៍          |

### ភាពខុសគ្នាសំខាន់ៗដែលកំណត់

បន្ថែមពីនេះ ទីនេះជាភាពខុសគ្នាចម្បងៗទៀតផង៖

- **លំនាំការប្រាស្រ័យទាក់ទង៖**
  - ការផ្ទុកស្ទ្រីម HTTP បែបបុរាណ៖ ប្រើរបៀបផ្ទុកជាលំដាប់ និងការបញ្ជូនទិន្នន័យជាផ្នែកតូចៗ
  - MCP streaming៖ ប្រើប្រព័ន្ធជូនដំណឹងមានរចនាសម្ព័ន្ធជាមួយប្រព័ន្ធ JSON-RPC

- **ទ្រង់ទ្រាយសារ៖**
  - ការផ្ទុកស្ទ្រីម HTTP បែបបុរាណ៖ សារចល័តទ្រង់ទ្រាយអក្សរដែលមានបន្ទាត់ទំនេរ
  - MCP៖ វត្ថុ LoggingMessageNotification មានរចនាសម្ព័ន្ធជាមួយមេតាឌាតា

- **ការអនុវត្តអតិថិជន៖**
  - ការផ្ទុកស្ទ្រីម HTTP បែបបុរាណ៖ អតិថិជនសាមញ្ញដំណើរការឆ្លើយតបស្ទ្រីម
  - MCP៖ អតិថិជនមានភាពស្មុគស្មាញជាមួយអ្នកដំណើរការសារដើម្បីដំណើរការប្រភេទសារផ្សេងៗ

- **ការធ្វើបច្ចុប្បន្នភាពកំណត់ត្រា៖**
  - ការផ្ទុកស្ទ្រីម HTTP បែបបុរាណ៖ កំណត់ត្រាជាសមាសធាតុក្នុងចម្លើយសំខាន់
  - MCP៖ កំណត់ត្រាត្រូវបានផ្ញើជាសារជូនដំណឹងខាងក្រៅ ខណៈពេលចម្លើយសំខាន់មកនៅចុងក្រោយ

### ការផ្តល់អនុសាសន៍

មានអ្វីខ្លះយើងផ្តល់អនុសាសន៍នៅពេលជ្រើសរើសរវាងការអនុវត្តការផ្ទុកស្ទ្រីមបែបបុរាណ (ជាចំណុចបញ្ចប់ដែលយើងបានបង្ហាញក្នុង `/stream`) និងការជ្រើសរើសការផ្ទុកស្ទ្រីមតាម MCP។

- **សម្រាប់តម្រូវការផ្ទុកស្ទ្រីមសាមញ្ញ៖** ការផ្ទុកស្ទ្រីម HTTP បែបបុរាណងាយស្រួលក្នុងការអនុវត្តន៍ និងគ្រប់គ្រាន់សម្រាប់តម្រូវការលំដាប់មូលដ្ឋាន។

- **សម្រាប់កម្មវិធីស្មុគស្មាញ និងអន្តរកម្ម៖** ការផ្ទុកស្ទ្រីម MCP ផ្ដល់នូវរបៀបរចនាសម្ព័ន្ធជាច្រើនជាមួយមេតាឌាតាល្អ និងការបំបែករវាងការជូនដំណឹង និងលទ្ធផលចុងក្រោយ។

- **សម្រាប់កម្មវិធី AI៖** ប្រព័ន្ធជូនដំណឹងរបស់ MCP មានប្រយោជន៏សម្រាប់ការងារ AI យូររបស់អ្នកដែលចង់រក្សាឲ្យអ្នកប្រើទាន់ដឹងពីកម្រិតវឌ្ឍនៈ។

## ការផ្ទុកស្ទ្រីមក្នុង MCP

អូខេ ចំពោះអ្នកបានមើលអនុសាសន៍ និងការប្រៀបធៀបរបស់ការផ្ទុកស្ទ្រីមបែបបុរាណ និង MCP រហូតមកមុន។ ឥឡូវ​តោះចូលទៅក្នុងព័ត៌មានលម្អិតហេតុអ្វីបានជាអ្នកអាចអនុវត្តការផ្ទុកស្ទ្រីមក្នុង MCP។

ការយល់ដឹងពីរបៀបដំណើរការជាស្ទ្រីមនៅក្នុងសណ្ឋាន MCP គឺសំខាន់សម្រាប់ការបង្កើតកម្មវិធីដែលឆ្លើយតបបានលឿន ដែលផ្ដល់មតិយោបល់ពេលវេលាពិតដល់អ្នកប្រើ ក្នុងអំឡុងពេលនៃប្រតិបត្តិការ​រយៈ​ពេលវែង។

នៅក្នុង MCP ការផ្ទុកស្ទ្រីមមិនមែនសម្រាប់ផ្ញើចម្លើយសំខាន់ជា​លំដាប់រំលែកទេ ប៉ុន្តែនៅលើការផ្ញើ **ការជូនដំណឹង** ទៅអតិថិជន ខណៈពេលក្រុមហ៊ុនកំពុងដំណើរការសំណើ។ ការជូនដំណឹងទាំងនេះអាចរួមមានបច្ចុប្បន្នភាពកំណត់ត្រា កំណត់ត្រាឬព្រឹត្តិការណ៍ផ្សេងៗ។

### របៀបវាដំណើរការ

លទ្ធផលសំខាន់នៅតែផ្ញើជាចម្លើយមួយដាច់។ ទោះជាយ៉ាងណា ការជូនដំណឹងអាចផ្ញើជាសារ​ផ្សេងៗខណៈពេលនោះ ដែលធ្វើឲ្យអតិថិជនទទួលបានការអាប់ដេតពេលវេលាពិត។ អតិថិជនត្រូវតែបំពាក់ជាមួយអ្នកដំណើរការសារដើម្បីគ្រប់គ្រង និងបង្ហាញការជូនដំណឹងទាំងនេះ។

## ការជូនដំណឹងគឺជាអ្វី?

យើងបាននិយាយ "ការជូនដំណឹង" តើវាមានន័យអ្វីនៅក្នុងបរិបទ MCP?

ការជូនដំណឹងគឺជាសារមួយដែលផ្ញើពីម៉ាស៊ីនមេទៅអតិថិជន ដើម្បីអោយដឹងពីភាពជ្រៅរភាព ការស្ថានភាព ឬព្រឹត្តិការណ៍ផ្សេងៗក្នុងអំឡុងការប្រតិបត្តិការយូរ។ ការជូនដំណឹងបង្កើនភាពច្បាស់លាស់ និងបទពិសោធន៍អ្នកប្រើ។

ឧទាហរណ៍ អតិថិជនគួរគ្នាផ្ញើការជូនដំណឹងមួយបន្ទាប់ពីការចុះហត្ថលេខារួចជាមួយម៉ាស៊ីនមេ។

ការជូនដំណឹងមើលទៅដូចជាសារសម្រាប់ JSON ឧទាហរណ៍៖

```json
{
  jsonrpc: "2.0";
  method: string;
  params?: {
    [key: string]: unknown;
  };
}
```

ការជូនដំណឹងស្ថិតក្នុងប្រធានបទមួយក្នុង MCP ដែលហៅថា ["Logging"](https://modelcontextprotocol.io/specification/draft/server/utilities/logging)។

> **សេចក្តីជូនដំណឹងលើកលែង៖** កំណែចេញផ្សាយ `2026-07-28` នៃការបញ្ជាក់ MCP បានកំណត់ចូលជាការចេញពីប្រព័ន្ធ Logging ដើម្បីទៅប្រើ `stderr` សម្រាប់ដឹកជញ្ជូន stdio និង OpenTelemetry សម្រាប់ការសង្កេតប្រព័ន្ធមានរចនាសម្ព័ន្ធ។ Logging នៅតែដំណើរការបាននៅក្នុងកំណែ `2025-11-25` ហើយយូរបំផុតមួយឆ្នាំបន្ទាប់ពីការចេញពីផ្លូវផ្លូវផ្លូវផ្លូវផ្លូវផ្លូវផ្លូវផ្លូវផ្លូវផ្លូវផ្លូវផ្លូវផ្លូវផ្លូវផ្លូវផ្លូវផ្លូវផ្លូវផ្លូវផ្លូវផ្លូវផ្លូវផ្លូវផ្លូវផ្លូវផ្លូវ។

ដើម្បីអោយ Logging ដំណើរការ ម៉ាស៊ីនមេត្រូវដំណើរការដូចជា feature/សមត្ថភាព​ដូចខាងក្រោម៖

```json
{
  "capabilities": {
    "logging": {}
  }
}
```

> [!NOTE]
> អាស្រ័យលើ SDK ដែលប្រើ Logging ប្រហែលត្រូវបានបើកដោយឡែក ឬក៏អ្នកប្រហែលត្រូវបើកវាដោយច្បាស់នៅក្នុងការកំណត់ម៉ាស៊ីនមេ។

| កំរិត     | ការពិពណ៌នា                  | ករណីប្រើប្រាស់ឧទាហរណ៍         |

| debug     | ព័ត៌មានវាយតម្លៃលម្អិតបំផុត | ចំណុចចូល/ចេញការងារ           |
| info      | សារព័ត៌មានទូទៅ             | ការធ្វើបច្ចុប្បន្នភាពកំណត់ត្រា    |
| notice    | ព្រឹត្តិការណ៍ធម្មតា ប៉ុន្តែសំខាន់ | ការផ្លាស់ប្តូរការកំណត់          |
| warning   | លក្ខខណ្ឌប្រកបដោយការព្រមាន      | ការប្រើប្រាស់មុខងារចាស់          |
| error     | លក្ខខណ្ឌកំហុស               | ការបរាជ័យប្រតិបត្តិការ          |
| critical  | លក្ខខណ្ឌវិបត្តិ              | កំហុសនៅគ្រឿងផ្សំប្រព័ន្ធ       |
| alert     | ត្រូវចាត់វិធានការយ៉ាងឆាប់រហ័ស   | រកឃើញការបំផ្លាញទិន្នន័យ        |
| emergency | ប្រព័ន្ធមិនអាចប្រើបាន       | បរាជ័យប្រព័ន្ធសរុប             |

## ការអនុវត្តការជូនដំណឹងក្នុង MCP

ដើម្បីអនុវត្តការជូនដំណឹងនៅក្នុង MCP អ្នកត្រូវតែរៀបចំទាំងម្ខាងម៉ាស៊ីនមេ និងអតិថិជន ដើម្បីគ្រប់គ្រងការធ្វើបច្ចុប្បន្នភាពពេលវេលាពិត។ វាអនុញ្ញាតឲ្យកម្មវិធីរបស់អ្នកផ្ដល់មតិយោបល់ភ្លាមភ្លាតទៅអ្នកប្រើពេលកំពុងប្រតិបត្ដិការយូរ។

### ផ្នែកម៉ាស៊ីនមេ៖ ផ្ញើការជូនដំណឹង

តោះចាប់ផ្តើមពីផ្នែកម៉ាស៊ីនមេ។ ក្នុង MCP អ្នកកំណត់ឧបករណ៍ដែលអាចផ្ញើការជូនដំណឹងខណៈពេលកំពុងដំណើរការសំណើ។ ម៉ាស៊ីនមេប្រើអង្គភាព context (ធម្មតា `ctx`) ដើម្បីផ្ញើសារទៅអតិថិជន។

#### Python

```python
@mcp.tool(description="A tool that sends progress notifications")
async def process_files(message: str, ctx: Context) -> TextContent:
    await ctx.info("Processing file 1/3...")
    await ctx.info("Processing file 2/3...")
    await ctx.info("Processing file 3/3...")
    return TextContent(type="text", text=f"Done: {message}")
```

នៅក្នុងឧទាហរណ៍ខាងលើ ឧបករណ៍ `process_files` ផ្ញើការជូនដំណឹងបីទៅអតិថិជន ខណៈពេលដំណើរការឯកសារ។ វិធីសាស្រ្ត `ctx.info()` ត្រូវបានប្រើប្រាស់សម្រាប់ផ្ញើសារព័ត៌មាន។

បន្ថែមពីនេះ ដើម្បីបើកការជូនដំណឹង ត្រូវប្រាកដថាម៉ាស៊ីនមេមានប្រព័ន្ធផ្ទុកស្ទ្រីម (ដូចជា `streamable-http`) និងអតិថិជនបានអនុវត្តអ្នកដំណើរការសារសម្រាប់ដំណើរការជូនដំណឹង។ នេះហើយជារបៀបដែលអ្នកអាចរៀបចំម៉ាស៊ីនមេប្រើប្រាស់ `streamable-http`៖

```python
mcp.run(transport="streamable-http")
```

#### .NET


នៅក្នុងឧទាហរណ៍ .NET នេះ ឧបករណ៍ `ProcessFiles` ត្រូវបានគេប្រើ `Tool` attribute ហើយផ្ញើសារជូនដំណឹងបីទៅអតិថិជន ខណៈពេលដំណើរការឯកសារ។ វិធីសាស្រ្ត `ctx.Info()` ត្រូវបានប្រើប្រាស់សម្រាប់ផ្ញើសារព័ត៌មាន។

ដើម្បីបើកការជូនដំណឹងនៅម៉ាស៊ីនមេ .NET MCP របស់អ្នក សូមប្រាកដថាអ្នកកំពុងប្រើប្រព័ន្ធផ្ទុកស្ទ្រីម៖

### ផ្នែកអតិថិជន៖ ទទួលការជូនដំណឹង

អតិថិជនត្រូវអនុវត្តអ្នកដំណើរការសារដើម្បីដំណើរការនិងបង្ហាញការជូនដំណឹងនៅពេលវាគឺមកដល់។

#### Python

```python
async def message_handler(message):
    if isinstance(message, types.ServerNotification):
        print("NOTIFICATION:", message)
    else:
        print("SERVER MESSAGE:", message)

async with ClientSession(
   read_stream, 
   write_stream,
   logging_callback=logging_collector,
   message_handler=message_handler,
) as session:
```

នៅក្នុងកូដខាងលើ អនុគមន៍ `message_handler` ពិនិត្យមើលថាសារមកប្រារព្ធជាការជូនដំណឹង ទេបើមិនមែន វាចាត់ទុកវាជាសារម៉ាស៊ីនមេសាមញ្ញ។ ក៏បញ្ជាក់ផងដែរថា `ClientSession` ត្រូវបានចាប់ផ្តើមជាមួយ `message_handler` ដើម្បីគ្រប់គ្រងការជូនដំណឹងមកដល់។

#### .NET

```csharp
// Define a message handler
void MessageHandler(IJsonRpcMessage message)
{
    if (message is ServerNotification notification)
    {
        Console.WriteLine($"NOTIFICATION: {notification}");
    }
    else
    {
        Console.WriteLine($"SERVER MESSAGE: {message}");
    }
}

// Create and use a client session with the message handler
var clientOptions = new ClientSessionOptions
{
    MessageHandler = MessageHandler,
    LoggingCallback = (level, message) => Console.WriteLine($"[{level}] {message}")
};

using var client = new ClientSession(readStream, writeStream, clientOptions);
await client.InitializeAsync();

// Now the client will process notifications through the MessageHandler
```

នៅក្នុងឧទាហរណ៍ .NET នេះ អនុគមន៍ `MessageHandler` ពិនិត្យមើលថាសារមកជាការជូនដំណឹង ឬមិនមែនបន្ទាប់មកវាបង្ហាញវា។ បើមិនមែន វាដំណើរការជាសារម៉ាស៊ីនមេសាមញ្ញ។ `ClientSession` ត្រូវបានចាប់ផ្តើមជាមួយអ្នកដំណើរការសារជាមួយ `ClientSessionOptions`។

ដើម្បីអនុញ្ញាតការជូនដំណឹង សូមប្រាកដថាម៉ាស៊ីនមេប្រើប្រព័ន្ធផ្ទុកស្ទ្រីម (ដូចជា `streamable-http`) និងអតិថិជនបានអនុវត្តអ្នកដំណើរការសារដើម្បីដំណើរការជូនដំណឹង។

## ការជូនដំណឹងបន្ទាន់វឌ្ឍនៈ និងសេណារីយ៉ូ

ផ្នែកនេះពន្យល់ពីគំនិតនៃការជូនដំណឹងបន្ទាន់វឌ្ឍនៈក្នុង MCP ហេតុអ្វីវាមានសារៈសំខាន់ និងរបៀបអនុវត្តវាដោយប្រើ Streamable HTTP។ អ្នកក៏នឹងបានឃើញការបម្លាស់បង់អនុវត្តជាក់លាក់ដើម្បីបង្កើនការយល់ដឹងរបស់អ្នកផងដែរ។

ការជូនដំណឹងបន្ទាន់វឌ្ឍនៈគឺជាសារពេលវេលាពិតដែលផ្ញើពីម៉ាស៊ីនមេទៅអតិថិជនក្នុងរយៈពេលប្រតិបត្តិការយូរ។ ជំនួសពីការរង់ចាំដំណើរការមួយទាំងមូលត្រូវសម្រេច បច្ចុប្បន្នភាពពីម៉ាស៊ីនមេទៅអតិថិជនធ្វើការកែប្រែភាពជ្រៅរភាព។ វាអាចជួយកែលម្អភាពច្បាស់លាស់ បទពិសោធន៍អ្នកប្រើ និងបង្កើនភាពងាយស្រួលក្នុងការធ្វើបច្ចុប្បន្នភាពផងដែរ។

### ហេតុអ្វីបានឲ្យប្រើការជូនដំណឹងបន្ទាន់វឌ្ឍនៈ?

ការជូនដំណឹងបន្ទាន់វឌ្ឍនៈមានសារៈសំខាន់មួយចំនួនគឺ៖

- **បទពិសោធន៍អ្នកប្រើល្អប្រសើរ:** អ្នកប្រើឃើញការអាប់ដេតនៅពេលដែលការងារបន្ត មិនមែនចុងបញ្ចប់ប៉ុណ្ណោះទេ។
- **មតិយោបល់ពេលវេលាពិត:** អតិថិជនអាចបង្ហាញរបារបន្ត កំណត់ត្រា ដែលធ្វើឲ្យកម្មវិធីមានអារម្មណ៍ឆ្លើយតបលឿន។
- **ងាយស្រួលក្នុងការធ្វើបច្ចុប្បន្នភាព និងត្រួតពិនិត្យ:** អ្នកអភិវឌ្ឍន៍ និងអ្នកប្រើអាចមើលឃើញកន្លែងដែលបាច់ការប្រតិបត្តិការកំពុងសាមួយ ឬឈប់រៀង។

### របៀបអនុវត្តការជូនដំណឹងបន្ទាន់វឌ្ឍនៈ

នេះជារបៀបដែលអ្នកអាចអនុវត្តការជូនដំណឹងបន្ទាន់វឌ្ឍនៈក្នុង MCP៖

- **នៅលើម៉ាស៊ីនមេ:** ប្រើ `ctx.info()` ឬ `ctx.log()` ដើម្បីផ្ញើការជូនដំណឹងរៀងរាល់ធាតុដែលត្រូវបានដំណើរការ។ វាផ្ញើសារទៅអតិថិជនមុនលទ្ធផលសំខាន់រួច។
- **នៅលើអតិថិជន:** អនុវត្តអ្នកដំណើរការសារដែលស្តាប់ និងបង្ហាញការជូនដំណឹងនៅពេលវាចូលមក។ អ្នកដំណើរការនេះបំបែកចេញពីការជូនដំណឹង និងលទ្ធផលចុងក្រោយ។

**ឧទាហរណ៍ម៉ាស៊ីនមេៈ**

```python
    return TextContent(type="text", text=f"Done: {message}")
```

សន្តិសុខគួរត្រូវបានទទួលការយកចិត្តទុកដាក់ជាលំដាប់ដំបូងពេលអនុវត្តសេវាកម្មណាមួយ ដោយជាក់ស្តែងជាពិសេសពេលប្រើអាកាសចរណ៍មូលដ្ឋាន HTTP ដូចជា Streamable HTTP ក្នុង MCP។

នៅពេលអនុវត្តសេវាកម្ម MCP ជាមួយអាកាសចរណ៍មូលដ្ឋាន HTTP សន្តិសុខក្លាយជាការព្រួយបារម្ភសំខាន់ណាស់ដែលទាមទារជំនាញយកចិត្តទុកដាក់យ៉ាងម៉ត់ចត់ចំពោះចំនុចវាយប្រហារច្រើន និងយន្តការពារ។

### សេចក្ដីផ្តើម

សន្តិសុខគឺមានសារៈសំខាន់ពេលបង្ហាញសេវាកម្ម MCP តាម HTTP។ Streamable HTTP បង្កើតផ្ទៃវាយប្រហារថ្មីៗ និងត្រូវការការកំណត់តំរូវត្រឹមត្រូវ។

នៅទីនេះមានចំនុចសន្តិសុខសំខាន់ៗ៖

- **ការផ្ទៀងផ្ទាត់ក្បាល Origin**: ត្រូវតែផ្ទៀងផ្ទាត់ក្បាល `Origin` ដើម្បីការពារការវាយប្រហារប្រភពឡើងវិញ DNS rebinding ។
- **ការចងលើ localhost**: សម្រាប់ការអភិវឌ្ឍន៍ក្នុងតំបន់, ចងសេវាកម្មទៅ `localhost` ដើម្បីមិនបង្ហាញវាទៅអ៊ីនធឺណិតសាធារណៈ។
- **ការផ្ទៀងផ្ទាត់អត្តសញ្ញាណ**: អនុវត្តការផ្ទៀងផ្ទាត់អត្តសញ្ញាណ (ឧ. គ្រាប់មេកូន API, OAuth) សម្រាប់ការចេញផ្សាយផលិតផល។
- **CORS**: កំណត់គោលនយោបាយចែករំលែកមកពីប្រភពផ្សេង (CORS) ដើម្បីដាក់កំណត់ការចូលប្រើ។
- **HTTPS**: ប្រើ HTTPS ក្នុងផលិតផលដើម្បីអ៊ិនគ្រីបចរាចរណ៍។

### អនុស្សរណៈល្អបំផុត

ជាប់ផងដែរ មានអនុស្សរណៈល្អបំផុតខ្លះៗដែលត្រូវអនុវត្តពេលអនុវត្តសន្តិសុខក្នុងសេវាកម្ម MCP streamable របស់អ្នក៖

- កុំទុកចិត្តនៅលើសំណើមកដោយគ្មានការផ្ទៀងផ្ទាត់។
- កត់ចំណាំ និងត្រួតពិនិត្យការចូលប្រើ និងកំហុសទាំងអស់។
- បន្ទាន់សម័យអាសយដ្ឋាន dependency ជាប្រចាំដើម្បីជួសជុលចំណុចចុចសន្តិសុខ។

### ប្រឈមមុខ

អ្នកនឹងប្រឈមមុខនឹងបញ្ហាខ្លះៗនៅពេលអនុវត្តសន្តិសុខក្នុងសេវាកម្ម MCP streamable៖

- ការរក្សាពាក់ព័ន្ធរវាងសន្តិសុខ និងភាពងាយស្រួលក្នុងការអភិវឌ្ឍ
- ប្រាកដថាផ្គូផ្គងជាមួយបរិយាកាសអតិថិជនផ្សេងៗ


## ការបង្ហဲរ​ពី SSE ទៅ Streamable HTTP

សម្រាប់កម្មវិធីដែលកំពុងប្រើ Server-Sent Events (SSE) ការផ្លាស់ប្តូរទៅ Streamable HTTP ផ្តល់នូវសមត្ថភាពកាន់តែខ្ពស់ និងការរីកចម្រើនជាអង្កេតរយៈពេលវែងសម្រាប់ការអនុវត្ត MCP របស់អ្នក។

### ហេតុផលក្នុងការវិវត្ត

មានហេតុផលពីរដ៏គួរឱ្យចាប់អារម្មណ៍សម្រាប់ការវិវត្តពី SSE ទៅ Streamable HTTP៖

- Streamable HTTP ផ្តល់នូវភាពអាចធ្វើបានកាន់តែច្រើន ការផ្គូផ្គងល្អជាង និងការគាំទ្រជូនដំណឹងដែលសម្បូរបែបជាង SSE។
- វាជាអាកាសចរណ៍ដែលបានផ្តល់អនុសាសន៍សម្រាប់កម្មវិធី MCP ថ្មីៗ។

### ជំហានក្នុងការផ្លាស់ប្តូរ

នេះជាវិធីដែលអ្នកអាចផ្លាស់ប្តូរពី SSE ទៅ Streamable HTTP ក្នុងកម្មវិធី MCP របស់អ្នក៖

- **ធ្វើបច្ចុប្បន្នកូដសេវាកម្ម** ដើម្បីប្រើ `transport="streamable-http"` ក្នុង `mcp.run()`។
- **ធ្វើបច្ចុប្បន្នកូដអតិថិជន** ដើម្បីប្រើ `streamablehttp_client` ជំនួស SSE client។
- **អនុវត្តកម្មវិធីរៀបចំសារជូនដំណឹង** នៅក្នុងអតិថិជនដើម្បីដំណើរការជូនដំណឹង។
- **សាកល្បងការផ្គូផ្គង** ជាមួយឧបករណ៍និងការងារដែលមានរួចហើយ។

### ការរក្សាបានភាពផ្គូផ្គង

មានការណែនាំឲ្យរក្សាបានភាពផ្គូផ្គងជាមួយ SSE client ដែលមានរួចស្រាប់នៅពេលផ្លាស់ប្តូរ។ ទីនេះមានយុទ្ធសាស្រ្តខ្លះ៖

- អ្នកអាចគាំទ្រទាំង SSE និង Streamable HTTP ដោយដំណើរការចំងាយនៃអាកាសចរណ៍ទាំងពីរនៅចំណុចចេញផ្សេងៗ។
- ពង្រឹងអតិថិជនទៅអាកាសចរណ៍ថ្មីៗយ៉ាងយឺតយ៉ាវ។

### ប្រឈមមុខ

ត្រូវប្រាកដថាអ្នកដោះស្រាយបញ្ហាខាងក្រោមក្នុងដំណើរការផ្លាស់ប្តូរ៖

- ប្រាកដថាអតិថិជនទាំងអស់បានបច្ចុប្បន្នក្រោយ
- ដោះស្រាយភាពខុសគ្នានៅការផ្ដល់ជូនដំណឹង

### ការងារ៖ បង្កើតកម្មវិធី MCP Streaming របស់អ្នកឯង

**សេណារីយ៉ូ:**
បង្កើតសេវាកម្ម MCP និងអតិថិជន ដែលសេវាកម្មដំណើរការចុះបញ្ជីធាតុ (ឧ. ហ្វាយល៍ ឬឯកសារ) ហើយផ្ញើនូវការជូនដំណឹងរាល់ធាតុដែលបានដំណើរការ។ អតិថិជនគួរតែបង្ហាញការជូនដំណឹងនីមួយៗនៅពេលវាចូល។

**ជំហាន៖**

1. អនុវត្តឧបករណ៍សេវាកម្មដែលដំណើរការចុះបញ្ជី ហើយផ្ញើជូនដំណឹងរាល់ធាតុ។
2. អនុវត្តអតិថិជនជាមួយកម្មវិធីរៀបចំសារដើម្បីបង្ហាញជូនដំណឹងក្នុងពេលពិត។
3. សាកល្បងការអនុវត្តរបស់អ្នកដោយដំណើរការ សេវាកម្ម និងអតិថិជន និងមើលការជូនដំណឹង។
