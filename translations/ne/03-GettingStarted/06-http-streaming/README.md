# मोडेल सन्दर्भ प्रोटोकल (MCP) सँग HTTPS स्ट्रिमिंग

यस अध्यायले HTTPS प्रयोग गरेर मोडेल सन्दर्भ प्रोटोकल (MCP) मार्फत सुरक्षित, स्केलेबल, र वास्तविक-समय स्ट्रिमिंग लागू गर्ने व्यावहारिक मार्गदर्शन प्रदान गर्दछ। यसले स्ट्रिमिंगको प्रेरणा, उपलब्ध ट्रान्सपोर्ट मेकानिज्महरू, MCP मा स्ट्रिमेबल HTTP कसरी लागू गर्ने, सुरक्षा उत्तम अभ्यासहरू, SSE बाट माइग्रेशन, र आफ्नै स्ट्रिमिंग MCP अनुप्रयोगहरू निर्माण गर्ने व्यावहारिक मार्गनिर्देशन समेट्छ।

> **अगाडि हेर्दै:** यो पाठले **MCP स्पेसिफिकेसन 2025-11-25** अन्तर्गत स्ट्रिमेबल HTTP वर्णन गर्दछ, जहाँ सत्र `initialize` मा स्थापना हुन्छ र `Mcp-Session-Id` हेडरसँग पिन गरिन्छ। `2026-07-28` रिलिज क्यान्डिडेटले ह्याण्डशेक र सत्र ID पूर्ण रूपमा हटाउनेछ, जसले प्रत्येक अनुरोधलाई आत्मनिर्भर र कुनै पनि सर्भर इन्स्ट्यान्समा रुटेबल बनाउँछ बिना स्टिकी सत्रहरू। विस्तृत जानकारीका लागि [MCP मा के के परिवर्तन हुँदैछ: 2026-07-28 रिलिज क्यान्डिडेट](../../01-CoreConcepts/mcp-2026-07-28-release-candidate.md) हेर्नुहोस्।

## MCP मा ट्रान्सपोर्ट मेकानिज्म र स्ट्रिमिंग

यस भागले MCP मा उपलब्ध विभिन्न ट्रान्सपोर्ट मेकानिज्महरू र क्लाइन्ट र सर्भरहरू बीच वास्तविक-समय संवादका लागि स्ट्रिमिंग क्षमताहरू सक्रिय पार्ने तिनको भूमिका अन्वेषण गर्दछ।

### ट्रान्सपोर्ट मेकानिज्म भनेको के हो?

ट्रान्सपोर्ट मेकानिज्मले डाटा क्लाइन्ट र सर्भर बीच कसरी आदान-प्रदान हुन्छ भन्ने निर्धारण गर्दछ। MCP ले विभिन्न वातावरण र आवश्यकताहरू सुहाउँदो बहु ट्रान्सपोर्ट प्रकारहरू समर्थन गर्दछ:

- **stdio**: स्ट्यान्डर्ड इनपुट/आउटपुट, स्थानीय र CLI-आधारित उपकरणहरूका लागि उपयुक्त। साधारण तर वेब वा क्लाउडका लागि उपयुक्त छैन।
- **SSE (सर्भर-सेन्ट इभेन्ट्स)**: सर्भरहरूले क्लाइन्टलाई HTTP मार्फत वास्तविक-समय अपडेट पठाउन अनुमति दिन्छ। वेब UI का लागि राम्रो, तर स्केलेबिलिटी र लचकपनमा सीमित। MCP स्पेसिफिकेसन 2025-06-18 अनुसार, स्वतन्त्र SSE ट्रान्सपोर्टलाई प्रतिबन्ध लगाइयो र "स्ट्रिमेबल HTTP" ट्रान्सपोर्टले प्रतिस्थापन गऱियो।
- **स्ट्रिमेबल HTTP**: आधुनिक HTTP-आधारित स्ट्रिमिंग ट्रान्सपोर्ट, सूचनाहरू र राम्रो स्केलेबिलिटी समर्थन गर्दछ। अधिकांश उत्पादन र क्लाउड परिदृश्यहरूका लागि सिफारिस गरिएको।

### तुलना तालिका

यी ट्रान्सपोर्ट मेकानिज्महरू बीचको भिन्नताहरू बुझ्न तलको तुलना तालिका हेर्नुहोस्:

| ट्रान्सपोर्ट         | वास्तविक-समय अपडेटहरू | स्ट्रिमिंग | स्केलेबिलिटी | प्रयोग केस              |
|-------------------|------------------|-----------|-------------|-------------------------|
| stdio             | छैन               | छैन        | कम         | स्थानीय CLI उपकरणहरू     |
| SSE               | छ                | छ         | मध्यम      | वेब, वास्तविक-समय अपडेटहरू |
| स्ट्रिमेबल HTTP   | छ                | छ         | उच्च       | क्लाउड, बहु क्लाइन्ट    |

> **टिप:** सही ट्रान्सपोर्ट चयनले प्रदर्शन, स्केलेबिलिटी, र प्रयोगकर्ता अनुभवमा प्रभाव पार्दछ। आधुनिक, स्केलेबल, र क्लाउड-तैयार अनुप्रयोगहरूको लागि **स्ट्रिमेबल HTTP** सिफारिस गरिएको छ।

ध्यान दिनुहोस् कि स्टैण्डर्ड इनपुट/आउटपुट (stdio) र SSE तपाईंलाई अघिल्लो अध्यायहरूमा देखाइएका थिए र यस अध्यायमा कभर गरिएको ट्रान्सपोर्ट स्ट्रिमेबल HTTP हो।

## स्ट्रिमिंग: अवधारणाहरू र प्रेरणा

स्ट्रिमिंगको आधारभूत अवधारणाहरू र प्रेरणाहरू बुझ्नु प्रभावकारी वास्तविक-समय संचार प्रणालीहरू कार्यान्वयन गर्न आवश्यक छ।

**स्ट्रिमिंग** नेटवर्क प्रोग्रामिङमा प्रयोग हुने प्रविधि हो जसले पूर्ण प्रतिक्रिया पर्खनुको सट्टा सानो-छोटो, व्यवस्थापनयोग्य टुक्राहरू वा घटनाहरूको श्रृंखलाको रूपमा डाटा पठाउन र प्राप्त गर्न अनुमति दिन्छ। यो विशेषगरी उपयोगी छ:

- ठूला फाइलहरू वा डाटासेटहरू।
- वास्तविक-समय अपडेटहरू (जस्तै, च्याट, प्रगति बारहरू)।
- लामो समयसम्म चल्ने गणनाहरू जहाँ तपाईं प्रयोगकर्तालाई जानकारी दिन चाहनुहुन्छ।

यहाँ तपाईंले उच्च स्तरमा स्ट्रिमिंगको बारेमा जान्नुपर्ने कुराहरू छन्:

- डाटा क्रमिक रूपमा डेलिभर हुन्छ, सबै एकसाथ होइन।
- क्लाइन्टले डाटा आइरहेको जस्तै प्रशोधन गर्न सक्छ।
- अनुमानित विलम्ब घटाउँछ र प्रयोगकर्ता अनुभव सुधार्छ।

### किन स्ट्रिमिंग प्रयोग गर्ने?

स्ट्रिमिंग प्रयोग गर्ने कारणहरू निम्न छन्:

- प्रयोगकर्ताहरू तत्काल प्रतिक्रिया प्राप्त गर्छन्, अन्त्यमा मात्र होइन।
- वास्तविक-समय अनुप्रयोगहरू र प्रतिक्रियाशील UI सक्षम पार्छ।
- नेटवर्क र कम्प्युट स्रोतहरूको बढी कुशल प्रयोग गर्छ।

### सरल उदाहरण: HTTP स्ट्रिमिंग सर्भर र क्लाइन्ट

यहाँ स्ट्रिमिंग कसरी लागू गर्न सकिने सरल उदाहरण छ:

#### पाइथन

**सर्भर (पाइथन, FastAPI र StreamingResponse प्रयोग गर्दै):**

```python
from fastapi import FastAPI
from fastapi.responses import StreamingResponse
import time

app = FastAPI()

async def event_stream():
    for i in range(1, 6):
        yield f"data: Message {i}\n\n"
        time.sleep(1)

@app.get("/stream")
def stream():
    return StreamingResponse(event_stream(), media_type="text/event-stream")
```

**क्लाइन्ट (पाइथन, requests प्रयोग गर्दै):**

```python
import requests

with requests.get("http://localhost:8000/stream", stream=True) as r:
    for line in r.iter_lines():
        if line:
            print(line.decode())
```

यो उदाहरणले देखाउँछ कि सर्भरले सबै सन्देशहरू तयार नहुँदासम्म कुर्नुको सट्टा उपलब्ध भइरहेका सन्देशहरूको श्रृंखला क्लाइन्टलाई पठाउँछ।

**कसरी काम गर्छ:**

- सर्भरले प्रत्येक सन्देश तयार हुँदासम्म ल्याउँछ।
- क्लाइन्टले प्रत्येक टुक्रा प्राप्त गरेर प्रिन्ट गर्छ।

**आवश्यकताहरू:**

- सर्भरले स्ट्रिमिंग प्रतिक्रिया प्रयोग गर्नुपर्छ (जस्तै, FastAPI मा `StreamingResponse`)।
- क्लाइन्टले प्रतिक्रिया स्ट्रिमको रूपमा प्रशोधन गर्नुपर्छ (`requests` मा `stream=True`)।
- सामग्री-प्रकार सामान्यतया `text/event-stream` वा `application/octet-stream` हुन्छ।

#### जाभा

**सर्भर (जाभा, Spring Boot र Server-Sent Events प्रयोग गर्दै):**

```java
@RestController
public class CalculatorController {

    @GetMapping(value = "/calculate", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    public Flux<ServerSentEvent<String>> calculate(@RequestParam double a,
                                                   @RequestParam double b,
                                                   @RequestParam String op) {
        
        double result;
        switch (op) {
            case "add": result = a + b; break;
            case "sub": result = a - b; break;
            case "mul": result = a * b; break;
            case "div": result = b != 0 ? a / b : Double.NaN; break;
            default: result = Double.NaN;
        }

        return Flux.<ServerSentEvent<String>>just(
                    ServerSentEvent.<String>builder()
                        .event("info")
                        .data("Calculating: " + a + " " + op + " " + b)
                        .build(),
                    ServerSentEvent.<String>builder()
                        .event("result")
                        .data(String.valueOf(result))
                        .build()
                )
                .delayElements(Duration.ofSeconds(1));
    }
}
```

**क्लाइन्ट (जाभा, Spring WebFlux WebClient प्रयोग गर्दै):**

```java
@SpringBootApplication
public class CalculatorClientApplication implements CommandLineRunner {

    private final WebClient client = WebClient.builder()
            .baseUrl("http://localhost:8080")
            .build();

    @Override
    public void run(String... args) {
        client.get()
                .uri(uriBuilder -> uriBuilder
                        .path("/calculate")
                        .queryParam("a", 7)
                        .queryParam("b", 5)
                        .queryParam("op", "mul")
                        .build())
                .accept(MediaType.TEXT_EVENT_STREAM)
                .retrieve()
                .bodyToFlux(String.class)
                .doOnNext(System.out::println)
                .blockLast();
    }
}
```

**जाभा कार्यान्वयन नोटहरू:**

- Spring Boot को प्रतिक्रियाशील स्ट्याक `Flux` सँग स्ट्रिमिंगका लागि प्रयोग गर्छ
- `ServerSentEvent` इभेन्ट प्रकारहरूसहित संरचित इभेन्ट स्ट्रिमिंग प्रदान गर्दछ
- `WebClient` सँग `bodyToFlux()` प्रतिक्रियाशील स्ट्रिमिंग खपत सक्षम पार्दछ
- `delayElements()` ले इभेन्टहरूबीच प्रशोधन समय अनुकरण गर्छ
- इभेन्टहरूमा प्रकारहरू (`info`, `result`) हुनसक्छन् जसले क्लाइन्टलाई राम्रोसँग ह्यान्डल गर्न मद्दत गर्छ

### तुलना: क्लासिक स्ट्रिमिंग र MCP स्ट्रिमिंग

"क्लासिक" तरिका र MCP मा कसरी स्ट्रिमिंग काम गर्छ भन्ने भिन्नताहरू यसरी देखाउन सकिन्छ:

| विशेषता              | क्लासिक HTTP स्ट्रिमिंग         | MCP स्ट्रिमिंग (सूचनाहरू)     |
|------------------------|-------------------------------|-------------------------------------|
| मुख्य प्रतिक्रिया       | टुक्रामा पठाइन्छ               | एकैपटक, अन्त्यमा पठाइन्छ           |
| प्रगति अपडेटहरू       | डाटा टुक्राहरूको रूपमा पठाइन्छ  | सूचनाको रूपमा पठाइन्छ              |
| क्लाइन्ट आवश्यकताहरू | स्ट्रिम प्रक्रिया गर्नुपर्छ      | सन्देश ह्यान्डलर कार्यान्वयन गर्नुपर्छ  |
| प्रयोग केस             | ठूला फाइलहरू, AI टोकन स्ट्रिमहरू | प्रगति, लगहरू, वास्तविक-समय प्रतिक्रिया  |

### प्रमुख भिन्नताहरू अवलोकन

थप रूपमा, यहाँ केही मुख्य भिन्नताहरू छन्:

- **सञ्चार ढाँचा:**
  - क्लासिक HTTP स्ट्रिमिंग: सरल टुक्रा ट्रान्सफर एन्कोडिङ प्रयोग गरी डाटा टुक्राहरूमा पठाउँछ
  - MCP स्ट्रिमिंग: JSON-RPC प्रोटोकलसहित संरचित सूचनात्मक प्रणाली प्रयोग गर्छ

- **सन्देश ढाँचा:**
  - क्लासिक HTTP: नयाँ लाइन सहित प्लेन टेक्स्ट टुक्राहरू
  - MCP: मेटाडाटा सहित संरचित LoggingMessageNotification वस्तुहरू

- **क्लाइन्ट कार्यान्वयन:**
  - क्लासिक HTTP: सरल क्लाइन्ट जसले स्ट्रिमिंग प्रतिक्रियाहरू प्रशोधन गर्छ
  - MCP: अधिक जटिल क्लाइन्ट जसले विभिन्न प्रकारका सन्देशहरू प्रशोधन गर्न सन्देश ह्यान्डलर राख्छ

- **प्रगति अपडेटहरू:**
  - क्लासिक HTTP: प्रगति मुख्य प्रतिक्रिया स्ट्रिमको भाग हो
  - MCP: प्रगति छुट्टै सूचनात्मक सन्देशहरूले पठाइन्छ भने मुख्य प्रतिक्रिया अन्त्यमा आउँछ

### सिफारिसहरू

क्लासिक स्ट्रिमिंग (जस्तै माथि `/stream` अन्तबिन्दु मार्फत देखाइएको) र MCP मार्फत स्ट्रिमिंग लागू गर्ने बीच चयन गर्दा केही सिफारिसहरू छन्।

- **सजिलो स्ट्रिमिंग आवश्यकताका लागि:** क्लासिक HTTP स्ट्रिमिंग सरल छ र आधारभूत स्ट्रिमिंग आवश्यकताहरूका लागि पर्याप्त छ।

- **जटिल, अन्तरक्रियात्मक अनुप्रयोगहरूका लागि:** MCP स्ट्रिमिंगले बढी संरचित दृष्टिकोण र धनी मेटाडाटा र सूचनाहरू र अन्तिम परिणामहरू बीच पृथकता प्रदान गर्छ।

- **AI अनुप्रयोगहरूका लागि:** लामो समयसम्म चल्ने AI टास्कहरूमा MCP को सूचना प्रणाली विशेष रूपमा उपयोगी छ जहाँ तपाईं प्रयोगकर्तालाई प्रगति जानकारी दिन चाहनुहुन्छ।

## MCP मा स्ट्रिमिंग

तपाईले अहिलेसम्म केही सिफारिसहरू र तुलना हेर्नु भएको छ क्लासिक स्ट्रिमिंग र MCP स्ट्रिमिंगबीच। अब विस्तृत रुपमा हेरौं कि MCP मा स्ट्रिमिंग कसरी उपयोग गर्ने।

MCP फ्रेमवर्क भित्र स्ट्रिमिंग कसरि काम गर्छ बुझ्नाले दिर्घकालीन अपरेशनहरूका दौरान प्रयोगकर्तालाई वास्तविक-समय प्रतिक्रिया दिन सक्षम अनुप्रयोगहरू बनाउन आवश्यक छ।

MCP मा स्ट्रिमिंग मुख्य प्रतिक्रिया टुक्रामा पठाउने विषय होइन, तर अनुरोध प्रशोधन हुँदै गर्दा क्लाइन्टलाई **सूचनाहरू** पठाउने विषय हो। यी सूचनाहरूमा प्रगति अपडेट, लगहरू, वा अन्य घटनाहरू समावेश हुन सक्छन्।

### कसरी काम गर्छ

मुख्य परिणाम अझै एक्लो प्रतिक्रियाको रूपमा पठाइन्छ। यद्यपि, सूचनाहरू प्रशोधनको क्रममा अलग सन्देशहरूका रूपमा पठाउन सकिन्छ र यसैले क्लाइन्टलाई वास्तविक समयमा अपडेट गर्न सकिन्छ। क्लाइन्टले यी सूचनाहरू ह्यान्डल गरी प्रदर्शन गर्न सक्षम हुनुपर्छ।

## सूचना भनेको के हो?

हामीले "सूचना" भनेका छौं, MCP सन्दर्भमा यसको अर्थ के हो?

सूचना भनेको सर्भरबाट क्लाइन्टलाई पठाइएको सन्देश हो जसले लामो समयसम्म चल्ने अपरेशनको क्रममा प्रगति, स्थिति, वा अन्य घटनाहरुको जानकारी दिन्छ। सूचनाले पारदर्शिता र प्रयोगकर्ता अनुभव सुधार्दछ।

उदाहरणका लागि, क्लाइन्टले सर्भरसँग प्रारम्भिक ह्याण्डशेक पूरा भएपछि सूचना पठाउनुपर्छ।

सूचना JSON सन्देशको रूपमा यस्तो देखिन्छ:

```json
{
  jsonrpc: "2.0";
  method: string;
  params?: {
    [key: string]: unknown;
  };
}
```

सूचनाहरू MCP मा ["Logging"](https://modelcontextprotocol.io/specification/draft/server/utilities/logging) भनिने विषय अन्तर्गत पर्छन्।

> **प्रतिबन्ध सूचना:** `2026-07-28` MCP स्पेसिफिकेसन रिलिज क्यान्डिडेटले Logging प्रिमिटिभलाई stdio ट्रान्सपोर्टका लागि `stderr` र संरचित अवलोकनका लागि OpenTelemetry को पक्षमा अप्रचलित घोषणा गर्दछ। Logging `2025-11-25` मा र कुनै पनि औपचारिक प्रतिबन्ध पछि कम्तिमा एक वर्षको लागि कार्यरत रहनेछ। विस्तृत जानकारीका लागि [MCP मा के के परिवर्तन हुँदैछ: 2026-07-28 रिलिज क्यान्डिडेट](../../01-CoreConcepts/mcp-2026-07-28-release-candidate.md) हेर्नुहोस्।

Logging कार्यान्वयन गर्न, सर्भरले यसलाई सुविधा/क्षमता रूपमा यसरी सक्षम पार्नुपर्छ:

```json
{
  "capabilities": {
    "logging": {}
  }
}
```

> [!NOTE]
> प्रयोग गरिएको SDK मा निर्भर गर्दै, logging डिफल्टमा सक्षम हुन सक्छ वा तपाईंले आफ्नो सर्भर कन्फिगरेसनमा स्पष्ट रूपमा सक्षम पार्नुपर्ने हुनसक्छ।

विभिन्न प्रकारका सूचनाहरू हुन्छन्:

| स्तर        | विवरण                         | उदाहरण प्रयोग केस             |
|------------|-------------------------------|-------------------------------|
| debug      | विस्तृत डिबगिङ जानकारी       | कार्य/फङ्क्शन प्रवेश र निकास पोइन्टहरू |
| info       | सामान्य जानकारी सन्देशहरू     | अपरेशन प्रगति अपडेटहरू         |
| notice     | सामान्य तर महत्वपूर्ण घटनाहरू | कन्फिगरेसन परिवर्तनहरू         |
| warning    | चेतावनी अवस्थाहरू             | अप्रचलित सुविधा प्रयोग          |
| error      | त्रुटि अवस्थाहरू              | अपरेशन असफलताहरू               |
| critical   | गम्भीर अवस्थाहरू              | प्रणाली कम्पोनेन्ट असफलताहरू    |
| alert      | तुरुन्तै कारबाही आवश्यक        | डेटा भ्रष्टाचार पत्ता लगाइयो    |
| emergency  | प्रणाली अपयोगयोग्य छैन        | पूर्ण प्रणाली असफलता            |

## MCP मा सूचनाहरू कार्यान्वयन

MCP मा सूचनाहरू कार्यान्वयन गर्न, तपाईंले दुवै सर्भर र क्लाइन्ट पक्षलाई वास्तविक-समय अपडेटहरू ह्यान्डल गर्ने गरी सेटअप गर्नुपर्छ। यसले तपाईंको अनुप्रयोगलाई दिर्घकालीन अपरेशनहरूको समयमा प्रयोगकर्तालाई तुरुन्त प्रतिक्रिया प्रदान गर्न सक्षम बनाउँछ।

### सर्भर पक्ष: सूचनाहरू पठाउने

सर्भर पक्षबाट सुरु गरौं। MCP मा, तपाईंले उपकरणहरू परिभाषित गर्नुहुन्छ जुन अनुरोध प्रशोधनको बेला सूचनाहरू पठाउन सक्छन्। सर्भरले सन्देशहरू क्लाइन्टमा पठाउन सन्दर्भ वस्तु (सामान्यतया `ctx`) प्रयोग गर्छ।

#### पाइथन

```python
@mcp.tool(description="A tool that sends progress notifications")
async def process_files(message: str, ctx: Context) -> TextContent:
    await ctx.info("Processing file 1/3...")
    await ctx.info("Processing file 2/3...")
    await ctx.info("Processing file 3/3...")
    return TextContent(type="text", text=f"Done: {message}")
```

माथिको उदाहरणमा, `process_files` उपकरणले प्रत्येक फाइल प्रशोधन गर्दा क्लाइन्टलाई तीनवटा सूचनाहरू पठाउँछ। `ctx.info()` मेथडले सूचनात्मक सन्देशहरू पठाउन प्रयोग गरिएको छ।

थप रूपमा, सूचनाहरू सक्षम गर्न, सुनिश्चित गर्नुहोस् कि सर्भरले स्ट्रिमिंग ट्रान्सपोर्ट (जस्तै `streamable-http`) प्रयोग गरिरहेको छ र क्लाइन्टले सूचनाहरू प्रशोधन गर्न सन्देश ह्यान्डलर कार्यान्वयन गरेको छ। सर्भरलाई `streamable-http` ट्रान्सपोर्ट प्रयोग गर्न कसरि सेटअप गर्ने:

```python
mcp.run(transport="streamable-http")
```

#### .NET

```csharp
[Tool("A tool that sends progress notifications")]
public async Task<TextContent> ProcessFiles(string message, ToolContext ctx)
{
    await ctx.Info("Processing file 1/3...");
    await ctx.Info("Processing file 2/3...");
    await ctx.Info("Processing file 3/3...");
    return new TextContent
    {
        Type = "text",
        Text = $"Done: {message}"
    };
}
```

यो .NET उदाहरणमा, `ProcessFiles` उपकरणलाई `Tool` विशेषता दिइएको छ र प्रत्येक फाइल प्रशोधन गर्दा क्लाइन्टलाई तीनवटा सूचनाहरू पठाउँछ। `ctx.Info()` मेथड सूचनात्मक सन्देशहरू पठाउन प्रयोग गरिएको छ।

तपाईंको .NET MCP सर्भरमा सूचनाहरू सक्षम गर्न, सुनिश्चित गर्नुहोस् कि तपाईं स्ट्रिमिंग ट्रान्सपोर्ट प्रयोग गर्दै हुनुहुन्छ:

```csharp
var builder = McpBuilder.Create();
await builder
    .UseStreamableHttp() // Enable streamable HTTP transport
    .Build()
    .RunAsync();
```

### क्लाइन्ट पक्ष: सूचनाहरू प्राप्त गर्ने

क्लाइन्टले सन्देश ह्यान्डलर कार्यान्वयन गरेर आएका सूचनाहरू प्रशोधन र प्रदर्शन गर्नुपर्छ।

#### पाइथन

```python
async def message_handler(message):
    if isinstance(message, types.ServerNotification):
        print("NOTIFICATION:", message)
    else:
        print("SERVER MESSAGE:", message)

async with ClientSession(
   read_stream, 
   write_stream,
   logging_callback=logging_collector,
   message_handler=message_handler,
) as session:
```

माथिको कोडमा, `message_handler` फङ्सनले आउने सन्देश सूचना हो कि होइन जाँच्छ। यदि हो भने, सूचना प्रिन्ट गर्छ; नत्र, यसलाई साधारण सर्भर सन्देशको रूपमा प्रशोधन गर्छ। क्लाइन्ट सत्र `ClientSession` सूचनाहरू ह्यान्डल गर्न `message_handler` को साथ इनिसियलाइज गरिएको छ।

#### .NET

```csharp
// Define a message handler
void MessageHandler(IJsonRpcMessage message)
{
    if (message is ServerNotification notification)
    {
        Console.WriteLine($"NOTIFICATION: {notification}");
    }
    else
    {
        Console.WriteLine($"SERVER MESSAGE: {message}");
    }
}

// Create and use a client session with the message handler
var clientOptions = new ClientSessionOptions
{
    MessageHandler = MessageHandler,
    LoggingCallback = (level, message) => Console.WriteLine($"[{level}] {message}")
};

using var client = new ClientSession(readStream, writeStream, clientOptions);
await client.InitializeAsync();

// Now the client will process notifications through the MessageHandler
```

यो .NET उदाहरणमा, `MessageHandler` फङ्सनले आउने सन्देश सूचना हो कि होइन जाँच्छ। यदि हो भने सूचनालाई प्रिन्ट गर्छ; नत्र, यसलाई साधारण सर्भर सन्देशको रूपमा प्रशोधन गर्छ। `ClientSession` सन्देश ह्यान्डलरको साथ `ClientSessionOptions` द्वारा इनिसियलाइज गरिएको छ।

सूचनाहरू सक्षम गर्न, सुनिश्चित गर्नुहोस् कि तपाईंको सर्भरले स्ट्रिमिंग ट्रान्सपोर्ट (जस्तै `streamable-http`) प्रयोग गरिरहेको छ र तपाईंको क्लाइन्टले सूचनाहरू प्रशोधन गर्न सन्देश ह्यान्डलर अपनाएको छ।

## प्रगति सूचनाहरू र परिदृश्यहरू

यस भागले MCP मा प्रगति सूचनाहरूको अवधारणा, तिनीहरू किन महत्त्वपूर्ण छन्, र स्ट्रिमेबल HTTP प्रयोग गरेर तिनीहरू कसरी कार्यान्वयन गर्ने व्याख्या गर्दछ। तपाईंले आफ्नो बुझाइलाई सुदृढ गर्न व्यावहारिक कार्यसमेत पाउनु हुनेछ।

प्रगति सूचनाहरू लामो समयसम्म चल्ने अपरेशनहरूको क्रममा सर्भरबाट क्लाइन्टलाई पठाइने वास्तविक-समय सन्देशहरू हुन्। सम्पूर्ण प्रक्रिया पूरा हुन कुर्नुको सट्टा, सर्भरले क्लाइन्टलाई वर्तमान स्थितिबारे निरन्तर अपडेट राख्छ। यसले पारदर्शिता, प्रयोगकर्ता अनुभव सुधार्छ र डिबगिङ सजिलो बनाउँछ।

**उदाहरण:**

```text

"Processing document 1/10"
"Processing document 2/10"
...
"Processing complete!"

```

### किन प्रगति सूचनाहरू प्रयोग गर्ने?

प्रगति सूचनाहरू आवश्यक पर्ने केही कारणहरू छन्:

- **राम्रो प्रयोगकर्ता अनुभव:** प्रयोगकर्ताले काम प्रगतिमा हुँदै गरेको अपडेटहरू देख्छन्, केवल अन्त्यमा होइन।
- **वास्तविक-समय प्रतिक्रिया:** क्लाइन्टले प्रगति बार वा लग प्रदर्शन गर्न सक्छन्, जसले अनुप्रयोगलाई प्रतिक्रियाशील बनाउँछ।
- **डिबगिङ र अनुगमन सजिलो:** विकासकर्ताहरू र प्रयोगकर्ताहरू देख्न सक्छन् प्रक्रिया कतामा ढिलाइ वा अड्किएको हुन्छ।

### प्रगति सूचनाहरू कार्यान्वयन गर्ने तरिका

यहाँ MCP मा प्रगति सूचनाहरू कसरी कार्यान्वयन गर्ने:

- **सर्भरमा:** प्रशोधन हरेक वस्तुका लागि `ctx.info()` वा `ctx.log()` प्रयोग गरी सूचनाहरू पठाउनुहोस्। यसले मुख्य परिणाम तयार हुनु अघि क्लाइन्टलाई सन्देश पठाउँछ।
- **क्लाइन्टमा:** सूचनाहरू सुन्न र प्रदर्शन गर्न सन्देश ह्यान्डलर कार्यान्वयन गर्नुहोस्। यसले सूचनाहरू र अन्तिम परिणामहरूलाई छुट्याउँछ।

**सर्भर उदाहरण:**


#### पाइथन

```python
@mcp.tool(description="A tool that sends progress notifications")
async def process_files(message: str, ctx: Context) -> TextContent:
    for i in range(1, 11):
        await ctx.info(f"Processing document {i}/10")
    await ctx.info("Processing complete!")
    return TextContent(type="text", text=f"Done: {message}")
```

**क्लाइन्ट उदाहरण:**

#### पाइथन

```python
async def message_handler(message):
    if isinstance(message, types.ServerNotification):
        print("NOTIFICATION:", message)
    else:
        print("SERVER MESSAGE:", message)
```

## सुरक्षा विचारहरू

कुनै पनि सर्भर लागू गर्दा सुरक्षा उच्च प्राथमिकता हुनुपर्छ, विशेष गरी MCP मा Streamable HTTP जस्ता HTTP-आधारित ट्रान्सपोर्टहरू प्रयोग गर्दा।

HTTP-आधारित ट्रान्सपोर्टहरूसँग MCP सर्भरहरू लागू गर्दा, सुरक्षा एक मुख्य चासो हुन्छ जसले धेरै आक्रमण भेक्टरहरू र सुरक्षा संयन्त्रहरूमा सावधानीपूर्वक ध्यान दिन आवश्यक हुन्छ।

### अवलोकन

MCP सर्भरहरूलाई HTTP मार्फत सार्वजनिक गर्दा सुरक्षा निकै महत्वपूर्ण हुन्छ। Streamable HTTP ले नयाँ आक्रमण सतहहरू सिर्जना गर्छ र सावधानीपूर्वक कन्फिगरेसन आवश्यक हुन्छ।

यहाँ केहि प्रमुख सुरक्षा विचारहरू छन्:

- **Origin हेडर मान्यता**: DNS रिबाइन्डिङ आक्रमणहरू रोक्न सधैं `Origin` हेडर मान्यता गर्नुहोस्।
- **Localhost बाइन्डिङ**: स्थानीय विकासकालागि सर्भरहरूलाई `localhost` मा बाइन्ड गर्नुहोस् ताकि ती सार्वजनिक इन्टरनेटमा खुल्ला नहोस्।
- **प्रमाणीकरण**: उत्पादन परिनियोजनको लागि प्रमाणीकरण लागू गर्नुहोस् (जस्तै API कुञ्जीहरू, OAuth)।
- **CORS**: पहुँच सीमित गर्न Cross-Origin Resource Sharing (CORS) नीति कन्फिगर गर्नुहोस्।
- **HTTPS**: यातायात एन्क्रिप्ट गर्न उत्पादनमा HTTPS प्रयोग गर्नुहोस्।

### सर्वोत्तम अभ्यासहरू

थप रूपमा, यहाँ तपाईंको MCP स्ट्रिमिङ सर्भरमा सुरक्षा लागू गर्दा पालन गर्नुपर्ने केही सर्वोत्तम अभ्यासहरू छन्:

- बिना मान्यता प्राप्त आउने अनुरोधहरूलाई कहिल्यै विश्वास नगर्नुहोस्।
- सबै पहुँच र त्रुटिहरू लग र निगरानी गर्नुहोस्।
- सुरक्षा कमजोरी मेटाउन आवधिक रूपमा निर्भरता अद्यावधिक गर्नुहोस्।

### चुनौतीहरू

MCP स्ट्रिमिङ सर्भरहरूमा सुरक्षा लागू गर्दा तपाईंले केहि चुनौतीहरूको सामना गर्नुहुनेछ:

- विकासको सहजता र सुरक्षाबीच सन्तुलन मिलाउन
- विभिन्न क्लाइन्ट वातावरणहरूसँग अनुकूलता सुनिश्चित गर्न


## SSE बाट Streamable HTTP मा उन्नयन

हाल Server-Sent Events (SSE) प्रयोग गर्ने अनुप्रयोगहरूका लागि, Streamable HTTP मा माइग्रेट गर्दा तपाईंको MCP कार्यान्वयनहरूका लागि सुधारिएको क्षमता र दीर्घकालीन दिगोपन प्रदान गर्दछ।

### किन उन्नयन गर्ने?

SSE बाट Streamable HTTP मा उन्नयन गर्न दुई प्रेरक कारणहरू छन्:

- Streamable HTTP ले SSE भन्दा राम्रो स्केलेबिलिटी, अनुकूलता, र समृद्ध सूचना समर्थन प्रदान गर्दछ।
- यो नयाँ MCP अनुप्रयोगहरूको लागि सिफारिस गरिएको ट्रान्सपोर्ट हो।

### माइग्रेशन चरणहरू

MCP अनुप्रयोगहरूमा SSE बाट Streamable HTTP मा कसरी माइग्रेट गर्ने यहाँ छ:

- `mcp.run()` मा `transport="streamable-http"` प्रयोग गर्न सर्भर कोड अपडेट गर्नुहोस्।
- SSE क्लाइन्टको सट्टा `streamablehttp_client` प्रयोग गर्न क्लाइन्ट कोड अपडेट गर्नुहोस्।
- सूचना प्रशोधन गर्न क्लाइन्टमा मेसेज ह्यान्डलर लागू गर्नुहोस्।
- अवस्थित उपकरण र वर्कफ्लोहरूसँग अनुकूलता परीक्षण गर्नुहोस्।

### अनुकूलता कायम राख्नु

माइग्रेशन प्रक्रियाको समयमा अवस्थित SSE क्लाइन्टहरू सँगको अनुकूलता कायम राख्न सिफारिस गरिन्छ। यहाँ केहि रणनीतिहरू छन्:

- तपाईंले फरक एन्डपोइन्टहरूमा दुबै SSE र Streamable HTTP ट्रान्सपोर्टहरू चलाएर दुवैलाई समर्थन गर्न सक्नुहुन्छ।
- क्लाइन्टहरूलाई नयाँ ट्रान्सपोर्टमा क्रमिक रूपमा माइग्रेट गर्नुहोस्।

### चुनौतीहरू

माइग्रेशनको क्रममा निम्न चुनौतीहरू समाधान गर्नुहोस्:

- सबै क्लाइन्टहरूलाई अपडेट गरिएको सुनिश्चित गर्नुहोस्
- सूचना वितरणमा फरकहरूलाई व्यवहार गर्नुहोस्

### कार्य: तपाईँको आफ्नै स्ट्रिमिङ MCP एप निर्माण गर्नुहोस्

**परिदृश्य:**
एउटा MCP सर्भर र क्लाइन्ट बनाउनुहोस् जहाँ सर्भरले वस्तुहरू (जस्तै फाइलहरू वा कागजातहरू) को सूची प्रक्रिया गरी प्रत्येक वस्तुका लागि सूचना पठाउँछ। क्लाइन्टले आइपुग्ने प्रत्येक सूचना देखाउनुपर्छ।

**चरणहरू:**

1. वस्तुहरूको सूची प्रक्रिया गर्ने र प्रत्येक वस्तुको लागि सूचना पठाउने सर्भर उपकरण लागू गर्नुहोस्।
2. सूचना वास्तविक समयमा देखाउन मेसेज ह्यान्डलर भएको क्लाइन्ट लागू गर्नुहोस्।
3. दुवै सर्भर र क्लाइन्ट चलाएर तपाइँको कार्यान्वयन परीक्षण गर्नुहोस् र सूचनाहरू अवलोकन गर्नुहोस्।
