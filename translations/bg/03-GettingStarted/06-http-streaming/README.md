## Транспортни механизми и поточно предаване в MCP

Този раздел разглежда различните транспортни механизми, налични в MCP, и тяхната роля за поддържане на възможности за поточно предаване за комуникация в реално време между клиенти и сървъри.

### Какво е транспортен механизъм?

Транспортният механизъм определя как се обменят данни между клиента и сървъра. MCP поддържа няколко вида транспорт, подходящи за различни среди и изисквания:

- **stdio**: Стандартен вход/изход, подходящ за локални и CLI-базирани инструменти. Прост, но не подходящ за уеб или облак.
- **HTTP+SSE**: Наследен отдалечен транспорт, декларирано изведен от MCP `2025-03-26`
    и заменен от Streamable HTTP. Не го използвайте за нови имплементации.
- **Streamable HTTP**: Модерен HTTP базиран поточен транспорт, поддържащ известия и по-добра мащабируемост. Препоръчва се за повечето продукционни и облачни сценарии.

### Таблица за сравнение

Вижте таблицата за сравнение по-долу, за да разберете разликите между тези транспортни механизми:

| Транспорт | Статус | Известия | Типична употреба |
|---|---|---|---|
| stdio | Текущ | Да | Локални под-процеси |
| HTTP+SSE | Изведен от употреба | Да | Наследени отдалечени имплементации |
| Streamable HTTP | Текущ | Да | Отдалечени и облачни сървъри |

> **Съвет:** Изборът на правилния транспорт влияе на производителността, мащабируемостта и потребителското изживяване. **Streamable HTTP** се препоръчва за модерни, мащабируеми и готови за облак приложения.

Стандартните транспортни механизми са stdio и Streamable HTTP. HTTP+SSE се среща само в
по-стари примери.

## Поточно предаване: Концепции и мотивация

Разбирането на основните концепции и мотивации зад поточното предаване е от съществено значение за реализиране на ефективни комуникационни системи в реално време.

**Поточно предаване** е техника в мрежовото програмиране, която позволява данните да се изпращат и получават на малки, управляеми парчета или като серия от събития, вместо да се чака цял отговор да е готов. Това е особено полезно за:

- Големи файлове или набори от данни.
- Актуализации в реално време (например чат, ленти за напредък).
- Дългосрочни изчисления, при които искате да държите потребителя информиран.

Ето какво трябва да знаете за поточното предаване на високо ниво:

- Данните се доставят постепенно, а не наведнъж.
- Клиентът може да обработва данните, докато пристигат.
- Намалява възприеманата латентност и подобрява изживяването на потребителя.

### Защо да използваме поточно предаване?

Причините за използване на поточно предаване са следните:

- Потребителите получават обратна връзка незабавно, не само в края
- Позволява приложения в реално време и отзивчиви потребителски интерфейси
- По-ефикасно използване на мрежови и изчислителни ресурси

### Прост пример: Поточен HTTP сървър и клиент

Ето един прост пример за това как може да се реализира поточно предаване:

#### Python

**Сървър (Python, използвайки FastAPI и StreamingResponse):**

```python
from fastapi import FastAPI
from fastapi.responses import StreamingResponse
import time

app = FastAPI()

async def event_stream():
    for i in range(1, 6):
        yield f"data: Message {i}\n\n"
        time.sleep(1)

@app.get("/stream")
def stream():
    return StreamingResponse(event_stream(), media_type="text/event-stream")
```

**Клиент (Python, използвайки requests):**

```python
import requests

with requests.get("http://localhost:8000/stream", stream=True) as r:
    for line in r.iter_lines():
        if line:
            print(line.decode())
```

Този пример показва сървър, който изпраща серия от съобщения към клиента, докато те стават налични, вместо да чака всички съобщения да бъдат готови.

**Как работи:**

- Сървърът доставя всяко съобщение веднага щом е готово.
- Клиентът получава и отпечатва всяко парче при пристигането му.

**Изисквания:**

- Сървърът трябва да използва поточен отговор (например `StreamingResponse` във FastAPI).
- Клиентът трябва да обработва отговора като поток (`stream=True` в requests).
- Content-Type обикновено е `text/event-stream` или `application/octet-stream`.

#### Java

**Сървър (Java, използвайки Spring Boot и Server-Sent Events):**

```java
@RestController
public class CalculatorController {

    @GetMapping(value = "/calculate", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    public Flux<ServerSentEvent<String>> calculate(@RequestParam double a,
                                                   @RequestParam double b,
                                                   @RequestParam String op) {
        
        double result;
        switch (op) {
            case "add": result = a + b; break;
            case "sub": result = a - b; break;
            case "mul": result = a * b; break;
            case "div": result = b != 0 ? a / b : Double.NaN; break;
            default: result = Double.NaN;
        }

        return Flux.<ServerSentEvent<String>>just(
                    ServerSentEvent.<String>builder()
                        .event("info")
                        .data("Calculating: " + a + " " + op + " " + b)
                        .build(),
                    ServerSentEvent.<String>builder()
                        .event("result")
                        .data(String.valueOf(result))
                        .build()
                )
                .delayElements(Duration.ofSeconds(1));
    }
}
```

**Клиент (Java, използвайки Spring WebFlux WebClient):**

```java
@SpringBootApplication
public class CalculatorClientApplication implements CommandLineRunner {

    private final WebClient client = WebClient.builder()
            .baseUrl("http://localhost:8080")
            .build();

    @Override
    public void run(String... args) {
        client.get()
                .uri(uriBuilder -> uriBuilder
                        .path("/calculate")
                        .queryParam("a", 7)
                        .queryParam("b", 5)
                        .queryParam("op", "mul")
                        .build())
                .accept(MediaType.TEXT_EVENT_STREAM)
                .retrieve()
                .bodyToFlux(String.class)
                .doOnNext(System.out::println)
                .blockLast();
    }
}
```

**Забележки за имплементация в Java:**

- Използва реактивния стек на Spring Boot с `Flux` за поточно предаване
- `ServerSentEvent` предоставя структурирано поточно предаване на събития с типове събития
- `WebClient` с `bodyToFlux()` позволява реактивна консумация на потока
- `delayElements()` симулира време за обработка между събитията
- Събитията могат да имат типове (`info`, `result`) за по-добро управление от клиента

### Сравнение: Класическо поточно предаване срещу Поточно предаване в MCP

Разликите между начина на работа на поточно предаване по "класически" начин спрямо как работи в MCP могат да се представят така:

| Функция               | Класическо HTTP поточно предаване   | MCP Поточно предаване (Известия)     |
|------------------------|-------------------------------|-------------------------------------|
| Основен отговор       | На части (chunked)             | Единствен, в края                    |
| Актуализации за напредък | Изпращат се като части данни   | Изпращат се като известия           |
| Изисквания към клиента | Трябва да обработва потока     | Трябва да реализира обработчик на съобщения |
| Употреба              | Големи файлове, AI токен потоци | Напредък, логове, обратна връзка в реално време |

### Наблюдавани ключови разлики

Освен това, ето някои ключови разлики:

- **Модел на комуникация:**
  - Класическо HTTP поточно предаване: Използва просто кодиране на пренасяне на части за изпращане на данни на части
  - MCP поточно предаване: Използва структуриран известителен механизъм с JSON-RPC протокол

- **Формат на съобщението:**
  - Класическо HTTP: Обикновени текстови части с нови редове
  - MCP: Структурирани LoggingMessageNotification обекти с метаданни

- **Имплементация на клиента:**
  - Класическо HTTP: Прост клиент, който обработва поточни отговори
  - MCP: По-сложен клиент с обработчик на съобщения за обработка на различни типове съобщения

- **Актуализации за напредък:**
  - Класическо HTTP: Напредъкът е част от основния поток на отговора
  - MCP: Напредъкът се изпраща чрез отделни известителни съобщения, докато основният отговор идва в края

### Препоръки

Има някои неща, които препоръчваме при избора между реализиране на класическо поточно предаване (като крайна точка, която ви показахме по-горе с `/stream`) спрямо използване на поточно предаване чрез MCP.

- **За прости нужди от поточно предаване:** Класическото HTTP поточно предаване е по-просто за реализиране и е достатъчно за основни нужди от поточно предаване.


- **За сложни, интерактивни приложения:** MCP стриймингът предоставя по-структуриран подход с по-богати метаданни и разделяне между уведомления и крайни резултати.

- **За AI приложения:** системата за уведомления на MCP е особено полезна за дълготрайни AI задачи, при които искате да държите потребителите информирани за напредъка.

## Стрийминг в MCP

Добре, вече видяхте някои препоръки и сравнения за разликата между класическия стрийминг и стрийминга в MCP. Нека преминем към детайлно обяснение как точно можете да използвате стрийминг в MCP.

Разбирането как работи стрийминга в рамките на MCP е от съществено значение за създаването на отзивчиви приложения, които предоставят обратна връзка в реално време на потребителите по време на дълготрайни операции.

В MCP стриймингът не се състои в изпращане на основния отговор на части, а в изпращане на **уведомления** към клиента, докато инструментът обработва заявката. Тези уведомления могат да включват актуализации на напредъка, логове или други събития.

### Как работи

Основният резултат все още се изпраща като един отговор. Въпреки това, уведомленията могат да се изпращат като отделни съобщения по време на обработката и по този начин актуализират клиента в реално време. Клиентът трябва да може да обработва и показва тези уведомления.

### По избор: свържете се с хостван MCP сървър

Можете също да използвате Streamable HTTP без да стартирате локален сървър. Този пример
се свързва с [Parallel Search MCP](https://docs.parallel.ai/integrations/mcp/search-mcp),
открива неговите инструменти и търси публична MCP документация, използвайки същия
Python SDK както [локалния клиент](../../../../03-GettingStarted/06-http-streaming/solution/python/client.py).

Анонимната крайна точка на Parallel не изисква акаунт или API ключ. Безплатният достъп е
ограничен по честота на заявките. Изпълнението на този скрипт изпраща търсещите заявки, целта и
случаен идентификатор на сесия към Parallel. Услугата предлага и `web_fetch`,
който изпраща исканите URL адреси и предоставения контекст към Parallel. Използвайте публична
информация за това упражнение; вижте нейните [условия](https://parallel.ai/customer-terms)
и [политика за поверителност](https://parallel.ai/privacy-policy).

С Python 3.10 или по-нова версия и активирана виртуална среда, инсталирайте SDK:

```sh
python -m pip install "mcp>=1.10,<2"
```

Запазете го като `hosted_search.py` и стартирайте с `python hosted_search.py`:

```python
import asyncio
from uuid import uuid4

from mcp import ClientSession
from mcp.client.streamable_http import streamablehttp_client


async def main() -> None:
    session_id = str(uuid4())
    async with streamablehttp_client("https://search.parallel.ai/mcp") as (
        read_stream,
        write_stream,
        _,
    ):
        async with ClientSession(read_stream, write_stream) as session:
            await session.initialize()
            tools = await session.list_tools()
            print("Available tools:", [tool.name for tool in tools.tools])

            result = await session.call_tool(
                "web_search",
                {
                    "objective": "Find the official MCP Streamable HTTP documentation",
                    "search_queries": ["MCP Streamable HTTP documentation"],
                    "session_id": session_id,
                },
            )
            if result.isError:
                raise RuntimeError(f"Search tool failed: {result.content}")
            for block in result.content:
                if block.type == "text":
                    print(block.text)


async def run() -> None:
    await asyncio.wait_for(main(), timeout=60)


if __name__ == "__main__":
    asyncio.run(run())
```

Очаквайте откритието да включва `web_search` и `web_fetch`, последвано от отговор с търсене,
съдържащ източници и откъси. Резултатите могат да варират или да са празни.
Скриптът проверява `isError`, защото инструмент може да се провали дори при успешна HTTP заявка.
Ако достъпът е ограничен по честота, изчакайте преди да опитате отново. Използвайте същия
`session_id`, ако разширите скрипта с допълнителни свързани търсения или извличания.

Streamable HTTP позволява както JSON, така и SSE отговори; този сървър може да върне
цялостен JSON резултат без уведомления за напредък. SDK обработва
транспортирането. Продължете с локалния пример по-долу, за да научите за уведомленията.
Този по избор скрипт прави едно експлицитно търсене и затваря връзката си при
завършване. Ако по-късно изложите тези инструменти на агент, агентът може да ги повика
по време на работата си; третирайте получения уеб текст като ненадеждни данни.

## Какво е уведомление?

Казахме "Уведомление", какво означава това в контекста на MCP?

Уведомление е JSON-RPC съобщение, което няма `id` и не
получава отговор. MCP използва уведомления за напредък, отказ и
други еднопосочни събития.

В MCP `2025-11-25`, клиент изпраща `notifications/initialized` след 

инициализационно ръкостискане. MCP `2026-07-28` няма инициализационно ръкостискане, така че
това известие е наследено поведение.

Известието изглежда така като JSON съобщение:

```json
{
  jsonrpc: "2.0";
  method: string;
  params?: {
    [key: string]: unknown;
  };
}
```

Логирането е една от функциите, която използва известия; самите известия са
общ тип съобщение JSON-RPC.

> **Отменено в MCP `2026-07-28`:** функцията Логиране остава налична
> за съвместимост, но подлежи на премахване в първия преглед на спецификацията,
> издаден на или след 28 юли 2027 г. Новите реализации трябва да използват
> `stderr` със stdio или OpenTelemetry за структурирана наблюдаемост.

За наследена реализация `2025-11-25` сървърът активира възможността за Логиране
по следния начин:

```json
{
  "capabilities": {
    "logging": {}
  }
}
```

> [!NOTE]
> В зависимост от използвания SDK, логването може да е активирано по подразбиране или може да се наложи да го активирате експлицитно във вашата конфигурация на сървъра.

Има различни типове известия:

| Ниво     | Описание                   | Примерен случай на използване       |
|----------|----------------------------|------------------------------------|
| debug    | Детайлна информация за отстраняване на грешки | Точки на влизане/излизане от функция |
| info     | Общи информативни съобщения | Актуализации на прогреса на операцията |
| notice   | Нормални, но значими събития | Промени в конфигурацията            |
| warning  | Предупредителни състояния  | Използване на остаряла функция      |
| error    | Грешки                    | Провали на операция                |
| critical | Критични състояния        | Провали на системни компоненти      |
| alert    | Трябва да се предприеме незабавно действие | Открито коруптиране на данни      |
| emergency| Системата е неизползваема | Пълен системен отказ               |

## Имплементиране на Известия в MCP

За да имплементирате известия в MCP, трябва да настроите както сървърната, така и клиентската страна за обработка на актуализации в реално време. Това позволява на вашето приложение да предоставя незабавна обратна връзка на потребителите по време на дълги операции.

### Сървърна страна: Изпращане на Известия

Нека започнем със сървърната страна. В MCP вие дефинирате инструменти, които могат да изпращат известия по време на обработка на заявки. Сървърът използва обекта контекст (обикновено `ctx`), за да изпраща съобщения към клиента.

#### Python

```python
@mcp.tool(description="A tool that sends progress notifications")
async def process_files(message: str, ctx: Context) -> TextContent:
    await ctx.info("Processing file 1/3...")
    await ctx.info("Processing file 2/3...")
    await ctx.info("Processing file 3/3...")
    return TextContent(type="text", text=f"Done: {message}")
```

В предходния пример, инструментът `process_files` изпраща три известия към клиента, докато обработва всеки файл. Методът `ctx.info()` се използва за изпращане на информационни съобщения.

Освен това, за да активирате известия, уверете се, че вашият сървър използва стрийминг транспорт (като `streamable-http`) и че клиентът ви имплементира обработчик на съобщения за обработка на известията. Ето как можете да настроите сървъра да използва транспорта `streamable-http`:

```python
mcp.run(transport="streamable-http")
```

#### .NET

```csharp
[Tool("A tool that sends progress notifications")]
public async Task<TextContent> ProcessFiles(string message, ToolContext ctx)
{
    await ctx.Info("Processing file 1/3...");
    await ctx.Info("Processing file 2/3...");
    await ctx.Info("Processing file 3/3...");
    return new TextContent
    {
        Type = "text",
        Text = $"Done: {message}"
    };
}
```

В този пример за .NET, инструментът `ProcessFiles` е декориран с атрибута `Tool` и изпраща три известия към клиента, докато обработва всеки файл. Методът `ctx.Info()` се използва за изпращане на информационни съобщения.

За да активирате известия във вашия .NET MCP сървър, уверете се, че използвате стрийминг транспорт:

```csharp
var builder = McpBuilder.Create();
await builder
    .UseStreamableHttp() // Enable streamable HTTP transport
    .Build()
    .RunAsync();
```

### Клиентска страна: Получаване на Известия

Клиентът трябва да имплементира обработчик на съобщения, за да обработва и показва известията веднага щом пристигнат.

#### Python

```python
async def message_handler(message):
    if isinstance(message, types.ServerNotification):
        print("NOTIFICATION:", message)
    else:
        print("SERVER MESSAGE:", message)

async with ClientSession(
   read_stream, 
   write_stream,
   logging_callback=logging_collector,
   message_handler=message_handler,
) as session:
```


В предходния код, функцията `message_handler` проверява дали входящото съобщение е уведомление. Ако е така, отпечатва уведомлението; в противен случай го обработва като обикновено сървърно съобщение. Също така обърнете внимание как `ClientSession` е инициализиран с `message_handler` за обработка на входящи уведомления. 

#### .NET

```csharp
// Define a message handler
void MessageHandler(IJsonRpcMessage message)
{
    if (message is ServerNotification notification)
    {
        Console.WriteLine($"NOTIFICATION: {notification}");
    }
    else
    {
        Console.WriteLine($"SERVER MESSAGE: {message}");
    }
}

// Create and use a client session with the message handler
var clientOptions = new ClientSessionOptions
{
    MessageHandler = MessageHandler,
    LoggingCallback = (level, message) => Console.WriteLine($"[{level}] {message}")
};

using var client = new ClientSession(readStream, writeStream, clientOptions);
await client.InitializeAsync();

// Now the client will process notifications through the MessageHandler
```


В този пример за .NET, функцията `MessageHandler` проверява дали входящото съобщение е уведомление. Ако е, отпечатва уведомлението; в противен случай го обработва като обикновено съобщение от сървъра. `ClientSession` се инициализира с обработчика на съобщения чрез `ClientSessionOptions`.

За да активирате уведомленията, уверете се, че вашият сървър използва стрийминг транспорт (като `streamable-http`), а клиентът ви реализира обработчик на съобщения за обработка на уведомления.

## Уведомления за напредъка и сценарии

Този раздел обяснява концепцията за уведомления за напредъка в MCP, защо са важни и как да ги имплементирате с помощта на Streamable HTTP. Ще намерите и практическо задание, за да затвърдите разбирането си.

Уведомленията за напредъка са съобщения в реално време, изпратени от сървъра към клиента по време на дълги операции. Вместо да чакате цялата обработка да завърши, сървърът поддържа клиента актуализиран за текущия статус. Това повишава прозрачността, потребителското преживяване и улеснява отстраняването на грешки.

**Пример:**

```text

"Processing document 1/10"
"Processing document 2/10"
...
"Processing complete!"

```

### Защо да използвате уведомления за напредъка?

Уведомленията за напредъка са важни по няколко причини:

- **По-добро потребителско преживяване:** Потребителите виждат актуализации, докато работата напредва, а не само в края.
- **Обратна връзка в реално време:** Клиентите могат да показват ленти за напредъка или журнали, което прави приложението по-отзивчиво.
- **По-лесно отстраняване на грешки и мониторинг:** Разработчиците и потребителите могат да видят къде даден процес се забавя или е блокиран.

### Как да имплементирате уведомления за напредъка

Ето как можете да имплементирате уведомления за напредъка в MCP:

- **На сървъра:** Използвайте `ctx.info()` или `ctx.log()`, за да изпращате уведомления, докато обработвате всеки елемент. Това изпраща съобщение към клиента преди основния резултат да е готов.
- **На клиента:** Имплементирайте обработчик на съобщения, който слуша и показва уведомления, щом пристигнат. Този обработчик разграничaва уведомленията и крайния резултат.

**Пример за сървър:**

#### Python

```python
@mcp.tool(description="A tool that sends progress notifications")
async def process_files(message: str, ctx: Context) -> TextContent:
    for i in range(1, 11):
        await ctx.info(f"Processing document {i}/10")
    await ctx.info("Processing complete!")
    return TextContent(type="text", text=f"Done: {message}")
```

**Пример за клиент:**

#### Python

```python
async def message_handler(message):
    if isinstance(message, types.ServerNotification):
        print("NOTIFICATION:", message)
    else:
        print("SERVER MESSAGE:", message)
```

## Съображения за сигурността

Сигурността трябва да е основен приоритет при имплементиране на всеки сървър, особено когато използвате HTTP базирани транспортни технологии като Streamable HTTP в MCP.

При имплементиране на MCP сървъри с HTTP базирани транспорти, сигурността се превръща в ключов въпрос, който изисква внимание към множество вектори на атака и механизми за защита.

### Обзор

Сигурността е критична при откриване на MCP сървъри през HTTP. Streamable HTTP въвежда нови потенциални врати за атаки и изисква внимателна конфигурация.

Ето някои ключови съображения за сигурността:

- **Валидация на Origin заглавката**: Винаги валидирайте `Origin` заглавката, за да предотвратите атаки чрез DNS ребайндъри.
- **Локално свързване (localhost):** За локална разработка, свързвайте сървърите на `localhost`, за да избегнете излагане към публичния интернет.
- **Автентикация:** Имплементирайте автентикация (например API ключове, OAuth) за продукционни среди.
- **CORS:** Конфигурирайте политики за Cross-Origin Resource Sharing (CORS), за да ограничите достъпа.
- **HTTPS:** Използвайте HTTPS в продукция, за да криптирате трафика.

### Най-добри практики

Освен това, ето някои най-добри практики за сигурност при имплементирането на MCP стрийминг сървър:

- Никога не се доверявайте на входящи заявки без валидиране.
- Регистрирайте и следете целия достъп и грешки.
- Редовно обновявайте зависимости, за да запушвате уязвимости.

### Предизвикателства

Ще срещнете някои предизвикателства при имплементацията на сигурност в MCP стрийминг сървъри:

- Балансиране на сигурността с лекотата на разработка
- Осигуряване на съвместимост с различни клиентски среди


## Надграждане от SSE към Streamable HTTP

За приложения, които в момента използват Server-Sent Events (SSE), миграцията към Streamable HTTP осигурява разширени възможности и по-добра дългосрочна устойчивост за вашите MCP имплементации.

### Защо да надграждате?

Има две силни причини да надградите от SSE към Streamable HTTP:

- Streamable HTTP предлага по-добра мащабируемост, съвместимост и по-богата поддръжка на уведомления спрямо SSE.
- Това е препоръчителният транспорт за нови MCP приложения.

### Стъпки при миграция

Ето как да мигрирате от SSE към Streamable HTTP в MCP приложенията си:

- **Актуализирайте сървърния код**, за да използва `transport="streamable-http"` в `mcp.run()`.
- **Актуализирайте клиентския код**, за да използва `streamablehttp_client` вместо SSE клиент.
- **Имплементирайте обработчик на съобщения** в клиента за обработка на уведомления.
- **Тествайте съвместимостта** с настоящи инструменти и работни процеси.

### Поддържане на съвместимост

Препоръчва се да поддържате съвместимост със съществуващите SSE клиенти по време на миграцията. Ето някои стратегии:

- Можете да поддържате и SSE, и Streamable HTTP като пускате и двата транспорта на различни крайни точки.
- Преминавайте постепенно клиентите към новия транспорт.

### Предизвикателства

Уверете се, че адресирате следните предизвикателства по време на миграцията:

- Обновяване на всички клиенти
- Обработка на разлики в доставката на уведомления
