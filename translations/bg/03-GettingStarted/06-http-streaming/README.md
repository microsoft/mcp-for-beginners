# HTTPS поточно предаване с протокол Model Context Protocol (MCP)

Тази глава предоставя изчерпателно ръководство за реализиране на сигурно, мащабируемо и в реално време поточно предаване с помощта на Model Context Protocol (MCP) чрез HTTPS. Обхваща мотивацията за поточното предаване, наличните механизми за транспорт, как да се реализира стрийминг HTTP в MCP, добри практики за сигурност, миграция от SSE и практическо ръководство за изграждането на собствени стрийминг MCP приложения.

> **Поглеждайки напред:** този урок описва Streamable HTTP по **MCP Specification 2025-11-25**, където сесията се установява по време на `initialize` и се фиксира с хедър `Mcp-Session-Id`. Кандидатът за издание `2026-07-28` премахва напълно ръкостискането и идентификатора на сесията, което прави всяка заявка самостоятелна и адресируема към всеки сървър без нужда от запазени сесии. ## Механизми за транспорт и стрийминг в MCP

Този раздел разглежда различните механизми за транспорт налични в MCP и тяхната роля в осигуряването на възможности за стрийминг за комуникация в реално време между клиенти и сървъри.

### Какво е транспортен механизъм?

Транспортен механизъм определя как данните се обменят между клиента и сървъра. MCP поддържа няколко типа транспорт, за да отговаря на различни среди и изисквания:

- **stdio**: Стандартен вход/изход, подходящ за локални инструменти и базирани на CLI. Прост, но не е подходящ за уеб или облак.
- **SSE (Server-Sent Events)**: Позволява на сървърите да изпращат актуализации в реално време към клиентите през HTTP. Добър за уеб UI, но с ограничена мащабируемост и гъвкавост. От MCP Specification 2025-06-18 самостоятелният SSE транспорт е отпаднал и заменен от транспорт "Streamable HTTP".
- **Streamable HTTP**: Модерен стрийминг транспорт базиран на HTTP, поддържащ известия и по-добра мащабируемост. Препоръчва се за повечето продукционни и облачни сценарии.

### Таблица за сравнение

Вижте таблицата за сравнение по-долу за да разберете разликите между тези транспортни механизми:

| Транспорт         | Актуализации в реално време | Стрийминг | Мащабируемост | Приложение           |
|-------------------|-----------------------------|-----------|---------------|----------------------|
| stdio             | Не                          | Не        | Ниска         | Локални CLI инструменти |
| SSE               | Да                          | Да        | Средна        | Уеб, актуализации в реално време |
| Streamable HTTP   | Да                          | Да        | Висока        | Облак, многоклиентска среда |

> **Съвет:** Изборът на подходящ транспорт влияе върху производителността, мащабируемостта и потребителския опит. **Streamable HTTP** се препоръчва за модерни, мащабируеми и готови за облак приложения.

Обърнете внимание на транспортите stdio и SSE, които бяха показани в предходните глави, и как стрийминг HTTP е транспортът, разгледан в тази глава.

## Поточно предаване: понятия и мотивация

Разбирането на основните концепции и мотивации зад стрийминга е ключово за реализиране на ефективни комуникационни системи в реално време.

**Поточно предаване** е техника в мрежовото програмиране, която позволява данните да се изпращат и получават на малки, управляеми порции или като поредица от събития, вместо да се чака цял отговор да е готов. Това е особено полезно при:

- Големи файлове или набори от данни.
- Актуализации в реално време (напр. чат, ленти за прогрес).
- Продължителни изчисления, при които искате да информирате потребителя.

Ето какво трябва да знаете за стрийминга на високо ниво:

- Данните се доставят прогресивно, не наведнъж.
- Клиентът може да обработва данните веднага щом пристигнат.
- Намалява възприеманото закъснение и подобрява потребителския опит.

### Защо да използваме стрийминг?

Причините за използване на стрийминг са следните:

- Потребителите получават обратна връзка веднага, не само в края.
- Позволява приложения в реално време и отзивчиви UI.
- По-ефективно използване на мрежовите и изчислителни ресурси.

### Прост пример: HTTP стрийминг сървър и клиент

Ето един прост пример как може да се реализира стрийминг:

#### Python

**Сървър (Python, използващ FastAPI и StreamingResponse):**

```python
from fastapi import FastAPI
from fastapi.responses import StreamingResponse
import time

app = FastAPI()

async def event_stream():
    for i in range(1, 6):
        yield f"data: Message {i}\n\n"
        time.sleep(1)

@app.get("/stream")
def stream():
    return StreamingResponse(event_stream(), media_type="text/event-stream")
```

**Клиент (Python, използващ requests):**

```python
import requests

with requests.get("http://localhost:8000/stream", stream=True) as r:
    for line in r.iter_lines():
        if line:
            print(line.decode())
```

Този пример показва сървър, който изпраща серия от съобщения към клиента веднага щом са налични, вместо да чака всичко да се подготви.

**Как работи:**

- Сървърът отдава всяко съобщение веднага щом е готово.
- Клиентът получава и отпечатва всяка порция веднага щом пристигне.

**Изисквания:**

- Сървърът трябва да използва стрийминг отговор (напр. `StreamingResponse` във FastAPI).
- Клиентът трябва да обработва отговора като поток (`stream=True` в requests).
- Content-Type обикновено е `text/event-stream` или `application/octet-stream`.

#### Java

**Сървър (Java, използващ Spring Boot и Server-Sent Events):**

```java
@RestController
public class CalculatorController {

    @GetMapping(value = "/calculate", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    public Flux<ServerSentEvent<String>> calculate(@RequestParam double a,
                                                   @RequestParam double b,
                                                   @RequestParam String op) {
        
        double result;
        switch (op) {
            case "add": result = a + b; break;
            case "sub": result = a - b; break;
            case "mul": result = a * b; break;
            case "div": result = b != 0 ? a / b : Double.NaN; break;
            default: result = Double.NaN;
        }

        return Flux.<ServerSentEvent<String>>just(
                    ServerSentEvent.<String>builder()
                        .event("info")
                        .data("Calculating: " + a + " " + op + " " + b)
                        .build(),
                    ServerSentEvent.<String>builder()
                        .event("result")
                        .data(String.valueOf(result))
                        .build()
                )
                .delayElements(Duration.ofSeconds(1));
    }
}
```

**Клиент (Java, използващ Spring WebFlux WebClient):**

```java
@SpringBootApplication
public class CalculatorClientApplication implements CommandLineRunner {

    private final WebClient client = WebClient.builder()
            .baseUrl("http://localhost:8080")
            .build();

    @Override
    public void run(String... args) {
        client.get()
                .uri(uriBuilder -> uriBuilder
                        .path("/calculate")
                        .queryParam("a", 7)
                        .queryParam("b", 5)
                        .queryParam("op", "mul")
                        .build())
                .accept(MediaType.TEXT_EVENT_STREAM)
                .retrieve()
                .bodyToFlux(String.class)
                .doOnNext(System.out::println)
                .blockLast();
    }
}
```

**Бележки за Java реализация:**

- Използва реактивния стек на Spring Boot с `Flux` за стрийминг
- `ServerSentEvent` предоставя структуриран стрийминг на събития с типове събития
- `WebClient` с `bodyToFlux()` позволява реактивно приемане на стрийминг
- `delayElements()` симулира време за обработка между събитията
- Събитията могат да имат типове (`info`, `result`) за по-добро обработване от клиента

### Сравнение: Класически стрийминг срещу MCP стрийминг

Разликите между начина, по който работи стриймингът "класически" и начина, по който работи в MCP, могат да бъдат илюстрирани така:

| Характеристика          | Класически HTTP стрийминг      | MCP стрийминг (Известия)        |
|------------------------|-------------------------------|---------------------------------|
| Основен отговор         | на парчета                     | Единен, в края                  |
| Актуализации на прогрес | Изпратени като данни на части  | Изпратени като известия         |
| Изисквания към клиента  | Трябва да обработва потока     | Трябва да имплементира обработчик на съобщения |
| Приложение             | Големи файлове, AI потоци от токени | Прогрес, лога, обратна връзка в реално време |

### Основни наблюдавани разлики

Освен това, ето някои ключови разлики:

- **Комуникационен модел:**
  - Класически HTTP стрийминг: Използва просто chunked transfer encoding за изпращане на данни на части
  - MCP стрийминг: Използва структурирана система за известия с JSON-RPC протокол

- **Формат на съобщенията:**
  - Класически HTTP: Обикновен текст на части с нови редове
  - MCP: Структурирани обекти LoggingMessageNotification с метаданни

- **Реализация на клиента:**
  - Класически HTTP: Прост клиент, който обработва стрийминг отговори
  - MCP: По-сложен клиент с обработчик на съобщения, който разбира различни типове съобщения

- **Актуализации на прогреса:**
  - Класически HTTP: Прогресът е част от основния поток на отговора
  - MCP: Прогресът се изпраща чрез отделни известителни съобщения, докато основният отговор идва накрая

### Препоръки

Ето някои препоръки, когато избирате между класически стрийминг (като крайна точка `/stream`, показана по-горе) и стрийминг чрез MCP.

- **За прости нужди от стрийминг:** Класическият HTTP стрийминг е по-лесен за имплементиране и достатъчен за базови нужди.

- **За сложни, интерактивни приложения:** MCP стрийминг предоставя структурирана система с богати метаданни и разделение между известия и крайни резултати.

- **За AI приложения:** Системата за известия на MCP е особено полезна при продължителни AI операции, когато искате да информирате потребителите за прогреса.

## Поточно предаване в MCP

Добре, видяхте някои препоръки и сравнения досега за разликата между класически стрийминг и стрийминг в MCP. Нека сега разгледаме подробно как точно можете да използвате стрийминг в MCP.

Разбирането на това как работи стриймингът в рамките на MCP е от съществено значение за създаване на отзивчиви приложения, които предоставят обратна връзка в реално време по време на дълготрайни операции.

В MCP, стриймингът не е за изпращане на основния отговор на части, а за изпращане на **известия** към клиента докато инструмент обработва заявка. Тези известия могат да включват актуализации на прогреса, логове или други събития.

### Как работи

Основният резултат все още се изпраща като единен отговор. Въпреки това, известията могат да се изпращат като отделни съобщения по време на обработката и по този начин да актуализират клиента в реално време. Клиентът трябва да може да обработва и показва тези известия.

## Какво е известие?

Споменахме "известие", какво означава това в контекста на MCP?

Известието е съобщение, изпратено от сървъра към клиента, за да информира за прогрес, статус или други събития по време на дълготрайна операция. Известието подобрява прозрачността и потребителското преживяване.

Например, клиентът би трябвало да изпрати известие веднага след като първоначалното ръкостискане със сървъра е извършено.

Известието изглежда така като JSON съобщение:

```json
{
  jsonrpc: "2.0";
  method: string;
  params?: {
    [key: string]: unknown;
  };
}
```

Известието се отнася до тема в MCP, наречена ["Logging"](https://modelcontextprotocol.io/specification/draft/server/utilities/logging).

> **Уведомление за отпадане:** Кандидатът за издание на MCP спецификацията `2026-07-28` отбелязва Logging примитива като отпаднал в полза на `stderr` за stdio транспортите и OpenTelemetry за структурирана наблюдаемост. Logging продължава да работи в `2025-11-25` и поне една година след официалното отпадане. Вижте [Какво се променя в MCP: Кандидат за издание 2026-07-28](../../01-CoreConcepts/mcp-2026-07-28-release-candidate.md).

За да работи логването, сървърът трябва да го активира като функция/възможност по следния начин:

```json
{
  "capabilities": {
    "logging": {}
  }
}
```

> [!NOTE]
> В зависимост от използвания SDK, логването може да бъде активно по подразбиране или да трябва да го активирате изрично в конфигурацията на сървъра.

Съществуват различни типове известия:

| Ниво      | Описание                      | Примерна употреба             |
|-----------|-------------------------------|------------------------------|
| debug     | Подробна отладъчна информация | Вход/изход на функция         |
| info      | Общи информационни съобщения  | Актуализации за прогрес       |
| notice    | Нормални, но значими събития  | Промени в конфигурацията      |
| warning   | Предупредителни условия       | Използване на отпаднала функция |
| error     | Грешки                       | Провали в операции            |
| critical  | Критични условия             | Повреди в системен компонент  |
| alert     | Трябва да се предприеме незабавно действие | Открита корупция на данни |
| emergency | Системата е неизползваема      | Пълна системна повреда        |

## Имплементиране на известия в MCP

За да имплементирате известия в MCP, трябва да настроите както сървърната, така и клиентската страна да обработват актуализации в реално време. Това позволява на вашето приложение да предоставя незабавна обратна връзка на потребителите по време на дълготрайни операции.

### Сървърна страна: Изпращане на известия

Нека започнем със сървърната страна. В MCP вие дефинирате инструменти, които могат да изпращат известия по време на обработка на заявки. Сървърът използва контекста (обикновено `ctx`), за да изпраща съобщения към клиента.

#### Python

```python
@mcp.tool(description="A tool that sends progress notifications")
async def process_files(message: str, ctx: Context) -> TextContent:
    await ctx.info("Processing file 1/3...")
    await ctx.info("Processing file 2/3...")
    await ctx.info("Processing file 3/3...")
    return TextContent(type="text", text=f"Done: {message}")
```

В предходния пример инструментът `process_files` изпраща три известия към клиента, докато обработва всеки файл. Методът `ctx.info()` се използва за изпращане на информационни съобщения.

Освен това, за да активирате известията, уверете се, че сървърът използва стрийминг транспорт (като `streamable-http`) и клиентът имплементира обработчик на съобщения за известия. Ето как можете да настроите сървъра да използва транспорт `streamable-http`:

```python
mcp.run(transport="streamable-http")
```

#### .NET

```csharp
[Tool("A tool that sends progress notifications")]
public async Task<TextContent> ProcessFiles(string message, ToolContext ctx)
{
    await ctx.Info("Processing file 1/3...");
    await ctx.Info("Processing file 2/3...");
    await ctx.Info("Processing file 3/3...");
    return new TextContent
    {
        Type = "text",
        Text = $"Done: {message}"
    };
}
```

В този .NET пример инструментът `ProcessFiles` е декориран с атрибута `Tool` и изпраща три известия към клиента при обработка на всеки файл. Методът `ctx.Info()` се използва за изпращане на информационни съобщения.

За да активирате известията във вашия .NET MCP сървър, уверете се, че използвате стрийминг транспорт:

```csharp
var builder = McpBuilder.Create();
await builder
    .UseStreamableHttp() // Enable streamable HTTP transport
    .Build()
    .RunAsync();
```

### Клиентска страна: Получаване на известия

Клиентът трябва да имплементира обработчик на съобщения, който да обработва и показва известията веднага щом пристигнат.

#### Python

```python
async def message_handler(message):
    if isinstance(message, types.ServerNotification):
        print("NOTIFICATION:", message)
    else:
        print("SERVER MESSAGE:", message)

async with ClientSession(
   read_stream, 
   write_stream,
   logging_callback=logging_collector,
   message_handler=message_handler,
) as session:
```

В предходния код функцията `message_handler` проверява дали полученото съобщение е известие. Ако е, го отпечатва; в противен случай го обработва като обикновено съобщение от сървъра. Обърнете внимание и как `ClientSession` се инициализира с `message_handler` за обработка на пристигащи известия.

#### .NET

```csharp
// Define a message handler
void MessageHandler(IJsonRpcMessage message)
{
    if (message is ServerNotification notification)
    {
        Console.WriteLine($"NOTIFICATION: {notification}");
    }
    else
    {
        Console.WriteLine($"SERVER MESSAGE: {message}");
    }
}

// Create and use a client session with the message handler
var clientOptions = new ClientSessionOptions
{
    MessageHandler = MessageHandler,
    LoggingCallback = (level, message) => Console.WriteLine($"[{level}] {message}")
};

using var client = new ClientSession(readStream, writeStream, clientOptions);
await client.InitializeAsync();

// Now the client will process notifications through the MessageHandler
```

В този .NET пример функцията `MessageHandler` проверява дали полученото съобщение е известие. Ако е, го отпечатва; в противен случай го обработва като обикновено съобщение от сървъра. `ClientSession` се инициализира с обработчика на съобщения чрез `ClientSessionOptions`.

За да активирате известия, уверете се, че сървърът използва стрийминг транспорт (като `streamable-http`) и клиентът имплементира обработчик на съобщения за известия.

## Известия за прогрес и сценарии

Този раздел обяснява концепцията за известия за прогрес в MCP, защо са важни и как да ги имплементирате с Streamable HTTP. Ще намерите и практическо задание за затвърждаване на разбирането.

Известията за прогрес са съобщения в реално време, изпращани от сървъра към клиента по време на дълготрайни операции. Вместо да се чака цялата процедура да приключи, сървърът поддържа клиента информиран за текущото състояние. Това подобрява прозрачността, потребителското изживяване и улеснява отстраняването на грешки.

**Пример:**

```text

"Processing document 1/10"
"Processing document 2/10"
...
"Processing complete!"

```

### Защо да използваме известия за прогрес?

Известията за прогрес са важни по няколко причини:

- **По-добро потребителско изживяване:** Потребителите виждат актуализации при напредъка на работата, не само накрая.
- **Обратна връзка в реално време:** Клиентите могат да показват ленти за прогрес или логове, което прави приложението по-отзивчиво.
- **По-лесно отстраняване на грешки и мониторинг:** Разработчиците и потребителите могат да виждат къде процесът се бави или е блокиран.

### Как да имплементирате известия за прогрес

Ето как можете да имплементирате известия за прогрес в MCP:

- **На сървъра:** Използвайте `ctx.info()` или `ctx.log()` за изпращане на известия докато всеки елемент се обработва. Това изпраща съобщение към клиента преди да е готов основният резултат.
- **На клиента:** Имплементирайте обработчик на съобщения, който слуша и показва известията веднага при пристигането им. Този обработчик различава известия от крайния резултат.

**Пример със сървър:**


#### Python

```python
@mcp.tool(description="A tool that sends progress notifications")
async def process_files(message: str, ctx: Context) -> TextContent:
    for i in range(1, 11):
        await ctx.info(f"Processing document {i}/10")
    await ctx.info("Processing complete!")
    return TextContent(type="text", text=f"Done: {message}")
```

**Пример за клиент:**

#### Python

```python
async def message_handler(message):
    if isinstance(message, types.ServerNotification):
        print("NOTIFICATION:", message)
    else:
        print("SERVER MESSAGE:", message)
```

## Съображения за сигурността

Сигурността трябва да бъде основен приоритет при имплементирането на всеки сървър, особено когато се използват базирани на HTTP трансфери като Streamable HTTP в MCP.

При имплементиране на MCP сървъри с HTTP-базирани трансфери, сигурността става основна грижа, която изисква внимателно отношение към множество вектори на атака и механизми за защита.

### Преглед

Сигурността е критична при експониране на MCP сървъри през HTTP. Streamable HTTP въвежда нови повърхности за атаки и изисква внимателна конфигурация.

Ето някои ключови съображения за сигурността:

- **Валидация на Origin хедъра**: Винаги валидирайте `Origin` хедъра, за да предотвратите DNS rebinding атаки.
- **Свързване към localhost**: За локално разработване свързвайте сървърите към `localhost`, за да избегнете експониране към публичния интернет.
- **Аутентикация**: Имплементирайте аутентикация (например API ключове, OAuth) за продукционни разгръщания.
- **CORS**: Конфигурирайте политиките за Cross-Origin Resource Sharing (CORS), за да ограничите достъпа.
- **HTTPS**: Използвайте HTTPS в продукция за криптиране на трафика.

### Най-добри практики

Освен това, ето някои най-добри практики, които да следвате при имплементиране на сигурност във вашия MCP стрийминг сървър:

- Никога не се доверявайте на постъпващи заявки без валидация.
- Водете лог и следете целия достъп и грешки.
- Редовно обновявайте зависимостите, за да поправите уязвимости в сигурността.

### Предизвикателства

Ще срещнете някои предизвикателства при имплементирането на сигурност в MCP стрийминг сървъри:

- Балансиране на сигурността с леснотата на разработка
- Осигуряване на съвместимост с различни клиентски среди


## Надграждане от SSE към Streamable HTTP

За приложения, които в момента използват Server-Sent Events (SSE), мигрирането към Streamable HTTP предоставя подобрени възможности и по-добра дългосрочна устойчивост за вашите MCP имплементации.

### Защо да надграждате?

Има две основателни причини да преминете от SSE към Streamable HTTP:

- Streamable HTTP предлага по-добра мащабируемост, съвместимост и по-богата поддръжка на уведомления в сравнение със SSE.
- Това е препоръчителният трансфер за нови MCP приложения.

### Стъпки за миграция

Ето как може да мигрирате от SSE към Streamable HTTP във вашите MCP приложения:

- **Обновете кода на сървъра** да използва `transport="streamable-http"` в `mcp.run()`.
- **Обновете кода на клиента** да използва `streamablehttp_client` вместо SSE клиент.
- **Имплементирайте обработчик на съобщения** в клиента за обработка на уведомления.
- **Тествайте за съвместимост** с налични инструменти и работни процеси.

### Поддържане на съвместимост

Препоръчително е да поддържате съвместимост със съществуващи SSE клиенти по време на процеса на миграция. Ето някои стратегии:

- Можете да поддържате и SSE, и Streamable HTTP чрез стартиране на двата трансфера на различни крайни точки.
- Постепенно мигрирайте клиентите към новия трансфер.

### Предизвикателства

Уверете се, че адресирате следните предизвикателства по време на миграция:

- Осигуряване, че всички клиенти са обновени
- Справяне с различията в доставката на уведомления
