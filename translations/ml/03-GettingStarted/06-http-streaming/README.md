# മോഡൽ കോൺടെക്സ്റ്റ് പ്രോട്ടോകോൾ (MCP) ഉപയോഗിച്ചുള്ള HTTPS സ്റ്റ്രീമിംഗ്

ഈ അധ്യായം HTTPS ഉപയോഗിച്ച് മോഡൽ കോൺടെക്സ്റ്റ് പ്രോട്ടോകോൾ (MCP) ഉപയോഗിച്ച് സുരക്ഷിതവും സ്കെയിലബിൾ എളുപ്പമുള്ള റിയൽ-ടൈം സ്റ്റ്രീമിംഗ് നടപ്പിലാക്കാനുള്ള സമഗ്ര ഗൈഡ് നൽകുന്നു. സ്റ്റ്രീമിംഗിന്റെ പ്രേരണ, ലഭ്യമായ ട്രാൻസ്പോർട്ട് മെക്കാനിസങ്ങൾ, MCP യിൽ സ്റ്റ്രീമബിൾ HTTP എങ്ങനെ നടപ്പിലാക്കാം, സുരക്ഷാ മികച്ച പ്രാക്ടിസുകൾ, SSE-യിൽ നിന്ന് മൈഗ്രേഷന്, നിങ്ങളുടെ സ്വന്തം സ്റ്റ്രീമിംഗ് MCP അപ്ലിക്കേഷനുകൾ നിർമ്മിക്കുന്നതിനുള്ള പ്രായോഗിക മാർഗ്ഗനിർദ്ദേശങ്ങൾ എന്നിവ ഇതിൽ ഉൾപ്പെടുത്തിയിരിക്കുന്നു.

> **ഭാവിക്കായി നോക്കുമ്പോൾ:** ഈ പാഠം **MCP സ്‌പെസിഫിക്കേഷൻ 2025-11-25** പ്രകാരം സ്റ്റ്രീമബിൾ HTTP-നെ വിവരണം ചെയ്യുന്നു, ഇവിടെ ഒരു സെഷൻ `initialize` സമയത്ത് സ്ഥാപിക്കുകയും `Mcp-Session-Id` ഹെഡറിൽ പിനാക്കുകയും ചെയ്യുന്നു. `2026-07-28` റിലീസ് കാൻഡിഡേറ്റ് ഹാൻഡ്ഷേക്ക്യും സെഷൻ ID-യും പൂർണ്ണമായും നീക്കം ചെയ്യുന്നു, ഇതോടെ ഓരോ അഭ്യർത്ഥനയും സ്വയം സമ്പൂർണ്ണവും സ്റ്റിക്കി സെഷ്യനുകളില്ലാതെ ഏതൊരു സെർവർ ഇൻസ്റ്റൻസിലേക്കും റൂട്ടു ചെയ്യാവുന്നതുമാകുന്നു. വിശദാംശങ്ങൾക്ക് [What's Changing in MCP: The 2026-07-28 Release Candidate](../../01-CoreConcepts/mcp-2026-07-28-release-candidate.md) കാണുക.

## MCP ൽ ട്രാൻസ്പോർട്ട് മെക്കാനിസങ്ങൾയും സ്റ്റ്രീമിംഗും

MCP-യിൽ ലഭ്യമായ വ്യത്യസ്ത ട്രാൻസ്പോർട്ട് മെക്കാനിസങ്ങളെയും ക്ലയന്റ്-സെർവർ შორის റിയൽ-ടൈം കമ്മ്യൂണിക്കേഷൻ അനുവദിക്കുന്നതിനുള്ള അവയുടെ പങ്ക് വിശദീകരിക്കുന്നു.

### ട്രാൻസ്പോർട്ട് മെക്കാനിസം എന്നത് എന്താണ്?

ഒരു ട്രാൻസ്പോർട്ട് മെക്കാനിസം ക്ലയന്റ്-സെർവർ ഇടയിലുള്ള ഡേറ്റാ എങ്ങനെ കൈമാറപ്പെടുന്നു എന്ന് നിർവ്വചിക്കുന്നു. MCP വ്യത്യസ്ത പരിസരങ്ങളിലും ആവശ്യകതകളിലും അനുയോജ്യമായ നിരവധി ട്രാൻസ്പോർട്ട് തരങ്ങൾ പിന്തുണയ്ക്കുന്നു:

- **stdio**: സ്റ്റാൻഡേർഡ് ഇൻപുട്ട്/ഔട്ട്പുട്ട്, ലൊക്കൽ CLI യാത്രകൾക്ക് അനുയോജ്യം. സിമ്പിൾ ആണെങ്കിലും വെബ് അല്ലെങ്കിൽ ക്ലൗഡ്‌ിനായി അനുയോജ്യം അല്ല.
- **SSE (സെർവർ-സെന്റ് ഇവന്റുകൾ)**: സെർവർ ക്ലയന്റുകൾക്ക് HTTP വഴി റിയൽ-ടൈം അപ്ഡേറ്റുകൾ പുഷ് ചെയ്യാൻ അനുവദിക്കുന്നു. വെബ് UI-കൾക്ക് നല്ലതാണ്, എന്നാൽ സ്കെയിലിബിലിറ്റിയിലും ഫ്ലെക്സിബിലിറ്റിയിലും പരിധിയുണ്ട്. MCP Specification 2025-06-18 മുതൽ സ്റ്റാൻഡലോൺ SSE (സെർവർ-സെന്റ് ഇവന്റുകൾ) ട്രാൻസ്പോർട്ട് ഒഴിവാക്കപ്പെട്ടു "Streamable HTTP" ട്രാൻസ്പോർട്ടായി മാറ്റി.
- **Streamable HTTP**: ആധുനിക HTTP അടിസ്ഥാനത്തിലുള്ള സ്റ്റ്രീമിംഗ് ട്രാൻസ്പോർട്ട്, നൊട്ടിഫിക്കേഷനുകളും മികച്ച സ്കെയിലിബിലിറ്റിയും പിന്തുണയ്ക്കുന്നു. മിക്ക പ്രൊഡക്ഷനും ക്ലൗഡ് സാഹചര്യങ്ങൾക്കും നിർദ്ദേശിക്കപ്പെടുന്നു.

### താരതമ്യ പട്ടിക

ഈ ട്രാൻസ്പോർട്ട് മെക്കാനിസങ്ങൾ തമ്മിലുള്ള വ്യത്യാസങ്ങൾ മനസ്സിലാക്കാൻ താഴെ നൽകിയ താരതമ്യ പട്ടിക കാണുക:

| ട്രാൻസ്പോർട്ട്        | റിയൽ-ടൈം അപ്ഡേറ്റുകൾ | സ്റ്റ്രീമിംഗ് | സ്കെയിലിബിലിറ്റി | ഉപയോഗക്കേസ്                |
|----------------------|-------------------------|------------|-----------------|--------------------------|
| stdio                | ഇല്ല                     | ഇല്ല        | കുറവ്          | ലൊക്കൽ CLI ഉപകരണങ്ങൾ   |
| SSE                  | ഉണ്ട്                    | ഉണ്ട്       | മധ്യസ്ഥം       | വെബ്, റിയൽ-ടൈം അപ്ഡേറ്റുകൾ |
| Streamable HTTP      | ഉണ്ട്                    | ഉണ്ട്       | ഉയർന്നത്        | ക്ലൗഡ്, മൾട്ടി-ക്ലയന്റ്  |

> **ടിപ്പ്:** ശരിയായ ട്രാൻസ്പോർട്ട് തിരഞ്ഞെടുക്കുന്നത് പ്രകടനവും സ്കെയിലിബിലിറ്റിയും ഉപഭോക്തൃ അനുഭവവും ബാധിക്കും. ആധുനികവും സ്കെയിലബിൾ ആയ ക്ലൗഡ്-റെഡി അപ്ലിക്കേഷനുകൾക്കായി **Streamable HTTP** നിർദ്ദേശിക്കുന്നു.

മുൻ അധ്യായങ്ങളിൽ നിങ്ങൾ കാണിച്ച stdio, SSE ട്രാൻസ്പോർട്ടുകൾ ശ്രദ്ധിക്കുക, അതേസമയം ഈ അധ്യായത്തിൽ അതിന്റെ പകരമായി സ്റ്റ്രീമബിൾ HTTP ആണ് കൊണ്ടുവരുന്നത്.

## സ്റ്റ്രീമിംഗ്: ആശയങ്ങളും പ്രേരണകളും

സ്റ്റ്രീമിംഗിന്റെ അടിസ്ഥാന ആശയങ്ങളും പ്രേരണകളും മനസ്സിലാക്കുക ഫലപ്രദമായ റിയൽ-ടൈം കമ്മ്യൂണിക്കേഷൻ സംവിധാനങ്ങൾ നടപ്പിലാക്കുന്നതിനായി അനിവാര്യമാണ്.

**സ്റ്റ്രീമിംഗ്** ഒരു നെറ്റ്‌വർക്ക് പ്രോഗ്രാമിങ്ങ് സാങ്കേതികതയാണ്, ഇതിൽ ഒരു പൂർണ്ണ പ്രതികരണം ഒരുക്കുന്നത് കാത്തിരിക്കാതെ ഡേറ്റാ ചെറുതായി, കൈകാര്യം ചെയ്യാൻ എളുപ്പമുള്ള കഷ്ണങ്ങളായി അല്ലെങ്കിൽ ഒരു സീരീസ് ഇവന്റുകളായി അയയ്ക്കാനും സ്വീകരിക്കാനും സാധിക്കും. ഇത് കൂടുതലായി സഹായിക്കുന്നതു:

- വലുതായ ഫയലുകളോ ഡാറ്റാസെറ്റുകളോ.
- റിയൽ-ടൈം അപ്ഡേറ്റുകൾ (ഉദാ: ചാറ്റ്, പ്രോഗ്രസ് ബാറുകൾ).
- ദൈർഘ്യമേറിയ കംപ്യൂട്ടേഷനുകൾ, ഉപയോക്താവിനെ വിവരമറിയിക്കാൻ.

ഉയർന്ന തലത്തിൽ സ്റ്റ്രീമിംഗിനെക്കുറിച്ച് നിങ്ങൾ അറിയേണ്ടത് ഇതാണ്:

- ഡേറ്റാ ഒരേ സമയം മുഴുവനായി അല്ല, കുതിർന്നു കണ്ട്രോളുള്ള വിധിയിൽ നൽകുന്നു.
- ഡേറ്റ എത്തുമ്പോൾ ക്ലയന്റ് അത് പ്രോസസ് ചെയ്യാൻ കഴിയും.
- അനുഭവത്തിൽ താമസം (ലാറ്റൻസി) കുറച്ചു ഉപഭോക്തൃ അനുഭവം മെച്ചപ്പെടുത്തുന്നു.

### സ്റ്റ്രീമിംഗ് ഉപയോഗിക്കുന്നതെന്തിനാണു?

സ്റ്റ്രീമിംഗ് ഉപയോഗിക്കുന്നതിനുള്ള കാരണം താഴെ പറയുന്നവയാണ്:

- ഉപയോക്താക്കൾ ഫലങ്ങൾ ഉടൻ പ്രാപിക്കുമെന്ന്, അവസാനം വരെ കാത്തിരിക്കേണ്ടതില്ല.
- യാഥാർത്ഥ്യ-സമയം ആപ്ലിക്കേഷനുകളും പ്രതികരണശീലമുള്ള UI വരും.
- നെറ്റ്‌വർക്ക്, കംപ്യൂട്ടിംഗ് വിഭവങ്ങളുടെ കാര്യക്ഷമമായ ഉപയോഗം.

### ലളിതമായ ഉദാഹരണം: HTTP സ്റ്റ്രീമിംഗ് സെർവർ & ക്ലയന്റ്

സ്റ്റ്രീമിംഗ് എങ്ങനെ നടപ്പിലാക്കാമെന്ന് ഒരു ലളിതമായ ഉദാഹരണം:

#### പൈത്തൺ

**സെർവർ (Python, FastAPI & StreamingResponse)**:

```python
from fastapi import FastAPI
from fastapi.responses import StreamingResponse
import time

app = FastAPI()

async def event_stream():
    for i in range(1, 6):
        yield f"data: Message {i}\n\n"
        time.sleep(1)

@app.get("/stream")
def stream():
    return StreamingResponse(event_stream(), media_type="text/event-stream")
```

**ക്ലയന്റ് (Python, requests ഉപയോഗിച്ച്)**:

```python
import requests

with requests.get("http://localhost:8000/stream", stream=True) as r:
    for line in r.iter_lines():
        if line:
            print(line.decode())
```

എല്ലാ സന്ദേശങ്ങളും ഒരുമിച്ച് ലഭിക്കുന്നതിന് കാത്തിരിക്കാതെ, ലഭ്യമായ പോലെ തന്നെ ഒരു നിരയിലെ സന്ദേശങ്ങൾ സെർവർ ക്ലയന്റിന് അയയ്ക്കുന്നത് ഈ ഉദാഹരണം തെളിയിക്കുന്നു.

**ഇത് എങ്ങനെ പ്രവർത്തിക്കുന്നു:**

- സെർവർ ഓരോ സന്ദേശവും തയ്യാറായപ്പോൾ ലഭ്യമാക്കുന്നു.
- ക്ലയന്റ് അവയും പ്രിന്റ് ചെയ്യുക.

**ആവശ്യകതകൾ:**

- സെർവർ ഒരു സ്റ്റ്രീമിംഗ് റെസ്പോൺസ് (`StreamingResponse` FastAPIയിൽ) ഉപയോഗിക്കണം.
- ക്ലയന്റ് റെസ്പോൺസ് ഒരു സ്റ്റ്രീമായി പ്രോസസ്സ് ചെയ്തിരിക്കണം (`stream=True` requestsൽ).
- Content-Type സാധാരണയായി `text/event-stream` അല്ലെങ്കിൽ `application/octet-stream` ആകും.

#### ജावा

**സെർവർ (Java, Spring Boot & Server-Sent Events):**

```java
@RestController
public class CalculatorController {

    @GetMapping(value = "/calculate", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    public Flux<ServerSentEvent<String>> calculate(@RequestParam double a,
                                                   @RequestParam double b,
                                                   @RequestParam String op) {
        
        double result;
        switch (op) {
            case "add": result = a + b; break;
            case "sub": result = a - b; break;
            case "mul": result = a * b; break;
            case "div": result = b != 0 ? a / b : Double.NaN; break;
            default: result = Double.NaN;
        }

        return Flux.<ServerSentEvent<String>>just(
                    ServerSentEvent.<String>builder()
                        .event("info")
                        .data("Calculating: " + a + " " + op + " " + b)
                        .build(),
                    ServerSentEvent.<String>builder()
                        .event("result")
                        .data(String.valueOf(result))
                        .build()
                )
                .delayElements(Duration.ofSeconds(1));
    }
}
```

**ക്ലയന്റ് (Java, Spring WebFlux WebClient):**

```java
@SpringBootApplication
public class CalculatorClientApplication implements CommandLineRunner {

    private final WebClient client = WebClient.builder()
            .baseUrl("http://localhost:8080")
            .build();

    @Override
    public void run(String... args) {
        client.get()
                .uri(uriBuilder -> uriBuilder
                        .path("/calculate")
                        .queryParam("a", 7)
                        .queryParam("b", 5)
                        .queryParam("op", "mul")
                        .build())
                .accept(MediaType.TEXT_EVENT_STREAM)
                .retrieve()
                .bodyToFlux(String.class)
                .doOnNext(System.out::println)
                .blockLast();
    }
}
```

**ജാവയുടെ നടപ്പാക്കൽ കുറിപ്പുകൾ:**

- Spring Bootന്റെ റിയാക്ടീവ് സ്റ്റാക്ക് `Flux` -ഉം ഉപയോഗിക്കുന്നു സ്റ്റ്രീമിംഗിന്
- `ServerSentEvent` ഇവന്റുകളുടെ തരങ്ങളുള്ള ഘടനയുള്ള ഇവന്റ് സ്റ്റ്രീമിംഗ് നൽകുന്നു
- `WebClient` உடന് `bodyToFlux()` ഉപയോഗിച്ച് റിയാക്ടീവ് സ്റ്റ്രീമിംഗ് ഉപഭോഗം സാദ്ധ്യമാക്കുന്നു
- `delayElements()` ഇവന്റുകൾക്ക് ഇടയ്ക്കുള്ള പ്രോസസ്സിംഗ് സമയം സിമുലേറ്റ് ചെയ്യുന്നു
- ഇവന്റുകൾക്ക് `info`, `result` പോലുള്ള തരം നൽകാൻ കഴിയും, മികച്ച ക്ലയന്റ് കൈകാര്യംക്ക്

### താരതമ്യം: ക്ലാസിക് സ്റ്റ്രീമിംഗ് vs MCP സ്റ്റ്രീമിംഗ്

"ക്ലാസിക്" രീതിയിൽ സ്റ്റ്രീമിംഗ് എങ്ങനെ പ്രവർത്തിക്കുന്നതിനും MCP-യിൽ എങ്ങനെ പ്രവർത്തിക്കുന്നതിനും ഉള്ള വ്യത്യാസങ്ങൾ താഴെ കാഴ്ചവെക്കുന്നു:

| സവിശേഷത           | ക്ലാസിക് HTTP സ്റ്റ്രീമിംഗ്       | MCP സ്റ്റ്രീമിംഗ് (നൊട്ടിഫിക്കേഷനുകൾ)     |
|----------------------|------------------------------|-------------------------------------------|
| പ്രധാന പ്രതികരണം    | കഷണങ്ങളായി                     | ഒറ്റത്തവണ, അവസാനത്തിൽ                     |
| പ്രോഗ്രസ് അപ്ഡേറ്റുകൾ| ഡാറ്റാ ചങ്കുകളായി അയയ്ക്കുന്നു  | നൊട്ടിഫിക്കേഷനുകളായി അയയ്ക്കുന്നു              |
| ക്ലയന്റ് ആവശ്യങ്ങൾ  | സ്‌ട്രീം പ്രോസസ്സ് ചെയ്യേണ്ടതാണ് | മെസേജ് ഹാൻഡ്ലർ നടപ്പിലാക്കണം               |
| ഉപയോഗക്കേസ്       | വലിയ ഫയലുകൾ, AI ടോക്ക്ൻ സ്ട്രീം | പ്രോഗ്രസ്, ലോഗുകൾ, റിയൽ-ടൈം ഫീഡ്ബാക്ക്    |

### കണ്ട വ്യത്യാസങ്ങളുടെ പ്രധാനകഥകൾ

കൂടാതെ ചില പ്രധാന വ്യത്യാസങ്ങൾ:

- **കമ്മ്യൂണിക്കേഷൻ പാറ്റേൺ:**
  - ക്ലാസിക് HTTP സ്റ്റ്രീമിംഗ്: സിമ്പിൾ ചങ്കഡ് ട്രാൻസ്ഫർ എൻകോഡിംഗ് ഉപയോഗിച്ച് ഡേറ്റ അയയ്ക്കുന്നു
  - MCP സ്റ്റ്രീമിംഗ്: JSON-RPC പ്രോട്ടോക്കോൾ ഉപയോഗിച്ച് ഘടനയുള്ള നൊട്ടിഫിക്കേഷൻ സംവിധാനമാണ് ഉപയോഗിക്കുന്നത്

- **മെസേജ് ഫോർമാറ്റ്:**
  - ക്ലാസിക് HTTP: പ്ലെയിൻ ടെക്സ്റ്റ് കഷ്ണങ്ങൾ, ന്യൂ ലൈൻസ് ഉപയോഗിച്ച്
  - MCP: മെറ്റാഡേറ്റയോടെ ഘടനയുള്ള LoggingMessageNotification ഒਬ്ജക്റ്റുകൾ

- **ക്ലയന്റ് നടപ്പാക്കൽ:**
  - ക്ലാസിക് HTTP: ലളിത ക്ലയന്റ്, സ്‌ട്രീംഡ് റെസ്പോൺസ് പ്രോസസ്സർ
  - MCP: മെസേജ് ഹാൻഡ്ലർ ഉള്ള കൂടുതൽ വിമർശനശീലമുള്ള ക്ലയന്റ്, വ്യത്യസ്ത തരത്തിലുള്ള സന്ദേശങ്ങൾ കൈകാര്യം ചെയ്യുന്നു

- **പ്രോഗ്രസ് അപ്ഡേറ്റുകൾ:**
  - ക്ലാസിക് HTTP: പ്രോഗ്രസ് പ്രധാന റെസ്പോൺസ് സ്ട്രീമിന്റെ ഭാഗമാണ്
  - MCP: പ്രോഗ്രസ് വേർതിരിച്ചിട്ടുള്ള നൊട്ടിഫിക്കേഷൻ സന്ദേശങ്ങളായി അയയ്ക്കുന്നു, പ്രധാന ഫലങ്ങൾ അവസാനത്തിൽ വരും

### ശിപാർശകൾ

ക്ലാസിക് സ്റ്റ്രീമിംഗ് (മുൻപ് `/stream` എൻഡ്‌പോയിന്റ് വഴി കാണിച്ചത്) നടപ്പിലാക്കൽ, MCP മുഖേന സ്റ്റ്രീമിംഗ് എന്നിവയിൽ തിരഞ്ഞെടുക്കുമ്പോൾ ചില ശിപാർശകൾ ഇവിടെ:

- **ലളിതമായ സ്റ്റ്രീമിംഗ് ആവശ്യങ്ങൾക്ക്:** ക്ലാസിക് HTTP സ്റ്റ്രീമിംഗ് ലളിതമാണ്, അടിസ്ഥാന സ്റ്റ്രീമിംഗ് ആവശ്യങ്ങൾക്ക് മതിയാണെന്ന് കരുതാം.

- **സങ്കീർണ്ണവും ഇടപെടലുള്ള ആപ്ലിക്കേഷനുകൾക്കായി:** MCP സ്റ്റ്രീമിംഗ് കൂടുതൽ ഘടനയുള്ള സമീപനം നൽകുന്നു, മെറ്റാഡേറ്റ കൂടുതലോടെ, നൊട്ടിഫിക്കേഷനും അവസാന ഫലവും വേർതിരിക്കുന്നു.

- **AI ആപ്ലിക്കേഷനുകൾക്കായി:** MCP നൊട്ടിഫിക്കേഷൻ സംവിധാനം ദൈർഘ്യമേറിയ AI ടാസ്കുകൾക്ക് പ്രോഗ്രസ് ഉപയോക്താക്കൾക്ക് അറിയിക്കാൻ വളരെ ഉപകാരപ്രദമാണ്.

## MCP ഇൽ സ്റ്റ്രീമിംഗ്

ഇതുവരെ ക്ലാസിക് സ്റ്റ്രീമിംഗ്, MCP സ്റ്റ്രീമിംഗ് തമ്മിലുള്ള ശിപാർശകളും താരതമ്യങ്ങളും കണ്ടു. ഇപ്പോൾ MCP-ൽ സ്റ്റ്രീമിംഗ് എങ്ങനെ ആക്കാം എന്ന് വിശദമായി നോക്കാം.

MCP ഫ്രെയിംവർക്കിനുള്ളിൽ സ്റ്റ്രീമിംഗ് എങ്ങനെ പ്രവർത്തിക്കുന്നു എന്ന് മനസ്സിലാക്കണം, ഇത് ഫലപ്രദമായ റിയൽ-ടൈം ഫീഡ്ബാക്ക് നൽകുന്ന പ്രതികരണശീലമുള്ള അപ്ലിക്കേഷനുകൾ നിർമ്മിക്കാൻ സഹായിക്കും.

MCP യിൽ, സ്റ്റ്രീമിംഗ് പ്രധാന പ്രകടന ഫലങ്ങൾ കഷണങ്ങളായി അയയ്ക്കൽ അല്ല, പകരം ഒരു ടൂൾ അഭ്യർത്ഥന പ്രോസസ്സ് ചെയ്യുന്ന സമയത്ത് ക്ലയന്റ്‌ക്ക് **നൊട്ടിഫിക്കേഷനുകൾ** അയച്ച് നൽകലാണ്. ഈ നൊട്ടിഫിക്കേഷനുകളിൽ പ്രോഗ്രസ് അപ്ഡേറ്റുകളും, ലോഗുകളും, മറ്റ് ഇവന്റുകളും അടങ്ങിയിരിക്കാം.

### ഇത് എങ്ങനെ പ്രവർത്തിക്കുന്നു

പ്രധാന ഫലം ഒറ്റത്തവണ റെസ്പോൺസ് ആയി അയയ്ക്കുന്നു. എങ്കിലും പ്രോസസ്സിംഗ് സമയത്ത് നൊട്ടിഫിക്കേഷനുകൾ വേർതിരിച്ച് അയച്ചുകൊടുത്ത് റിയൽ-ടൈം അപ്ഡേറ്റുകൾ ക്ലയന്റിന് നൽകാം. ക്ലയന്റ് ഇവ കൈകാര്യം ചെയ്ത് പ്രദർശിപ്പിക്കാൻ സജ്ജമായിരിക്കണം.

## നൊട്ടിഫിക്കേഷൻ എന്താണ്?

"നൊട്ടിഫിക്കേഷൻ" എന്നു പറഞ്ഞാൽ MCP പരിസരത്തിൽ എന്താണർത്ഥം?

ഒരു നൊട്ടിഫിക്കേഷൻ സെർവറിൽ നിന്ന് ക്ലയന്റിലേക്ക് അയയ്ക്കുന്ന ഒരു സന്ദേശമാണ്, ഒരു ദൈർഘ്യമേറിയ ഓപ്പറേഷൻ മേൽ പുരോഗതിയെയും സ്റ്റാറ്റസിനെയും അല്ലെങ്കിൽ മറ്റു ഇവന്റുകളെയും അറിയിക്കുന്നതിന്. നൊട്ടിഫിക്കേഷനുകൾ സുതാര്യതയും ഉപയോക്തൃ അനുഭവവും മെച്ചപ്പെടുത്തുന്നു.

ഉദാഹരണത്തിന്, സെർവറുമായുള്ള ആദ്യം ഹാൻഡ്ഷേക്ക് പൂർത്തിയായതിനുശേഷം ഒരു നൊട്ടിഫിക്കേഷൻ ക്ലയന്റ് അയയ്ക്കണമെന്നും നിര്‍ദേശിക്കുന്നു.

JSON മെസേജായി ഒരു നൊട്ടിഫിക്കേഷൻ ഇങ്ങനെ കാണപ്പെടും:

```json
{
  jsonrpc: "2.0";
  method: string;
  params?: {
    [key: string]: unknown;
  };
}
```

Notifications MCP-യിലെ ["Logging"](https://modelcontextprotocol.io/specification/draft/server/utilities/logging) വിഷയത്തിന് കീഴിലാണ്.

> **മാറ്റശേഷിക്കുന്ന അറിയിപ്പ്:** `2026-07-28` MCP സ്‌പെസിഫിക്കേഷൻ റിലീസ് കാൻഡിഡേറ്റ് ലോഗിംഗ് പ്രിമിറ്റീവ് `stderr`യ്‌ക്കായി stdio ട്രാൻസ്പോർട്ടുകൾക്കും ഘടനാപരമായ ഓബ്സർവബിലിറ്റിക്കായി OpenTelemetry-ക്കുമായി മാറ്റി വക്കുന്നു.  `2025-11-25` പതിപ്പിലും ഔദ്യോഗികമായ ഡിപ്രിക്കേഷൻ ശേഷം കുറഞ്ഞത് ഒരു വർഷം ഇതു പ്രവർത്തിക്കും. കൂടുതൽ വിവരങ്ങൾക്ക് [What's Changing in MCP: The 2026-07-28 Release Candidate](../../01-CoreConcepts/mcp-2026-07-28-release-candidate.md) കാണുക.

ലോഗിംഗ് പ്രവർത്തിപ്പിക്കാൻ സെർവർ ഫീച്ചർ/തിരിച്ചറിയൽ ആയി ചുവടെപോലെ സജ്ജമാക്കണം:

```json
{
  "capabilities": {
    "logging": {}
  }
}
```

> [!NOTE]
> ഉപയോഗിക്കുന്ന SDK-യെ ആശ്രയിച്ച്, ലോഗിംഗ് by default രാവിലെ പ്രവർത്തനക്ഷമമാംവാനാകാം അല്ലെങ്കിൽ സെർവർ കോൺഫിഗറേഷനിൽ വ്യക്തമായി പ്രവർത്തനക്ഷമമാക്കേണ്ടതുണ്ടാകും.

വിവിധ തരത്തിലുള്ള നൊട്ടിഫിക്കേഷനുകൾ ഇവയാണ്:

| തലക്ക്       | വിവരണം                          | ഉപയോഗിച്ച ഉദാഹരണം              |
|-------------|---------------------------------|-----------------------------------|
| debug       | വിശദമായ ഡീബഗിംഗ് വിവരങ്ങൾ     | ഫംഗ്ഷൻ എൻട്രി/എക്സിറ്റ് പോയന്റുകൾ  |
| info        | സാധാരണ വിവരം സർവ്വീസ് സന്ദേശങ്ങൾ| ഓപ്പറേഷൻ പുരോഗതി അപ്ഡേറ്റുകൾ      |
| notice      | സാധാരണ എന്നാൽ പ്രധാന സംഭവങ്ങൾ | കോൺഫിഗറേഷൻ മാറ്റങ്ങൾ              |
| warning     | മുന്നറിയിപ്പ് അവസ്ഥകൾ            | ഉപയോഗത്തിൽ നിന്നും ഒഴിവാക്കേണ്ട ഫീച്ചറുകൾ |
| error       | പിശക് അവസ്ഥകൾ                   | ഓപ്പറേഷൻ പരാജയങ്ങൾ              |
| critical    | ഗുരുതര അവസ്ഥകൾ                 | സിസ്റ്റം ഘടക പരാജയങ്ങൾ            |
| alert       | ഉടൻ നടപടി എടുക്കണം              | ഡാറ്റ ഭ്രഷ്ട്ടി കണ്ടുപിടിച്ചു          |
| emergency   | സിസ്റ്റം ഉപയോഗിക്കാനാകാത്തതാണ്   | സമ്പൂർണ്ണ സിസ്റ്റം പരാജയം           |

## MCP-ൽ നൊട്ടിഫിക്കേഷനുകൾ നടപ്പിലാക്കൽ

MCPയിൽ നൊട്ടിഫിക്കേഷനുകൾ നടപ്പിലാക്കാൻ, റിയൽ ടൈം അപ്ഡേറ്റുകൾ കൈകാര്യം ചെയ്യുന്നതിനായി സെർവർ, ക്ലയന്റ് ഇരുവശത്തും സജ്ജമാക്കണം. ഇതുമൂലം നിങ്ങളുടെ അപ്ലിക്കേഷൻ ദൈർഘ്യമേറിയ പ്രവർത്തനങ്ങളിൽ ഉപയോക്താക്കളെ ഉടൻ ഫീഡ്ബാക്ക് നൽകാൻ കഴിയും.

### സെർവർ വശം: നൊട്ടിഫിക്കേഷനുകൾ അയയ്ക്കൽ

സെർവർ വശത്തിൽ തുടങ്ങാം. MCP-യിൽ, അഭ്യർത്ഥനകൾ പ്രോസസ്സ് ചെയ്യുമ്പോൾ നൊട്ടിഫിക്കേഷൻ അയക്കാൻ കഴിയുന്ന ടൂളുകൾ നിർവ്വചിക്കുന്നു. സെർവർ `ctx` പോലുള്ള കോൺടെക്സ്റ്റ് ഒബ്ജക്ട് ഉപയോഗിച്ച് ക്ലയന്റിന് മെസേജുകൾ അയയ്ക്കുന്നു.

#### പൈത്തൺ

```python
@mcp.tool(description="A tool that sends progress notifications")
async def process_files(message: str, ctx: Context) -> TextContent:
    await ctx.info("Processing file 1/3...")
    await ctx.info("Processing file 2/3...")
    await ctx.info("Processing file 3/3...")
    return TextContent(type="text", text=f"Done: {message}")
```

മുകളിൽ നൽകിയ ഉദാഹരണത്തിൽ, `process_files` ടൂൾ ഓരോ ഫയലും പ്രോസസ്സ് ചെയ്യുമ്പോൾ മൂന്ന് നൊട്ടിഫിക്കേഷനുകൾ ക്ലയന്റിന് അയയ്ക്കുന്നു. `ctx.info()` മെത്തഡ് ഇൻഫർമേഷനൽ സന്ദേശങ്ങൾ അയയ്ക്കാൻ ഉപയോഗിക്കുന്നു.

കൂടാതെ, നൊട്ടിഫിക്കേഷനുകൾ പ്രവർത്തിപ്പിക്കാൻ സെർവർ `streamable-http` പോലുള്ള സ്ട്രീമിംഗ് ട്രാൻസ്പോർട്ട് ഉപയോഗിക്കണം, ക്ലയന്റ് നൊട്ടിഫിക്കേഷനുകൾ പ്രോസസ്സ് ചെയ്യാനുള്ള മെസേജ് ഹാൻഡ്ലർ നടപ്പിലാക്കണം. സെർവർ `streamable-http` ട്രാൻസ്പോർട്ട് ഉപയോഗിച്ച് എങ്ങനെ സജ്ജമാക്കാം:

```python
mcp.run(transport="streamable-http")
```

#### .NET

```csharp
[Tool("A tool that sends progress notifications")]
```

ഈ .NET ഉദാഹരണത്തിൽ, `ProcessFiles` ടൂൾ `Tool` ആട്രിബ്യൂട്ട് ഉപയോഗിച്ച് അലങ്കരിച്ചിരിക്കുകയാണ്, ഓരോ ഫയലും പ്രോസസ്സ് ചെയ്യുമ്പോൾ മൂന്ന് നൊട്ടിഫിക്കേഷനുകൾ ക്ലയന്റിന് അയയ്ക്കുന്നു. `ctx.Info()` മെതഡ് ഇൻഫർമേഷൻ സന്ദേശങ്ങൾ അയയ്ക്കാൻ ഉപയോഗിക്കുന്നു.

.NET MCP സെർവറിൽ നൊട്ടിഫിക്കേഷൻ പ്രവർത്തനക്ഷമമാക്കാൻ ഉറപ്പാക്കുക നിങ്ങൾ സ്ട്രീമിംഗ് ട്രാൻസ്പോർട്ട് ഉപയോഗിക്കുന്നു എന്ന്:

```csharp
var builder = McpBuilder.Create();
await builder
    .UseStreamableHttp() // Enable streamable HTTP transport
    .Build()
    .RunAsync();
```

### ക്ലയന്റ് വശം: നൊട്ടിഫിക്കേഷനുകൾ സ്വീകരിക്കൽ

ക്ലയന്റ് നൊട്ടിഫിക്കേഷനുകൾ കൈകാര്യം ചെയ്ത് പ്രദർശിപ്പിക്കുന്ന മെസേജ് ഹാൻഡ്ലർ നടപ്പിലാക്കണം.

#### Python

```python
async def message_handler(message):
    if isinstance(message, types.ServerNotification):
        print("NOTIFICATION:", message)
    else:
        print("SERVER MESSAGE:", message)

async with ClientSession(
   read_stream, 
   write_stream,
   logging_callback=logging_collector,
   message_handler=message_handler,
) as session:
```

മുകളിൽ കൊടുത്ത കോഡിൽ `message_handler` ഫങ്ഷൻ വരുന്ന സന്ദേശം നൊട്ടിഫിക്കേഷനാണോ എന്ന് പരിശോധിക്കുന്നു. ആണെങ്കിൽ അച്ചുതണ്ടി പ്രിന്റ് ചെയ്യുന്നു; അല്ലെങ്കിൽ സാധാരണ സർവർ സന്ദേശമായി പ്രോസസ്സ് ചെയ്യുന്നു. കൂടാതെ `ClientSession` `message_handler` ഉപയോഗിച്ച് തുടക്കം കുറിക്കുന്നു incoming notifications ചികിത്സിക്കാൻ.

#### .NET

```csharp
// Define a message handler
void MessageHandler(IJsonRpcMessage message)
{
    if (message is ServerNotification notification)
    {
        Console.WriteLine($"NOTIFICATION: {notification}");
    }
    else
    {
        Console.WriteLine($"SERVER MESSAGE: {message}");
    }
}

// Create and use a client session with the message handler
var clientOptions = new ClientSessionOptions
{
    MessageHandler = MessageHandler,
    LoggingCallback = (level, message) => Console.WriteLine($"[{level}] {message}")
};

using var client = new ClientSession(readStream, writeStream, clientOptions);
await client.InitializeAsync();

// Now the client will process notifications through the MessageHandler
```

ഈ .NET ഉദാഹരണത്തിൽ, `MessageHandler` ഫങ്ഷൻ വരുന്ന സന്ദേശം നൊട്ടിഫിക്കേഷനാണോ എന്ന് പരിശോധിക്കുന്നു. ആണെങ്കിൽ അച്ചുതണ്ടി പ്രിന്റ് ചെയ്യുന്നു; അല്ലെങ്കിൽ സാധാരണ സർവർ സന്ദേശമായി പ്രോസസ്സ് ചെയ്യുന്നു. `ClientSession` മെസേജ് ഹാൻഡ്ലർ ഉപയോഗിച്ച് `ClientSessionOptions` വഴി ആരംഭിക്കുന്നു.

നൊട്ടിഫിക്കേഷനുകൾ പ്രവർത്തനക്ഷമമാക്കാൻ, സെർവർ സ്ട്രീമിംഗ് ട്രാൻസ്പോർട്ട് (streamable-http പോലുള്ള) ഉപയോഗിക്കുന്നുവെന്ന് ഉറപ്പാക്കുക, ക്ലയന്റ് നൊട്ടിഫിക്കേഷൻ പ്രോസസ്സ് ചെയ്യാനുള്ള മെസേജ് ഹാൻഡ്ലർ നടപ്പിലാക്കിയിരിക്കുന്നു.

## പ്രോഗ്രസ് നൊട്ടിഫിക്കേഷനുകളും സെന്നാരിയോകളും

MCP-ൽ പ്രോഗ്രസ് നൊട്ടിഫിക്കേഷനുകളുടെ ആശയം, അതിന്റെ പ്രാധാന്യം, Streamable HTTP ഉപയോഗിച്ച് എങ്ങനെ നടപ്പിലാക്കാം എന്നിവ വിശദീകരിക്കുന്നു. നിങ്ങളുടെ മനസ്സിലാക്കൽ ശക്തിപ്പെടുത്തുന്നതിനായി പ്രായോഗിക അസൈൻമെന്റും ഇതിൽ ഉൾപ്പെടുന്നു.

പ്രോഗ്രസ് നൊട്ടിഫിക്കേഷനുകൾ ദൈർഘ്യമേറിയ ഓപ്പറേഷനുകളെ തുടർന്ന് സെർവറിൽ നിന്ന് ക്ലയന്റിലേക്ക് റിയൽ-ടൈം സന്ദേശങ്ങളാണ്. മുഴുവൻ പ്രക്രിയ പൂർത്തിയാകാൻ കാത്തിരിക്കാൻ പകരം, സേവർ ക്ലയന്റ് നിലവിലുള്ള സ്ഥിതി അറിയിക്കുകയാണ്‌. ഇത് സുതാര്യതയും വ്യവസ്ഥ നിരീക്ഷണവും മെച്ചപ്പെടുത്തുന്നു, ഡീബഗിംഗ് എളുപ്പമാക്കുന്നു.

**ഉദാഹരണം:**

```text

"Processing document 1/10"
"Processing document 2/10"
...
"Processing complete!"

```

### പ്രോഗ്രസ് നൊട്ടിഫിക്കേഷനുകൾ ഉപയോഗിക്കുന്നതെന്തിനാണു?

പ്രോഗ്രസ് നൊട്ടിഫിക്കേഷനുകൾ വിവിധ കാരണങ്ങളാൽ അനിവാര്യമാണ്:

- **മികച്ച ഉപയോക്തൃ അനുഭവം:** ജോലി പുരോഗമിക്കുമ്പോൾ തന്നെ ഉപയോക്താക്കളെ അപ്ഡേറ്റുകൾ കാണാം, ആത്യന്തരം അവസാനത്തെല്ലാത്തത്.
- **റിയൽ-ടൈം ഫീഡ്ബാക്ക്:** ക്ലയന്റ് പ്രോഗ്രസ് ബാർ അല്ലെങ്കിൽ ലോഗുകൾ പ്രദർശിപ്പിക്കാൻ കഴിയും, ആപ്പ് പ്രതികരണശീലമുള്ളതായി തോന്നും.
- **ഡീബഗിംഗ്, നിരീക്ഷണം എളുപ്പം:** വികസിപ്പിപ്പിക്കുന്നവരും ഉപയോക്താക്കളും പ്രക്രിയ എവിടെ മന്ദമാകുന്നു അല്ലെങ്കിൽ തടഞ്ഞുവെന്നു വീക്ഷിക്കാം.

### പ്രോഗ്രസ് നൊട്ടിഫിക്കേഷനുകൾ എങ്ങനെ നടപ്പിലാക്കാം

MCP-ൽ പ്രോഗ്രസ് നൊട്ടിഫിക്കേഷനുകൾ നടപ്പിലാക്കുന്ന വിധം:

- **സെർവർ വശം:** ഓരോ ഇനവും പ്രോസസ്സ് ചെയ്യുമ്പോൾ `ctx.info()` അല്ലെങ്കിൽ `ctx.log()` ഉപയോഗിച്ച് നൊട്ടിഫിക്കേഷനുകൾ അയയ്‌ക്കുക. ഇത് പ്രധാന ഫലം തയ്യാറാകുന്നതിനു മുമ്പ് ക്ലയന്റിന് സന്ദേശം അയക്കും.
- **ക്ലയന്റ് വശം:** നൊട്ടിഫിക്കേഷനുകൾ സ്വീകരിച്ച് പ്രദർശിപ്പിക്കുന്ന മെസേജ് ഹാൻഡർ നടപ്പിലാക്കുക. നൊട്ടിഫിക്കേഷനും അന്തിമ ഫലവും വേർതിരിച്ച് കൈകാര്യം ചെയ്യണം.

**സെർവർ ഉദാഹരണം:**


#### Python

```python
@mcp.tool(description="A tool that sends progress notifications")
async def process_files(message: str, ctx: Context) -> TextContent:
    for i in range(1, 11):
        await ctx.info(f"Processing document {i}/10")
    await ctx.info("Processing complete!")
    return TextContent(type="text", text=f"Done: {message}")
```

## സുരക്ഷാ പരിഗണനകൾ

ഏതെങ്കിലും സെർവർ നടപ്പാക്കുമ്പോൾ സുരക്ഷ ഏറ്റവും പ്രധാനപ്പെട്ട കാര്യമാകണം, പ്രത്യേകിച്ച് MCP-യിലേയ്ക്കുള്ള Streamable HTTP പോലുള്ള HTTP അടിസ്ഥാനമുള്ള ട്രാൻസ്പോർട്ടുകൾ ഉപയോഗിക്കുമ്പോൾ.

HTTP അടിസ്ഥാനമുള്ള ട്രാൻസ്പോർട്ടുകൾ ഉപയോഗിച്ച് MCP സെർവർകൾ നടപ്പാക്കുമ്പോൾ, നിരവധി ആക്രമണ മാർഗ്ഗങ്ങളും സംരക്ഷണ സംവിധാനങ്ങളും സൂക്ഷ്മമായി പരിഗണിക്കേണ്ടതായ മനസ്സിലാക്കേണ്ട നിർണായക കാര്യമാകുന്നു.

### അവലോകനം

MCP സെർവർകൾ HTTP വഴി പരസ്യം ചെയ്യുമ്പോൾ സുരക്ഷ അത്യന്താപേക്ഷിതമാണ്. Streamable HTTP പുതിയ ആക്രമണ സാധ്യതകൾ ഉണ്ടാക്കുകയും സൂക്ഷ്മമായി ക്രമീകരണം ആവശ്യപ്പെടുകയും ചെയ്യുന്നു.

ചില പ്രധാന സുരക്ഷാ പരിഗണനകൾ ഇവിടെ കൊടുക്കുന്നു:

- **Origin ഹെഡർ പരിശോദന**: DNS റിബൈൻഡിംഗ് ആക്രമണങ്ങൾ തടയാൻ എന്നും `Origin` ഹെഡർ പരിശോധിക്കുക.
- **ഹോഷ്റ്റ് ബൈണ്ടിംഗ്**: പ്രാദേശിക വികസനത്തിനായി, സെർവർകൾ പൊതു ഇന്റർനറ്റിൽ പുറത്തുവരാതിരിക്കാൻ `localhost`-ലേക്ക് ബൈൻഡ് ചെയ്യുക.
- **പ്രാമാണീകരണം**: ഉൽപ്പാദന വിന്യാസങ്ങൾക്ക് പ്രാമാണീകരണം (ഉദാ: API കീകൾ, OAuth) നടപ്പാക്കുക.
- **CORS**: ആക്സസ് നിയന്ത്രിക്കാൻ Cross-Origin Resource Sharing (CORS) നയം ക്രമീകരിക്കുക.
- **HTTPS**: ഉൽപ്പാദനത്തിൽ ട്രാഫിക് എൻക്രിപ്റ്റ് ചെയ്യുന്നതിനായി HTTPS ഉപയോഗിക്കുക.

### മികച്ച രീതികൾ

കൂടാതെ, നിങ്ങളുടെ MCP സ്റ്റ്രീമിംഗ് സെർവറിൽ സുരക്ഷ നടപ്പാക്കുമ്പോൾ പാലിക്കേണ്ട ചില മികച്ച പ്രഥകങ്ങളുണ്ട്:

- വരവിലെ അഭ്യർത്ഥനകളെ സ്ഥിരീകരണം കൂടാതെ ഒരുപക്ഷേ വിശ്വസിക്കണ്ട.
- മുഴുവൻ ആക്സസ്, പിശകുകൾ രേഖപ്പെടുത്തുകയും നിരീക്ഷിക്കുകയും ചെയ്യുക.
- സുരക്ഷ പരിശോധനകൾ പാച്ച് ചെയ്യുന്നതിന് ആവശ്യമായ ഡിപ്പൻഡൻസികൾ നിത്യമായി അപ്ഡേറ്റ് ചെയ്യുക.

### വെല്ലുവിളികൾ

MCP സ്റ്റ്രീമിംഗ് സെർവറുകളിൽ സുരക്ഷ നടപ്പാക്കുമ്പോൾ നിങ്ങൾ നേരിടേണ്ട ചില വെല്ലുവിളികൾ:

- വികസന സൗകര്യവുമൊപ്പം സുരക്ഷ ചേർക്കൽ
- വിവിധ ക്ലയന്റ് പരിസ്ഥിതികളുമായി പൊരുത്തക്കേട് ഉറപ്പാക്കൽ


## SSE-യിൽ നിന്ന് Streamable HTTP-യിലേക്ക് അപ്‌ഗ്രേഡ് ചെയ്യൽ

ներկայമുള്ള Server-Sent Events (SSE) ഉപയോഗിക്കുന്ന ആപ്ലിക്കേഷനുകൾക്ക്, Streamable HTTP-യിലേക്ക് മാറ്റിവയ്ക്കുന്നത് മികവാർന്ന ശേഷികളും ദീർഘകാല സ്ഥിരതയും MCP നടപ്പാക്കലുകൾക്ക് നൽകുന്നു.

### എന്തുകൊണ്ട് അപ്‌ഗ്രേഡ് ചെയ്യണം?

SSE-യിൽ നിന്ന് Streamable HTTP-യിലേക്ക് അപ്‌ഗ്രേഡ് ചെയ്യാനുള്ള രണ്ടുപ്രധാന കാരണങ്ങൾ ഉണ്ട്:

- Streamable HTTP SSE നാൽ മെച്ചപ്പെട്ട സ്കെയിലബിലിറ്റി, പൊരുത്തക്കേട്, സമ്പന്നമായ അറിയിപ്പ് പിന്തുണ നൽകുന്നു.
- പുതിയ MCP ആപ്ലിക്കേഷനുകൾക്കുള്ള ശുപാർശ ചെയ്യുന്ന ട്രാൻസ്പോർട്ടാണ് ഇത്.

### മാറ്റം നടത്താനുള്ള ഘട്ടങ്ങൾ

നിങ്ങളുടെ MCP ആപ്ലിക്കേഷനുകളിൽ SSE-യിൽ നിന്ന് Streamable HTTP-യിലേക്ക് മാറ്റം എങ്ങനെ ചെയ്യാം:

- **സർവർ കോഡ് അപ്ഡേറ്റ് ചെയ്യുക** `mcp.run()`-ൽ `transport="streamable-http"` ഉപയോഗിക്കാൻ.
- **ക്ലയന്റ് കോഡ് അപ്ഡേറ്റ് ചെയ്യുക** SSE ക്ലയന്റിന്റെ പകരം `streamablehttp_client` ഉപയോഗിക്കാൻ.
- **ക്ലയന്റിൽ സന്ദേശ ഹാൻഡ്ലർ നടപ്പാക്കുക** അറിയിപ്പുകൾ പ്രോസസ് ചെയ്യാൻ.
- ** നിലവിലുള്ള ടൂളുകളുമായി പൊരുത്തക്കേട് for പരിശോധിക്കുക**.

### പൊരുത്തക്കേട് നിലനിർത്തൽ

മാറ്റസമയത്ത് നിലവിലുള്ള SSE ക്ലയന്റ്‌കളുമായി പൊരുത്തക്കേട് നിലനിർത്തുന്നത് ശുപാർശ ചെയ്യപ്പെടുന്നു. ചില സ്റ്റ്രാറ്റജികൾ:

- SSEയും Streamable HTTP യും വേർതിരിച്ചിട്ടുള്ള എന്റ്പോയിന്റുകളിൽ പ്രവർത്തിപ്പിച്ച് രണ്ട് ട്രാൻസ്പോർട്ടുകൾക്കും പിന്തുണ നൽകുക.
- കാര്യമായ ക്ലയന്റുകൾക്കു പുതിയ ട്രാൻസ്പോർട്ടിലേക്ക് ക്രമികമായി മാറുക.

### വെല്ലുവിളികൾ

മാറ്റസമയത്ത് താഴെപ്പറയുന്ന വെല്ലുവിളികൾ പരിഹരിക്കുക:

- എല്ലാ ക്ലയന്റുകളും അപ്ഡേറ്റ് ചെയ്തത് ഉറപ്പാക്കുക
- അറിയിപ്പുകളുടെ വിതരണം വ്യത്യാസങ്ങൾ കൈകാര്യം ചെയ്യുക

### അസൈൻമെന്റ്: നിങ്ങളുടെ സ്വന്തം സ്റ്റ്രീമിംഗ് MCP ആപ്പ് നിർമ്മിക്കുക

**സെനാരിയോ:**
ഒരു MCP സെർവർ-ക്ലയന്റ് നിർമ്മിക്കുക, അവിടെ സെർവർ ഒരു ലിസ്റ്റ് ഉൾപ്പെടുന്ന (ഉദാ., ഫയലുകൾ അല്ലെങ്കിൽ ഡോക്യുമെന്റുകൾ) ഓരോ ഐറ്റത്തിന്റെയും പ്രോസസിങ്ങ് നടത്തുകയും ഓരോ പ്രോസസ്സ് ചെയ്ത ഐറ്റത്തിലേക്കും അറിയിപ്പുകൾ അയയ്ക്കുകയും ചെയ്യുക. ക്ളയന്റ് ഓരോ അറിയിപ്പും എത്തിയാൽ അത് പ്രദർശിപ്പിക്കണം.

**ഘട്ടങ്ങൾ:**

1. ലിസ്റ്റ് പ്രോസസ് ചെയ്ത് ഓരോ ഐറ്റത്തിനും അറിയിപ്പുകൾ അയക്കുന്ന സെർവർ ടൂൾ നടപ്പാക്കുക.
2. അറിയിപ്പുകൾ ഡയറക്ട് കാണിക്കുന്ന സന്ദേശ ഹാൻഡ്ലർ ഉള്ള क्लയന്റ് നടപ്പാക്കുക.
3. സെർവർ, ക്ലയന്റ് രണ്ടും പ്രവർത്തിപ്പിച്ച് നിങ്ങളുടെ നടപ്പാക്കലുകൾ പരിശോദിക്കുക, അറിയിപ്പുകൾ ശ്രദ്ധിക്കുക.
