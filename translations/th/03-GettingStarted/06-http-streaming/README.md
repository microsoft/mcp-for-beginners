# การสตรีม HTTPS ด้วยโปรโตคอล Model Context Protocol (MCP)

บทนี้ให้คำแนะนำอย่างครอบคลุมในการใช้สตรีมแบบปลอดภัย ขยายขนาดได้ และเรียลไทม์ด้วย Model Context Protocol (MCP) ผ่าน HTTPS ครอบคลุมแรงจูงใจสำหรับการสตรีม กลไกขนส่งที่มีอยู่ วิธีการใช้งาน HTTP ที่รองรับการสตรีมใน MCP แนวทางปฏิบัติที่ดีที่สุดด้านความปลอดภัย การย้ายจาก SSE และคำแนะนำเชิงปฏิบัติสำหรับการสร้างแอปพลิเคชัน MCP สตรีมของคุณเอง

> **มองไปข้างหน้า:** บทเรียนนี้อธิบาย Streamable HTTP ภายใต้ **MCP Specification 2025-11-25** ซึ่งการเซสชันจะถูกตั้งขึ้นระหว่าง `initialize` และตรึงด้วยส่วนหัว `Mcp-Session-Id` ตัวอย่างการเปิดตัว `2026-07-28` จะลบการจับมือและ ID เซสชันทั้งหมด ทำให้แต่ละคำขอเป็นตนเองและสามารถส่งไปยังอินสแตนซ์เซิร์ฟเวอร์ใดก็ได้โดยไม่ต้องใช้เซสชันที่ผูกติด ดู [มีอะไรเปลี่ยนแปลงใน MCP: ตัวอย่างการเปิดตัว 2026-07-28](../../01-CoreConcepts/mcp-2026-07-28-release-candidate.md) สำหรับรายละเอียด

## กลไกการขนส่งและการสตรีมใน MCP

ส่วนนี้สำรวจกลไกการขนส่งต่าง ๆ ที่มีใน MCP และบทบาทของพวกมันในการเปิดใช้งานความสามารถในการสตรีมเพื่อการสื่อสารแบบเรียลไทม์ระหว่างไคลเอนต์และเซิร์ฟเวอร์

### กลไกขนส่งคืออะไร?

กลไกขนส่งกำหนดวิธีที่ข้อมูลถูกแลกเปลี่ยนระหว่างไคลเอนต์กับเซิร์ฟเวอร์ MCP รองรับประเภทการขนส่งหลายแบบให้เหมาะสมกับสภาพแวดล้อมและความต้องการที่แตกต่างกัน:

- **stdio**: อินพุต/เอาต์พุตมาตรฐาน เหมาะกับเครื่องมือในเครื่องและ CLI แบบพื้นฐาน ง่ายแต่ไม่เหมาะกับเว็บหรือคลาวด์
- **SSE (Server-Sent Events)**: อนุญาตให้เซิร์ฟเวอร์ส่งอัปเดตเรียลไทม์ไปยังไคลเอนต์ผ่าน HTTP ดีสำหรับ UI เว็บ แต่จำกัดในเรื่องขยายขนาดและความยืดหยุ่น ตาม MCP Specification 2025-06-18 การขนส่ง SSE แบบแยกเดี่ยวถูกเลิกใช้และถูกแทนที่ด้วยการขนส่ง "Streamable HTTP"
- **Streamable HTTP**: การขนส่งแบบสตรีมด้วย HTTP สมัยใหม่ รองรับการแจ้งเตือนและขยายขนาดได้ดีขึ้น แนะนำสำหรับกรณีการผลิตและคลาวด์ส่วนใหญ่

### ตารางเปรียบเทียบ

ดูตารางเปรียบเทียบด้านล่างเพื่อเข้าใจความแตกต่างระหว่างกลไกการขนส่งเหล่านี้:

| การขนส่ง      | การอัปเดตเรียลไทม์ | การสตรีม | ขยายขนาดได้ | กรณีการใช้งาน           |
|--------------|---------------------|----------|--------------|--------------------------|
| stdio        | ไม่                  | ไม่       | ต่ำ          | เครื่องมือ CLI ในเครื่อง  |
| SSE          | ใช่                  | ใช่       | กลาง         | เว็บ, อัปเดตเรียลไทม์    |
| Streamable HTTP | ใช่                 | ใช่       | สูง          | คลาวด์, หลายไคลเอนต์     |

> **เคล็ดลับ:** การเลือกกลไกขนส่งที่เหมาะสมส่งผลต่อประสิทธิภาพ การขยายขนาด และประสบการณ์ผู้ใช้ **Streamable HTTP** แนะนำสำหรับแอปสมัยใหม่ที่ขยายขนาดได้และพร้อมคลาวด์

สังเกตกลไกขนส่ง stdio และ SSE ที่คุณเห็นในบทก่อนหน้า และ Streamable HTTP ที่กล่าวถึงในบทนี้

## การสตรีม: แนวคิดและแรงจูงใจ

การเข้าใจแนวคิดพื้นฐานและแรงจูงใจเบื้องหลังการสตรีมเป็นสิ่งจำเป็นสำหรับการสร้างระบบสื่อสารแบบเรียลไทม์ที่มีประสิทธิภาพ

**การสตรีม** เป็นเทคนิคในโปรแกรมมิ่งเครือข่ายที่ช่วยให้ข้อมูลถูกส่งและรับเป็นชิ้นเล็ก ๆ ที่จัดการได้ หรือเป็นลำดับของเหตุการณ์ แทนที่จะรอให้การตอบสนองทั้งหมดพร้อมก่อน เทคนิคนี้มีประโยชน์อย่างยิ่งสำหรับ:

- ไฟล์ขนาดใหญ่หรือชุดข้อมูลขนาดใหญ่
- การอัปเดตเรียลไทม์ (เช่น แชท, แถบความคืบหน้า)
- การคำนวณระยะยาวที่คุณต้องการให้ผู้ใช้รับทราบข้อมูลสถานะ

นี่คือสิ่งที่คุณควรรู้เกี่ยวกับการสตรีมในระดับสูง:

- ข้อมูลถูกส่งอย่างค่อยเป็นค่อยไป ไม่ใช่ทั้งหมดในครั้งเดียว
- ไคลเอนต์สามารถประมวลผลข้อมูลขณะที่มันมาถึง
- ลดความล่าช้าที่รับรู้และปรับปรุงประสบการณ์ผู้ใช้

### ทำไมต้องใช้การสตรีม?

เหตุผลในการใช้การสตรีมมีดังนี้:

- ผู้ใช้ได้รับข้อมูลตอบกลับทันที ไม่ใช่แค่ตอนจบ
- เปิดใช้งานแอปเรียลไทม์และ UI ที่ตอบสนอง
- ใช้ทรัพยากรเครือข่ายและการประมวลผลอย่างมีประสิทธิภาพมากขึ้น

### ตัวอย่างง่าย ๆ: เซิร์ฟเวอร์ & ไคลเอนต์ HTTP Streaming

นี่คือตัวอย่างง่าย ๆ ของการใช้งานสตรีม:

#### Python

**เซิร์ฟเวอร์ (Python ใช้ FastAPI และ StreamingResponse):**

```python
from fastapi import FastAPI
from fastapi.responses import StreamingResponse
import time

app = FastAPI()

async def event_stream():
    for i in range(1, 6):
        yield f"data: Message {i}\n\n"
        time.sleep(1)

@app.get("/stream")
def stream():
    return StreamingResponse(event_stream(), media_type="text/event-stream")
```

**ไคลเอนต์ (Python ใช้ requests):**

```python
import requests

with requests.get("http://localhost:8000/stream", stream=True) as r:
    for line in r.iter_lines():
        if line:
            print(line.decode())
```

ตัวอย่างนี้แสดงเซิร์ฟเวอร์ส่งข้อความต่อเนื่องไปยังไคลเอนต์ทันทีที่พร้อม แทนที่จะรอให้มีข้อความทั้งหมดพร้อมก่อน

**การทำงาน:**

- เซิร์ฟเวอร์ส่งข้อความแต่ละข้อความทันทีที่พร้อม
- ไคลเอนต์รับและพิมพ์ข้อความแต่ละชิ้นขณะที่มันมาถึง

**ความต้องการ:**

- เซิร์ฟเวอร์ต้องใช้การตอบสนองแบบสตรีม (เช่น `StreamingResponse` ใน FastAPI)
- ไคลเอนต์ต้องประมวลผลการตอบสนองเป็นสตรีม (`stream=True` ใน requests)
- ประเภทเนื้อหามักจะเป็น `text/event-stream` หรือ `application/octet-stream`

#### Java

**เซิร์ฟเวอร์ (Java ใช้ Spring Boot และ Server-Sent Events):**

```java
@RestController
public class CalculatorController {

    @GetMapping(value = "/calculate", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    public Flux<ServerSentEvent<String>> calculate(@RequestParam double a,
                                                   @RequestParam double b,
                                                   @RequestParam String op) {
        
        double result;
        switch (op) {
            case "add": result = a + b; break;
            case "sub": result = a - b; break;
            case "mul": result = a * b; break;
            case "div": result = b != 0 ? a / b : Double.NaN; break;
            default: result = Double.NaN;
        }

        return Flux.<ServerSentEvent<String>>just(
                    ServerSentEvent.<String>builder()
                        .event("info")
                        .data("Calculating: " + a + " " + op + " " + b)
                        .build(),
                    ServerSentEvent.<String>builder()
                        .event("result")
                        .data(String.valueOf(result))
                        .build()
                )
                .delayElements(Duration.ofSeconds(1));
    }
}
```

**ไคลเอนต์ (Java ใช้ Spring WebFlux WebClient):**

```java
@SpringBootApplication
public class CalculatorClientApplication implements CommandLineRunner {

    private final WebClient client = WebClient.builder()
            .baseUrl("http://localhost:8080")
            .build();

    @Override
    public void run(String... args) {
        client.get()
                .uri(uriBuilder -> uriBuilder
                        .path("/calculate")
                        .queryParam("a", 7)
                        .queryParam("b", 5)
                        .queryParam("op", "mul")
                        .build())
                .accept(MediaType.TEXT_EVENT_STREAM)
                .retrieve()
                .bodyToFlux(String.class)
                .doOnNext(System.out::println)
                .blockLast();
    }
}
```

**หมายเหตุการใช้งาน Java:**

- ใช้ reactive stack ของ Spring Boot กับ `Flux` สำหรับการสตรีม
- `ServerSentEvent` ให้สตรีมเหตุการณ์ที่มีโครงสร้างพร้อมประเภทเหตุการณ์
- `WebClient` พร้อม `bodyToFlux()` ช่วยให้รับสตรีมแบบ reactive
- `delayElements()` จำลองเวลาประมวลผลระหว่างเหตุการณ์
- เหตุการณ์สามารถมีประเภท (`info`, `result`) เพื่อจัดการง่ายกว่าในไคลเอนต์

### การเปรียบเทียบ: การสตรีมแบบคลาสสิกกับการสตรีม MCP

ความแตกต่างระหว่างการสตรีมแบบ "คลาสสิก" กับใน MCP สามารถบรรยายได้ดังนี้:

| คุณสมบัติ               | การสตรีม HTTP แบบคลาสสิก       | การสตรีม MCP (การแจ้งเตือน)   |
|-----------------------|-------------------------------|-------------------------------|
| การตอบสนองหลัก        | แบ่งเป็นชิ้น                   | ครั้งเดียวที่ตอนท้าย          |
| อัปเดตความคืบหน้า   | ส่งเป็นส่วนข้อมูลชิ้น ๆ         | ส่งเป็นการแจ้งเตือน          |
| ความต้องการของไคลเอนต์ | ต้องประมวลผลสตรีม               | ต้องมีตัวจัดการข้อความ         |
| กรณีการใช้งาน         | ไฟล์ขนาดใหญ่, สตรีมโทเค็น AI  | ความคืบหน้า, บันทึก, ตอบรับเรียลไทม์ |

### ความแตกต่างที่สำคัญที่สังเกตได้

เพิ่มเติม นี่คือความแตกต่างที่สำคัญบางส่วน:

- **รูปแบบการสื่อสาร:**
  - การสตรีม HTTP แบบคลาสสิก: ใช้การเข้ารหัสแบบ chunked ธรรมดาเพื่อส่งข้อมูลเป็นชิ้น
  - การสตรีม MCP: ใช้ระบบแจ้งเตือนที่มีโครงสร้างพร้อมโปรโตคอล JSON-RPC

- **รูปแบบข้อความ:**
  - HTTP แบบคลาสสิก: ข้อความธรรมดาเป็นชิ้น ๆ พร้อมบรรทัดใหม่
  - MCP: วัตถุ LoggingMessageNotification ที่มีโครงสร้างพร้อมเมตาดาต้า

- **การใช้งานไคลเอนต์:**
  - HTTP แบบคลาสสิก: ไคลเอนต์ง่าย ๆ ที่ประมวลผลการตอบสนองแบบสตรีม
  - MCP: ไคลเอนต์มีความซับซ้อนมากขึ้นพร้อมตัวจัดการข้อความสำหรับข้อความประเภทต่าง ๆ

- **การอัปเดตความคืบหน้า:**
  - HTTP แบบคลาสสิก: ความคืบหน้าเป็นส่วนหนึ่งของสตรีมการตอบสนองหลัก
  - MCP: ความคืบหน้าส่งผ่านข้อความแจ้งเตือนแยกต่างหากในขณะที่ผลลัพธ์หลักมาถึงตอนท้าย

### คำแนะนำ

นี่คือบางสิ่งที่เราแนะนำเมื่อเลือกระหว่างการใช้งานสตรีมแบบคลาสสิก (เป็น endpoint ที่เราแสดงให้ดูด้านบนโดยใช้ `/stream`) กับการเลือกสตรีมผ่าน MCP

- **สำหรับความต้องการสตรีมง่าย ๆ:** การสตรีม HTTP แบบคลาสสิกง่ายต่อการใช้งานและเพียงพอสำหรับความต้องการสตรีมพื้นฐาน

- **สำหรับแอปพลิเคชันที่ซับซ้อนและโต้ตอบ:** การสตรีม MCP ให้แนวทางที่มีโครงสร้างมากขึ้นพร้อมเมตาดาต้าที่ร่ำรวยและแยกส่วนระหว่างการแจ้งเตือนกับผลลัพธ์สุดท้าย

- **สำหรับแอป AI:** ระบบแจ้งเตือนของ MCP มีประโยชน์อย่างยิ่งสำหรับงาน AI ที่ทำงานนานซึ่งต้องการให้ผู้ใช้รับทราบความคืบหน้า

## การสตรีมใน MCP

ดี คุณได้เห็นคำแนะนำและการเปรียบเทียบจนถึงตอนนี้เกี่ยวกับความแตกต่างระหว่างการสตรีมแบบคลาสสิกกับใน MCP แล้ว ตอนนี้เรามาเจาะลึกว่าคุณจะใช้สตรีมใน MCP ได้อย่างไร

การเข้าใจวิธีการทำงานของสตรีมในกรอบ MCP เป็นสิ่งสำคัญสำหรับการสร้างแอปพลิเคชันที่ตอบสนองดีซึ่งมอบข้อมูลตอบรับเรียลไทม์ให้ผู้ใช้ในระหว่างการทำงานระยะยาว

ใน MCP การสตรีมไม่ได้หมายถึงการส่งผลลัพธ์หลักเป็นชิ้น แต่มอบหมายให้ส่ง **การแจ้งเตือน** ไปยังไคลเอนต์ในขณะที่เครื่องมือกำลังประมวลผลคำขอ การแจ้งเตือนเหล่านี้อาจรวมถึงการอัปเดตความคืบหน้า บันทึก หรือเหตุการณ์อื่น ๆ

### การทำงาน

ผลลัพธ์หลักยังคงถูกส่งเป็นการตอบสนองครั้งเดียว อย่างไรก็ตาม การแจ้งเตือนสามารถส่งเป็นข้อความแยกต่างหากระหว่างการประมวลผลและอัปเดตไคลเอนต์แบบเรียลไทม์ได้ ไคลเอนต์ต้องสามารถจัดการและแสดงการแจ้งเตือนเหล่านี้ได้

## การแจ้งเตือนคืออะไร?

เราพูดถึง "การแจ้งเตือน" หมายถึงอะไรในบริบทของ MCP?

การแจ้งเตือนคือข้อความที่ส่งจากเซิร์ฟเวอร์ไปยังไคลเอนต์เพื่อแจ้งเกี่ยวกับความคืบหน้า สถานะ หรือเหตุการณ์อื่น ๆ ในระหว่างการดำเนินงานระยะยาว การแจ้งเตือนช่วยเพิ่มความโปร่งใสและประสบการณ์ผู้ใช้

ตัวอย่างเช่น ไคลเอนต์ควรส่งการแจ้งเตือนทันทีที่ทำการจับมือเริ่มต้นกับเซิร์ฟเวอร์เรียบร้อยแล้ว

การแจ้งเตือนมีลักษณะดังนี้ในรูปแบบข้อความ JSON:

```json
{
  jsonrpc: "2.0";
  method: string;
  params?: {
    [key: string]: unknown;
  };
}
```

การแจ้งเตือนเป็นของหัวข้อใน MCP ที่เรียกว่า ["Logging"](https://modelcontextprotocol.io/specification/draft/server/utilities/logging)

> **ประกาศเลิกใช้:** ตัวอย่างการเปิดตัว MCP `"2026-07-28"` ประกาศเลิกใช้ Logging primitive zugunsten von `stderr` สำหรับการขนส่ง stdio และ OpenTelemetry สำหรับการสังเกตการณ์แบบมีโครงสร้าง Logging จะยังทำงานใน `"2025-11-25"` และอย่างน้อยหนึ่งปีหลังจากประกาศเลิกใช้อย่างเป็นทางการ ดู [มีอะไรเปลี่ยนแปลงใน MCP: ตัวอย่างการเปิดตัว 2026-07-28](../../01-CoreConcepts/mcp-2026-07-28-release-candidate.md)

เพื่อให้การบันทึกทำงาน เซิร์ฟเวอร์จำเป็นต้องเปิดใช้งานคุณสมบัตินี้ดังนี้:

## การใช้งานการแจ้งเตือนใน MCP

เพื่อใช้งานการแจ้งเตือนใน MCP คุณต้องตั้งค่าเซิร์ฟเวอร์และไคลเอนต์ให้สามารถจัดการการอัปเดตแบบเรียลไทม์ได้ ซึ่งช่วยให้แอปของคุณมอบข้อมูลตอบรับทันทีในขณะดำเนินงานระยะยาว

### ฝั่งเซิร์ฟเวอร์: การส่งการแจ้งเตือน

เริ่มต้นจากฝั่งเซิร์ฟเวอร์ ใน MCP คุณกำหนดเครื่องมือที่สามารถส่งการแจ้งเตือนในขณะประมวลผลคำขอ เซิร์ฟเวอร์ใช้วัตถุ context (โดยปกติเรียกว่า `ctx`) เพื่อส่งข้อความไปยังไคลเอนต์

#### Python

```python
@mcp.tool(description="A tool that sends progress notifications")
async def process_files(message: str, ctx: Context) -> TextContent:
    await ctx.info("Processing file 1/3...")
    await ctx.info("Processing file 2/3...")
    await ctx.info("Processing file 3/3...")
    return TextContent(type="text", text=f"Done: {message}")
```

ในตัวอย่างก่อนหน้า เครื่องมือ `process_files` ส่งการแจ้งเตือนสามรายการไปยังไคลเอนต์ในขณะที่ประมวลผลแต่ละไฟล์ เมธอด `ctx.info()` ใช้เพื่อส่งข้อความข้อมูล

นอกจากนี้ เพื่อเปิดใช้งานการแจ้งเตือน ตรวจสอบให้แน่ใจว่าเซิร์ฟเวอร์ของคุณใช้การขนส่งแบบสตรีม (เช่น `streamable-http`) และไคลเอนต์ของคุณมีตัวจัดการข้อความสำหรับประมวลผลการแจ้งเตือน นี่คือตัวอย่างการตั้งค่าเซิร์ฟเวอร์ให้ใช้การขนส่ง `streamable-http`:

```python
mcp.run(transport="streamable-http")
```

#### .NET

```csharp
[Tool("A tool that sends progress notifications")]
public async Task<TextContent> ProcessFiles(string message, ToolContext ctx)
{
    await ctx.Info("Processing file 1/3...");
    await ctx.Info("Processing file 2/3...");
    await ctx.Info("Processing file 3/3...");
    return new TextContent
    {
        Type = "text",
        Text = $"Done: {message}"
    };
}
```

ในตัวอย่าง .NET นี้ เครื่องมือ `ProcessFiles` ตกแต่งด้วยแอตทริบิวต์ `Tool` และส่งการแจ้งเตือนสามรายการไปยังไคลเอนต์ในขณะประมวลผลแต่ละไฟล์ เมธอด `ctx.Info()` ใช้เพื่อส่งข้อความข้อมูล

เพื่อเปิดใช้งานการแจ้งเตือนใน MCP เซิร์ฟเวอร์ .NET ของคุณ ตรวจสอบให้แน่ใจว่าคุณใช้การขนส่งแบบสตรีม:

```csharp
var builder = McpBuilder.Create();
await builder
    .UseStreamableHttp() // Enable streamable HTTP transport
    .Build()
    .RunAsync();
```

### ฝั่งไคลเอนต์: การรับการแจ้งเตือน

ไคลเอนต์ต้องมีตัวจัดการข้อความเพื่อประมวลผลและแสดงการแจ้งเตือนทันทีที่มาถึง

#### Python

```python
async def message_handler(message):
    if isinstance(message, types.ServerNotification):
        print("NOTIFICATION:", message)
    else:
        print("SERVER MESSAGE:", message)

async with ClientSession(
   read_stream, 
   write_stream,
   logging_callback=logging_collector,
   message_handler=message_handler,
) as session:
```

ในโค้ดก่อนหน้า ฟังก์ชัน `message_handler` ตรวจสอบว่าข้อความที่เข้ามาเป็นการแจ้งเตือนหรือไม่ หากใช่ จะพิมพ์การแจ้งเตือน ถ้าไม่ใช่จะประมวลผลเป็นข้อความเซิร์ฟเวอร์ปกติ นอกจากนี้สังเกตว่ามีการเริ่มต้น `ClientSession` ด้วย `message_handler` เพื่อจัดการการแจ้งเตือนที่เข้ามา

#### .NET

```csharp
// Define a message handler
void MessageHandler(IJsonRpcMessage message)
{
    if (message is ServerNotification notification)
    {
        Console.WriteLine($"NOTIFICATION: {notification}");
    }
    else
    {
        Console.WriteLine($"SERVER MESSAGE: {message}");
    }
}

// Create and use a client session with the message handler
var clientOptions = new ClientSessionOptions
{
    MessageHandler = MessageHandler,
    LoggingCallback = (level, message) => Console.WriteLine($"[{level}] {message}")
};

using var client = new ClientSession(readStream, writeStream, clientOptions);
await client.InitializeAsync();

// Now the client will process notifications through the MessageHandler
```

ในตัวอย่าง .NET นี้ ฟังก์ชัน `MessageHandler` ตรวจสอบว่าข้อความที่เข้ามาเป็นการแจ้งเตือนหรือไม่ ถ้าใช่จะพิมพ์การแจ้งเตือน มิฉะนั้นจะประมวลผลเป็นข้อความเซิร์ฟเวอร์ปกติ `ClientSession` ถูกเริ่มต้นด้วยตัวจัดการข้อความผ่าน `ClientSessionOptions`

เพื่อเปิดใช้งานการแจ้งเตือน ตรวจสอบให้แน่ใจว่าเซิร์ฟเวอร์ของคุณใช้การขนส่งแบบสตรีม (เช่น `streamable-http`) และไคลเอนต์ของคุณมีตัวจัดการข้อความสำหรับประมวลผลการแจ้งเตือน

## การแจ้งเตือนความคืบหน้าและสถานการณ์

ส่วนนี้อธิบายแนวคิดของการแจ้งเตือนความคืบหน้าใน MCP ทำไมถึงสำคัญ และวิธีใช้งานผ่าน Streamable HTTP คุณจะพบภารกิจปฏิบัติที่ช่วยเสริมความเข้าใจด้วย

การแจ้งเตือนความคืบหน้าเป็นข้อความเรียลไทม์ที่ส่งจากเซิร์ฟเวอร์ไปยังไคลเอนต์ในระหว่างการดำเนินงานที่ใช้เวลานาน แทนที่จะรอให้กระบวนการทั้งหมดเสร็จ เซิร์ฟเวอร์จะอัปเดตไคลเอนต์เกี่ยวกับสถานะปัจจุบัน การทำเช่นนี้เพิ่มความโปร่งใส ประสบการณ์ผู้ใช้ และช่วยให้ง่ายต่อการดีบัก

**ตัวอย่าง:**

```text

"Processing document 1/10"
"Processing document 2/10"
...
"Processing complete!"

```

### ทำไมต้องใช้การแจ้งเตือนความคืบหน้า?

การแจ้งเตือนความคืบหน้ามีความสำคัญด้วยหลายเหตุผล:

- **ประสบการณ์ผู้ใช้ที่ดีขึ้น:** ผู้ใช้เห็นการอัปเดตขณะทำงาน ไม่ใช่แค่ตอนจบ
- **ข้อมูลตอบรับแบบเรียลไทม์:** ไคลเอนต์สามารถแสดงแถบความคืบหน้าหรือบันทึก ทำให้แอปดูตอบสนองได้ดี
- **ง่ายต่อการดีบักและติดตาม:** นักพัฒนาและผู้ใช้สามารถเห็นได้ว่ากระบวนการส่วนใดช้า หรือค้างอยู่

### วิธีการใช้งานการแจ้งเตือนความคืบหน้า

นี่คือตัวอย่างวิธีใช้งานการแจ้งเตือนความคืบหน้าใน MCP:

- **ฝั่งเซิร์ฟเวอร์:** ใช้ `ctx.info()` หรือ `ctx.log()` เพื่อส่งการแจ้งเตือนในขณะที่แต่ละรายการถูกประมวลผล ส่งข้อความไปยังไคลเอนต์ก่อนที่ผลลัพธ์หลักจะพร้อม
- **ฝั่งไคลเอนต์:** สร้างตัวจัดการข้อความที่รอฟังและแสดงการแจ้งเตือนทันทีที่มาถึง ตัวจัดการนี้จะแยกแยะระหว่างการแจ้งเตือนกับผลลัพธ์สุดท้าย

**ตัวอย่างฝั่งเซิร์ฟเวอร์:**


#### Python

```python
async def process_files(message: str, ctx: Context) -> TextContent:
    for i in range(1, 11):
        await ctx.info(f"Processing document {i}/10")
    await ctx.info("Processing complete!")
    return TextContent(type="text", text=f"Done: {message}")
```

## ข้อควรพิจารณาด้านความปลอดภัย

ความปลอดภัยควรเป็นสิ่งสำคัญอันดับต้น ๆ เมื่อดำเนินการเซิร์ฟเวอร์ใด ๆ โดยเฉพาะอย่างยิ่งเมื่อใช้การขนส่งแบบ HTTP เช่น Streamable HTTP ใน MCP

เมื่อดำเนินการเซิร์ฟเวอร์ MCP ด้วยการขนส่งแบบ HTTP ความปลอดภัยจึงเป็นข้อกังวลสำคัญที่ต้องให้ความใส่ใจอย่างรอบคอบกับหลายช่องทางการโจมตีและกลไกการป้องกัน

### ภาพรวม

ความปลอดภัยเป็นเรื่องสำคัญเมื่อเปิดเผยเซิร์ฟเวอร์ MCP ผ่าน HTTP Streamable HTTP เพิ่มพื้นผิวการโจมตีใหม่และต้องการการกำหนดค่าที่ระมัดระวัง

นี่คือข้อควรพิจารณาด้านความปลอดภัยที่สำคัญ:

- **การตรวจสอบ Origin Header**: ตรวจสอบ `Origin` header เสมอเพื่อป้องกันการโจมตี DNS rebinding
- **การผูกกับ Localhost**: สำหรับการพัฒนาในเครื่อง ให้ผูกเซิร์ฟเวอร์กับ `localhost` เพื่อป้องกันการเปิดเผยสู่สาธารณะ
- **การตรวจสอบสิทธิ์**: ดำเนินการตรวจสอบสิทธิ์ (เช่น API keys, OAuth) สำหรับการใช้งานจริง
- **CORS**: กำหนดนโยบาย Cross-Origin Resource Sharing (CORS) เพื่อจำกัดการเข้าถึง
- **HTTPS**: ใช้ HTTPS ในการใช้งานจริงเพื่อเข้ารหัสการรับส่งข้อมูล

### แนวทางปฏิบัติที่ดีที่สุด

นอกจากนี้ นี่คือแนวทางปฏิบัติที่ดีที่สุดเมื่อดำเนินการด้านความปลอดภัยในเซิร์ฟเวอร์ MCP แบบสตรีมมิ่งของคุณ:

- อย่าเชื่อคำขอเข้ามาโดยไม่มีการตรวจสอบ
- บันทึกและเฝ้าติดตามการเข้าถึงและข้อผิดพลาดทั้งหมด
- อัปเดต dependencies อย่างสม่ำเสมอเพื่อแก้ไขช่องโหว่ด้านความปลอดภัย

### ความท้าทาย

คุณจะพบกับความท้าทายบางอย่างเมื่อดำเนินการด้านความปลอดภัยในเซิร์ฟเวอร์ MCP แบบสตรีมมิ่ง:

- การสร้างสมดุลระหว่างความปลอดภัยกับความสะดวกในการพัฒนา
- การรับประกันความเข้ากันได้กับสภาพแวดล้อมของไคลเอนต์หลากหลาย


## การอัปเกรดจาก SSE เป็น Streamable HTTP

สำหรับแอปพลิเคชันที่กำลังใช้ Server-Sent Events (SSE) การย้ายไปใช้ Streamable HTTP จะมอบความสามารถที่ดีขึ้นและความยั่งยืนในระยะยาวที่ดีขึ้นสำหรับการใช้งาน MCP ของคุณ

### ทำไมต้องอัปเกรด?

มีเหตุผลที่น่าสนใจสองประการในการอัปเกรดจาก SSE เป็น Streamable HTTP:

- Streamable HTTP มอบความสามารถในการขยายตัว ความเข้ากันได้ และการสนับสนุนการแจ้งเตือนที่มากกว่า SSE
- เป็นการขนส่งที่แนะนำสำหรับแอป MCP ใหม่

### ขั้นตอนการย้ายข้อมูล

นี่คือวิธีที่คุณสามารถย้ายจาก SSE เป็น Streamable HTTP ในแอป MCP ของคุณ:

- **อัปเดตโค้ดเซิร์ฟเวอร์** เพื่อใช้ `transport="streamable-http"` ใน `mcp.run()`
- **อัปเดตโค้ดไคลเอนต์** เพื่อใช้ `streamablehttp_client` แทนไคลเอนต์ SSE
- **ดำเนินการตัวจัดการข้อความ** ในไคลเอนต์เพื่อประมวลผลการแจ้งเตือน
- **ทดสอบความเข้ากันได้** กับเครื่องมือและเวิร์กโฟลว์ที่มีอยู่

### การรักษาความเข้ากันได้

แนะนำให้รักษาความเข้ากันได้กับไคลเอนต์ SSE ที่มีอยู่ในระหว่างกระบวนการย้ายข้อมูล นี่คือกลยุทธ์บางอย่าง:

- คุณสามารถรองรับทั้ง SSE และ Streamable HTTP ได้โดยการรันทั้งสองโปรโตคอลบนจุดปลายที่แตกต่างกัน
- ค่อย ๆ ย้ายไคลเอนต์ไปยังโปรโตคอลใหม่

### ความท้าทาย

ให้แน่ใจว่าคุณแก้ไขความท้าทายต่อไปนี้ระหว่างการย้ายข้อมูล:

- รับประกันว่าไคลเอนต์ทั้งหมดได้รับการอัปเดต
- จัดการความแตกต่างในการส่งมอบการแจ้งเตือน

### แบบฝึกหัด: สร้างแอป MCP Streaming ของคุณเอง

**สถานการณ์:**
สร้างเซิร์ฟเวอร์และไคลเอนต์ MCP ที่เซิร์ฟเวอร์จะประมวลผลรายการของไอเท็ม (เช่น ไฟล์หรือเอกสาร) และส่งการแจ้งเตือนสำหรับแต่ละไอเท็มที่ประมวลผล ไคลเอนต์ควรแสดงการแจ้งเตือนแต่ละรายการเมื่อได้รับ

**ขั้นตอน:**

1. ดำเนินการเครื่องมือเซิร์ฟเวอร์ที่ประมวลผลรายการและส่งการแจ้งเตือนสำหรับแต่ละไอเท็ม
2. ดำเนินการไคลเอนต์พร้อมตัวจัดการข้อความเพื่อแสดงการแจ้งเตือนแบบเรียลไทม์
3. ทดสอบการดำเนินการโดยรันทั้งเซิร์ฟเวอร์และไคลเอนต์ และสังเกตการแจ้งเตือน

[วิธีแก้ปัญหา](./solution/README.md)

## การอ่านเพิ่มเติม & ก้าวต่อไป?

เพื่อดำเนินการต่อในเส้นทางกับ MCP streaming และขยายความรู้ของคุณ ส่วนนี้ให้แหล่งข้อมูลเพิ่มเติมและขั้นตอนที่แนะนำสำหรับการสร้างแอปพลิเคชันขั้นสูงขึ้น

### การอ่านเพิ่มเติม

- [Microsoft: บทนำสู่ HTTP Streaming](https://learn.microsoft.com/aspnet/core/fundamentals/http-requests?view=aspnetcore-8.0&WT.mc_id=%3Fwt.mc_id%3DMVP_452430#streaming)
- [Microsoft: Server-Sent Events (SSE)](https://learn.microsoft.com/azure/application-gateway/for-containers/server-sent-events?tabs=server-sent-events-gateway-api&WT.mc_id=%3Fwt.mc_id%3DMVP_452430)
- [Microsoft: CORS ใน ASP.NET Core](https://learn.microsoft.com/aspnet/core/security/cors?view=aspnetcore-8.0&WT.mc_id=%3Fwt.mc_id%3DMVP_452430)
- [Python requests: Streaming Requests](https://requests.readthedocs.io/en/latest/user/advanced/#streaming-requests)

### ก้าวต่อไป?

- ทดลองสร้างเครื่องมือ MCP ขั้นสูงที่ใช้การสตรีมมิ่งสำหรับการวิเคราะห์แบบเรียลไทม์ การแชท หรือการแก้ไขร่วมกัน
- สำรวจการรวม MCP streaming กับ frontend frameworks (React, Vue, ฯลฯ) สำหรับการอัปเดต UI แบบสด
- ถัดไป: [การใช้ AI Toolkit สำหรับ VSCode](../07-aitk/README.md)
